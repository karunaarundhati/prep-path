Clean code, refactoring and code health

Clean code is code that a colleague can read, change and trust without help from its author. It is not a set of tricks. It is a set of habits: names say what things are, each function does one job, and repeated logic lives in one place. Interviewers ask about these habits because they predict how a candidate will work in a real codebase.

Readable names and small functions

A name should tell the reader what a value means, not how it is stored. d is a poor name; days_since_signup is a good one. A function should do one thing at one level of detail. If you need the word "and" to describe it, it probably has two jobs. Short functions are easier to test, easier to name and easier to reuse.

Comments should explain why, because the code already says what. A comment that repeats the next line is noise. A comment that records a surprising business rule is gold.

Code smells and refactoring

A code smell is a sign that the code may have a deeper problem. Smells are not bugs. They are warnings. Common ones are a long function, duplicated code, a long parameter list, magic numbers (unexplained literals such as 0.85 in the middle of a formula), and feature envy (a method that uses another object's data more than its own).

Refactoring changes the structure of code without changing its behaviour. The safe way to refactor is to have tests first, make one small change, run the tests, and repeat. The most common refactorings are renaming, extracting a function, replacing a magic number with a named constant, and removing duplication. The example below shows the last two.

DISCOUNT_BY_TIER = {"vip": 0.20, "member": 0.10}   # named rates instead of magic numbers

def price_after_discount(price, tier):
    """Return the price after the discount for the customer's tier."""
    rate = DISCOUNT_BY_TIER.get(tier, 0.0)           # unknown tiers get no discount
    return round(price * (1 - rate), 2)

print(price_after_discount(100, "vip"))
print(price_after_discount(80, "member"))
print(price_after_discount(50, "guest"))
80.0
72.0
50.0

The before-version of this code was a chain of if statements, each with its own literal rate. Adding a tier meant editing the logic. Now adding a tier is one line of data. The behaviour is the same for the three example customers, which is exactly what a refactoring must preserve.

Key ideaRefactoring is changing the shape of code while keeping its behaviour. Tests are what make that claim believable.

Technical debt

Technical debt is a metaphor from Ward Cunningham: shipping a quick solution is like borrowing money. It is sometimes the right choice, such as to meet a deadline, but the code then pays interest, meaning every future change takes longer. Debt is deliberate when the team knows and records the shortcut, and inadvertent when nobody noticed it was there. Good teams track debt, pay down the expensive parts, and do not treat every imperfection as urgent.

Linters, formatters and documentation

A linter reports likely problems: unused variables, suspicious comparisons, undefined names. A formatter rewrites layout (indentation, line breaks, quotes) so that style is never debated in review. Common Python tools include flake8, pylint, ruff and black. Running them automatically, for example through a pre-commit hook or a CI step, keeps the codebase consistent without anyone policing it by hand.

Documentation has three layers: docstrings for functions and classes, a README that explains how to run the project, and short decision records (for example, architecture decision records) that explain why something was built a certain way. Docstrings can also double as tests. The doctest module runs the examples written inside a docstring and fails if the printed result changes.

import doctest

def average(numbers):
    """Return the arithmetic mean of a non-empty list.

    >>> average([2, 4, 6])
    4.0
    >>> average([1, 2])
    1.5
    """
    return sum(numbers) / len(numbers)

print(doctest.testmod())
TestResults(failed=0, attempted=2)

doctest.testmod() runs every example it finds in the module. It prints nothing when all examples pass, so the outcome shown here comes from the print around it, which reports how many failed and how many were attempted. If you change average to return something different, the count of failed examples becomes non-zero.

Code review etiquette

Earlier you saw how review works on pull requests. The etiquette matters just as much. Reviews should be fast (a small change should not wait a week), specific (say which line and why), and kind (criticise the code, not the author). Label minor preferences as optional, and separate blocking issues from suggestions. When you receive a review, assume good intent, answer every comment, and push back politely with evidence when you disagree.

What is the difference between refactoring and rewriting?

Refactoring changes the structure of code in small steps, keeping behaviour the same and checked by tests after each step. A rewrite replaces the code wholesale, which usually changes behaviour in ways nobody fully tracks. Refactoring is safer because each step is small enough to review and undo.

Debugging, profiling, semantic versioning and feature flags

This unit covers three practical skills: finding the cause of a bug, finding where a slow program spends its time, and shipping changes without fear.

Debugging: a method, not a guess

Good debugging follows a loop. First, reproduce the bug reliably, ideally with a small input. Second, read the error completely, because the message and the traceback usually name the line. Third, form a hypothesis about the cause and test it with the smallest experiment you can. Fourth, fix the cause, not the symptom, and add a test that would have caught it.

The simplest tool is a clear error message. The next is a breakpoint: in Python 3.7 and later, breakpoint() pauses the program in the debugger pdb, where you can inspect variables and step through lines. Logging and the bisect tool from the Git unit are also debugging tools.

def average_of(values):
    return sum(values) / len(values)

try:
    average_of([])
except ZeroDivisionError as error:
    print("caught:", error)
caught: division by zero

Reading the message is the first step. It says the division needed a non-zero divisor, and the traceback would point to the line. The real fix is a decision: should an empty list return 0, return None, or raise a clearer error? The code should make that choice explicit instead of letting a generic error escape.

Profiling: measure before you optimise

Profiling measures where a program spends its time. A profiler records how many times each function runs and how long it takes. Python's built-in profiler is run with python -m cProfile -s cumtime script.py, which sorts functions by cumulative time. The usual rule is to find the hot spot first, because most programs spend nearly all their time in a few places. Optimising anywhere else is wasted effort, and it makes the code harder to read.

TrapOptimising by intuition. Developers are often wrong about where time goes. Profile, change one thing, and measure again.

Semantic versioning

Semantic versioning (SemVer) gives a version number the meaning of a promise. The version has three parts, MAJOR.MINOR.PATCH. Increase PATCH for backward-compatible bug fixes, MINOR for backward-compatible new features, and MAJOR for changes that break existing users. Pre-release labels such as 2.0.0-rc.1 mark versions that are not yet final.

Comparing versions as text is a classic bug. The strings "1.10.0" and "1.2.3" sort in the wrong order if you compare them character by character. Parse them into integer tuples instead, because tuples compare element by element. The program below does that and also checks compatibility: a dependency is compatible if the major version matches and the installed version is at least the required one.

def parse_version(text):
    major, minor, patch = (int(part) for part in text.split("."))
    return (major, minor, patch)

def is_compatible(required, installed):
    r, i = parse_version(required), parse_version(installed)
    return i[0] == r[0] and i >= r      # same major version, and not older

versions = ["1.10.0", "1.2.3", "2.0.0", "1.2.10"]
print(sorted(versions, key=parse_version))
print(sorted(versions))                 # plain string sort gets the order wrong
print(is_compatible("1.2.0", "1.10.0"))
print(is_compatible("1.2.0", "2.0.0"))
['1.2.3', '1.2.10', '1.10.0', '2.0.0']
['1.10.0', '1.2.10', '1.2.3', '2.0.0']
True
False

The second line is the trap. Plain string sorting puts "1.10.0" before "1.2.3", because the character "1" sorts before "2". The tuple key fixes it. The compatibility check accepts 1.10.0 for a requirement of 1.2.0 because the major version is the same, and rejects 2.0.0 because a major change may break callers.

Feature flags

A feature flag is a switch in code that turns a behaviour on or off at runtime, usually from configuration. Flags separate deploying code (putting it on the servers) from releasing it (letting users see it). You can deploy a half-finished feature behind a flag, turn it on for staff first, then roll it out to a percentage of users, and turn it off instantly if it misbehaves.

Rollouts need a stable answer per user. If a user flips between enabled and disabled on each request, the product feels broken. The usual approach is to hash the user ID together with the flag name into a number from 0 to 99, then enable the flag for buckets below the rollout percentage. The same user always lands in the same bucket.

import hashlib

FLAGS = {"new-checkout": {"enabled": True, "rollout_percent": 25}}

def bucket(user_id, flag):
    """A stable number from 0 to 99 for this user and flag."""
    digest = hashlib.sha256(f"{flag}:{user_id}".encode()).hexdigest()
    return int(digest[:8], 16) % 100

def is_enabled(flag, user_id):
    cfg = FLAGS.get(flag)
    if not cfg or not cfg["enabled"]:
        return False                                  # unknown or off: safe default
    return bucket(user_id, flag) < cfg["rollout_percent"]

for user in ["u1", "u2", "u3", "u4", "u5", "u6", "u7", "u8"]:
    print(user, bucket(user, "new-checkout"), is_enabled("new-checkout", user))
print("unknown flag:", is_enabled("missing", "u1"))

Testing foundations: the pyramid, TDD and BDD

Tests are the safety net that makes refactoring and frequent releases possible. The first question is how many tests of each kind to write. The test pyramid answers it with a shape:

  • Unit tests check one function or class in isolation. They are fast (milliseconds), numerous, and point straight at the faulty line. Most of your tests should be here.
  • Integration tests check that several parts work together, such as a repository and a real test database. They are slower and fewer.
  • End-to-end (E2E) tests drive the whole system through its user interface or public API. They are the most realistic, and the slowest and most fragile. Keep only a few, for the journeys that matter most.

The pyramid is about cost and feedback speed. A failing E2E test takes minutes to diagnose, while a failing unit test names the function.

Test-driven development

Test-driven development (TDD) reverses the usual order: you write a failing test first, then the code that makes it pass. Its loop has three steps, often called red, green and refactor. Red: write a test for the next small behaviour and watch it fail. Green: write the simplest code that passes. Refactor: tidy the code while the tests stay green. Here is a small example. The tests come first in the file so you can read the specification before the implementation.

def is_leap_year(year):
    return year % 4 == 0 and (year % 100 != 0 or year % 400 == 0)

assert is_leap_year(2024) is True
assert is_leap_year(2023) is False
assert is_leap_year(1900) is False
assert is_leap_year(2000) is True
print("all tests passed")
all tests passed

The four asserts cover the rules that matter: ordinary leap years, ordinary non-leap years, a century that is not a leap year, and a century divisible by 400 that is. Writing the century cases first is what drives the second condition in the function.

If any one of them were false, Python would stop with an AssertionError that names the failing line.

Behaviour-driven development (BDD) takes the same idea and writes the examples in plain language, so product owners and developers share one description. Scenarios use the Given, When, Then pattern:

Feature: Member discount
  Scenario: A member pays 10 percent less
    Given a member with a cart worth 80
    When the member checks out
    Then the total charged is 72

Tools such as Cucumber and pytest-bdd turn these scenarios into executable tests. The value is the conversation the scenarios force, not the tool.

Coverage: useful, but not proof

Coverage measures which lines (and often branches) of code run during the tests. Tools such as coverage.py report it as a percentage. Coverage tells you which code is never executed, which is useful. It does not tell you whether the tests check anything. A test that calls a function and asserts nothing gives full coverage and catches no bugs. Treat coverage as a map of gaps, not as a quality score, and do not chase a number at the cost of meaningful assertions.

TrapSaying "we have 100 percent coverage, so the code is correct". Coverage shows which lines ran, not whether the results were checked.

Why does the test pyramid recommend few end-to-end tests?

End-to-end tests are slow, depend on many components at once, and fail for many unrelated reasons such as network or data problems. Unit tests are fast and pinpoint the cause. Keeping most checks at the bottom gives quick feedback, and E2E tests are kept for the few journeys that must work end to end.

What are the red, green and refactor steps in TDD?

Red: write a test for the next behaviour and watch it fail, which proves the test can fail. Green: write the simplest code that makes it pass. Refactor: improve the code's structure while the tests stay green. Then repeat for the next behaviour.

Mocking with unittest.mock

A unit test should not depend on the network, a real payment provider or the clock. A test double is an object that stands in for a real dependency. The general term covers several kinds: a stub returns fixed answers, a fake is a simple working implementation (such as an in-memory repository), and a mock records how it was called so that the test can check the interaction. Python's standard unittest.mock module provides Mock, which can be any of these, and patch, which temporarily replaces a name in a module.

A mock that records calls

The function under test receives a gateway object. The test gives it a Mock, sets what the mock returns, and then checks what it was called with. No real payment happens.

from unittest.mock import Mock, patch
import os

def checkout(cart, gateway):
    total = sum(cart)
    return gateway.charge(total)

gateway = Mock()
gateway.charge.return_value = "approved"       # the stub part: a fixed answer
print(checkout([10, 15], gateway))
gateway.charge.assert_called_once_with(25)     # the mock part: check the call
print(gateway.charge.call_count)

with patch("os.getcwd", return_value="/fake/dir"):   # temporarily replace a function
    print(os.getcwd())                                 # the patched value is seen here
approved
1
/fake/dir

assert_called_once_with(25) fails if the gateway was called with any other value, or more than once. That is the strength of a mock: it tests the conversation between the code and its dependency. The patch context manager restores the original os.getcwd when the block ends, so other tests are unaffected.

TrapPatching where the function is defined instead of where it is used. Patch the name in the module that imports it, for example "myapp.payments.gateway", not "gateway_library.Client".

Interviewers ask"When do you mock and when do you not?" Mock slow, unreliable or external dependencies, and mock things you do not own. Do not mock the code under test, and avoid mocking so much that the test only checks the mock.

What is the difference between a stub, a fake and a mock?

A stub returns canned answers so the code under test can continue. A fake is a working but simplified implementation, such as an in-memory dictionary in place of a database. A mock records calls so the test can assert on how the dependency was used. A Mock object in unittest.mock can act as any of the three.

Load testing basics, Selenium and Playwright

Two more kinds of testing complete the picture. Load testing checks how a system behaves under expected or heavy traffic. Browser automation checks the user interface by driving a real browser.

Load testing basics

A load test sends realistic traffic to a system and measures what happens. Tools such as k6, Locust and JMeter generate the requests. Three numbers matter most. Throughput is requests per second the system completes. Latency is how long each request takes. Error rate is the share of requests that fail.

Latency should be reported as percentiles, not as an average. The 50th percentile (p50) is the typical request, and the 95th (p95) is the slow tail that one user in twenty sees. An average can look healthy while the tail is terrible. The nearest-rank method below computes a percentile from sorted measurements.

import math

def percentile(sorted_values, pct):
    """Nearest-rank percentile: the value at position ceil(pct/100 * n), counting from 1."""
    rank = math.ceil(pct / 100 * len(sorted_values))
    return sorted_values[rank - 1]

latencies_ms = sorted([120, 95, 310, 88, 101, 97, 1500, 110, 99, 105])
print("p50:", percentile(latencies_ms, 50))
print("p90:", percentile(latencies_ms, 90))
print("p95:", percentile(latencies_ms, 95))
print("mean:", sum(latencies_ms) / len(latencies_ms))
p50: 101
p90: 310
p95: 1500
mean: 262.5

The mean is 262.5 ms, a number that describes no real request. Four of the ten requests took about 100 ms, and the single 1,500 ms request pulls the mean up while the median stays at 101 ms. The p95 rank lands on that slow request, which is exactly what a load test should surface. In a real test you would also watch error rates and throughput, and increase the load step by step until latency or errors grow.

TrapRunning a load test against production without agreement, or against a shared staging system that other teams are using. Load tests can take a service down.

Browser automation: Selenium and Playwright

Some behaviour can only be checked in a real browser, such as a login form that redirects, JavaScript that updates the page, or a checkout that depends on the layout. Selenium and Playwright are libraries that control a browser from code. Both can click, type, read text and wait for elements. They differ mainly in how they manage the browser and waiting.

Selenium has been the standard for many years. It talks to a browser driver through the WebDriver protocol, and it needs explicit waits (for example WebDriverWait) when the page is still loading. Playwright is newer, ships its own browser builds, and waits automatically before each action on an element. The examples below show the same login flow in each tool. They need a browser and a live site, so they are shown without printed output.

from selenium import webdriver
from selenium.webdriver.common.by import By

driver = webdriver.Chrome()                          # starts a Chrome browser
driver.get("https://example.com/login")
driver.find_element(By.ID, "email").send_keys("ada@example.com")
driver.find_element(By.CSS_SELECTOR, "button[type=submit]").click()
driver.quit()                                         # always close the browser
from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.goto("https://example.com/login")
    page.fill("#email", "ada@example.com")           # waits for the field to be ready
    page.click("button[type=submit]")                # waits for the button to be clickable
    browser.close()

TipSelect elements by stable attributes such as data-testid, not by long CSS paths or by text that a designer might change. Brittle selectors are the main cause of flaky browser tests.

Why are browser tests usually at the top of the pyramid?

They start a real browser, load real pages and depend on timing, so they are the slowest and most prone to flakiness. Teams keep a small number of them for critical user journeys and cover the rest of the logic with faster unit and integration tests.

Interview questions

Answer each question out loud before opening the model answer. Interviewers listen for the trade-off, not for a memorised definition.

What is a code smell, and how does refactoring respond to one?

A code smell is a surface sign of a deeper design problem, such as duplicated logic or a magic number. Refactoring responds with a small, behaviour-preserving change, such as extracting a function or naming a constant, and tests confirm that behaviour did not change.

What is technical debt, and when is it acceptable?

It is the extra future cost created by a shortcut, like interest on a loan. It is acceptable when the team knows it, records it and has a plan to repay it, for example to meet a deadline that has real value. It is dangerous when it is unknown or never repaid.

Explain semantic versioning with an example.

A version is MAJOR.MINOR.PATCH. Going from 2.4.1 to 2.4.2 is a bug fix, to 2.5.0 is a backward-compatible feature, and to 3.0.0 is a breaking change. Consumers can rely on the rule that a higher major number may break them, while a higher minor or patch number should not.

What is the difference between deploying and releasing, and how do feature flags help?

Deploying puts code on the servers. Releasing makes a feature visible to users. A feature flag lets you deploy first and release later, to a few users or a percentage of users, and switch it off without redeploying.

What is the test pyramid?

It is a guideline for how many tests of each kind to write: many fast unit tests at the base, fewer integration tests in the middle, and few slow end-to-end tests at the top. The shape keeps the feedback loop fast and makes failures easy to diagnose.

What is the difference between a unit test and an integration test?

A unit test checks one unit, such as a function, with its dependencies replaced by test doubles, so it is fast and isolated. An integration test checks that real components work together, such as a repository talking to a real database.

Why is high coverage not the same as good tests?

Coverage shows which lines ran, not whether the results were checked. A test that calls code without asserting anything raises coverage and catches nothing. Good tests make specific assertions about behaviour, and coverage is useful mainly for finding untested code.

When would you use mock.patch?

When the code under test calls something slow, external or nondeterministic, such as a network call, the clock or a random number. patch temporarily replaces that name with a Mock during the test, and it must patch the name where the code looks it up.

Why report latency as percentiles instead of an average?

An average hides the slow tail. A system can have a healthy mean while one request in twenty takes seconds. The p95 and p99 show what the unlucky users experience, and that is what load tests and service level objectives usually track.

What is the difference between Selenium and Playwright?

Both automate real browsers from code. Selenium uses the WebDriver protocol and usually needs explicit waits. Playwright ships its own browser builds and waits automatically before actions, which makes it less flaky by default. The choice depends on the team's existing tooling and languages.

DSA: Dynamic programming, two dimensions

A two-dimensional DP table answers a question about two things at once: a prefix of the first input and a prefix of the second, a position in a grid, or a total and a number of items. Each cell dp[i][j] stores the answer for one pair, and each cell is built from a few neighbouring cells that are already filled.

The table, step by step

  1. State. Write down the meaning of dp[i][j] in words, for example "the length of the longest common subsequence of the first i letters of A and the first j letters of B".
  2. Size. Make the table one larger than the inputs in each dimension, so row 0 and column 0 represent the empty prefix.
  3. Base cases. Fill row 0 and column 0 directly. They usually hold zeros, ones, or the number of ways to do nothing.
  4. Recurrence and order. Fill cells row by row, left to right, so that the cells a cell depends on are already known.
  5. Answer. Read the bottom-right cell (or wherever the problem points).

Once the table works, check whether a cell needs only the previous row. If so, keep two rows instead of the whole table. This reduces space from O(m times n) to O(n) without changing the logic.

Medium: Longest Common Subsequence (LeetCode 1143)

Longest Common Subsequence (LeetCode 1143)

A subsequence keeps the order of the original string but may skip letters. Given two strings, return the length of the longest subsequence they share. Example: "abcde" and "ace" share "ace", so the answer is 3. Unlike a substring, the letters do not need to be next to each other.

How to think about it

  1. Understand. Order matters, gaps are allowed, and the answer can be zero.
  2. Brute force. Each letter of the first string is either used or skipped, and so is each letter of the second. Checking every combination is exponential.
  3. Find the waste. The question "LCS of A[i:] and B[j:]" appears again and again when the recursion branches. Only about m times n distinct pairs exist.
  4. Optimise. Let dp[i][j] be the LCS of the first i letters of A and the first j letters of B. If A[i-1] equals B[j-1], that letter can extend the best answer for the shorter prefixes, so dp[i][j] = dp[i-1][j-1] + 1. Otherwise, drop one letter from either side and take the better result: dp[i][j] = max(dp[i-1][j], dp[i][j-1]).
  5. Dry run. A = "ace", B = "abc". The table below shows rows for A (with an empty row first) and columns for B. Only matching letters add one to the diagonal.
(empty)abc
(empty)0000
a0111
c0112
e0112

The bottom-right cell is 2, which is the length of "ac". Reading the table shows why: the "a" and "c" matches add one to the diagonal, and "e" never matches.

Code

def longest_common_subsequence(text1, text2):
    m, n = len(text1), len(text2)
    dp = [[0] * (n + 1) for _ in range(m + 1)]   # row 0 and column 0 stay 0
    for i in range(1, m + 1):
        for j in range(1, n + 1):
            if text1[i - 1] == text2[j - 1]:
                dp[i][j] = dp[i - 1][j - 1] + 1      # the letters match: extend
            else:
                dp[i][j] = max(dp[i - 1][j], dp[i][j - 1])   # drop one letter
    return dp[m][n]

print(longest_common_subsequence("abcde", "ace"))
print(longest_common_subsequence("abc", "abc"))
print(longest_common_subsequence("abc", "def"))
print(longest_common_subsequence("ezupkr", "ubmrapg"))

Medium: Target Sum (LeetCode 494)

Target Sum (LeetCode 494)

You have a list of non-negative integers. For each number you may put a plus or a minus sign in front of it. Count the sign assignments whose total equals the target. Example: nums = [1, 1, 1, 1, 1] and target 3 give 5 ways, because exactly one of the five 1s must be negative.

How to think about it

  1. Understand. Every number is used exactly once, with either sign. We count assignments, not distinct totals.
  2. Brute force. There are 2 to the power n sign patterns. Trying each one and summing is exponential.
  3. Find the waste. Split the numbers into a positive group P and a negative group N. The sum of P minus the sum of N equals the target, and the sum of P plus the sum of N equals the total. Adding the two equations gives sum of P = (total + target) / 2. So the problem becomes: count the subsets whose sum is that value. That is a classic knapsack-style count.
  4. Optimise. dp[i][s] is the number of subsets of the first i numbers that sum to s. Base case dp[0][0] = 1 (the empty subset). For each number x, a subset either leaves x out (dp[i-1][s]) or includes it (dp[i-1][s-x], when s is at least x). Add the two.
  5. Dry run. nums = [1, 1], target 0. Total is 2 and the goal is (2 + 0) / 2 = 1. Row 0: dp = [1, 0]. After the first 1: dp[1] = [1, 1] (empty subset, or the single 1). After the second 1: dp[2][1] = dp[1][1] + dp[1][0] = 1 + 1 = 2. Answer 2: +1 -1 and -1 +1.

Code

def find_target_sum_ways(nums, target):
    total = sum(nums)
    if abs(target) > total or (total + target) % 2:
        return 0                          # no assignment can reach the target
    goal = (total + target) // 2          # the sum of the positive group
    n = len(nums)
    dp = [[0] * (goal + 1) for _ in range(n + 1)]
    dp[0][0] = 1                          # one way to make 0 from nothing
    for i in range(1, n + 1):
        x = nums[i - 1]
        for s in range(goal + 1):
            dp[i][s] = dp[i - 1][s]       # x is left out of the positive group
            if s >= x:
                dp[i][s] += dp[i - 1][s - x]   # x is put in the positive group
    return dp[n][goal]

Medium: Unique Paths (LeetCode 62)

Unique Paths (LeetCode 62)

A robot starts at the top-left corner of an m by n grid and wants to reach the bottom-right corner. It can move only right or down. Return the number of distinct paths. Example: a 3 by 7 grid has 28 paths.

How to think about it

  1. Understand. Only right and down moves, so every path has the same number of moves.
  2. Brute force. Try every sequence of moves. The count of sequences is a binomial coefficient, and enumerating them is far too slow for large grids.
  3. Find the waste. The number of paths to a cell is the same whatever route led to it. Every cell can be reached from above or from the left, so its count is the sum of those two.
  4. Optimise. dp[r][c] = dp[r-1][c] + dp[r][c-1]. The first row and first column are all 1, because there is only one way to walk straight along an edge.
  5. Dry run. On a 3 by 3 grid, the table starts as rows [1, 1, 1], [1, ?, ?], [1, ?, ?]. Cell (1,1) = 1 + 1 = 2. Cell (1,2) = 1 + 2 = 3. Cell (2,1) = 2 + 1 = 3. Cell (2,2) = 3 + 3 = 6. Answer 6.

Code

def unique_paths(m, n):
    dp = [[1] * n for _ in range(m)]        # first row and column stay 1
    for r in range(1, m):
        for c in range(1, n):
            dp[r][c] = dp[r - 1][c] + dp[r][c - 1]   # from above plus from the left
    return dp[m - 1][n - 1]

print(unique_paths(3, 7))
print(unique_paths(3, 2))
print(unique_paths(1, 1))
print(unique_paths(10, 10))

Hard: Regular Expression Matching (LeetCode 10)

Regular Expression Matching (LeetCode 10)

Implement matching for a pattern that supports two symbols: . matches any single character, and * matches zero or more of the element right before it. The match must cover the whole string. Examples: "aa" does not match "a"; "aa" matches "a*"; "ab" matches ".*"; "aab" matches "c*a*b".

How to think about it

  1. Understand. The whole string must match, not a part of it. A * always belongs to the character before it, so the pattern is read in pairs when a star appears. The star can match zero copies, which is what makes it tricky.
  2. Brute force. Recurse on the first character. If the next pattern symbol is a star, try matching zero copies (skip the pair) or one more copy (consume one string character and keep the same pattern). Without memory, the same pairs of positions are explored again and again.
  3. Find the waste. Whether the string from position i matches the pattern from position j depends only on i and j. That is at most (m + 1) times (n + 1) questions.
  4. Optimise. dp[i][j] is true when the first i characters of the string match the first j pattern symbols. Base: dp[0][0] is true. Empty string against a pattern like "a*b*" is true when each star removes its pair, so dp[0][j] = dp[0][j-2] when the pattern symbol at j is a star. For the rest: if the pattern symbol equals the string character or is a dot, dp[i][j] = dp[i-1][j-1]. If it is a star, dp[i][j] = dp[i][j-2] (zero copies) or, if the character before the star matches the current string character, dp[i][j] = dp[i][j] or dp[i-1][j] (one more copy).
  5. Dry run. s = "aa", p = "a*". dp[0][0] is true. The star at p[1] gives dp[0][2] = dp[0][0] = true. For i=1, j=1, "a" matches "a", so dp[1][1] is true. For i=1, j=2 (star): zero copies gives dp[1][0] = false, but the star's element "a" matches s[0], so dp[1][2] = dp[1][2] or dp[0][2] = true. For i=2, j=2: the element "a" matches s[1], so dp[2][2] = dp[1][2] = true. The answer is true.

Code

def is_match(s, p):
    m, n = len(s), len(p)
    dp = [[False] * (n + 1) for _ in range(m + 1)]
    dp[0][0] = True                       # empty string matches empty pattern
    for j in range(2, n + 1):
        if p[j - 1] == "*":
            dp[0][j] = dp[0][j - 2]       # a star with its element can match nothing
    for i in range(1, m + 1):
        for j in range(1, n + 1):
            if p[j - 1] in (s[i - 1], "."):
                dp[i][j] = dp[i - 1][j - 1]          # plain match on the last character
            elif p[j - 1] == "*":
                dp[i][j] = dp[i][j - 2]              # use the star for zero copies
                if p[j - 2] in (s[i - 1], "."):
                    dp[i][j] = dp[i][j] or dp[i - 1][j]   # or one more copy of p[j-2]
    return dp[m][n]

print(is_match("aa", "a"))
print(is_match("aa", "a*"))
print(is_match("ab", ".*"))
print(is_match("mississippi", "mis*is*p*."))
print(is_match("aab", "c*a*b"))

Pattern to rememberFor matching with optional or repeated symbols, let dp[i][j] mean "the first i characters match the first j pattern symbols", and handle each symbol type with its own transition.

Summary

Revise from these one-line definitions. Each term is explained in the unit it names.

Clean code
Code a colleague can read and change safely, with clear names and single-purpose functions.
Code smell
A surface sign of a deeper design problem, such as duplication, magic numbers or a long function.
Refactoring
Changing code structure in small steps while keeping its behaviour, checked by tests.
Magic number
An unexplained literal in code, best replaced by a named constant.
Technical debt
The future cost created by shortcuts, paid back as interest through slower changes.
Linter
A tool that reports likely bugs and suspicious code without changing it.
Formatter
A tool that rewrites layout so style is consistent and never debated in review.
Docstring and doctest
A documentation string, and a test runner that checks the examples written inside it.
Debugging loop
Reproduce, read the error, hypothesise, test the smallest experiment, fix the cause and add a test.
Profiling
Measuring where a program spends its time, so optimisation targets real hot spots.
Semantic versioning
MAJOR.MINOR.PATCH, where major means breaking, minor means compatible features and patch means fixes.
Feature flag
A runtime switch that separates deploying code from releasing it to users.
Percentage rollout
Enabling a flag for a stable share of users, chosen by hashing the user ID.
Test pyramid
Many unit tests, fewer integration tests and few end-to-end tests.
Unit test
A test of one unit in isolation, with dependencies replaced by test doubles.
Integration test
A test that checks several real components working together.
End-to-end test
A test that drives the whole system through its user interface or public API.
TDD
Test-driven development: write a failing test, make it pass, then refactor.
BDD
Behaviour-driven development: examples written as Given, When, Then scenarios.
Test double
A stand-in for a dependency: a stub, a fake or a mock.
Mock
A test double that records calls so the test can assert how it was used.
Coverage
The share of lines or branches that ran during tests. It shows gaps, not correctness.
Throughput
How many requests per second a system completes under load.
Latency percentile
The value below which a given share of requests finish, such as p50 or p95.
Selenium
A library that controls browsers through the WebDriver protocol, usually with explicit waits.
Playwright
A library that controls bundled browsers and waits automatically before actions.
Subsequence
A sequence that keeps the original order but may skip elements.
2D dynamic programming
A table over two dimensions, where each cell is built from neighbouring cells.
Knapsack-style count
Counting subsets that reach a total, filled in a table of items used against sums reached.
