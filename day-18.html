SQL command types and the sample schema

SQL (Structured Query Language) is the language of relational databases. Its statements are grouped into families by what they do. Interviewers often ask you to name them, so learn the families first:

  • DDL (data definition language). Creates and changes structure: CREATE, ALTER, DROP. Day 16 used these.
  • DML (data manipulation language). Changes the rows: INSERT, UPDATE, DELETE.
  • DQL (data query language). Reads rows: SELECT. Many courses fold this into DML.
  • DCL (data control language). Grants and revokes permissions: GRANT, REVOKE.
  • TCL (transaction control language). Manages transactions: BEGIN, COMMIT, ROLLBACK, SAVEPOINT (Day 17).

Almost every interview query is a single SELECT. Its clauses run in a fixed logical order, which explains many surprises, so memorise this order:

  1. FROM and JOIN: build the combined rows.
  2. WHERE: keep only the rows that match a condition. This runs before grouping.
  3. GROUP BY: combine rows into groups.
  4. HAVING: keep only the groups that match a condition.
  5. SELECT: compute the output columns. Aliases defined here cannot be used in WHERE.
  6. DISTINCT, then ORDER BY, then LIMIT.

Key ideaThe order in which the clauses are written is not the order in which they run. WHERE runs before SELECT, so an alias from SELECT cannot appear in WHERE, but it can appear in ORDER BY.

Filtering, NULL and CASE

The WHERE clause keeps rows for which a condition is true. Conditions use comparison operators (=, <> meaning not equal, <, >, <=, >=), the logical operators AND, OR and NOT, and a few helpers:

  • BETWEEN a AND b includes both ends, so it means >= a AND <= b.
  • IN (x, y, z) is a shorthand for a list of equalities.
  • LIKE matches text patterns: % stands for any run of characters, and _ for exactly one character. ILIKE is the case-insensitive version in PostgreSQL.
  • IS NULL and IS NOT NULL test for missing values.

NULL is not a value

NULL means "unknown" or "not applicable". It is not zero, not an empty string, and not equal to anything, including another NULL. A comparison with NULL gives the third truth value, UNKNOWN, and WHERE keeps only rows where the condition is TRUE. Rows where it is FALSE or UNKNOWN are both removed. That single rule causes most NULL surprises.

The truth tables below show how NULL propagates. Read UNKNOWN as "could be true or false":

-- Wrong: never true, because x = NULL is UNKNOWN for every x
SELECT emp_name FROM employees WHERE bonus = NULL;

-- Right: the IS NULL test
SELECT emp_name FROM employees WHERE bonus IS NULL;

The first query returns no rows, because every comparison with NULL is UNKNOWN. The second returns the employees whose bonus is missing: Ben, Dana, Farah and Gus. These are the same rows you would get by reading the employees table and marking the blank bonus cells.

COALESCE and handling NULL values

COALESCE(a, b, c) returns the first argument that is not NULL. It is the standard way to replace missing values for display or arithmetic. Adding a NULL to a number gives NULL, so salary + bonus is NULL for anyone with no bonus, while salary + COALESCE(bonus, 0) gives the total pay.

CASE expressions

CASE is SQL's if-else. It tests conditions in order and returns the value of the first one that is TRUE. If none is TRUE and there is no ELSE, the result is NULL. A CASE can appear anywhere a value can appear, including in SELECT, WHERE and ORDER BY:

SELECT emp_name,
       salary,
       CASE
           WHEN salary >= 90000 THEN 'High'
           WHEN salary >= 60000 THEN 'Mid'
           ELSE 'Entry'
       END AS band
FROM employees
ORDER BY emp_id;

The conditions are checked from top to bottom, so 95000 gets 'High' because the first WHEN matches. Reversing the order would put every salary at 60000 or above into 'Mid' first, which is a common bug. The result is:

Interviewers askWhat does COUNT(*) count compared with COUNT(bonus)? COUNT(*) counts all rows. COUNT(column) counts only the rows where that column is not NULL. On the sample table COUNT(*) is 8 and COUNT(bonus) is 4, because only Asha, Chen, Eli and Hana have a bonus value (Hana's is 0, which is not NULL).

What rows does WHERE NOT (bonus > 0) return on the sample table?

Only rows where bonus is 0 or lower. Hana has bonus 0, so she is returned. Ben, Dana, Farah and Gus have NULL bonus, which makes the condition UNKNOWN, so they are removed. The rows with bonus 15000, 5000 and 2000 are FALSE and also removed.

Why does WHERE dept_id NOT IN (1, 2) not return Farah?

Farah's dept_id is NULL. NULL NOT IN (1, 2) is UNKNOWN, so the row is removed. Only rows that are definitely outside the list are kept. On the sample table that leaves Gus and Hana, whose dept_id is 3.

Aggregation with GROUP BY and HAVING

An aggregate function takes many rows and returns one value. The five standard ones are COUNT, SUM, AVG, MIN and MAX. Without GROUP BY, an aggregate treats the whole filtered table as one group. With GROUP BY, the rows are split into groups by one or more columns, and the aggregate is computed for each group.

Two rules matter in every grouped query:

  • Every column in SELECT must either appear in GROUP BY or be inside an aggregate. Asking for emp_name next to AVG(salary) with no grouping on name is an error, because one group has many names.
  • WHERE filters rows before grouping, so it cannot use an aggregate. HAVING filters groups after grouping, so it can. Filtering on COUNT(*) must use HAVING.

Query 4 counts employees per department, averages the salary, and keeps only departments with at least two employees. NULL is treated as a group of its own, so Farah's row (dept_id NULL) forms a group of size 1, which HAVING removes:

SELECT dept_id,
       COUNT(*) AS headcount,
       ROUND(AVG(salary), 2) AS avg_salary
FROM employees
GROUP BY dept_id
HAVING COUNT(*) >= 2
ORDER BY dept_id;

Query 4 result. Engineering averages (120000 + 95000 + 95000) / 3 = 103333.33, which is rounded to two decimals. Sales averages (70000 + 65000) / 2 = 67500.00. Marketing averages (72000 + 61000) / 2 = 66500.00.

Key ideaThe order is: rows are filtered by WHERE, grouped, filtered by HAVING, and then the SELECT list is computed. Keeping this order in mind answers most "why does this fail" questions.

What is the difference between COUNT(*) and COUNT(bonus) on a grouped query?

COUNT(*) counts every row in each group. COUNT(bonus) counts only the rows in the group where bonus is not NULL. Use COUNT(*) for headcount and COUNT(column) for how many rows have a value.

Joins: inner, outer, cross and self

A join combines rows from two tables that satisfy a condition. The condition is written in the ON clause. Think of the result as a set of pairs, each pair being one row from the left table and one from the right. The join type decides which pairs and which unmatched rows survive.

  • INNER JOIN. Keeps only the pairs where the condition is TRUE. A row with no match on either side disappears.
  • LEFT OUTER JOIN. Keeps all left rows. When a left row has no match, the right-side columns are filled with NULL.
  • RIGHT OUTER JOIN. The mirror image: all right rows are kept. It is rarely used, because a LEFT JOIN with the tables swapped says the same thing.
  • FULL OUTER JOIN. Keeps all rows from both sides, filling in NULL where either side has no match.
  • CROSS JOIN. Every left row paired with every right row, with no condition. Its size is the product of the two row counts.
  • SELF JOIN. A table joined to itself, using two aliases.

Inner join

Query 5 lists each employee with the name of their department. Farah has no department, so she is absent. The Research department has no employees, so it is also absent:

Left join and counting the unmatched

A left join is the tool for "all of the left side, with matches where they exist". Query 6 lists every department with its headcount. Research must still appear, with a count of zero. The count must be COUNT(e.emp_id), not COUNT(*), because COUNT(*) would count the one NULL-filled row that Research produces:

SELECT d.dept_name,
       COUNT(e.emp_id) AS headcount
FROM departments AS d
LEFT JOIN employees AS e ON e.dept_id = d.dept_id
GROUP BY d.dept_id, d.dept_name
ORDER BY d.dept_id;

Full outer join and the anti-join pattern

A full outer join keeps unmatched rows from both sides. Adding a WHERE that asks for rows missing on either side finds all the mismatches in one query. This is the anti-join pattern: "rows in A that have no partner in B", and the same idea in the other direction. Query 7 finds an employee without a department and a department without employees:

SELECT e.emp_name, d.dept_name
FROM employees AS e
FULL OUTER JOIN departments AS d ON d.dept_id = e.dept_id
WHERE e.emp_id IS NULL OR d.dept_id IS NULL
ORDER BY d.dept_name NULLS LAST;

Query 7 result. Two rows. Research has no employee, so its employee column is NULL. Farah has no department, so her department column is NULL.

How many rows does a CROSS JOIN of the 8 employees and the 4 departments produce?

8 times 4, which is 32 rows. A cross join has no condition, so every employee is paired with every department.

Why is Research missing from the inner join but present in the left join?

The inner join keeps only pairs with a matching employee, and Research has none, so it produces no rows. The left join keeps every department and fills the employee columns with NULL when there is no match.

Subqueries, EXISTS versus IN, and set operations

A subquery is a query nested inside another. It can return a single value, a single column, or a whole table, and where it sits decides what it may return:

  • Scalar subquery. Returns exactly one value, used like a constant, for example in a comparison.
  • Column subquery. Returns one column, used with IN or ANY.
  • Table subquery (derived table). Returns rows, used in the FROM clause, and must be given an alias.
  • Correlated subquery. Refers to a column of the outer query, so it is re-evaluated for each outer row.

Query 9: a scalar subquery

The average salary of all employees is 79500, because the eight salaries add up to 636000 and 636000 / 8 = 79500. The subquery computes that value once, and the outer query keeps the rows above it:

SELECT emp_name, salary
FROM employees
WHERE salary > (SELECT AVG(salary) FROM employees)
ORDER BY emp_name;

Query 9 result. Only Asha, Ben and Chen earn more than 79500. Gus, at 72000, does not.

EXISTS versus IN, and the NULL trap

To find departments that have no employees, there are two common forms. NOT EXISTS asks, for each department, whether a matching employee row exists. NOT IN asks whether the department's id is missing from a list of ids. They look similar, but they behave differently when the list contains NULL.

Query 10 uses NOT EXISTS, and it is correct on this data. Research is the only department without employees:

SELECT d.dept_name
FROM departments AS d
WHERE NOT EXISTS (
    SELECT 1
    FROM employees AS e
    WHERE e.dept_id = d.dept_id
);

Query 10 result. One row.

dept_name
Research

Now the same question written with NOT IN. It looks reasonable, and it returns nothing:

SELECT dept_name
FROM departments
WHERE dept_id NOT IN (SELECT dept_id FROM employees);

Result. Zero rows. The subquery returns the dept_id of every employee, and Farah's dept_id is NULL. The test for Research becomes 4 NOT IN (1, 2, 3, NULL). Because the list contains NULL, the answer is UNKNOWN rather than TRUE, and the row is removed. NOT IN is safe only when the list cannot contain NULL.

TrapThe NOT IN result is empty for every department, not only Research. A single NULL in the subquery silently empties the whole answer. Prefer NOT EXISTS for anti-joins, or add WHERE dept_id IS NOT NULL to the subquery.

Key ideaEXISTS asks "is there at least one matching row?" and handles NULL correctly, because a NULL in the inner table never matches anything. IN compares values, and a NULL in its list makes the comparison UNKNOWN.

Set operations

Set operations combine the results of two queries with the same number of columns and compatible types. They treat the results as sets of rows:

  • UNION returns rows from either query, with duplicates removed.
  • UNION ALL returns all rows from both, duplicates included. It is faster, because it skips the duplicate check.
  • INTERSECT returns rows that appear in both queries.
  • EXCEPT returns rows from the first query that do not appear in the second.

Two queries show the difference between UNION and UNION ALL. The first selects dept_id for employees earning at least 95000, which gives 1, 1 and 1 (Asha, Ben and Chen). The second selects dept_id for employees with a positive bonus, which gives 1, 1 and 2 (Asha, Chen and Eli):

SELECT dept_id FROM employees WHERE salary >= 95000
UNION ALL
SELECT dept_id FROM employees WHERE bonus > 0
ORDER BY 1;

Interviewers askWhat is the difference between a correlated and a non-correlated subquery, and which one is re-run for each row? The correlated one refers to the outer query and is re-evaluated for each outer row. The non-correlated one runs once. Databases often rewrite correlated subqueries as joins to speed them up.

Why does NOT IN return zero rows here, even though Research has no employees?

The list of dept_ids from employees includes NULL (Farah). For Research, the test becomes "4 is not equal to 1, 2, 3, or NULL", and a comparison with NULL is UNKNOWN, so the row is removed.

How many rows does SELECT dept_id FROM employees UNION ALL SELECT dept_id FROM departments return?

Eight employee rows plus four department rows, which is 12. UNION ALL keeps duplicates, so the employee values 1, 2 and 3 and the NULL are kept as they are.

Interview questions

Name the SQL command families and give one example of each.

DDL: CREATE TABLE. DML: INSERT, UPDATE, DELETE. DQL: SELECT. DCL: GRANT. TCL: COMMIT.

In what order do the clauses of a SELECT logically run?

FROM and JOIN, then WHERE, then GROUP BY, then HAVING, then SELECT, then DISTINCT, ORDER BY and LIMIT. This is why a WHERE cannot use a column alias from SELECT, but ORDER BY can.

What does WHERE bonus = NULL return, and what should you write instead?

No rows, because a comparison with NULL is UNKNOWN. Write WHERE bonus IS NULL.

What is the difference between WHERE and HAVING?

WHERE filters individual rows before grouping and cannot use aggregates. HAVING filters groups after grouping and can use aggregates such as COUNT(*) or AVG(salary).

How does a LEFT JOIN differ from an INNER JOIN?

An inner join keeps only matching pairs. A left join keeps every row of the left table, filling the right-side columns with NULL when there is no match.

How do you find rows in A that have no partner in B?

Use NOT EXISTS with a correlated subquery, or a LEFT JOIN from A to B with WHERE B.key IS NULL. Both handle NULL correctly. NOT IN is risky when the list can contain NULL.

What is the difference between UNION and UNION ALL?

UNION removes duplicate rows from the combined result and must sort or hash to do so. UNION ALL keeps every row and is faster.

Why is a correlated subquery potentially slow?

It refers to the outer row, so the engine may evaluate it once per outer row. Good indexes on the join columns, or a rewrite as a join, usually fix this.

How do you find the second highest salary?

Use SELECT MAX(salary) FROM employees WHERE salary < (SELECT MAX(salary) FROM employees). On the sample data the answer is 95000, which is shared by Ben and Chen. Using DISTINCT or a window function (Day 19) handles ties explicitly.

DSA: graphs with BFS and DFS

A graph is a set of nodes (vertices) joined by edges. A grid can be a graph too: each cell is a node, and it is joined to its four neighbours (up, down, left and right). Many interview problems on grids are graph problems in disguise.

Two traversals visit every reachable node once:

  • Depth-first search (DFS) goes as deep as possible along one path before backtracking. It uses a stack, which can be the call stack of recursion or an explicit list. It suits "is it reachable" and "fill this region" questions.
  • Breadth-first search (BFS) visits nodes in rings of increasing distance from the start. It uses a queue. It is the right tool for the fewest steps in an unweighted graph, because the first time a node is reached is always by a shortest path.

Both need a visited set. Without it, a graph with a cycle sends the search around forever. Mark a node as visited when you add it to the stack or queue, not when you remove it, or the same node can be added many times.

The four problems today follow the same plan: a region fill (DFS), a copy of a graph (DFS or BFS with a map from original to copy), a multi-source BFS in time (BFS), and a shortest path between words (BFS).

Flood Fill (LeetCode 733)

You are given an image as a grid of colours, a starting cell (sr, sc) and a new colour. Change the starting cell's colour, and every cell connected to it through cells of the same original colour (up, down, left or right). For the image [[1, 1, 1], [1, 1, 0], [1, 0, 1]], starting at row 1, column 1, with new colour 2, the result is [[2, 2, 2], [2, 2, 0], [2, 0, 1]].

How to think about it

  1. Understand. Only cells connected to the start, through cells of the original colour, change. Cells of other colours block the fill. If the new colour equals the old one, nothing needs to change.
  2. Brute force. Scan the whole grid, and for each cell check whether a path of matching colour leads back to the start. That is quadratic work in the number of cells.
  3. Find the waste. The connected region is found once by a traversal from the start. Each cell in the region is visited once, and the traversal never leaves the region.
  4. Optimise. Start a DFS with an explicit stack at the start cell. Record the old colour, paint the start, and then for each popped cell paint and push every neighbour whose colour equals the old colour. Painting before pushing marks the cell as visited. Each cell is handled once, so the work is O(rows times cols).
  5. Dry run. The start cell (1, 1) holds 1, so old is 1, and it is painted 2. Its neighbours (0, 1) and (1, 0) also hold 1, so they are painted and pushed. From those, the fill reaches (0, 0), (0, 2) and (2, 0). The cells (1, 2) and (2, 1) hold 0, so they block the fill. The cell (2, 2) holds 1, but both of its neighbours are 0, so it is not connected to the region and stays 1.

Code

def flood_fill(image, sr, sc, color):
    rows, cols = len(image), len(image[0])
    old = image[sr][sc]
    if old == color:                     # nothing to do, and avoids an endless loop
        return image
    image[sr][sc] = color
    stack = [(sr, sc)]
    while stack:
        r, c = stack.pop()
        for dr, dc in ((1, 0), (-1, 0), (0, 1), (0, -1)):
            nr, nc = r + dr, c + dc
            if 0 <= nr < rows and 0 <= nc < cols and image[nr][nc] == old:
                image[nr][nc] = color    # paint before pushing, so it is visited once
                stack.append((nr, nc))
    return image


image = [[1, 1, 1], [1, 1, 0], [1, 0, 1]]
for row in flood_fill(image, 1, 1, 2):
    print(row)
[2, 2, 2]
[2, 2, 0]
[2, 0, 1]

Time O(rows times cols) · Space O(rows times cols) in the worst case for the stack

TrapIf the new colour equals the old colour and you skip the early return, the algorithm keeps finding cells of the "old" colour that it has just painted, and it never terminates. Always check this case first.

Pattern to rememberA connected region on a grid is one DFS or BFS from a start cell. Mark cells when you push them so none is processed twice.

Clone Graph (LeetCode 133)

Given a reference to a node in a connected undirected graph, return a deep copy of the whole graph. Each node has a value and a list of neighbours. The copy must have new node objects, with the same values and the same connections. For the graph where node 1 is joined to 2 and 4, node 2 to 1 and 3, node 3 to 2 and 4, and node 4 to 1 and 3, the copy has the same four connections.

How to think about it

  1. Understand. A copy must not share any node with the original. The graph has cycles, so a naive recursive copy would loop forever. Each original node must map to exactly one copy.
  2. Brute force. Recursively copy each neighbour, creating a new node every time you reach one. This copies a node once for each path that leads to it, which is exponential in the worst case, and it never stops on a cycle.
  3. Find the waste. What is needed is a single copy per original node, and a way to find it when it is reached again. A dictionary from original node to copy does both.
  4. Optimise. Traverse the original graph with a stack. When a node is first seen, create its copy and store it in the dictionary. For each neighbour, create its copy if it has none yet, and add the copy of the neighbour to the copy of the current node. Every node is processed once, and every edge is added once from each side.
  5. Dry run. Start at node 1. Its copy is created. Neighbour 2 gets a copy and is pushed, and so does 4. Node 2 is processed: its neighbour 1 already has a copy, and 3 gets one. The dictionary holds all four copies by the time the stack is empty.

Code

class Node:
    def __init__(self, val=0, neighbors=None):
        self.val = val
        self.neighbors = neighbors if neighbors is not None else []


def clone_graph(node):
    if node is None:
        return None
    copies = {node: Node(node.val)}          # original node -> its single copy
    stack = [node]
    while stack:
        current = stack.pop()
        for nb in current.neighbors:
            if nb not in copies:
                copies[nb] = Node(nb.val)
                stack.append(nb)
            copies[current].neighbors.append(copies[nb])
    return copies[node]


def build(adj):
    nodes = {v: Node(v) for v in adj}
    for v, nbs in adj.items():
        nodes[v].neighbors = [nodes[u] for u in nbs]
    return nodes[1]


def adjacency(start):
    result = {}
    seen = {start}
    stack = [start]
    while stack:
        node = stack.pop()
        result[node.val] = sorted(n.val for n in node.neighbors)
        for n in node.neighbors:
            if n not in seen:
                seen.add(n)
                stack.append(n)
    return [result[v] for v in sorted(result)]

Rotting Oranges (LeetCode 994)

A grid holds 0 for an empty cell, 1 for a fresh orange and 2 for a rotten one. Every minute, each fresh orange next to a rotten one (up, down, left or right) becomes rotten. Return the minimum number of minutes until no fresh orange is left, or -1 if some never rot. For [[2, 1, 1], [1, 1, 0], [0, 1, 1]] the answer is 4.

How to think about it

  1. Understand. Rot spreads from every rotten orange at the same time, one ring per minute. The answer is the number of rings needed to reach the last fresh orange. If a fresh orange is not connected to any rotten one, the answer is -1. If there are no fresh oranges, the answer is 0.
  2. Brute force. Simulate minute by minute: each minute, scan the whole grid and rot every fresh orange next to a rotten one. Each minute costs a full scan, and there can be many minutes, so this is O(minutes times cells).
  3. Find the waste. The scan looks at every cell, but only the cells that rotted in the previous minute can spread rot further. Only those cells need to be visited.
  4. Optimise. Multi-source BFS. Put all initially rotten oranges in a queue at once. Process the queue one layer at a time: each layer is one minute. Each fresh orange that a rotten one reaches is marked rotten and added to the next layer. Count the layers, and track the number of fresh oranges so the answer is known at the end. Every cell enters the queue at most once, so the work is O(rows times cols).
  5. Dry run. For the example, the rotten orange at (0, 0) is the only source. Minute 1 rots (0, 1) and (1, 0). Minute 2 rots (0, 2) and (1, 1). Minute 3 rots (2, 1), because (1, 1) is rotten and (2, 1) is fresh. Cell (1, 2) is empty, so it never rots. Minute 4 rots (2, 2), which is reached from (2, 1). No fresh orange remains, so the answer is 4.

Code

from collections import deque


def oranges_rotting(grid):
    rows, cols = len(grid), len(grid[0])
    grid = [row[:] for row in grid]          # work on a copy
    queue = deque()
    fresh = 0
    for r in range(rows):
        for c in range(cols):
            if grid[r][c] == 2:
                queue.append((r, c))
            elif grid[r][c] == 1:
                fresh += 1
    minutes = 0
    while queue and fresh:
        for _ in range(len(queue)):          # one layer = one minute
            r, c = queue.popleft()
            for dr, dc in ((1, 0), (-1, 0), (0, 1), (0, -1)):
                nr, nc = r + dr, c + dc
                if 0 <= nr < rows and 0 <= nc < cols and grid[nr][nc] == 1:
                    grid[nr][nc] = 2
                    fresh -= 1
                    queue.append((nr, nc))
        minutes += 1
    return minutes if fresh == 0 else -1


print(oranges_rotting([[2, 1, 1], [1, 1, 0], [0, 1, 1]]))
print(oranges_rotting([[2, 1, 1], [0, 1, 1], [1, 0, 1]]))
print(oranges_rotting([[0, 2]]))
4
-1
0

Time O(rows times cols) · Space O(rows times cols)

TrapRunning one BFS per rotten orange and taking the maximum is wrong and slow. All rotten oranges must start together, so that the minutes are counted from the same moment.

Pattern to rememberWhen many sources spread at the same speed and you want the time until everything is reached, push all sources into the queue first and count BFS layers.

Word Ladder (LeetCode 127)

Given a begin word, an end word and a list of words, find the length of the shortest transformation sequence from begin to end. Each step changes exactly one letter, and every intermediate word must be in the list. The end word must be in the list. Return 0 if no sequence exists. For begin "hit", end "cog" and the list hot, dot, dog, lot, log, cog, the answer is 5: hit, hot, dot, dog, cog.

How to think about it

  1. Understand. Words are nodes, and two words are joined when they differ in exactly one letter. We want the shortest path, so the answer is the number of words on the path, counting both ends.
  2. Brute force. Try every ordering of the word list and check each one for valid steps. This is factorial in the number of words.
  3. Find the waste. Comparing every pair of words costs O(N squared) and checks many pairs that differ in more than one letter. Each word has at most L times 26 possible one-letter changes, where L is the word length. Generating those neighbours directly is much cheaper.
  4. Optimise. Breadth-first search from the begin word. The queue holds (word, steps). For each word, generate every one-letter change, keep the ones in the list that are not visited yet, mark them visited and enqueue them with steps plus one. The first time the end word is dequeued, its steps are the shortest. The cost is O(N times L times 26), which is fast enough.
  5. Dry run. Start with (hit, 1). Changing one letter of hit gives hot, so (hot, 2) is queued. From hot the words dot and lot are queued at 3. From dot the word dog is queued at 4. From dog the word cog is queued at 5, and it is dequeued at 5, which is the answer.

Code

from collections import deque


def ladder_length(begin, end, word_list):
    words = set(word_list)
    if end not in words:
        return 0
    queue = deque([(begin, 1)])
    visited = {begin}
    while queue:
        word, steps = queue.popleft()
        if word == end:
            return steps
        for i in range(len(word)):
            for ch in "abcdefghijklmnopqrstuvwxyz":
                candidate = word[:i] + ch + word[i + 1:]
                if candidate in words and candidate not in visited:
                    visited.add(candidate)
                    queue.append((candidate, steps + 1))
    return 0


print(ladder_length("hit", "cog", ["hot", "dot", "dog", "lot", "log", "cog"]))
print(ladder_length("hit", "cog", ["hot", "dot", "dog", "lot", "log"]))

0

Time O(N times L times 26) · Space O(N times L)

Interviewers askHow would you speed this up? Build a map from each wildcard pattern, such as h*t, to the words that match it. Then each neighbour lookup is one dictionary access, and the total work drops because fewer candidates are generated.

TrapCounting edges instead of words gives one less than the answer. The problem counts the words in the sequence, so the begin word counts as 1.

Pattern to rememberShortest path in an unweighted graph is BFS. Whenever the neighbours of a node can be generated, you do not need to store the graph at all.
