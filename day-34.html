How React turns code into the screen

React is a JavaScript library for building user interfaces. Its core idea is that you describe what the screen should look like for a given set of data, and React works out how to change the page to match. This style is called declarative. The opposite style is imperative: you write each step yourself, such as "find this button, change its text, add a CSS class, then hide that panel."

The page the browser shows is built from the DOM (Document Object Model), a tree of elements that JavaScript can read and change. Changing the DOM by hand works for small pages, but it becomes error prone when many parts of the screen depend on the same data. React lets you write the description once and keeps the DOM in step with it.

Components: functions that return UI

A component is a function that takes an input object called props and returns a description of UI. Component names start with a capital letter, because React uses that rule to tell your components apart from built-in HTML tags such as div or button.

function Greeting({ name }) {
  return <h1>Hello, {name}!</h1>;
}

export default function App() {
  return (
    <main>
      <Greeting name="Asha" />
      <Greeting name="Ravi" />
    </main>
  );
}

Read this example step by step. Greeting receives one prop called name. The curly braces in {name} mean "put the value of this JavaScript expression here". App renders two Greeting components, each with a different name. The screen therefore shows two headings, "Hello, Asha!" and "Hello, Ravi!". Because each component is just a function, you can call it many times with different props and get different output.

JSX: HTML-like syntax inside JavaScript

JSX is the syntax used in the examples above. It looks like HTML, but it is JavaScript. A build tool (Babel, SWC or esbuild, depending on the project) turns each JSX tag into a plain function call. For example, <h1>Hello</h1> becomes a call that creates an object describing an h1 element with the text "Hello". You never write those calls yourself, but knowing this explains most JSX rules.

These are the rules you must know for interviews and for everyday code:

  • A component must return one root element. Use a fragment, written <>...</>, when you need several siblings without an extra wrapper div.
  • Use className instead of class, and htmlFor instead of for, because class and for are reserved words in JavaScript.
  • Event handlers use camelCase names such as onClick and onChange, and you pass a function, not a string.
  • Every tag must be closed. Void elements such as input need a self-closing slash, as in <input />.
  • Comments inside JSX use the form {/* comment */}.

TrapWriting {count && <p>...</p>} when count is the number 0 renders the digit 0 on the screen, because 0 && anything evaluates to 0 and React draws numbers. Compare with {count > 0 && ...} instead, which gives a true or false value that React skips.

function Inbox({ count }) {
  return (
    <div>
      {count > 0 && <p>You have {count} new messages</p>}
    </div>
  );
}

Rendering, the virtual DOM and reconciliation

When state or props change, React calls your component function again. The function returns a new description of the UI, which is a tree of plain JavaScript objects called React elements. This tree is the virtual DOM: a lightweight copy of the UI kept in memory. Creating these objects is cheap. Touching the real DOM is expensive, so React avoids it when it can.

The next step is reconciliation. React compares the new tree with the previous one and works out the smallest set of changes needed. Then it applies those changes to the real DOM in one batch. It is a common mistake to think the virtual DOM is always faster than manual DOM updates. The real benefit is that you write simple declarative code and React handles the updating efficiently.

Reconciliation follows two rules that interviewers like to ask about:

  1. Different element type at the same position. React throws away the old subtree, removes its DOM nodes and destroys all state inside it, then builds the new subtree from scratch. Changing a div into a section counts as a different type.
  2. Same element type at the same position. React keeps the DOM node and any state, updates the props that changed, and then compares the children in the same way.
function Profile({ isEditing }) {
  return isEditing ? <input defaultValue="Asha" /> : <p>Asha</p>;
}

Toggling isEditing swaps an input for a p. These are different types, so the input and whatever the user typed into it are destroyed. Keep a component in the same position and the same type if you want its state to survive.

Keys: how React matches list items

When you render a list, React needs a way to match each item in the old list with the same item in the new list. You give each item a key. A key must be stable (the same item always has the same key), unique among its siblings, and must not be random, because random keys change on every render and force React to rebuild the item each time.

function TodoList({ todos }) {
  return (
    <ul>
      {todos.map((todo) => (
        <li key={todo.id}>{todo.text}</li>
      ))}
    </ul>
  );
}

Suppose the list is [A, B, C] and the user adds X at the front. With stable ids, React sees that A, B and C still exist and only inserts a new item for X. With array indexes as keys, index 0 now holds X, so React reuses the item that used to be A for X. Any text the user typed into A's input now appears inside X. Index keys are acceptable for lists that never change order, but they cause bugs as soon as items are inserted, removed or reordered.

TrapKeys are used by React for matching and are not passed to the component as props. If the child needs the id, pass it as a separate prop such as id={todo.id}.

Why this matters in an interview

A crisp answer covers four points: React re-runs component functions when state changes, it builds a virtual tree, it reconciles that tree against the previous one using element types and keys, and it commits only the necessary changes to the DOM. Those four points explain most React behaviour, including why state is lost when a component changes type and why index keys cause bugs.

What does React do when a component's state changes?

React calls the component function again to get a new tree of elements (the virtual DOM). It compares that tree with the previous one during reconciliation, works out the smallest set of changes, and applies them to the real DOM. The component's own variables are recreated on each render, so state is kept by React, not by the function's local variables.

Why should you avoid using array indexes as keys for a list that can be reordered?

React matches old and new children by key. If the key is the index, the item at position 0 is always matched with the old item at position 0, even if the data at that position is now a different item. React then reuses the old item's DOM node and state for the wrong data, so input text and focus can end up attached to the wrong row. Stable, unique ids such as database ids fix this.

State, props and data flow

Every React application is a tree of components, and data moves through that tree in a predictable way. Understanding where each piece of data lives is the foundation for everything else in React.

Props: inputs owned by the parent

Props are the inputs a parent passes to a child, such as name="Asha" in the earlier example. A child must treat props as read-only. It may read them and use them to decide what to render, but it must never change them. This is the rule of one-way data flow: data flows down the tree through props, and when a child needs to tell its parent that something happened, the parent passes down a function and the child calls it.

State: data a component owns

State is data that a component owns and that changes over time, such as the current value of a counter or whether a menu is open. In a function component, you create state with the useState hook (explained fully later in this page). When you change state with its setter function, React schedules a new render of that component.

One detail trips up many candidates. A state variable keeps the same value for the whole render in which it was read. Calling the setter does not change the variable in the code that is currently running. It asks React to render again with the new value.

import { useState } from "react";

function Counter() {
  const [count, setCount] = useState(0);

  function handleDoubleClick() {
    setCount(count + 1);
    setCount(count + 1);
  }

  return <button onClick={handleDoubleClick}>Clicked {count} times</button>;
}

Both calls in handleDoubleClick read the same count, which is 0 in that render. Both set the state to 0 + 1, so one click increases the count by only 1. The fix is the updater form, which receives the latest queued value as an argument:

function handleDoubleClick() {
  setCount((c) => c + 1);
  setCount((c) => c + 1);
}

Now React runs the two updaters in order, first 0 becomes 1, then 1 becomes 2, so one click adds 2. Use the updater form whenever the new state depends on the old state.

State must also be treated as immutable. Changing an object or array in place does not tell React anything happened, so the screen will not update. Create a new object or array instead:

// Wrong: mutates the existing object, so React does not re-render
user.name = "Ravi";
setUser(user);

// Right: creates a new object with the changed field
setUser({ ...user, name: "Ravi" });

A useful test: if the value is needed by a parent, a sibling or a distant component, it probably belongs higher up. If only one component reads and writes it, keep it as local state.

Prop drilling and lifting state up

Prop drilling happens when a value is passed through several components that do not use it, only to reach a component deep in the tree. It is not a bug, and for two or three levels it is often the clearest option. It becomes painful when many layers repeat the same prop.

Lifting state up means moving state to the nearest common ancestor of the components that need it. If two sibling components must show the same value, the state goes in their parent, which passes the value down and passes an update function down to the child that changes it. This keeps a single source of truth.

Context versus Redux

Context is React's built-in way to make a value available to a whole subtree without passing it as props at every level. You create a context with createContext, supply a value with a Provider, and read it with useContext.

import { createContext, useContext, useState } from "react";

const ThemeContext = createContext("light");

function SaveButton() {
  const theme = useContext(ThemeContext);
  return <button className={theme}>Save</button>;
}

export function App() {
  const [theme, setTheme] = useState("dark");
  return (
    <ThemeContext.Provider value={theme}>
      <SaveButton />
      <button onClick={() => setTheme(theme === "dark" ? "light" : "dark")}>
        Toggle theme
      </button>
    </ThemeContext.Provider>
  );
}

SaveButton reads the theme without receiving it as a prop. The button in App changes the state, and the new value flows into the provider. If there were no provider above SaveButton, useContext would return the default value passed to createContext, here "light".

TrapContext does not make a value cheaper to pass. When the provider's value changes, every component that reads the context re-renders. Passing an object literal such as value={{ theme, setTheme }} also creates a new object on every render of the provider, so consumers re-render even when nothing they use has changed. Wrap such objects in useMemo.

Redux is a separate state management library. It keeps the application state in one store. Components read slices of that store with selectors, and they change it by dispatching actions that reducers handle. Reducers are pure functions that return a new state. The official recommended way to write Redux today is Redux Toolkit, which provides helpers such as createSlice and configureStore and removes most of the boilerplate that older Redux code needed. Redux also offers developer tools that show each action and the state before and after it.

The clean interview answer is this: Context is a delivery mechanism, not a state manager. It delivers a value down the tree. Redux, Zustand and similar libraries manage state and decide how updates happen. Context works well for values that change rarely, such as the current user, the theme or the language. For frequently changing state shared across many components, a store with selectors (Redux Toolkit or Zustand) usually performs better because components subscribe only to the data they select.

What is the difference between props and state?

Props are inputs passed from a parent to a child, and the child must treat them as read-only. State is data owned by a component that changes over time, and the component changes it through a setter. A change to state re-renders the component that owns it, while a change to props happens when the parent re-renders with new values.

When would you choose Context over Redux, and when is the reverse true?

Choose Context to share a value that changes rarely with many components, such as the theme, the logged-in user or the locale, instead of passing it through many layers. Choose a store library such as Redux Toolkit when the shared state changes often, has complex update logic, or must be read selectively by many components, because selectors let each component re-render only when the data it reads changes. Context delivers values, while Redux manages state.

Hooks in depth

Hooks are functions whose names start with use. They let a function component hold state, run side effects and read shared values. Before hooks, state and lifecycle behaviour needed class components, and most new React code is written with hooks.

The rules of hooks

Hooks depend on the order in which they are called. React stores the state of a component's hooks in a list, and on each render it reads that list by position. So the rules are:

  1. Call hooks only at the top level of a component or a custom hook. Never call them inside a condition, a loop or a nested function.
  2. Call hooks in the same order on every render.
  3. Call hooks only from React function components or from custom hooks.
function Broken({ loggedIn }) {
  if (loggedIn) {
    // Breaks rule 1: this hook is skipped when loggedIn is false
    const [name, setName] = useState("guest");
  }
  const [count, setCount] = useState(0);
  return <p>{count}</p>;
}

When loggedIn changes from true to false, the list of hooks changes shape. The useState that holds count then receives the state that belonged to name, and the component shows the wrong data. The eslint plugin eslint-plugin-react-hooks reports these mistakes, and it is worth enabling it in every React project.

useState: local state with a setter

The signature is const [value, setValue] = useState(initialValue). The initial value is used only on the first render. If computing it is expensive, pass a function instead, so React calls it only once:

const [rows, setRows] = useState(() => buildLargeTable());

Without the arrow function, buildLargeTable() would run on every render even though its result is ignored after the first one. Updates from one event handler are batched, which means React groups several setter calls into a single render. Because of batching, reading state right after calling the setter still shows the old value. The new value appears in the next render.

useEffect: synchronising with the outside world

An effect is code that connects a component to something outside React, such as a timer, a subscription, a browser API or a network request. Effects are declared with useEffect(setup, dependencies). React runs the setup function after the component has rendered and the screen has been updated. The dependency array controls when the effect runs again:

  • No array: the effect runs after every render.
  • An empty array []: the effect runs once, after the first render.
  • An array with values, such as [userId]: the effect runs after the first render and again whenever one of those values changes (React compares them with Object.is).

If the setup function returns a function, React calls it as cleanup before the effect runs again and when the component is removed. Cleanup is how you stop timers and remove listeners so they do not leak.

import { useEffect, useState } from "react";

function Clock() {
  const [now, setNow] = useState(() => new Date().toLocaleTimeString());

  useEffect(() => {
    const id = setInterval(() => {
      setNow(new Date().toLocaleTimeString());
    }, 1000);
    return () => clearInterval(id);
  }, []);

  return <p>{now}</p>;
}

The empty dependency array means the timer starts once when the clock appears. The cleanup function stops it when the clock is removed. Without the cleanup, the interval would keep running and calling setNow on a component that no longer exists.

In development, React's StrictMode mounts each component, runs its effects, runs the cleanup and runs the effects again. This is deliberate. It exposes effects that have no cleanup or that break if they run twice. If your app shows different behaviour after this double run, the effect is missing a cleanup.

Data fetching needs a cleanup too

A common bug is a race condition. Suppose the user changes userId quickly, so two requests are in flight. If the first response arrives last, it overwrites the newer data. An ignore flag in the cleanup prevents that:

useEffect(() => {
  let ignore = false;
  fetch(`/api/users/${userId}`)
    .then((res) => res.json())
    .then((data) => {
      if (!ignore) setUser(data);
    });
  return () => {
    ignore = true;
  };
}, [userId]);

When userId changes, React runs the cleanup for the previous effect first, which sets ignore to true for that request. The old response is then discarded. An AbortController can also cancel the request itself. Frameworks and libraries such as TanStack Query handle this and caching for you, which is usually a better choice than hand-written fetch effects in large apps.

TrapDo not use an effect to compute a value from props or state. Calculate it during render, as in const total = items.length * price. An effect that copies derived values into state causes an extra render and can show stale values for a moment. Use useMemo only when the calculation is actually expensive.

useRef: a value that persists without re-rendering

useRef(initial) returns an object with a single property, current. React keeps the same object for the lifetime of the component, and changing current does not trigger a render. Two common uses are reading a DOM element and storing a value such as a timer id.

import { useRef } from "react";

function SearchBox() {
  const inputRef = useRef(null);
  return (
    <>
      <input ref={inputRef} placeholder="Search" />
      <button onClick={() => inputRef.current.focus()}>Focus
    </>
  );
}

React sets inputRef.current to the real input element after it mounts. The click handler then calls focus() on that element. The ref is read in an event handler, which runs after rendering, so it is safe there.

Remember the difference between a ref and state. Use state for anything that should appear on screen and cause a re-render when it changes. Use a ref for values the rendering does not depend on.

useReducer: state with many related transitions

When state has several fields that change together, or when the next state depends on a named action, useReducer keeps the logic in one place. A reducer is a pure function that takes the current state and an action and returns the next state.

import { useReducer } from "react";

function reducer(state, action) {
  switch (action.type) {
    case "increment":
      return { count: state.count + 1 };
    case "reset":
      return { count: 0 };
    default:
      throw new Error("Unknown action: " + action.type);
  }
}

function Tally() {
  const [state, dispatch] = useReducer(reducer, { count: 0 });
  return (
    <>
      <p>{state.count}</p>
      <button onClick={() => dispatch({ type: "increment" })}>Add</button>
      <button onClick={() => dispatch({ type: "reset" })}>Reset</button>
    </>
  );
}

The component describes what happened (dispatches an action) and the reducer decides how the state changes. Reducers are easy to test on their own because they have no side effects. The same reducer works with Context to share state across a subtree, a pattern that handles many small apps without Redux.

useMemo and useCallback: keeping values stable

useMemo(() => compute(), dependencies) caches the result of a calculation and recomputes it only when a dependency changes. useCallback(fn, dependencies) does the same job for a function: it returns the same function object until a dependency changes. useCallback(fn, deps) is equivalent to useMemo(() => fn, deps).

These hooks matter in two situations. The first is an expensive calculation that would run on every render. The second is a value passed to a child wrapped in React.memo, or used as a dependency of another hook. A new function object on every render would make the memoised child re-render or make an effect run again. Measure first with the React DevTools Profiler, because memoising everything adds code, comparisons and memory with no benefit.

useContext: reading shared values

useContext(MyContext) returns the value from the nearest matching provider above the component. It re-renders the component whenever that value changes. The Context example in the state section shows the basic pattern.

Other hooks worth knowing

  • useId generates a unique id that is stable between server and client rendering. It is used to connect a label and an input for accessibility.
  • useLayoutEffect has the same signature as useEffect, but React runs it after the DOM changes and before the browser paints. Use it to measure layout and apply an immediate correction. Prefer useEffect for everything else.
  • useTransition marks a state update as non-urgent, so typing and clicking stay responsive while a slow update renders. useDeferredValue does something similar for a value: it lets an expensive view lag slightly behind a fast-changing input.
  • useSyncExternalStore subscribes a component to an external store, such as a browser API or a third-party state container, in a way that is safe during concurrent rendering.
  • use (added in React 19) reads a promise or a context. Unlike other hooks, it may be called inside a condition or a loop.

Custom hooks: sharing stateful logic

A custom hook is a function whose name starts with use and that calls other hooks. It lets you reuse stateful logic across components. Each component that calls the custom hook gets its own separate state. The hook shares code, not state.

import { useCallback, useState } from "react";

export function useToggle(initial = false) {
  const [on, setOn] = useState(initial);
  const toggle = useCallback(() => setOn((value) => !value), []);
  return [on, toggle];
}

A component uses it as const [open, toggleOpen] = useToggle();. The updater form setOn((value) => !value) reads the latest value itself, so the toggle function needs no dependencies and useCallback can return the same function on every render. This is a good example of why the updater form and useCallback work well together.

Why must hooks always be called in the same order?

React keeps a component's hook state in an ordered list and matches each call to its entry by position. If a hook is skipped or called in a different order on a later render, the list no longer matches the calls, and state from one hook is read by another. That is why hooks must be called at the top level, unconditionally, in every render.

What does an empty dependency array mean for useEffect, and why does a cleanup function matter?

An empty array means the effect runs once after the first render, not on every render. The cleanup function returned from the effect runs before the next run of the effect and when the component unmounts. It stops timers, cancels subscriptions and discards stale work. Without it, a timer or listener created by the effect keeps running after the component is gone.

What is the difference between useRef and useState?

Both keep a value across renders. Changing state with its setter schedules a re-render, and the new value is returned on the next render. Changing ref.current does not re-render the component, and the object is the same on every render. Use state for values shown on screen and refs for DOM nodes, timer ids and other values that rendering does not depend on.

Forms: controlled and uncontrolled inputs

Forms are where many React questions come from, because they combine state, events and validation. The central idea is who owns the value of an input: React or the browser DOM.

Controlled inputs

In a controlled input, React owns the value. The input's value comes from state, and its onChange handler writes the new text back into state. The state is the single source of truth, so you can validate or transform the value at any time.

import { useState } from "react";

export function SignupForm() {
  const [email, setEmail] = useState("");

  function handleSubmit(event) {
    event.preventDefault();
    console.log("submitting", email);
  }

  return (
    <form onSubmit={handleSubmit}>
      <label htmlFor="email">Email</label>
      <input
        id="email"
        type="email"
        value={email}
        onChange={(event) => setEmail(event.target.value)}
      />
      <button type="submit">Sign up</button>
    </form>
  );
}

Each keystroke fires onChange. The handler reads event.target.value, which is the text now in the box, and stores it. React re-renders, and the input shows the value from state. event.preventDefault() stops the browser from reloading the page on submit, which is the default form behaviour. The htmlFor attribute connects the label to the input by id, which lets screen readers and clicks on the label reach the field.

TrapIf you write value={email} without an onChange handler, React makes the field read-only and logs a warning, because the state can never change. Either add the handler or use defaultValue for an uncontrolled field.

Uncontrolled inputs

In an uncontrolled input, the DOM holds the value and React only reads it when needed. You set the starting text with defaultValue and read the final text with a ref, or with the browser's FormData object during submit. Uncontrolled inputs are simpler for small forms where you do not need to react to each keystroke. File inputs are always uncontrolled, because the browser does not allow scripts to set their value.

Validation and submission

Store error messages in state, and compute them from the current values. Validate on change for instant feedback, or on submit to avoid showing errors while the user is still typing. Disable the submit button while a request is in progress, and show a message when it fails. Keep the validation rules in plain functions so they can be unit tested without rendering anything.

React 19 adds form actions. A form can receive a function through its action prop, and the hooks useActionState (from react) and useFormStatus (from react-dom) help track the result and the pending state. Libraries such as React Hook Form also manage large forms, reducing re-renders by using uncontrolled inputs under the hood. Mention these in an interview, but explain the controlled model first, because it is what the others build on.

What is the difference between a controlled and an uncontrolled input?

In a controlled input, React state holds the value. The input's value prop comes from state and the onChange handler updates the state, so React knows the value at every moment. In an uncontrolled input, the DOM holds the value and React reads it only when needed, for example on submit through a ref or FormData. Controlled inputs make validation and transformation easy. Uncontrolled inputs need less code.

Why does a form submit call event.preventDefault()?

The browser's default behaviour for a form submit is to send a request to the server and load a new page. Calling preventDefault() on the submit event stops that navigation, so the JavaScript handler can validate the data and send it with fetch or an action instead.

Routing, memoisation, code splitting and Suspense

Client-side routing with React Router

A single-page application loads one HTML document and then changes what is shown when the user navigates. Changing the URL without a full page load is called client-side routing. React Router is the most common library for it. The main pieces are BrowserRouter (the context that keeps the router going), Routes and Route (match the URL to a component), Link (navigation without a reload), useParams (read URL parameters), useNavigate (navigate from code) and Outlet (where a nested child route renders).

import { BrowserRouter, Routes, Route, Link, useParams } from "react-router-dom";

function UserPage() {
  const { userId } = useParams();
  return <h2>User {userId}</h2>;
}

export default function App() {
  return (
    <BrowserRouter>
      <nav>
        <Link to="/users/7">User 7</Link>
      </nav>
      <Routes>
        <Route path="/users/:userId" element={<UserPage />} />
        <Route path="*" element={<p>Page not found</p>} />
      </Routes>
    </BrowserRouter>
  );
}

The :userId part of the path is a dynamic segment. Visiting /users/7 makes useParams() return an object whose userId is the string "7". The final route with path="*" matches any URL that no other route matches, which gives a "page not found" screen. In React Router version 7 the same names are also exported from the react-router package, so check which package your project uses.

Nested routes work through Outlet. A layout route renders its shared header and an Outlet, and the matching child route's element appears where the outlet sits. This is how a dashboard can keep a sidebar while the content area changes.

React.memo: skipping renders when props have not changed

React.memo(Component) returns a version of the component that React re-renders only when its props change. React compares each prop with Object.is, which is a shallow comparison: objects and functions are equal only if they are the same object. The parent re-rendering alone does not re-render a memoised child whose props are unchanged.

import { memo, useState } from "react";

const ExpensiveList = memo(function ExpensiveList({ items }) {
  // Imagine this component renders thousands of rows
  return <ul>{items.map((item) => <li key={item}>{item}</li>)}</ul>;
});

export function Page() {
  const [text, setText] = useState("");
  const items = ["apple", "banana"];
  return (
    <>
      <input value={text} onChange={(e) => setText(e.target.value)} />
      <ExpensiveList items={items} />
    </>
  );
}

Typing updates text, which re-renders Page. However, items is a new array on every render, so ExpensiveList still re-renders. To make memo effective here, move items out of the component or wrap it in useMemo. This is the classic trap: memo only works when the props are stable, and inline objects, arrays and functions are new on every render.

Code splitting with lazy and Suspense

A bundler puts all the code of an app into one or more JavaScript files. Code splitting separates rarely used code into its own file that the browser downloads when it is needed. The standard way in React is React.lazy, which takes a function that calls a dynamic import().

import { lazy, Suspense } from "react";

const Chart = lazy(() => import("./Chart"));

export default function Dashboard() {
  return (
    <Suspense fallback={<p>Loading chart...</p>}>
      <Chart />
    </Suspense>
  );
}

The first time Chart renders, React starts downloading its file. While it loads, Suspense shows the fallback. When the module arrives, React swaps in the real chart. The module must have a default export for lazy to work. Splitting by route is the most common pattern: each page is lazy-loaded, so the first visit downloads only the code for the page shown.

Suspense is more general than lazy loading. It is a boundary that shows a fallback while anything beneath it is not ready. Data frameworks, server rendering and the use hook all report "not ready yet" to the nearest Suspense boundary. Place boundaries near the parts of the screen that should load independently, so one slow part does not hide the whole page.

Key ideaMemoisation avoids re-rendering when inputs are unchanged, and code splitting avoids downloading code that is not needed yet. Both improve speed, but neither helps if you have not first found the slow part with a profiler or a network trace.

Why might React.memo fail to prevent a re-render?

React.memo compares props with a shallow equality check. If the parent creates a new object, array or function on each render and passes it as a prop, the comparison fails every time and the child re-renders. Fix this by moving the value outside the component, or by memoising it with useMemo or useCallback.

What does React.lazy need, and what does Suspense do?

React.lazy needs a function that returns a dynamic import of a module with a default export that is a React component. Suspense is the boundary that shows its fallback while the lazily loaded component is not yet available. Without a Suspense boundary above a lazy component, React has nothing to show during the load, so the boundary is required.

Server components, Next.js and testing

Server components and client components

A server component is a component that runs only on the server. Its output is sent to the browser as a compact description of the UI, not as the JavaScript that produced it. Because it never runs in the browser, it can read a database or the file system directly, it adds nothing to the JavaScript bundle, and it cannot use state, effects or event handlers.

A client component runs in the browser, and it is the place for interactivity. You mark a file as a client component by putting "use client" at its top. A client component can be imported by a server component, and a server component can be passed into a client component as children. The boundary is drawn at the client file.

// products/page.js: a server component, because there is no "use client" line
import { getProducts } from "@/lib/products";

export default async function ProductsPage() {
  const products = await getProducts();
  return (
    <ul>
      {products.map((p) => (
        <li key={p.id}>{p.name}</li>
      ))}
    </ul>
  );
}
// add-to-cart.js: a client component, because it uses state and a click handler
"use client";

import { useState } from "react";

export default function AddToCart() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>Added {count}</button>;
}

The product page awaits its data directly, because the function is async. There is no loading state in the client code and no API call from the browser for this list. The button, on the other hand, needs the browser, so it is marked as a client component. Server Actions are functions marked with "use server" that a client component can call, usually from a form, to run code on the server. They are an important part of the server model in frameworks such as Next.js.

Interviewers askWhat is the benefit of server components? Crisp answer: they run on the server, so they can fetch data close to the source, keep heavy libraries and secrets out of the browser bundle, and send less JavaScript to the client. Client components are still needed for interactivity.

Next.js basics

Next.js is a React framework. It adds routing, rendering modes, data loading conventions and build tooling so you do not have to assemble them yourself. Its current App Router uses the app directory, in which folders define URLs and special files define the UI. The most important files are page.js (the UI for a route), layout.js (UI shared by child routes and kept while navigating), loading.js (fallback shown while a route loads, built on Suspense) and error.js (UI shown when a route throws). A route.js file defines API endpoints.

Next.js can render pages in several ways. Static rendering builds the HTML at build time. Dynamic rendering builds it per request. Incremental static regeneration serves a static page and rebuilds it in the background after a set time or on demand. In the App Router, components are server components by default, and you opt into client code with "use client".

In an interview, you do not need every Next.js option. Explain the model: folders are routes, server components fetch data, client components handle interaction, and the framework chooses how to render each route.

Testing with React Testing Library

React Testing Library (usually paired with Jest or Vitest as the test runner) tests components the way a user meets them. Instead of checking internal state or component names, you find elements by their role, label or visible text, perform actions such as typing and clicking, and check what appears on screen. This approach keeps tests valid when the implementation changes.

The query methods have clear meanings. getBy... finds exactly one element and throws if none exists. queryBy... returns null instead of throwing, which is useful for asserting that something is absent. findBy... returns a promise for elements that appear later, such as after a fetch. The preferred query is getByRole, because it uses the same accessibility information that screen readers use.

import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { SignupForm } from "./SignupForm";

test("the typed email is kept after submitting", async () => {
  const user = userEvent.setup();
  render(<SignupForm />);

  await user.type(screen.getByLabelText("Email"), "a@b.com");
  await user.click(screen.getByRole("button", { name: "Sign up" }));

  expect(screen.getByLabelText("Email")).toHaveValue("a@b.com");
});

render mounts the component into a virtual document. screen is the entry point for queries. userEvent simulates real user actions, and its methods return promises, so you await them. getByLabelText finds the input through the label we wrote in the form example, which also tests the accessibility of the form. toHaveValue is a matcher from the jest-dom library, which you usually load once in the test setup file.

TipIf you cannot write a query for an element with getByRole or getByLabelText, the element may be missing a meaningful role or label. Fixing that improves the app for screen reader users as well as the test.

What is the difference between a server component and a client component?

A server component runs only on the server, can access server-only resources, adds no JavaScript to the browser bundle, and cannot use state, effects or event handlers. A client component is marked with "use client", runs in the browser, and can use state, effects and handlers. Server components are the default in the Next.js App Router, and client components are used where interactivity is needed.

Why does React Testing Library prefer getByRole over getByTestId?

getByRole finds elements by their accessible role and name, which is how users and assistive technology identify them, so the test checks the user-facing behaviour. getByTestId depends on a test-only attribute that users never see, so the test passes even when the element is not accessible. Use test ids only when no role or label fits.

Interview questions

Answer each question out loud before opening the model answer. Aim for a crisp answer of two or three sentences, then offer an example if the interviewer wants more.

What is the virtual DOM, and does using it make React faster than manual DOM updates?

The virtual DOM is an in-memory tree of plain objects that describes the UI. After a state change React builds a new tree, compares it with the previous one, and applies only the differences to the real DOM. It is not inherently faster than carefully written manual DOM code. Its value is that developers describe the UI declaratively and React handles efficient updates consistently.

What happens when a component is replaced by a different component type in the same position?

React unmounts the old subtree, destroying its DOM nodes and all of its state, and mounts the new one from scratch. The same type in the same position keeps the DOM and state and only updates changed props. This is why toggling between two components that look similar can still reset an input.

Why does calling setCount(count + 1) twice in one handler add only 1?

Both calls read the value of count from the render that created the handler, which is the same number for both calls. Each sets the state to that number plus one, so the final state is one more than before. Use the updater form, setCount(c => c + 1), which receives the latest queued value, to add 2.

What are the rules of hooks, and why do they exist?

Call hooks only at the top level of function components or custom hooks, and always in the same order. React stores hook state in an ordered list per component and identifies each hook by its call position. Conditional or looping calls shift the positions, so state is read by the wrong hook.

When does useEffect run, and what do the dependencies control?

useEffect runs after the component has rendered and the screen has been updated. Without a dependency array it runs after every render. With an empty array it runs once after the first render. With values in the array it runs again only when one of them changes, compared with Object.is. Effects are for synchronising with external systems, not for computing values for rendering.

How do Context and Redux differ?

Context delivers a value down a subtree without prop passing. It is not a state manager, and every consumer re-renders when the value changes. Redux, in its modern form Redux Toolkit, is a store with reducers and selectors. Components subscribe to the parts of the state they read, which makes frequent updates efficient and keeps update logic in one predictable place.

When does React.memo help, and when does it not?

React.memo helps when a component re-renders often with the same props, and its render is expensive. It does nothing when props contain new objects, arrays or functions on every render, because the shallow comparison sees them as changed. Stabilise those props with useMemo or useCallback, and measure with the profiler before adding memo everywhere.

What is the difference between a controlled and an uncontrolled input, and which would you choose for a simple search box?

A controlled input takes its value from state and updates it on every change, so React always knows the value. An uncontrolled input lets the DOM hold the value and reads it when needed. For a simple search box that only needs the text on submit, an uncontrolled input is enough. For live search that reacts to each keystroke, the controlled form is clearer.

What does React.lazy with Suspense accomplish?

React.lazy loads a component's module only when the component first renders, so the code is split into a separate file and downloaded on demand. Suspense shows a fallback while that download happens. Together they reduce the initial bundle, which speeds up the first page load on slow connections.

What is the difference between a server component and a client component in Next.js?

Server components run on the server, can fetch data directly, send no component JavaScript to the browser, and cannot use state or event handlers. Client components, marked with the "use client" directive, run in the browser and handle interactivity. Server components are the default in the App Router, so you add "use client" only where needed.

How do you test that a form submits the typed value with React Testing Library?

Render the component, find the input with getByLabelText and the button with getByRole, use userEvent to type and click, and then assert on what is on screen with expect and a matcher such as toHaveValue. The test interacts with the form the way a user does, so it does not depend on internal state or implementation details.

DSA: mixed arrays and strings

Today's set mixes three problems that look different but share one habit: find the state that actually changes, and update it incrementally instead of recomputing it. The first problem tracks character counts, the second rearranges an array by finding one pivot, and the third slides a window across fixed-size word slots. Each Python program below runs on its own, and each prints its results.

Longest Substring with At Least K Repeating Characters (LeetCode 395)

Given a string s and an integer k, return the length of the longest substring in which every character appears at least k times. A substring is a contiguous piece of the string. Example 1: s = "aaabb", k = 3 gives 3, because "aaa" qualifies and no longer piece does. Example 2: s = "ababbc", k = 2 gives 5, because "ababb" has two a and three b, while the c makes any longer piece fail.

How to think about it

  1. Understand. The substring must be contiguous, and the answer can be 0 when no substring qualifies (for example "abc" with k = 2). Lowercase letters only, so at most 26 distinct characters.
  2. Brute force. Try every start and end pair, count the characters in each piece, and keep the longest piece in which every count is at least k. There are about n squared pieces and each count takes time, so the cost is roughly O(n cubed) if you recount, or O(26 times n squared) if you update counts as the end moves.
  3. Find the waste. Suppose a character appears fewer than k times in the whole string. Then no valid substring can contain it, because a substring never holds more copies of a character than the whole string does, and the whole string has fewer than k. Every such character is a wall. The brute force keeps checking pieces that cross a wall, and every such check is wasted.
  4. Optimise. Split the string at every wall. Each piece contains no wall character, so any valid substring lies entirely inside one piece, and the answer is the best answer among the pieces. Apply the same test inside each piece. If no wall exists, the whole string is valid. Each split removes at least one letter from the alphabet of the piece, so the recursion is at most 26 levels deep.
  5. Dry run. Walk through the examples below.
CallCountsWall foundPieces after splitResult
longest("ababbc", 2)a 2, b 3, c 1c (1 is below 2)"ababb", ""max(longest("ababb"), 0) = 5
longest("ababb", 2)a 2, b 3nonen/alen = 5
longest("aaabb", 3)a 3, b 2b (2 is below 3)"aaa", "", ""max(3, 0, 0) = 3

Code

def longest_substring(s, k):
    if len(s) < k:
        return 0
    counts = {}
    for ch in s:
        counts[ch] = counts.get(ch, 0) + 1
    # A character with fewer than k occurrences is a wall: split on it.
    for ch, cnt in counts.items():
        if cnt < k:
            return max(longest_substring(part, k) for part in s.split(ch))
    # Every character appears at least k times, so the whole string is valid.
    return len(s)

print(longest_substring("aaabb", 3))
print(longest_substring("ababbc", 2))
print(longest_substring("bbaaacbd", 3))

The brute force version is useful to explain the baseline in an interview. It checks every substring directly:

from collections import Counter

def longest_substring_brute(s, k):
    best = 0
    for i in range(len(s)):
        for j in range(i + 1, len(s) + 1):
            counts = Counter(s[i:j])
            if all(v >= k for v in counts.values()):
                best = max(best, j - i)
    return best

print(longest_substring_brute("aaabb", 3))
print(longest_substring_brute("ababbc", 2))

Next Permutation (LeetCode 31)

A permutation is one arrangement of a list. Rearrange the numbers in nums into the next permutation in lexicographic (dictionary) order, in place, using constant extra memory. If no larger arrangement exists, rearrange the numbers into the smallest arrangement, which is ascending order. Example: [1, 2, 3] becomes [1, 3, 2]. [3, 2, 1] becomes [1, 2, 3]. [1, 1, 5] becomes [1, 5, 1].

How to think about it

  1. Understand. In place means you modify the list you were given, and return nothing. Duplicates are allowed. Dictionary order compares the first element, then the second, and so on, so [1, 3, 2] comes after [1, 2, 3].
  2. Brute force. Generate every permutation, sort them, find the current one and return the one after it. There are n factorial permutations, so this costs O(n times n!) time and memory.
  3. Find the waste. Most of the list does not need to change. Scan from the right. A suffix that is already in descending order is the largest arrangement of its own elements, so rearranging inside it can only make the result smaller. The change must happen at the first position, from the right, whose value is smaller than the value after it.
  4. Optimise. Let the pivot be the rightmost index i where nums[i] < nums[i + 1]. Everything to its right is descending. Find the rightmost value to the right of the pivot that is larger than nums[i] (in the descending suffix it is the smallest such value), and swap them. The suffix stays descending, so reversing it gives the smallest arrangement for that suffix, which is the next permutation. If there is no pivot, the whole list is descending, so reverse it to get the smallest arrangement.
  5. Dry run. Trace [1, 3, 2].
StepListAction
Start[1, 3, 2]Scan for the pivot
Pivot[1, 3, 2]i = 1 has 3 and 2, and 3 is not less than 2, so move left. i = 0 has 1 and 3, and 1 is less than 3, so the pivot is index 0
Swap[2, 3, 1]Index 2 holds 2, which is the rightmost value greater than 1. Swap index 0 and index 2

Code

def next_permutation(nums):
    # Step 1: find the pivot, the rightmost index i with nums[i] < nums[i + 1].
    i = len(nums) - 2
    while i >= 0 and nums[i] >= nums[i + 1]:
        i -= 1
    # Step 2: if there is a pivot, swap it with the smallest larger value to its right.
    if i >= 0:
        j = len(nums) - 1
        while nums[j] <= nums[i]:
            j -= 1
        nums[i], nums[j] = nums[j], nums[i]
    # Step 3: reverse the suffix after the pivot, which is in descending order.
    nums[i + 1:] = reversed(nums[i + 1:])

for case in ([1, 2, 3], [3, 2, 1], [1, 1, 5], [1, 3, 2]):
    nums = case[:]  # copy, so the original list is kept for printing
    next_permutation(nums)
    print(case, "->", nums)

Substring with Concatenation of All Words (LeetCode 30)

You are given a string s and an array words. All words have the same length. Return the starting index of every substring of s that is a concatenation of each word in words exactly once, in any order, with no extra characters between the words. Example 1: s = "barfoothefoobarman", words = ["foo", "bar"] gives [0, 9], because "barfoo" at index 0 is "bar" then "foo", and "foobar" at index 9 is "foo" then "bar". Example 2: s = "wordgoodgoodgoodbestword", words = ["word", "good", "best", "word"] gives an empty list, because "word" must appear twice and the string has it only in the first and last positions. Example 3: s = "barfoofoobarthefoobarman", words = ["bar", "foo", "the"] gives [6, 9, 12].

How to think about it

  1. Understand. Let m be the number of words and L the length of each word. A valid substring has length m * L. Words can repeat, so the counts matter, not just which words appear. The output order does not matter, so we sort it for a fixed answer.
  2. Brute force. For each start index, cut the next m * L characters into m chunks of length L, count the chunks and compare the counts with the counts of words. That is O(n) starts, each costing O(m * L) to cut and count, so O(n * m * L) in total.
  3. Find the waste. The windows starting at neighbouring indices overlap almost completely, so the brute force cuts and counts the same chunks again and again. The useful observation is about alignment: the chunks of a window start at i, i + L, i + 2L and so on. Positions with the same remainder when divided by L form a separate lane, and inside a lane the chunks are the same words at neighbouring slots.
  4. Optimise. For each starting offset from 0 to L - 1, walk along its lane one word at a time, and keep a sliding window of consecutive lane words together with a count of each word inside the window. Add the new word on the right. If that word now appears more often than words allows, remove words from the left until it does not. If the window holds exactly m words that all fit, record its left edge. Then remove the leftmost word so the window can slide on. A word that is not in words at all clears the window, because no valid window can contain it. Each word enters and leaves the window at most once, so each lane costs time linear in its length.
  5. Dry run. Trace the offset 0 lane for s = "barfoothefoobarman" and words = ["foo", "bar"]. The lane slots are at indices 0, 3, 6, 9, 12 and 15.

from collections import Counter

def find_substring_brute(s, words):
    word_len = len(words[0])
    total_len = word_len * len(words)
    need = Counter(words)
    result = []
    for i in range(len(s) - total_len + 1):
        chunks = [s[i + j * word_len : i + (j + 1) * word_len] for j in range(len(words))]
        if Counter(chunks) == need:
            result.append(i)
    return result

from collections import Counter

def find_substring(s, words):
    if not s or not words:
        return []
    word_len = len(words[0])
    word_count = len(words)
    need = Counter(words)            # how many of each word we need
    result = []
    for offset in range(word_len):   # one lane for each starting offset
        left = offset                # left edge of the window
        seen = Counter()             # how many of each word the window holds
        matched = 0                  # how many words the window holds in total
        right = offset               # next slot to read in this lane
        while right + word_len <= len(s):
            word = s[right:right + word_len]
            right += word_len
            if word not in need:
                # A foreign word breaks every window that contains it.
                seen.clear()
                matched = 0
                left = right
                continue
            seen[word] += 1
            matched += 1
            # Too many copies of this word: shrink from the left until it fits.
            while seen[word] > need[word]:
                seen[s[left:left + word_len]] -= 1
                matched -= 1
                left += word_len
            if matched == word_count:
                result.append(left)
                # Drop the leftmost word so the window can slide on.
                seen[s[left:left + word_len]] -= 1
                matched -= 1
                left += word_len
    return sorted(result)

print(find_substring("barfoothefoobarman", ["foo", "bar"]))
print(find_substring("wordgoodgoodgoodbestword", ["word", "good", "best", "word"]))
print(find_substring("barfoofoobarthefoobarman", ["bar", "foo", "the"]))
[0, 9]
[]
[6, 9, 12]

A few details in the code deserve attention. The window is always made of whole lane slots, so every candidate starts at a real word boundary. The shrink loop only runs when a word is over-counted, and each index is moved past at most once per lane. The result list collects starts from several lanes, so it is sorted before returning.

Brute: Time O(n · m · L) · Space O(m · L). Optimised: Time O(n · L) · Space O(m · L) for the counters, plus the output list

Pattern to rememberWhen all items have the same length, group the positions by their remainder when divided by that length. Each group becomes a line of slots, and a sliding window over the slots replaces repeated substring comparisons.
