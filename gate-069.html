Merge Sort & Quick Sort

Merge sort and quick sort are the two most common fast sorting methods. Both split the problem into smaller parts and solve those parts, but they do the hard work in different places. GATE asks for their complexity, their stability, and the state of an array after some recursive calls.

The idea in plain words

Suppose you must sort a pile of 1000 exam papers by score. Sorting all 1000 at once is hard. But you could split the pile into two piles of 500, sort each pile, and then combine the two sorted piles into one. Splitting again would turn 500 into two piles of 250. This strategy is called divide and conquer. You divide the problem into smaller copies of itself, you conquer the small copies, and you combine the answers.

Both merge sort and quick sort use this strategy. The difference is where the work happens:

  • Merge sort splits the array in the middle, sorts each half, and does its real work when it merges two sorted halves. The splitting itself is easy.
  • Quick sort does its real work first. It picks a pivot value and moves the smaller values to its left and the bigger values to its right. Then it sorts each side. The final combining step is free.

Because of this difference, the two methods behave differently in speed, memory and stability. GATE tests all three.

Why this matters for GATE. Expect questions on the time complexity of each method, on whether each one is stable, and on the array after a given number of partitions or merges. The trace method is the same as in the earlier sorting page: write the array, follow the steps, and record the result.

Key terms

Divide and conquer
A method that splits a problem into smaller subproblems of the same kind, solves them, and combines the answers.
Recursion
A function that calls itself on a smaller input. Both sorts here are recursive.
Base case
The smallest input, which is already sorted and needs no work. For merge sort, a list of 0 or 1 items.
Merge
Combining two sorted lists into one sorted list by repeatedly taking the smaller front item.
Slice
A part of a list, written with a colon. arr[:mid] is the items from position 0 up to, but not including, mid. arr[mid:] is the items from mid to the end.
Pivot
The value chosen to split the array in quick sort.
Partition
Rearranging a part of the array so that values less than or equal to the pivot come before it, and bigger values come after it. The pivot ends in its final position.
Lomuto partition
A common partition method, which uses the last item as the pivot and scans with one index. It is the method used in the code on this page.
In place
Sorting by rearranging the items inside the same array, with only a small amount of extra memory.
Stable sort
A sort that keeps items with equal keys in their original relative order.
O(n log n)
Work that grows a little faster than n, by the factor log n. A common target for fast sorts.
Level
One layer of the recursion tree. All the calls in a level work on pieces of the array at the same size.

Merge sort and the merge step

The method

Merge sort works in three steps:

  1. Divide: if the list has 0 or 1 items, it is already sorted, so return it. Otherwise, cut it into two halves at the middle.
  2. Conquer: sort the left half and the right half, by calling merge sort on each.
  3. Combine: merge the two sorted halves into one sorted list.

How the merge step works

Think of two queues of people, each already in height order, who must join into one queue in height order. You look at the person at the front of each queue. The shorter one goes into the new queue, and you look again. When one of the queues is empty, the rest of the other queue joins the end in its existing order.

Take the lists [2, 5] and [1, 4, 6]. Compare the fronts 2 and 1. The 1 is smaller, so it goes into the result. Now the fronts are 2 and 4. The 2 goes next. Then 5 and 4: the 4 goes next. Then 5 and 6: the 5 goes next. Now the left list is empty, so the 6 from the right list is copied at the end. The result is 1, 2, 4, 5, 6.

A runnable example

The code below defines the merge step and the recursive merge sort. The function merge_sort prints each merge, so you can see the halves being combined. The first lines printed are the smallest merges, and the last line is the big merge at the top.

def merge(left, right):
    result = []
    i = 0
    j = 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            result.append(left[i])
            i = i + 1
        else:
            result.append(right[j])
            j = j + 1
    while i < len(left):
        result.append(left[i])
        i = i + 1
    while j < len(right):
        result.append(right[j])
        j = j + 1
    return result

def merge_sort(arr):
    if len(arr) <= 1:
        return arr
    mid = len(arr) // 2
    left = merge_sort(arr[:mid])
    right = merge_sort(arr[mid:])
    merged = merge(left, right)
    print("merge", left, right, "->", merged)
    return merged

print(merge_sort([38, 27, 43, 3, 9, 82, 10]))

Read the first merge line. The left half [27] and the right half [43] are each one item, so they are already sorted. Merging them gives [27, 43]. The merge of 38 with [27, 43] comes next, and it gives [27, 38, 43]. The last line shows the top merge, which joins two sorted halves of length 3 and 4.

Why the merge is fast

Each merge step copies one item into the result, and it never goes back. So merging two lists with a total of m items takes about m comparisons. Merge sort splits the array about log n times before reaching single items, and each level of the recursion tree does about n merging work in total. Multiply the two and you get n times log n. This is the reason for the O(n log n) time.

Cost and memory

  • Time: O(n log n) in the best, worst and average cases. The work does not depend on the order of the input.
  • Extra space: O(n). The merge needs a new result list as large as the input. This is the main weakness of merge sort compared with quick sort.
  • Stable: yes, when the merge takes from the left list on a tie. The line if left[i] <= right[j] does this. An equal item on the left is taken first, so it stays in front.

TrapIf you change the test to <, equal items would be taken from the right first, and merge sort would stop being stable. Expect a GATE question that makes this one small change.

How many items does the merge step copy in total when merging [1, 3] and [2, 4]?

All 4 items. Each item is copied once into the result, whichever list it comes from.

What does arr[:mid] give when arr is [10, 20, 30, 40, 50] and mid is 2?

It gives [10, 20]. The slice starts at 0 and stops before position 2.

Quick sort and the partition step

The method

Quick sort works in three steps:

  1. Pick a pivot. In this page the pivot is the last item of the range.
  2. Partition. Rearrange the range so that all items less than or equal to the pivot come before it, and all bigger items come after it. The pivot then sits in its final position.
  3. Conquer. Quick sort the part before the pivot, and the part after it. Nothing needs to be combined, because the pivot is already in place and each side is in the right group.

How the partition works

Think of a class lining up by height. The teacher picks one student as the reference. Everyone shorter moves to the left of that student, and everyone taller moves to the right. The reference student is now in the place where they belong among the class. Then the teacher does the same thing to the left group and to the right group.

The Lomuto partition in the code uses one index i that marks the boundary of the "small" group. The loop index j scans forward. When a[j] is small enough, i moves right and the item is swapped into the small group. At the end, the pivot is swapped into position i + 1.

A runnable example

The next program sorts the list [38, 27, 43, 3, 9, 82, 10]. It also counts the comparisons made in three runs, using a global counter. The global variable is changed inside partition, so the function uses the keyword global.

count = 0

def partition(a, low, high):
    global count
    pivot = a[high]
    i = low - 1
    for j in range(low, high):
        count = count + 1
        if a[j] <= pivot:
            i = i + 1
            temp = a[i]
            a[i] = a[j]
            a[j] = temp
    temp = a[i + 1]
    a[i + 1] = a[high]
    a[high] = temp
    return i + 1

def quick_sort(a, low, high):
    if low < high:
        p = partition(a, low, high)
        print("pivot", a[p], "placed at", p, a)
        quick_sort(a, low, p - 1)
        quick_sort(a, p + 1, high)

data = [38, 27, 43, 3, 9, 82, 10]
quick_sort(data, 0, len(data) - 1)
print("sorted:", data, "comparisons:", count)

Trace the first partition by hand, because it is the most useful exercise on this page. The pivot is the last item, 10. Start with i = -1. Scan j from 0 to 5. Position 0 holds 38, which is not at most 10, so nothing happens. Position 1 holds 27, no. Position 2 holds 43, no. Position 3 holds 3, which is at most 10, so i becomes 0 and 3 is swapped with position 0. The array is 3, 27, 43, 38, 9, 82, 10. Position 4 holds 9, which is small, so i becomes 1 and 9 is swapped with position 1. The array is 3, 9, 43, 38, 27, 82, 10. Position 5 holds 82, no. Now swap the pivot 10 with position i + 1, which is position 2. The array is 3, 9, 10, 38, 27, 82, 43. The pivot 10 is in its final place, and the output line matches.

Cost and memory

  • Partition cost: a range of m items needs m - 1 comparisons, one for each item except the pivot.
  • Extra space: the sort is in place, so it needs no big result list. Its recursion uses stack space, about log n levels on a good split.
  • Stable: no. The swaps move items past equal items. For example, in the list 2a, 2b, 1 with a last pivot, 2a is swapped to the end, past 2b.
In the first partition above, where did 43 end up, and why?

It ended at index 6, the last position. It is bigger than the pivot 10, so it belongs to the right group. The final swap of the pivot with position 2 moved 43 from position 2 to position 6.

How many comparisons does one partition of 5 items make?

Four. The loop runs from the first to the second last position, one comparison each, and the pivot is not compared with itself.

Pivot choices and the worst case

Why the pivot matters

Quick sort is fast only when each partition splits the range into two roughly equal parts. If the pivot is always the smallest or the largest item, one side is empty and the other side has everything except the pivot. Then each partition removes just one item, and the sort does about n steps for each of n items.

Common ways to choose the pivot are:

  • First item: simple, but bad on sorted input.
  • Last item: used in this page. Also bad on sorted input.
  • Middle item: good on sorted input, because the middle is roughly the median.
  • Random item: makes the bad case very unlikely for any input.
  • Median of three: the median of the first, middle and last items. It is a common practical choice.

The worst case, worked out

Take the sorted list 1, 2, 3, 4, 5, 6 with the last item as pivot. The first partition uses 6 as the pivot. It makes 5 comparisons and places 6 at the end. The next partition uses 5 on a range of 5 items. It makes 4 comparisons. Continue: 3, 2, 1 comparisons. The total is 5 + 4 + 3 + 2 + 1 = 15. For n items the total is n(n - 1)/2, which is O(n²). The code run earlier gave 15, which matches.

The average case

If the pivot is roughly in the middle on average, each level of the recursion tree does about n comparisons, and there are about log n levels. So the average time is O(n log n). This is why quick sort is fast in practice, even though its worst case is O(n²).

Key ideaMerge sort is always O(n log n). Quick sort is usually O(n log n) but can be O(n²). The difference is caused entirely by the choice of pivot.

What is the worst-case number of comparisons of quick sort on a sorted list of 4 items with the last item as pivot?

3 + 2 + 1 = 6, which is 4 * 3 / 2 = 6.

Which pivot choice avoids the bad case on a sorted list?

The middle item, or a random item. Both give a split near the middle for a sorted list, and the random choice avoids the bad case for any input with high probability.

The practical choice depends on the situation. Merge sort is the choice when a stable, predictable sort is needed, or for data that does not fit neatly in memory. Quick sort is the choice when memory is tight and the average speed matters most. A GATE question will usually ask about one specific property from this table, so learn the rows, not the whole story.

GATE loves thisBe ready for a question that asks which sort is stable, which sort has O(n²) worst case, and which sort uses extra space. Answer each row of the table separately, because the answers differ.

Which sort is always O(n log n), merge sort or quick sort with the last item as pivot?

Merge sort. Quick sort with the last item as pivot can take O(n²) on sorted input.

Which sort needs an extra array as large as the input?

Merge sort. The merge writes its result into a new list, which takes O(n) extra space.

Tracing both sorts

Tracing merge sort

To trace merge sort by hand, first draw the recursion tree. Split the list in half at each level, using mid = len // 2, until every piece has one item. Then go back up the tree and merge each pair of sorted pieces. Write each merge on its own line. The number of merges for n items is n - 1, one for each internal node of the tree.

Here is a shorter example. Take [5, 2, 4, 6, 1, 3]. The top split gives [5, 2, 4] and [6, 1, 3]. The left part splits into [5] and [2, 4]. The merge of [5] with the sorted [2, 4] is [2, 4, 5]. The right part gives [1, 3, 6]. The final merge of [2, 4, 5] and [1, 3, 6] is [1, 2, 3, 4, 5, 6].

Tracing quick sort

To trace quick sort, redo the partition for each range. Write the array, circle the pivot, and then mark the boundary of the small group. After the partition, the pivot is fixed. Then trace the left range and the right range separately. Remember that the left and right ranges never swap items with each other again.

TipWrite the range as "low to high" beside each step. Many mistakes come from forgetting that the left call is p - 1 and the right call is p + 1.

In merge sort on 6 items, how many merges happen in total?

5. For n items there are n - 1 merges, because each merge joins two groups into one, and the process ends with one group.

After the first quick sort partition, are items to the left of the pivot always sorted?

No. They are only smaller than or equal to the pivot. They are not yet in order among themselves, and they still need their own quick sort calls.

Solved GATE-style problems

Comparisons in a merge

Merge step with the code on this page is applied to the sorted lists [2, 5] and [1, 4, 6]. Each comparison of two fronts counts as one. How many comparisons are made?

How to think about it

  1. What is asked. The number of times two fronts are compared.
  2. Which idea applies. Each comparison takes one item into the result, until one list runs out.
  3. Work it out. Compare 2 with 1: take 1. Compare 2 with 4: take 2. Compare 5 with 4: take 4. Compare 5 with 6: take 5. Now the left list is empty, so no more comparisons. That is 4 comparisons.
  4. Check. The result has 5 items, and the 6 at the end was copied without any comparison, so 4 is 5 minus the one item copied at the end.

Answer: 4

True statements about the sorts

Select all true statements. (A) Merge sort as written on this page is stable. (B) Merge sort takes O(n log n) time in the worst case. (C) Quick sort with the last item as pivot takes O(n²) time on a sorted list. (D) The in-place quick sort on this page needs O(n) extra space.

How to think about it

  1. What is asked. Every true statement.
  2. Which idea applies. Stability, complexity, and memory of each method.
  3. Work it out. (A) is true, because the merge takes from the left on ties. (B) is true, as the table shows. (C) is true, as the worst-case section shows. (D) is false, because the partition works in place and needs only a few variables and recursion stack.
  4. Check. Statement D is the usual trap, since merge sort, not quick sort, needs the O(n) extra space.

Comparisons in a three and three merge

Merge step is applied to the sorted lists [1, 3, 5] and [2, 4, 6]. Each comparison of two fronts counts as one. How many comparisons are made in total?

How to think about it

  1. What is asked. The number of front comparisons.
  2. Which idea applies. The merge stops comparing when one list is empty.
  3. Work it out. Compare 1 with 2: take 1. Compare 3 with 2: take 2. Compare 3 with 4: take 3. Compare 5 with 4: take 4. Compare 5 with 6: take 5. The left list is now empty. That is 5 comparisons, and the 6 is copied with no comparison.

One partition step

The array is 4, 7, 2, 9, 5, with positions 0 to 4. Quick sort partitions the whole array using the last item as the pivot, with the Lomuto method from this page. Give the final index of the pivot, then the array after the partition, using commas.

  1. What is asked. The pivot position and the array after one partition.
  2. Which idea applies. The pivot is 5, the last item. Items at most 5 are moved to the left group, using the boundary index.

Comparisons on a sorted list

Quick sort with the last item as pivot is run on the sorted list 1, 2, 3, 4, 5. Count the total number of comparisons over the whole sort.

Which sublist comes first

Merge sort, with mid = len(arr) // 2, is run on the list 5, 2, 4, 6, 1, 3. Give the list printed by the first merge that produces a list of three items.

How to think about it

  1. What is asked. The first merge result that has exactly three items, in the order the recursion finishes.
  2. Which idea applies. The recursion finishes the left half first, and the left half is 5, 2, 4.
  3. Work it out. The left half 5, 2, 4 has length 3, so mid = 3 // 2 = 1. It splits into 5 and 2, 4. The piece 2, 4 is sorted first by merging 2 and 4, which gives a two-item list. Then the merge of 5 with 2, 4 gives 2, 4, 5. This is the first merge that produces three items.
  4. Check. The merge of 5 with 2 and 4 uses the fronts 5 and 2 first, takes 2, then 5 and 4 take 4, then 5 is copied, which gives 2, 4, 5.

Summary

Divide and conquer
Split a problem, solve the parts, and combine the answers.
Merge sort
Splits at the middle, sorts each half, and merges them. Does its work when merging.
Merge step
Joins two sorted lists by repeatedly taking the smaller front item.
Quick sort
Chooses a pivot, partitions around it, and sorts each side. Does its work before recursing.
Pivot
The value used to split the array in quick sort.
Partition
Moves items at most the pivot to the left, and bigger items to the right.
Lomuto partition
A partition with the last item as pivot and one scanning index.
Slice
A part of a list, such as arr[:mid].
Level
One layer of the recursion tree.
O(n log n)
The time of merge sort in every case, and of quick sort on average.
O(n²)
The worst case of quick sort with a bad pivot.
In place
Rearranging the array itself, with little extra memory.
Stable
Keeps equal items in their original order. Merge sort yes, quick sort no.
Median of three
A practical pivot choice: the median of the first, middle and last items.

Remember these

  1. Merge sort is O(n log n) in every case, and it needs O(n) extra space.
  2. Quick sort is O(n log n) on average, but O(n²) when the pivot is always the smallest or largest item.
  3. A partition of m items makes m - 1 comparisons, and the pivot ends in its final place.
  4. Merge sort is stable when the merge takes from the left on a tie. Quick sort is not stable.
  5. Merge sort does its work in the merge. Quick sort does its work in the partition.
  6. For n sorted items with the last item as pivot, quick sort makes n(n - 1)/2 comparisons.
