The network layers: OSI and TCP/IP

A network is a stack of cooperating rules. Each rule, or protocol, solves one problem and relies on the layers below it to solve the others. Engineers describe this stack in two models. The OSI model has seven layers and is mostly used as a teaching and vocabulary tool. The TCP/IP model has four layers and describes what the Internet actually runs. Interviewers expect you to know both and to map a protocol to its layer.

The two columns line up loosely. TLS is the awkward one: it does not fit neatly anywhere, so textbooks place it between the transport and application layers, and that is a fine answer in an interview as long as you explain why.

Encapsulation: how a message travels down the stack

When a program sends data, each layer wraps the data from the layer above in its own header, and the result becomes the payload of the layer below. The receiving machine reverses the process, removing one header at each layer and handing the payload upward. This wrapping is called encapsulation, and it is why a single HTTP request is carried inside a TCP segment, which is carried inside an IP packet, which is carried inside an Ethernet frame.

  • Application data. The HTTP request, for example GET /index.html with headers.
  • Transport segment. The same bytes with a TCP header that carries source and destination ports, sequence numbers and flags.
  • Network packet. The segment with an IP header that carries source and destination IP addresses and a time-to-live field.
  • Link frame. The packet with a link header carrying the MAC addresses of the next device on the local network.

Two details matter in practice. First, an IP address identifies a machine on a network, and it can change across networks. Second, a port identifies a service or a socket on that machine. A connection is identified by the four values: source IP, source port, destination IP and destination port. A web server on port 443 can serve thousands of clients at once, because each client connection has a different source port.

TrapDo not say that a router works at layer 4 because it looks at IP addresses. Routing is layer 3 (IP). Port-aware load balancers and firewalls work at layer 4, and HTTP-aware proxies work at layer 7.

Name the TCP/IP layer for HTTP, TCP, IP and Ethernet.

HTTP is in the application layer, TCP is in the transport layer, IP is in the internet layer, and Ethernet is in the network access (link) layer. In the OSI model these are layers 7, 4, 3 and 2.

TCP versus UDP

Both TCP and UDP are transport protocols. They deliver data between two processes using port numbers, and they differ in what they promise. This is one of the most common interview questions, and the answer is about guarantees and cost.

TCP (Transmission Control Protocol) is connection-oriented and reliable. Before any data flows, the two ends perform a three-way handshake. The client sends a SYN segment with a starting sequence number. The server replies with SYN-ACK, acknowledging that number and offering its own. The client sends an ACK, and the connection is open. TCP then numbers every byte, acknowledges what it receives, retransmits anything that is not acknowledged in time, and delivers bytes to the application in order without gaps or duplicates. It also controls the rate. The receive window stops a fast sender from overwhelming a slow receiver (flow control), and congestion control reduces the sending rate when the network drops packets (for example, by halving the window on loss, then growing it slowly again).

UDP (User Datagram Protocol) is connectionless and best effort. There is no handshake. Each datagram is sent independently, with an 8-byte header that carries only ports, a length and a checksum. UDP does not retransmit, does not order datagrams and does not control the rate. A datagram can be lost, arrive out of order, or arrive twice, and the application has to deal with that if it matters.

PropertyTCPUDP

Some applications build their own reliability on top of UDP. QUIC, the transport under HTTP/3, does this: it provides reliable, encrypted streams in user space over UDP, which avoids some of the delays that TCP's ordering imposes on every stream of a connection.

Key ideaTCP gives you a reliable byte stream at the cost of a handshake and waiting for lost data. UDP gives you cheap, immediate datagrams and leaves reliability to you.

Trap"UDP is faster" is not the whole story. UDP has less overhead, but an application that needs reliability and rebuilds it poorly will be slower and buggier than TCP. Choose UDP for latency-sensitive data where a lost packet is better than a late one, such as a live video frame.

Why does a TCP connection start with three messages?

Each side must learn that the other is reachable and agree on its starting sequence number, so that both can number and acknowledge bytes reliably. The client's SYN sends its number, the server's SYN-ACK acknowledges it and sends the server's number, and the client's ACK acknowledges the server's number. After the third message, both sides can send data.

What does UDP not do that TCP does?

UDP does not set up a connection, does not acknowledge or retransmit, does not guarantee order or uniqueness, and does not perform flow or congestion control. It only adds ports, a length and a checksum to the datagram.

HTTP, HTTPS and TLS

HTTP (Hypertext Transfer Protocol) is the application protocol of the web. A client sends a request, and a server returns a response. HTTP is stateless: each request stands alone, and any memory of the user, such as a login, is carried by cookies or tokens sent with each request.

A request has a method, a path, headers and an optional body. A response has a status code, headers and an optional body. The most important methods are GET (read a resource), POST (create or submit something), PUT (replace a resource), PATCH (change part of a resource), and DELETE (remove a resource). Status codes are grouped by their first digit: 2xx means success (200 OK, 201 Created, 204 No Content), 3xx means redirection (301 Moved Permanently, 304 Not Modified), 4xx means the client made an error (400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict, 422 Unprocessable Content), and 5xx means the server failed (500 Internal Server Error, 503 Service Unavailable).

Trap401 means "not authenticated": the caller has not proved who they are. 403 means "authenticated but not allowed". Many candidates swap them.

How HTTP versions differ

  • HTTP/1.1 is text-based. It reuses one TCP connection for several requests in turn (keep-alive), but a response must finish before the next can start on that connection, which causes head-of-line blocking.
  • HTTP/2 is binary and multiplexes many streams on one TCP connection, so requests can be in flight at the same time. It also compresses headers.
  • HTTP/3 carries HTTP over QUIC, which runs over UDP, so a lost packet delays only the stream it belongs to.

HTTPS and TLS

HTTPS is simply HTTP sent over TLS (Transport Layer Security), normally on port 443. TLS gives three things: confidentiality (eavesdroppers cannot read the traffic), integrity (tampering is detected), and authentication of the server (the client knows it is talking to the owner of the domain name). TLS 1.2 and 1.3 are the versions in use; TLS 1.3 is the current standard and is faster to set up.

A TLS 1.3 handshake works in broad steps:

  1. The client sends a ClientHello with supported cipher suites, a key share for a key exchange (usually elliptic-curve Diffie-Hellman), and the host name it wants, in the Server Name Indication extension, so one IP address can serve many sites.
  2. The server replies with its own key share and its certificate, which binds its public key to a domain name. The certificate is signed by a certificate authority (CA), and the client checks the signature against the CA certificates in its trust store. The server also signs part of the handshake with its private key, proving it holds that key.
  3. Both sides compute the same shared secret from the key exchange and derive session keys. From here on, everything is encrypted with a fast symmetric cipher such as AES-GCM.

The key exchange uses asymmetric cryptography, which is slow but needs no shared secret in advance. The bulk data uses symmetric cryptography, which is fast. Using both is the standard design. Ephemeral keys give forward secrecy: if the server's long-term key is stolen later, past sessions still cannot be decrypted.

Key ideaThe certificate proves who the server is, the key exchange creates a secret that only the two ends know, and symmetric encryption protects the data after that.

What does TLS protect against, and what does it not protect?

TLS protects the confidentiality and integrity of data in transit and authenticates the server. It does not protect data on the endpoints themselves, does not stop a compromised browser or server, and does not stop a user from being fooled by a look-alike domain name.

What does the Server Name Indication extension do?

SNI lets the client send the host name in the first TLS message, before encryption starts. The server uses it to choose the right certificate, so several HTTPS sites can share one IP address.

DNS, the journey of a URL, and SNMP

DNS (Domain Name System) translates human-readable names such as example.com into IP addresses. It is a distributed, hierarchical database. No single server knows everything. Each level delegates the next: the root servers point to the servers for each top-level domain (such as .com), which point to the authoritative servers for each domain, which hold the actual records.

A recursive resolver, usually run by your ISP or a public service, does the walking on your behalf. It asks a root server where .com lives, asks the .com server where the domain's authoritative server is, then asks that server for the record. Every answer carries a TTL (time to live) in seconds, and caches at the resolver, the operating system and the browser keep the answer until it expires. DNS normally uses UDP port 53, and falls back to TCP for large responses and zone transfers.

What happens when you type a URL

This question tests whether you can connect the layers into one story. Here is a typical sequence for https://example.com/docs. Each step depends on the previous one.

  1. Parse the URL. The browser reads the scheme (https), the host (example.com), the default port for the scheme (443) and the path (/docs).
  2. Check caches. The browser checks its own caches, the list of sites that must always use HTTPS (HSTS), and the operating system's DNS cache.
  3. Resolve the name. If nothing is cached, the recursive resolver walks the DNS hierarchy and returns an IP address with a TTL.
  4. Open a TCP connection. The client performs the three-way handshake with that IP address on port 443.
  5. Negotiate TLS. The TLS handshake validates the certificate for example.com and establishes encryption keys.
  6. Send the HTTP request. The browser sends GET /docs with headers such as Host, cookies and Accept. The Host header tells the server which site is wanted.
  7. Receive the response. The server, or a load balancer or reverse proxy in front of it, returns a status code. A 301 or 302 means the browser must request the new location.
  8. Render. The browser parses the HTML, builds the DOM and CSS rules, then requests images, scripts and styles, often in parallel, and paints the page.

Below the transport layer, every IP packet is routed hop by hop across routers. On the local network, the machine uses ARP to find the MAC address of its default gateway, because frames on a LAN are addressed by MAC, not IP.

Interviewers askWhat happens when you type a URL? Give the eight steps in order, then say which step is slowest on a cold cache (usually DNS and the TCP and TLS round trips) and how caching and HTTP/2 or HTTP/3 reduce it.

SNMP: managing network devices

SNMP (Simple Network Management Protocol) is used to monitor and configure network devices such as routers, switches and printers. It has two roles. A manager (for example a monitoring system) asks questions. An agent runs on each device and answers. SNMP runs over UDP: the manager sends requests to port 161 on the agent, and the agent sends unsolicited traps (alerts) to port 162 on the manager.

The data is organised as a tree called a MIB (Management Information Base). Each variable has an OID (object identifier), a dotted sequence of numbers such as 1.3.6.1.2.1.1.1.0, which names the system description. The operations are GET (read one value), GETNEXT and GETBULK (walk a table), SET (change a value), and the agent-initiated trap or inform.

SNMP has three versions. Version 1 and version 2c use a community string as a shared password, sent in clear text, so they must be used only on trusted networks. Version 3 adds authentication and encryption through the User-based Security Model. Using v3 in production is the correct answer when security is asked about.

TrapA community string is not a password in the security sense. It is sent in the clear with every request, so anyone who can sniff the network can read it.

What is the difference between a DNS A record and a CNAME record?

An A record maps a name directly to an IPv4 address. A CNAME record maps a name to another name, and the resolver then looks up that name. A CNAME cannot sit at the zone apex alongside other records, so the apex of a domain normally uses A or AAAA records.

Which transport and ports does SNMP use?

SNMP uses UDP. Requests from the manager go to port 161 on the agent, and traps from the agent go to port 162 on the manager.

REST, idempotency, JWT, OAuth and API styles

An API (application programming interface) lets one program call another over the network. Most web APIs follow the REST style. REST is an architectural style, not a standard, and its key constraints are: a client-server split, statelessness (each request carries everything the server needs), cacheability, and a uniform interface built on resources and HTTP.

Designing resources and using HTTP methods

In REST, the URL names a resource, and the HTTP method says what to do with it. Use plural nouns and avoid verbs in paths: GET /books/42 reads book 42, and DELETE /books/42 removes it. Nested resources express ownership, as in GET /authors/7/books. Responses use status codes to say what happened: 201 with a Location header after a create, 404 when the resource is missing, and 422 when the body fails validation.

Idempotency and safety

An operation is safe if it does not change server state (GET, HEAD and OPTIONS are safe). An operation is idempotent if doing it several times has the same effect on the server as doing it once. GET, PUT, DELETE, HEAD and OPTIONS are idempotent by definition. POST is not: sending the same POST twice usually creates two resources. PATCH is not guaranteed to be idempotent, since "add 1 to the counter" repeated gives a different result each time.

Idempotency matters because networks retry requests. If a client times out and resends a PUT, the server must end in the same state. For a payment POST, the standard fix is an idempotency key: the client sends a unique key with the request, and the server remembers the result for that key and returns it on a retry.

TrapDELETE is idempotent even though its status code changes. The first call returns 204, and a retry returns 404, but the server state is the same: the resource is gone.

JWT: a signed token

A JSON Web Token (JWT) is a compact token with three parts separated by dots: a header, a payload and a signature. Each part is base64url-encoded. The header names the signing algorithm (such as HS256). The payload contains claims, such as sub (the subject), exp (expiry time) and iss (issuer). The signature is computed over the first two parts with a secret key (HMAC) or a private key (RSA or ECDSA).

The most important point is that a JWT is signed, not encrypted. The payload is readable by anyone who holds the token. The signature only proves the content was not changed and was made by someone with the key. The following program builds a token, then reads its payload without any key.

import base64
import hashlib
import hmac
import json


def b64url(data):
    """Base64url without padding, the encoding JWT uses."""
    return base64.urlsafe_b64encode(data).rstrip(b"=").decode("ascii")


header = {"alg": "HS256", "typ": "JWT"}
payload = {"sub": "42", "role": "reader"}
header_part = b64url(json.dumps(header, separators=(",", ":")).encode("utf-8"))
payload_part = b64url(json.dumps(payload, separators=(",", ":")).encode("utf-8"))
signing_input = header_part + "." + payload_part
signature = hmac.new(b"demo-secret", signing_input.encode("ascii"), hashlib.sha256).digest()
token = signing_input + "." + b64url(signature)
print(token)

middle = token.split(".")[1]
padded = middle + "=" * (-len(middle) % 4)     # base64 decoding needs padding to a multiple of 4
print(base64.urlsafe_b64decode(padded).decode("utf-8"))

The program signs the token with the HMAC of the header and payload, using a demo key. The second print decodes the payload with no key at all, which shows why sensitive data must never go into a JWT unless the token is also encrypted (JWE). A server verifies a token by recomputing the signature with its key, comparing it, and then checking exp and the audience. It must pin the algorithm it expects, because accepting "none" or a different algorithm is a well-known vulnerability.

TrapA JWT cannot be revoked simply by deleting it on the server, because the server does not store it. Keep lifetimes short, and use a server-side deny list or token version for logout and password changes.

OAuth 2.0: delegated access

OAuth 2.0 is a framework for delegated authorisation: it lets an application access a user's data on another service without receiving the user's password. It is about what an app may do, not who the user is. OpenID Connect adds an ID token on top of OAuth so that the app can learn who the user is, which is authentication.

OAuth has four roles: the resource owner (the user), the client (the app), the authorisation server (issues tokens after the user consents), and the resource server (the API that holds the data). In the authorisation code flow with PKCE, the app redirects the user to the authorisation server, the user signs in and consents, the server returns a short-lived code to the app, and the app exchanges the code, plus a secret proof called the PKCE verifier, for an access token. The access token is then sent as Authorization: Bearer ... on API calls. Client credentials flow is for machine-to-machine calls where no user is involved.

Key ideaOAuth answers "may this app act on the user's behalf, and with which scopes?", while login answers "who is this user?". OpenID Connect provides the second answer.

GraphQL has its own risks. A client can ask for deeply nested data, so servers limit query depth and cost. A naive resolver can run one database query per item in a list, which is the N+1 problem. gRPC needs a proxy such as gRPC-Web to be called from a browser directly.

What does idempotent mean, and which HTTP methods are idempotent?

An idempotent operation has the same effect on the server whether it runs once or many times. GET, HEAD, OPTIONS, PUT and DELETE are idempotent. POST is not, and PATCH is not guaranteed to be.

Is a JWT encrypted?

No. A standard JWT is signed (JWS), so its payload is only base64url-encoded and anyone can read it. The signature protects integrity, not confidentiality. Encrypted tokens use JWE, which is a different format.

Security basics: CIA, hashing, encryption and OWASP

Security engineering starts from three goals, which together are called the CIA triad. Confidentiality means only authorised parties can read data. Integrity means data cannot be changed without detection. Availability means the system works when it is needed. Every control you learn maps onto one or more of these goals. Authentication (who are you?), authorisation (what may you do?) and accounting or auditing (what did you do?) are the other concepts interviewers mention next.

Hashing versus encryption

These two are often confused. Encryption is reversible: with the right key, ciphertext becomes plaintext again. Symmetric encryption, such as AES, uses one key for both directions. Asymmetric encryption, such as RSA, uses a public key to encrypt and a private key to decrypt. Hashing is one-way: a hash function maps any input to a fixed-size digest, such as 256 bits for SHA-256, and there is no key and no way to get the input back. The same input always gives the same digest, and a tiny change in input gives a completely different digest.

Hashing is used for integrity checks, digital signatures (where the hash of the message is signed) and password storage. Encoding, such as base64, is a third thing: it is a reversible change of format with no secret, so it provides no security at all.

import hashlib

print(hashlib.sha256(b"password").hexdigest())
print(hashlib.pbkdf2_hmac("sha256", b"password", b"8f1c", 1000).hex()[:16])
print(hashlib.pbkdf2_hmac("sha256", b"password", b"c3d9", 1000).hex()[:16])

The first line is a plain SHA-256 digest of the word password. Plain hashing is too fast for passwords, because an attacker can test billions of guesses per second on a GPU. The next two lines use PBKDF2 with a salt. A salt is a random value stored with each password, so two users with the same password get different hashes, and precomputed tables cannot be reused. PBKDF2 also repeats the hash many times to slow each guess. In production, use a dedicated password hash such as Argon2, scrypt or bcrypt, with settings chosen by current guidance. The two salted outputs differ even though the password is the same, which is the point of salting.

TrapDo not store passwords with encryption. If the key is ever exposed, every password is exposed too. Hash them with a slow, salted password hash, and check the password by hashing the attempt and comparing the results.

OWASP and the three attacks to know

OWASP (the Open Worldwide Application Security Project) publishes a list of the most critical web application risks, called the OWASP Top 10. Injection, which includes SQL injection and cross-site scripting, has appeared on it for many years. The three attacks below are the ones interviewers expect you to explain with a fix.

SQL injection

SQL injection happens when user input is pasted into a SQL query as code. The database then reads part of the input as SQL. The program below builds one query by joining strings, then a second query with a placeholder. The input is an attack string that tries to make the WHERE clause always true.

import sqlite3

con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE users (name TEXT, secret TEXT)")
con.executemany("INSERT INTO users VALUES (?, ?)", [("alice", "a-pass"), ("bob", "b-pass")])

user_input = "x' OR '1'='1"
unsafe = "SELECT name FROM users WHERE name = '" + user_input + "'"
print(unsafe)
print(con.execute(unsafe).fetchall())

safe = "SELECT name FROM users WHERE name = ?"
print(con.execute(safe, (user_input,)).fetchall())
SELECT name FROM users WHERE name = 'x' OR '1'='1'
[('alice',), ('bob',)]
[]

In the first query, the quote in the input closes the string early, and OR '1'='1' is always true, so every row is returned. In the second query, the question mark is a placeholder. The driver sends the query and the value separately, so the input is treated only as a name, and no row matches it. The fix is always parameterised queries (prepared statements), which an ORM uses under the hood. Escaping strings by hand is error-prone and should be avoided.

Key ideaKeep code and data separate. Parameters are data, never part of the SQL text.

Cross-site scripting (XSS)

XSS happens when a site includes untrusted input in its HTML, and the browser runs that input as script. A stored XSS saves the input and shows it to later visitors. A reflected XSS echoes a value from the current request, often in a link. A DOM-based XSS is created by client-side code that writes untrusted data into the page. The attacker's script then runs with the victim's privileges on that site: it can read the page, send requests as the user, or steal data the page can reach.

The defence is output encoding: turn characters that have meaning in HTML into harmless entities when you place data in a page. The code below shows the encoding for an HTML body.

import html

comment = '<script>alert("hi")</script>'
print(html.escape(comment))
&lt;script&gt;alert(&quot;hi&quot;)&lt;/script&gt;

The output line is the escaped form. Written into an HTML page, the browser displays it as the plain text of the tag, and never runs it as script. The entities for less-than, greater-than, ampersand and quotes are what keep the input from being read as markup. Modern frameworks escape by default, so the rules to remember are: never use innerHTML or an equivalent with untrusted data, prefer text-setting APIs, add a Content Security Policy to limit where scripts can load from, and set session cookies to HttpOnly so that script cannot read them.

TrapEscaping is context-specific. Text inside an HTML attribute, inside a script block, and inside a URL each need different encoding. Using the HTML body encoder everywhere is not enough.

Cross-site request forgery (CSRF)

CSRF tricks a logged-in user's browser into sending a state-changing request to a site where the user is authenticated. The browser attaches the site's cookies automatically, so the server sees a valid session. Imagine a page on another domain that contains a hidden form posting to a bank's transfer endpoint. If the user is logged in to the bank, the cookie goes along with the form, and the transfer happens without the user's intent. The attacker never sees the response, and does not need to.

The defences are to use the SameSite cookie attribute (Lax or Strict), which stops the browser sending the cookie on most cross-site requests; to require an anti-CSRF token that a cross-site page cannot read; to check the Origin header; and never to perform state changes with GET. Many modern browsers treat cookies without a SameSite attribute as Lax by default, which removes much of the risk, but tokens remain the robust answer.

Interviewers askHow do you prevent SQL injection, XSS and CSRF? Parameterised queries for SQL, output encoding and a Content Security Policy for XSS, and SameSite cookies plus anti-CSRF tokens for CSRF. Name the one-line principle for each: separate code from data, encode for the context, and prove the request came from your own page.

Why is a salted slow hash used for passwords, instead of SHA-256 alone?

A salt makes every password hash unique, so precomputed tables do not help an attacker. A slow hash makes each guess expensive, so brute force is impractical. SHA-256 is designed to be fast, which is the wrong property for passwords.

How does a parameterised query stop SQL injection?

The SQL statement and the parameter values are sent to the database separately. The database parses the statement first, so each parameter is treated as a plain value, even if it contains quotes or SQL keywords.

Framework unit: FastAPI

FastAPI is a Python web framework for building APIs. It uses Python type hints for three jobs at once: to validate request data, to convert it into Python values, and to generate interactive API documentation automatically. It is built on Starlette for the web layer and Pydantic for data models, and it can run async code. The code below is not run here, because the framework is not part of the standard library, so read each line carefully. A later section shows the response it returns.

The complete app, line by line

from fastapi import Depends, FastAPI, HTTPException, Query, status
from pydantic import BaseModel, Field

app = FastAPI(title="Books API", version="1.0.0")


class BookIn(BaseModel):
    title: str = Field(min_length=1, max_length=200)
    year: int = Field(ge=0, le=2100)


class Book(BookIn):
    id: int


class BookStore:
    def __init__(self) -> None:
        self.books: dict[int, Book] = {}
        self.next_id = 1

    def add(self, data: BookIn) -> Book:
        book = Book(id=self.next_id, **data.model_dump())
        self.books[book.id] = book
        self.next_id += 1
        return book


store = BookStore()


def get_store() -> BookStore:
    return store


@app.post("/books", response_model=Book, status_code=status.HTTP_201_CREATED)
def create_book(data: BookIn, db: BookStore = Depends(get_store)) -> Book:
    return db.add(data)


@app.get("/books", response_model=list[Book])
def list_books(limit: int = Query(10, ge=1, le=100), db: BookStore = Depends(get_store)) -> list[Book]:
    return list(db.books.values())[:limit]


@app.get("/books/{book_id}", response_model=Book)
def get_book(book_id: int, db: BookStore = Depends(get_store)) -> Book:
    book = db.books.get(book_id)
    if book is None:
        raise HTTPException(status_code=404, detail="Book not found")
    return book
  • from fastapi import ... brings in the app class, the dependency helper Depends, the error type HTTPException, the query parameter helper Query, and the named HTTP status codes.
  • from pydantic import BaseModel, Field brings in the base class for data models and the helper for adding validation rules.
  • app = FastAPI(title=..., version=...) creates the application. The title and version appear in the generated documentation.
  • class BookIn(BaseModel) defines the shape of data a client sends. title must be a string of 1 to 200 characters, and year an integer from 0 to 2100. Pydantic checks these rules before our code runs.
  • class Book(BookIn) inherits the same fields and adds id. This separates input from output: clients never choose the id.
  • BookStore keeps books in a dictionary keyed by id. It is an in-memory stand-in for a database, which is fine for learning but lost when the process restarts. -> None is a return type annotation saying the initialiser returns nothing.
  • book = Book(id=self.next_id, **data.model_dump()) converts the validated input into a dictionary with model_dump(), then unpacks it into the new model together with the generated id.
  • store = BookStore() creates one shared instance, and get_store returns it. This is the dependency.
  • @app.post("/books", ...) is a decorator that registers the function as the handler for POST requests to /books. response_model=Book filters the output so only the declared fields are sent. status_code=201 sets the success code to Created.
  • data: BookIn in the function signature tells FastAPI to read the request body as JSON and validate it. db: BookStore = Depends(get_store) asks FastAPI to call get_store and pass its result as db. This is dependency injection: the handler does not create its own store, so a test can supply a different one.
  • limit: int = Query(10, ge=1, le=100) is a query parameter, read from the URL such as /books?limit=5. The default is 10, and values outside 1 to 100 are rejected.
  • book_id: int in /books/{book_id} is a path parameter. FastAPI reads it from the URL and converts it to an integer, so /books/abc fails validation before the function runs.
  • raise HTTPException(status_code=404, ...) stops the request and returns a JSON error with the given code and detail.

Async endpoints

Each handler above is a normal def. FastAPI runs such functions in a thread pool, so a slow blocking call does not freeze the server. If a handler uses await with an async library, declare it with async def. The rule is simple: never call a blocking function (such as time.sleep or a synchronous database driver) inside an async def handler, because it blocks the event loop for every other request.

Automatic documentation

Because every route declares its types, FastAPI builds an OpenAPI description of the API. Running the app with a server, such as uvicorn main:app --reload, makes the interactive documentation available at /docs (Swagger UI) and /redoc, and the raw specification at /openapi.json.

FastAPI provides a test client that sends requests to the app in memory, without starting a server. It needs the httpx package installed. The test below creates a book and reads it back.

A successful create returns status 201 and the new book, including its generated id. A request for a missing book returns 404 with a detail message. Interviewers askWhy use Pydantic models and dependency injection in FastAPI? Models give validation, typed conversion and documentation from one definition. Dependencies make handlers testable and keep the wiring of shared resources in one place.

What is the difference between a path parameter and a query parameter?

A path parameter is part of the URL path, as in /books/{book_id}, and is required. A query parameter follows a question mark, as in /books?limit=5, and can have a default value. FastAPI decides which one a function argument is from the route: names that appear in braces in the path are path parameters, and other simple arguments are query parameters.

Why does the framework return 422 for an invalid body?

422 Unprocessable Content means the request was well formed but its content failed validation. FastAPI validates the body against the Pydantic model before calling the handler, and returns 422 with a description of each failing field if validation fails.

Interview questions

Which OSI layer does TCP work at, and what identifies a connection?

TCP is a transport protocol, layer 4 in the OSI model. A connection is identified by four values: the source IP and port and the destination IP and port. The ports let many connections share one IP address.

Explain the TCP three-way handshake and why UDP has none.

The client sends SYN with its starting sequence number, the server replies SYN-ACK with its own number and an acknowledgement, and the client sends ACK. Both sides then agree on the numbers used for reliable delivery. UDP has no handshake because it does not promise reliability or ordering, so it has no state to agree on.

What happens when you type a URL into a browser?

The browser parses the URL and checks caches, then resolves the host name through DNS. It opens a TCP connection to the IP address on port 443, performs the TLS handshake to validate the certificate and establish keys, and sends the HTTP GET request. The server responds, possibly with a redirect, and the browser fetches the resources the page needs and renders it.

What is the difference between HTTP/1.1, HTTP/2 and HTTP/3?

HTTP/1.1 is text-based and handles one response at a time per connection, so it suffers head-of-line blocking. HTTP/2 is binary and multiplexes many streams over one TCP connection. HTTP/3 uses QUIC over UDP, so loss in one stream does not block the others.

What does idempotent mean, and why does it matter for APIs?

An idempotent operation has the same effect on the server however many times it is applied. Networks retry requests, so an idempotent PUT or DELETE is safe to repeat. A non-idempotent POST needs an idempotency key so that a retry does not create a duplicate.

What is the difference between OAuth 2.0 and OpenID Connect?

OAuth 2.0 is for delegated authorisation: it issues access tokens that let an app call an API for a user, with limited scopes. OpenID Connect adds an ID token so the app can authenticate the user. OAuth alone does not tell the app who the user is.

Is a JWT secret? Can the server trust its contents?

A JWT is not secret: its payload is readable. The server can trust the contents only after verifying the signature with its key, checking the algorithm it expects, and checking expiry and audience claims.

Hashing versus encryption: when do you use each?

Encryption is reversible with a key and protects confidentiality, for example data in transit or at rest. Hashing is one-way and fixed in size, and it is used for integrity, signatures and password storage. Passwords need a salted, slow password hash, not plain encryption.

How do you stop SQL injection and XSS?

For SQL injection, use parameterised queries so that input is never part of the SQL text. For XSS, encode untrusted output for the context it is placed in, avoid writing raw HTML from untrusted data, and add a Content Security Policy.

What is CSRF, and what stops it?

CSRF makes a logged-in user's browser send an unwanted state-changing request to a site where the user has a session cookie. SameSite cookies, anti-CSRF tokens checked on the server, and never changing state with GET stop it.

What is the difference between REST and GraphQL?

REST exposes resources through endpoints whose responses the server defines, and it uses HTTP caching well. GraphQL exposes one schema through a single endpoint, and the client chooses which fields it needs, which avoids over-fetching but makes caching and query cost control harder.

DSA: Trees and traversals

A binary tree is a structure where each node holds a value and has at most two children, called left and right. A tree with no nodes is empty, represented by None in Python. Most tree problems share one method: write a function that answers the question for a single subtree, using the answers for its left and right children, and handle the empty tree as the base case. Once you can state what the function returns for a subtree, the recursion is almost mechanical.

There are two ways to visit every node. Depth-first traversal goes as deep as possible before backtracking, and comes in three orders that differ only in when the node itself is handled: preorder (node, left, right), inorder (left, node, right) and postorder (left, right, node). Breadth-first traversal, also called level order, visits all nodes at one depth before the next, and it uses a queue.

TraversalVisit orderTypical useExtra space
PreorderNode, left, rightCopying or serialising a tree; the first item is the rootO(h) recursion, h is the height
InorderLeft, node, rightGives sorted values for a binary search treeO(h)
PostorderLeft, right, nodeComputing things from children first, such as sizes or deletionO(h)
Level orderLevel by level, left to rightShortest depth, printing levels, right-side viewO(w), the widest level

Every traversal visits each node once, so it takes O(n) time. The extra space depends on the shape: O(h) for recursion, where h is the height, and O(w) for a queue in level order.

Maximum Depth of Binary Tree (LeetCode 104)

Given the root of a binary tree, return its maximum depth, which is the number of nodes on the longest path from the root down to a leaf. For example, the tree with values 3, 9, 20, then 15 and 7 under 20 has depth 3. A single node has depth 1, and an empty tree has depth 0.

How to think about it

  1. Understand. Depth counts nodes, not edges. An empty tree returns 0, which is the base case.
  2. Brute force. Walk every root-to-leaf path, count its length, and keep the maximum. Correct, but it needs an explicit list of paths and is harder to write cleanly.
  3. Find the waste. The depth of the whole tree is one more than the larger of the depths of its two subtrees. That is the subproblem structure that a recursive function can use directly.
  4. Optimise. Recurse: return 0 for None, otherwise return 1 plus the maximum of the two child depths. Each node is visited once, so the cost is O(n).
  5. Dry run. Tree 3 with children 9 and 20; 20 has children 15 and 7. Depth of 9 is 1 and depth of 15 and 7 is 1 each, so depth of 20 is 2. Depth of 3 is 1 plus max(1, 2), which is 3.

Code

from collections import deque


class TreeNode:
    def __init__(self, val=0, left=None, right=None):
        self.val = val
        self.left = left
        self.right = right


def build_level_order(values):
    """Build a tree from LeetCode's level-order list, where None marks a missing child."""
    if not values or values[0] is None:
        return None
    root = TreeNode(values[0])
    queue = deque([root])
    i = 1
    while queue and i < len(values):
        node = queue.popleft()
        if i < len(values) and values[i] is not None:
            node.left = TreeNode(values[i])
            queue.append(node.left)
        i += 1
        if i < len(values) and values[i] is not None:
            node.right = TreeNode(values[i])
            queue.append(node.right)
        i += 1
    return root


def max_depth(root):
    if root is None:
        return 0
    return 1 + max(max_depth(root.left), max_depth(root.right))


print(max_depth(build_level_order([3, 9, 20, None, None, 15, 7])))
print(max_depth(build_level_order([1, None, 2])))
print(max_depth(build_level_order([])))
3
2
0

Pattern to rememberFor a tree answer, ask what a subtree returns, handle None first, then combine the children's answers.

Binary Tree Level Order Traversal (LeetCode 102)

Given the root of a binary tree, return the values of its nodes grouped by level, from top to bottom and from left to right within each level. For the tree 3, then 9 and 20, then 15 and 7, the answer is [[3], [9, 20], [15, 7]].

How to think about it

  1. Understand. The output is a list of lists. Each inner list is one level. An empty tree gives an empty list.
  2. Brute force. Compute the depth of the tree, then for each depth d collect the nodes at depth d with a recursive walk. This visits the tree once per level, so the cost is O(n times the height).
  3. Find the waste. Each level is visited again and again. A single pass that processes whole levels at a time would avoid that.
  4. Optimise. Use a queue, which holds the nodes of the current level. Before processing a level, record its size. Then pop exactly that many nodes, collect their values, and push their children, which form the next level. The queue must be a deque, because popping from the front of a Python list is O(n).
  5. Dry run. Start with queue [3]. Level size 1: pop 3, record [3], push 9 and 20. Level size 2: pop 9 and 20, record [9, 20], push 15 and 7. Level size 2: pop 15 and 7, record [15, 7], push nothing. The queue is empty, so the answer is [[3], [9, 20], [15, 7]].

Construct Binary Tree from Preorder and Inorder Traversal (LeetCode 105)

You are given two integer arrays: preorder, the preorder traversal of a binary tree, and inorder, the inorder traversal of the same tree. The values are unique. Rebuild and return the tree. For example, preorder [3, 9, 20, 15, 7] and inorder [9, 3, 15, 20, 7] give the tree 3, with 9 on the left and 20 on the right, and 15 and 7 as the children of 20.

How to think about it

  1. Understand. The arrays have the same length n, and each value appears once. A single array is not enough to rebuild a tree, but two traversals usually are.
  2. Brute force. Try to find the root by scanning, split both arrays by hand, and recurse. Each split copies slices of the arrays, so the cost is O(n^2) in the worst case.
  3. Find the waste. Finding the root's position in the inorder array takes a scan, and this is repeated at every level. A dictionary from value to inorder index answers that in O(1).
  4. Optimise. The first item of the preorder list is always the root of the current subtree. Find that value's position in the inorder list. Everything to its left in the inorder list is the left subtree, and everything to its right is the right subtree. Preorder lists the left subtree's nodes right after the root, then the right subtree's nodes, so the next items in preorder belong to the left subtree first. Keep one shared index into preorder, advance it once per node, and build the left subtree before the right subtree. Each node is created once, so the total cost is O(n).
  5. Dry run. preorder [3, 9, 20, 15, 7], inorder [9, 3, 15, 20, 7]. The root is 3, at inorder index 1. The left subtree is inorder [9], and the right subtree is inorder [15, 20, 7]. Next preorder value 9 is the left child, and its inorder range is empty on both sides. Next preorder value 20 is the right child, which has inorder [15, 20, 7]. Its root is 20, at inorder index 3 of the whole list. Its left range is [15] and right range is [7], so 15 and 7 are its children.

Code

from collections import deque


class TreeNode:
    def __init__(self, val=0, left=None, right=None):
        self.val = val
        self.left = left
        self.right = right


def build_tree(preorder, inorder):
    """Rebuild the tree from its preorder and inorder traversals."""
    index_of = {v: i for i, v in enumerate(inorder)}   # value to inorder position, O(1) lookup
    pre_pos = 0                                        # next unused item in preorder

    def build(lo, hi):
        """Build the subtree whose values are inorder[lo:hi]."""
        nonlocal pre_pos
        if lo >= hi:
            return None
        root_val = preorder[pre_pos]                   # the next preorder item is this subtree's root
        pre_pos += 1
        mid = index_of[root_val]                       # where the root splits the inorder range
        node = TreeNode(root_val)
        node.left = build(lo, mid)                     # left first: preorder lists it next
        node.right = build(mid + 1, hi)
        return node

    return build(0, len(inorder))


def level_order(root):
    if root is None:
        return []
    result = []
    queue = deque([root])
    while queue:
        level = []
        for _ in range(len(queue)):
            node = queue.popleft()
            level.append(node.val)
            if node.left is not None:
                queue.append(node.left)
            if node.right is not None:
                queue.append(node.right)
        result.append(level)
    return result


print(level_order(build_tree([3, 9, 20, 15, 7], [9, 3, 15, 20, 7])))
print(level_order(build_tree([1, 2], [2, 1])))
print(level_order(build_tree([1, 2, 3], [2, 1, 3])))
[[3], [9, 20], [15, 7]]
[[1], [2]]
[[1], [2, 3]]

Time O(n) · Space O(n) for the dictionary and the recursion stack

TrapBuild the left subtree before the right one. The shared preorder index only works if the recursion consumes preorder in the same order that preorder lists the nodes.

Interviewers askWhy can't you rebuild a tree from preorder alone? Preorder does not show where the left subtree ends and the right one begins. Inorder supplies that boundary. Postorder with inorder works the same way, reading from the end.

Pattern to rememberIn a traversal, one list gives the root and the other gives the split. Use a value-to-index map to find the split in constant time.

Binary Tree Maximum Path Sum (LeetCode 124)

A path in a binary tree is a sequence of nodes where each adjacent pair is connected by an edge, and no node appears twice. The path does not have to pass through the root, and it may contain only one node. Return the largest possible sum of the values along any path. For example, with the tree 1, then 2 and 3, the best path is 2, 1, 3 with sum 6. With the tree -10, then 9 and 20, where 20 has children 15 and 7, the best path is 15, 20, 7 with sum 42, which does not include the root.

How to think about it

  1. Understand. The path can bend at any node, so there is a top point of the path that may not be the root. Values can be negative, so a branch that lowers the sum should be ignored. The tree has at least one node.
  2. Brute force. For every node, consider every pair of paths that go down its left and right subtrees, and take the best. Enumerating paths for every node repeats the same downward work, so it is O(n^2) or worse.
  3. Find the waste. Two different kinds of value appear at each node. One is the best path that bends at the node and uses both children; that is a candidate answer, and it does not continue upward. The other is the best one-sided path that starts at the node and goes down one child; that is what the parent can use, because a path to the parent can extend only one way.
  4. Optimise. Write a function that returns the best one-sided downward path from a node, and while computing it, update a global best with the bent path through that node. Negative branches contribute nothing, so take max(child gain, 0) for each child. For a node with value v, the bent path is v plus the two clipped child gains, and the value returned to the parent is v plus the larger clipped child gain. Each node is visited once, so the cost is O(n).
  5. Dry run. Tree -10, then 9 and 20, with 15 and 7 under 20. Node 9 has no children, so its one-sided gain is 9 and the best is 9. Node 15 returns 15, node 7 returns 7. Node 20 has clipped gains 15 and 7, so the bent path is 20 + 15 + 7 = 42, which becomes the best. It returns 20 + max(15, 7) = 35 to its parent. At the root, the clipped gains are 9 and 35, so the bent path is -10 + 9 + 35 = 34, which is less than 42. The answer is 42.

Code

from collections import deque


class TreeNode:
    def __init__(self, val=0, left=None, right=None):
        self.val = val
        self.left = left
        self.right = right


def build_level_order(values):
    if not values or values[0] is None:
        return None
    root = TreeNode(values[0])
    queue = deque([root])
    i = 1
    while queue and i < len(values):
        node = queue.popleft()
        if i < len(values) and values[i] is not None:
            node.left = TreeNode(values[i])
            queue.append(node.left)
        i += 1
        if i < len(values) and values[i] is not None:
            node.right = TreeNode(values[i])
            queue.append(node.right)
        i += 1
    return root


def max_path_sum(root):
    """Return the largest sum of any path in the tree; the path may bend at any node."""
    best = root.val                       # at least one node exists, so start from its value

    def gain(node):
        """Return the best one-sided downward path sum starting at node."""
        nonlocal best
        if node is None:
            return 0
        left = max(gain(node.left), 0)    # a negative branch is better left out
        right = max(gain(node.right), 0)
        best = max(best, node.val + left + right)   # the path that bends at this node
        return node.val + max(left, right)          # the path the parent can extend

    gain(root)
    return best


print(max_path_sum(build_level_order([1, 2, 3])))
print(max_path_sum(build_level_order([-10, 9, 20, None, None, 15, 7])))
print(max_path_sum(build_level_order([-3])))
6
42

Time O(n) · Space O(h) for the recursion stack

TrapReturning the bent path sum to the parent is wrong. A path that bends at a node cannot continue upward, because it would then visit the node twice. Only the one-sided gain can be returned.

Interviewers askWhy clip the child gains at zero? A child whose best path is negative would make the sum smaller, so the best choice is to leave that branch out entirely. Clipping expresses "use this branch only if it helps".

Pattern to rememberWhen a tree problem asks for a best path rather than a best value, separate what a node reports to its parent from what it records as a candidate answer.
