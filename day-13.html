Virtualization: many machines on one computer

Virtualization is a technique where software makes one physical computer behave like several separate computers. Each separate computer is called a virtual machine (VM). A VM has its own virtual CPU, memory, disk and network card, and it runs its own operating system, called the guest OS. Nothing inside the VM can directly touch the real hardware. Every access goes through the software layer that created it.

The software that creates and runs VMs is called a hypervisor, also known as a virtual machine monitor (VMM). Its job is to share the real CPU, memory and devices among the guests and to keep the guests isolated from each other. Hypervisors are classified by where they sit in the software stack.

Type 1 and type 2 hypervisors

A type 1 hypervisor (also called bare-metal) runs directly on the hardware, with no general-purpose operating system underneath it. VMware ESXi, Microsoft Hyper-V and Xen are common examples. KVM is built into the Linux kernel, so the Linux kernel itself becomes a type 1 hypervisor; it is usually classed as type 1 as well. Data centers mostly use type 1 hypervisors because there is one less layer between the guests and the hardware.

A type 2 hypervisor (also called hosted) runs as an ordinary application on top of a host operating system. VirtualBox and VMware Workstation are examples. They are very convenient on a laptop, because you can run a Linux VM inside Windows or macOS, but every guest instruction has to pass through the host OS as well, so they usually carry more overhead.

TrapDo not say "type 1 is always faster". The usual, correct statement is that type 1 has less overhead because there is no host operating system in the middle, and this matters most in servers that run many VMs.

Types of virtualization

The three words you will hear most are full, para and hardware-assisted virtualization. They describe how the guest is presented to the hypervisor, not how far it is isolated.

  • Full virtualization. The guest OS is completely unmodified. It believes it owns the whole machine. The hypervisor catches the guest's privileged instructions (the instructions only the kernel is allowed to run, such as ones that change page tables) and handles them safely. Older hypervisors did this with binary translation, rewriting those instructions on the fly. Modern hypervisors do it much faster with hardware support.
  • Paravirtualization. The guest OS is modified to know it is virtualized. Instead of issuing a privileged instruction and hoping it is caught, the guest makes an explicit call to the hypervisor, called a hypercall. The Xen hypervisor's paravirtual mode is the classic example. The guest is faster, but it must be modified, so you cannot run an arbitrary closed-source OS this way.
  • Hardware-assisted virtualization. CPUs contain special support for running guests, such as Intel VT-x and AMD-V. The CPU runs most guest instructions directly at full speed and only switches back to the hypervisor when the guest does something that needs control. This is what makes modern full virtualization fast, and it is what KVM depends on.

There is also OS-level virtualization, which is what containers use. It does not run a separate guest kernel at all. Section 2 explains it.

ApproachGuest kernelGuest modified?Typical example

Virtualization gives you consolidation (fewer physical servers), isolation (a crashed guest does not take down its neighbours) and flexibility (you can snapshot, move and clone a VM as a set of files). Its cost is that every VM carries a full operating system, which means gigabytes of disk, a few gigabytes of memory and boot times measured in seconds to minutes.

What is the difference between a type 1 and a type 2 hypervisor?

A type 1 hypervisor runs directly on the hardware, so there is no host operating system between it and the machine. A type 2 hypervisor runs as an application on top of a host operating system. Type 1 is the usual choice for servers because it has less overhead.

Containers versus virtual machines

A container is an ordinary process, or a small group of processes, that the Linux kernel has been told to isolate. It does not have its own kernel. It shares the host's kernel and uses two kernel features to pretend it is alone: namespaces and cgroups. The difference from a VM is the boundary. A VM is cut off by virtual hardware and a guest kernel. A container is cut off by the kernel itself, which is one piece of software, so the container is lighter and starts faster, but the isolation is weaker.

Because a container is just a process, starting one takes milliseconds to seconds, and a small container image can be a few megabytes. There is no boot sequence, no init system to wait for and no second kernel in memory.

Namespaces: what a process can see

A namespace wraps one kind of global system resource so that a process only sees its own copy. Linux has several namespace types, and a container usually gets a fresh copy of each of these:

  • PID namespace. The process gets its own process numbering. The first process inside becomes PID 1, even though on the host it might be PID 48213. From inside, ps shows only the container's processes.
  • NET namespace. The container gets its own network interfaces, routing table, firewall rules and port space. Two containers can both listen on port 80 because each has its own port space.
  • MNT namespace. The container gets its own view of the filesystem mount points. The root directory it sees is the image's filesystem, not the host's.
  • UTS namespace. The container gets its own hostname and domain name.
  • IPC namespace. Shared memory and message queues are private to the container.
  • USER namespace. User IDs can be mapped so that root inside the container is an unprivileged user on the host. This is an important hardening option.
  • CGROUP namespace. The container sees its own part of the control group hierarchy, so it cannot see how the host is arranged.

cgroups: how much a process can use

A control group (cgroup) limits, accounts for and prioritises the resources a group of processes may use. Namespaces answer "what can I see?" and cgroups answer "how much can I consume?". Typical limits are CPU time, memory, disk and network bandwidth, and the number of processes.

Docker exposes these as flags:

docker run --memory=256m --cpus=1.5 nginx

This starts an nginx container that may use at most 256 MB of memory and about one and a half CPU cores. If the container tries to use more memory than its limit, the kernel's out-of-memory killer ends one of its processes. Docker reports this as exit code 137, which is 128 plus 9, the number of the SIGKILL signal.

Key ideaA container is an isolated process, not a small computer. Namespaces control what it can see, cgroups control what it can use, and both are features of the one shared Linux kernel.

What does a namespace do, and what does a cgroup do?

A namespace gives a process its own view of a global resource, such as process IDs, network interfaces or the filesystem mounts, so it cannot see the host's copy. A cgroup limits and accounts for how much CPU, memory, I/O or processes a group of processes may use. Namespaces control visibility; cgroups control consumption.

Docker: images, layers, volumes and networks

Docker is a set of tools that builds, stores and runs containers. Its central idea is the image: a read-only package that contains an application and everything it needs to run, such as the runtime, libraries and configuration. A container is a running instance of an image. When Docker starts a container, it adds one thin writable layer on top of the image, and every change the running process makes goes into that layer. The image itself never changes.

This split is why one image can start many identical containers at once, and why deleting a container throws away its changes but leaves the image in place.

Layers and the build cache

An image is built from layers. Each instruction in a Dockerfile that changes the filesystem creates a new layer that stores only the difference from the layer below. Layers are identified by a SHA-256 digest of their contents, so two images that share a base layer store it only once on disk and download it only once from a registry.

Docker also caches layers. If an instruction and its inputs have not changed since the last build, Docker reuses the cached layer instead of running the instruction again. The important rule is that a changed layer invalidates every layer after it. This is why the order of instructions matters, as the next example shows.

The Dockerfile

A Dockerfile is a text file of instructions that describes how to build an image. Here is a typical one for a small Python web app, with a line-by-line explanation:

FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 8000
CMD ["python", "app.py"]
  • FROM chooses the base image. Every later instruction adds a layer on top of it.
  • WORKDIR /app sets the directory for the following instructions and creates it if it is missing.
  • COPY requirements.txt . copies only the dependency list into the image first.
  • RUN pip install ... installs the dependencies. This layer is slow, so it is placed before the source code. As long as requirements.txt is unchanged, Docker reuses this layer on every rebuild.
  • COPY . . copies the rest of the source. Your code changes often, and this layer is rebuilt each time, but the slow install above is not.
  • EXPOSE 8000 documents the port the app listens on. It does not publish the port by itself.
  • CMD is the default command to run when a container starts from the image. The JSON array form runs the program directly, without a shell in between.

TrapCopying the whole source before installing dependencies (COPY . . above RUN pip install) forces the slow install to run on every code change. Copy the dependency file first.

Other instructions you should recognise are ENV (sets an environment variable), ARG (a build-time variable), USER (the user the container runs as, which should not be root in production), ENTRYPOINT (the fixed program, with CMD supplying default arguments) and ADD (like COPY but with extra features such as extracting archives; prefer COPY unless you need them).

TrapDeleting a file in a later layer does not remove it from the image. The earlier layer still stores it, and anyone who pulls the image can extract it. Never copy a password or a private key into an image, even if you delete it in the next line.

The commands to build and run it look like this:

docker build -t myapp:1.0 .
docker run -d -p 8000:8000 --name web myapp:1.0
docker ps
docker logs web
docker exec -it web sh
docker stop web
docker rm web

docker build -t myapp:1.0 . builds the image in the current directory and tags it with a name and version. -d runs the container in the background. -p 8000:8000 publishes the container's port 8000 on port 8000 of the host, in the form host:container. docker exec -it web sh opens an interactive shell inside a running container.

Volumes: data that outlives a container

The container's writable layer disappears when the container is removed. Anything that must survive, such as a database's files, belongs in a volume. A named volume is storage created and managed by Docker. A bind mount maps a directory from the host into the container. A tmpfs mount keeps data in memory only.

docker volume create pgdata
docker run -d -v pgdata:/var/lib/postgresql/data --name db postgres:16
docker run -d -v "$(pwd)/site:/usr/share/nginx/html:ro" -p 8080:80 nginx

The first run mounts the named volume pgdata at the path where the database keeps its files. The second run is a bind mount: the host's site folder is mounted read-only (the :ro suffix) into nginx's web root. Removing the db container leaves pgdata intact, so a new container can attach to the same data.

Networks: how containers find each other

Docker creates networks for containers. The three you will meet are bridge (the default for standalone containers, which gives each container a private address behind a virtual switch on the host), host (the container shares the host's network stack, with no isolation) and none (no networking at all).

A user-defined bridge network is the one you should create for multi-container apps. Containers on the same user-defined network can reach each other by container name, because Docker runs a small DNS server for the network. The legacy default bridge does not provide this name lookup.

docker network create appnet
docker run -d --network appnet --name db postgres:16
docker run -d --network appnet --name api myapp:1.0
# inside the api container, the database is reachable at the hostname "db"

Key ideaPublishing a port (-p) is for traffic from outside the host. Container-to-container traffic on a shared user-defined network does not need published ports at all.

Docker Compose: several containers as one file

Docker Compose describes a multi-container application in one YAML file. Each entry under services is a container, and Compose creates the networks and volumes it names. One command starts everything:

services:
  web:
    build: .
    ports:
      - "8000:8000"
    environment:
      DATABASE_HOST: db
    depends_on:
      - db
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - pgdata:/var/lib/postgresql/data
volumes:
  pgdata:

Compose puts both services on a shared network, so web can reach the database at the name db. The value ${DB_PASSWORD} is read from the shell or a .env file, which keeps the secret out of the committed YAML. Use docker compose up -d to start the stack and docker compose down to stop and remove its containers and networks. The named volume survives down unless you add -v. The modern command is docker compose (a plugin); the older standalone tool docker-compose is legacy.

Why should the dependency install come before COPY . . in a Dockerfile?

Docker caches each layer and rebuilds a layer whenever its inputs change, and every later layer is rebuilt with it. Source code changes on almost every build, so if the source is copied first, the dependency install below it is re-run every time. Copying only the dependency file first keeps the slow install cached until the dependencies actually change.

Why does a user-defined network matter for multi-container apps?

On a user-defined bridge network, Docker's embedded DNS resolves container names, so an API container can connect to a database simply at the host name db. The legacy default bridge does not provide this name resolution, so you would need to use IP addresses or links.

Kubernetes: running containers across many machines

Docker runs containers on one host. Production systems need dozens or thousands of containers across many hosts, which raises new questions: which machine should run each container, what happens when a machine dies, how do you roll out a new version without downtime, and how does one service find another when its containers keep moving. Kubernetes (often written K8s) answers these questions. You describe the state you want, and Kubernetes keeps reality matching that description.

Architecture: control plane and nodes

A Kubernetes installation is a cluster. It has two kinds of machines. The control plane makes global decisions. Nodes (worker machines) run the containers.

  • kube-apiserver is the front door. Every command, including those from the kubectl tool, is a REST request to this server. It validates requests and is the only component that reads and writes the cluster state directly.
  • etcd is a consistent key-value store that holds the whole cluster state: which objects exist and what they contain.
  • kube-scheduler decides which node should run each new pod, by checking resource requests, node labels and rules you define.
  • kube-controller-manager runs the controllers, which watch the state and push it toward what you asked for.
  • kubelet runs on every node. It makes sure the containers described for that node are running and reports their health back to the control plane.
  • kube-proxy runs on every node and maintains the network rules that send traffic addressed to a Service to one of its healthy pods.
  • The container runtime, such as containerd or CRI-O, actually creates and runs the containers. Kubernetes talks to it through a standard interface.

The declarative model and the reconciliation loop

Kubernetes is declarative. You do not write "start three containers now". You write "the cluster should have three copies of this container running", and you store that as an object. Each controller then runs a reconciliation loop: it reads the desired state from the API server, observes the actual state, and takes actions to close the gap. If a pod crashes, the actual count drops to two, the controller notices, and it creates a replacement. Nobody has to press a button.

Key ideaKubernetes does not run commands in sequence. It stores a description of the desired state and keeps comparing reality with it forever. Almost every object behaves this way.

The main objects

  • Pod. The smallest unit Kubernetes schedules. A pod holds one or more containers that share a network namespace (one IP address and one port space) and can share volumes. Most pods hold a single container. A pod is ephemeral: when it dies, it is replaced by a new pod with a new IP address, never revived.
  • ReplicaSet. Keeps a fixed number of identical pods running. You rarely write one yourself.
  • Deployment. The object you use for stateless applications. It manages a ReplicaSet and adds rolling updates and rollbacks: when you change the image, it creates pods with the new image and removes old ones gradually, and you can roll back to the previous ReplicaSet.
  • Service. A stable virtual IP address and DNS name in front of a set of pods. Clients use the Service name, and traffic is spread across the pods that match its selector. Pod IPs change; the Service name does not. Service types include ClusterIP (reachable only inside the cluster, the default), NodePort and LoadBalancer.
  • Ingress. HTTP and HTTPS routing rules from outside the cluster to Services, based on host name and path. An Ingress does nothing on its own; a running ingress controller has to implement the rules.
  • ConfigMap. Non-secret configuration, stored as key-value pairs and injected into pods as environment variables or files.
  • Secret. Sensitive values such as passwords and tokens, injected the same way as ConfigMaps.
  • Labels and selectors. Labels are key-value tags on objects, such as app: web. Selectors query by label. A Deployment finds its pods, and a Service finds its backends, this way. Labels are the glue of Kubernetes.

Writing objects as YAML

Objects are usually written in YAML. Every object has apiVersion (the API group and version), kind (the object type), metadata (name and labels) and spec (the desired state). Here is a Deployment and a Service that exposes it:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: nginx:1.27
          ports:
            - containerPort: 80
          readinessProbe:
            httpGet:
              path: /
              port: 80
---
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80

The Deployment asks for three replicas of an nginx pod, and labels each pod app: web. The selector must match the template's labels, or the Deployment would never find its own pods. The readinessProbe asks the kubelet to call GET / on port 80. Until the probe succeeds, the pod is not added to Service endpoints, so no traffic reaches a container that is still starting. The Service selects every pod labelled app: web, gives them one stable address, and forwards port 80 to port 80 on each pod.

ConfigMaps and Secrets

A Secret stores its values base64-encoded. Base64 is an encoding that turns binary data into printable characters so it can be written in YAML or JSON. It is not encryption, because anyone who can read the Secret can decode it instantly. Encryption at rest must be enabled separately in the cluster, and access must be limited with role-based access control (RBAC).

import base64

secret = "s3cret-pass"
encoded = base64.b64encode(secret.encode("utf-8")).decode("ascii")
print(encoded)
print(base64.b64decode(encoded).decode("utf-8"))
czNjcmV0LXBhc3M=
s3cret-pass

The first line is the encoded form. The second line decodes it back, which proves the point: a Secret is readable by anyone with access to it. In Kubernetes you would create one with kubectl create secret generic db-secret --from-literal=password=s3cret-pass, and the cluster stores the value encoded.

Running and inspecting the cluster

kubectl is the command-line client for the API server. These are the commands you will use most often:

kubectl apply -f deployment.yaml      # create or update objects described in the file
kubectl get pods                      # list pods in the current namespace
kubectl get deploy,svc                # list Deployments and Services together
kubectl describe pod web-7d9f8-abcde  # events and status, the first place to look when a pod fails
kubectl logs web-7d9f8-abcde          # standard output of the container
kubectl scale deployment web --replicas=5
kubectl rollout status deployment/web
kubectl rollout undo deployment/web  # return to the previous ReplicaSet
kubectl port-forward svc/web 8080:80 # local test access to a Service

kubectl apply is declarative: running it twice with the same file changes nothing the second time. kubectl rollout undo is the fast way to recover from a bad release, because the previous ReplicaSet still exists and Kubernetes only has to scale it back up.

Health probes

Kubernetes uses two probes to check containers. A liveness probe asks "is this container stuck?". If it fails repeatedly, the kubelet restarts the container. A readiness probe asks "can this container take traffic right now?". If it fails, the pod stays running but is removed from the Service's endpoints, so no requests reach it. A slow-starting app needs a readiness probe so traffic waits for it, and a deadlocked app needs a liveness probe so it gets restarted.

TrapDo not point the liveness probe at a dependency such as the database. If the database is briefly down, every pod fails its liveness check and is restarted, which makes recovery slower. Liveness should check only the container itself.

Typical mistakes

  • Storing data in the container. Pods are replaceable, so data must go to a PersistentVolume or to an external service.
  • Connecting to pod IP addresses. Pod IPs change every time a pod is replaced. Connect through a Service name.
  • Creating bare pods for production. A pod created directly is not replaced when its node fails. Use a Deployment, whose ReplicaSet keeps the count correct.
  • Trusting base64 Secrets. Enable encryption at rest and restrict who can read Secrets.
What is the difference between a Deployment and a Pod?

A pod is the smallest unit Kubernetes runs: one or more containers sharing a network address. A Deployment is a controller that manages a set of identical pods through a ReplicaSet. It keeps the requested number of pods running, replaces failed ones and performs rolling updates. A bare pod has no controller, so nothing recreates it if its node fails.

What does a Service give you that a pod IP does not?

A pod's IP address changes whenever the pod is replaced. A Service provides a stable virtual IP and DNS name, selects the healthy pods that match its labels, and spreads traffic across them. Clients connect to the Service name and never need to know which pods exist.

Interview questions

What is a hypervisor, and what is the difference between type 1 and type 2?

A hypervisor is software that creates and runs virtual machines and isolates them from each other. A type 1 hypervisor runs directly on the hardware, as in VMware ESXi, Hyper-V and Xen. A type 2 hypervisor runs as an application on a host operating system, as in VirtualBox. Type 1 has less overhead, which is why servers use it.

What is the difference between a VM and a container?

A VM includes its own guest kernel and virtual hardware, so it is heavier, takes longer to start and is isolated by the hypervisor. A container is an isolated process that shares the host kernel. It starts in milliseconds and is small, but the isolation is provided by the shared kernel, so it is weaker. Containers must use a compatible kernel, while VMs can run a different operating system.

What do namespaces and cgroups each do?

Namespaces control what a process can see: its process IDs, network interfaces, mounts, hostname and more. Cgroups control how much a process can use: CPU, memory, I/O and the number of processes. Together they are the foundation of Linux containers.

What is an image, and how is it different from a container?

An image is a read-only template built from layers. A container is a running instance of an image with one extra writable layer on top. Many containers can run from one image, and removing a container discards its writable layer but leaves the image.

Why does the order of instructions in a Dockerfile matter?

Docker caches each layer, and a changed layer invalidates all the layers after it. Put instructions that change rarely, such as installing dependencies, before instructions that change often, such as copying source code. This keeps the build cache useful.

What is the difference between a named volume and a bind mount?

A named volume is storage created and managed by Docker, referenced by a name, and is the usual choice for application data. A bind mount maps a specific directory on the host into the container, which is common for development. Both survive when the container is removed.

What is the role of the Kubernetes scheduler and the controller manager?

The scheduler chooses a node for each new pod based on resource requests, labels and placement rules. The controller manager runs controllers that compare the desired state with the actual state and act to close the gap, such as creating replacement pods when some have failed.

What is the difference between a Service and an Ingress?

A Service gives a set of pods a stable IP address and DNS name inside the cluster, and load balances across them. An Ingress holds HTTP and HTTPS routing rules, based on host name and path, that send outside traffic to Services. An ingress controller has to be running to enforce the rules.

Are Kubernetes Secrets encrypted?

Not by default. Secret values are base64-encoded, which is an encoding anyone can reverse. You must enable encryption at rest in the cluster and restrict access with RBAC. Base64 hides nothing.

What is the difference between a liveness probe and a readiness probe?

A liveness probe decides whether a container should be restarted because it is stuck. A readiness probe decides whether a pod should receive traffic. A failing readiness probe removes the pod from its Service without restarting it.

Why does quick sort have an O(n^2) worst case, and how do real implementations avoid it?

Quick sort's speed depends on its pivot splitting the data roughly in half. If the pivot is always the smallest or largest element, one side is empty and the recursion does n levels of work, giving O(n^2). Choosing a random pivot, or the median of three values, makes the bad case extremely unlikely for any input. Introsort switches to heap sort when the recursion gets too deep.

DSA: Sorting algorithms

Sorting is the classic place to practise divide and conquer: split a problem into smaller copies of itself, solve the copies, then combine the answers. Merge sort and quick sort are the two algorithms you must be able to write from memory, and interviewers often ask you to compare them. Before the problems, here is the vocabulary you need.

  • Comparison sort. Sorts only by comparing two elements at a time. No comparison sort can beat O(n log n) comparisons in the worst case.
  • In-place. Uses only a constant amount of extra memory, beyond the input array.
  • Stable. Equal elements keep their original relative order. This matters when you sort records by one key after sorting by another.
AlgorithmBestAverageWorstExtra spaceStable
Merge sortO(n log n)O(n log n)O(n log n)O(n)Yes
Quick sortO(n log n)O(n log n)O(n^2)O(log n) stack, on averageNo (typical versions)
Heap sortO(n log n)O(n log n)O(n log n)O(1)No
Counting sortO(n + k)O(n + k)O(n + k)O(k)Yes

In the table, k is the range of the values. Counting sort is not a comparison sort, so the O(n log n) lower bound does not apply to it, but it works only when the values are small integers. Python's built-in sorted uses Timsort, which is stable and runs in O(n log n) worst case. In an interview, you use the built-in only if the question allows it; otherwise write the algorithm.

Sort an Array (LeetCode 912)

Given an array of integers nums, sort it in ascending order. The problem asks you to do it without relying on a library sort, so the point is to write the algorithm yourself. For example, [5, 2, 3, 1] becomes [1, 2, 3, 5]. The array can hold up to 50,000 values, so an O(n^2) algorithm is too slow.

How to think about it

  1. Understand. Values can be negative and can repeat. The input can be large, so the expected cost is O(n log n). Returning a new list or sorting in place are both acceptable.
  2. Brute force. Selection sort or bubble sort: repeatedly find the smallest remaining element and move it forward. Correct, but each pass scans the rest of the array, so the cost is O(n^2).
  3. Find the waste. Selection sort compares pairs of elements many times and never reuses what it learned from earlier comparisons. Divide and conquer avoids this: sorting two halves independently is cheaper, and merging two sorted halves takes only linear time.
  4. Optimise. Merge sort splits the array in half, sorts each half recursively, and merges the results with two pointers. The depth of the recursion is log n and each level does O(n) work, so the total is O(n log n). Quick sort instead picks a pivot, partitions the array into smaller and larger values, and recurses. Its average cost is O(n log n).
  5. Dry run. Merging [1, 5] with [2, 3]: compare 1 and 2, take 1; compare 5 and 2, take 2; compare 5 and 3, take 3; the left side is not finished, so take 5 at the end. Result: [1, 2, 3, 5].

Code

def merge_sort(nums):
    """Return a new sorted list using divide and conquer."""
    if len(nums) <= 1:
        return nums[:]                # a list of length 0 or 1 is already sorted
    mid = len(nums) // 2
    left = merge_sort(nums[:mid])     # sort the left half
    right = merge_sort(nums[mid:])    # sort the right half
    merged = []
    i = j = 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:        # <= keeps equal items in order (stable)
            merged.append(left[i])
            i += 1
        else:
            merged.append(right[j])
            j += 1
    merged.extend(left[i:])           # at most one of these two is non-empty
    merged.extend(right[j:])
    return merged


def quick_sort(nums):
    """Return a new sorted list by partitioning around a pivot."""
    if len(nums) <= 1:
        return nums[:]
    pivot = nums[len(nums) // 2]      # the middle value is the pivot
    smaller = [x for x in nums if x < pivot]
    equal = [x for x in nums if x == pivot]
    larger = [x for x in nums if x > pivot]
    return quick_sort(smaller) + equal + quick_sort(larger)


def quick_sort_in_place(nums, lo=0, hi=None):
    """Sort nums[lo..hi] in place using Lomuto partitioning."""
    if hi is None:
        hi = len(nums) - 1
    if lo >= hi:
        return nums
    mid = (lo + hi) // 2
    nums[mid], nums[hi] = nums[hi], nums[mid]   # move the middle value to the end as pivot
    pivot = nums[hi]
    i = lo                            # nums[lo:i] holds values smaller than pivot
    for j in range(lo, hi):
        if nums[j] < pivot:
            nums[i], nums[j] = nums[j], nums[i]
            i += 1
    nums[i], nums[hi] = nums[hi], nums[i]       # put the pivot in its final place
    quick_sort_in_place(nums, lo, i - 1)
    quick_sort_in_place(nums, i + 1, hi)
    return nums


print(merge_sort([5, 2, 3, 1]))
print(quick_sort([5, 1, 1, 2, 0, 0]))
print(quick_sort_in_place([-3, 7, 0, 7, -1]))
[1, 2, 3, 5]
[0, 0, 1, 1, 2, 5]
[-3, -1, 0, 7, 7]

Merge sort: time O(n log n) · space O(n) · stable. Quick sort (list version): time O(n log n) on average, O(n^2) worst · space O(n).

Pattern to rememberWhen you see "sort" with a target of n log n, think divide and conquer: halve, solve each half, merge in linear time.

Sort Colors (LeetCode 75)

You get an array whose values are only 0, 1 or 2, standing for red, white and blue. Sort the array so that all 0s come first, then all 1s, then all 2s. Do it in one pass with constant extra space. For example, [2, 0, 2, 1, 1, 0] becomes [0, 0, 1, 1, 2, 2].

How to think about it

  1. Understand. There are only three possible values, which is a strong hint. The result is determined entirely by how many 0s, 1s and 2s there are, but the problem asks for an in-place rearrangement.
  2. Brute force. Count the 0s, 1s and 2s, then overwrite the array. That is two passes and O(1) extra space, which is acceptable, but the problem asks for a one-pass solution.
  3. Find the waste. Counting is an extra pass. Better is to partition the array into three zones while scanning it once.
  4. Optimise. This is the Dutch national flag algorithm, named after the flag's three bands. Keep three pointers: low marks the end of the 0 zone, high marks the start of the 2 zone, and mid scans the unknown middle. If the value at mid is 0, swap it into the 0 zone and advance both low and mid. If it is 1, leave it and advance mid. If it is 2, swap it into the 2 zone and move high left without advancing mid, because the value swapped in has not been examined yet. The loop ends when mid passes high.
  5. Dry run. Start with [2, 0, 1], low = 0, mid = 0, high = 2. Each row shows the state before one step.
StepArraylowmidhighAction
1[2, 0, 1]002value 2, swap with high, high becomes 1
2[1, 0, 2]001value 1, advance mid
3[1, 0, 2]011value 0, swap with low, advance low and mid
4[0, 1, 2]121mid is past high, stop

Code

def sort_colors(nums):
    """Dutch national flag: 0s to the front, 2s to the back, 1s in the middle."""
    low = 0                       # nums[:low] are all 0
    mid = 0                       # nums[low:mid] are all 1; nums[mid] is the scanner
    high = len(nums) - 1          # nums[high + 1:] are all 2
    while mid <= high:
        if nums[mid] == 0:
            nums[low], nums[mid] = nums[mid], nums[low]
            low += 1
            mid += 1
        elif nums[mid] == 1:
            mid += 1
        else:                     # the value is 2
            nums[mid], nums[high] = nums[high], nums[mid]
            high -= 1             # do not advance mid: the swapped-in value is unchecked
    return nums                   # LeetCode's version returns nothing and edits in place


print(sort_colors([2, 0, 2, 1, 1, 0]))
print(sort_colors([2, 0, 1]))
print(sort_colors([]))
[0, 0, 1, 1, 2, 2]
[0, 1, 2]
[]

Time O(n) · Space O(1)

TrapWhen the value at mid is 2, do not advance mid. Advancing it would skip a value that was just swapped in from the end and has never been examined.

Pattern to rememberWhen you must partition an array into groups in one pass, keep one pointer per boundary and a scanner. This is the same idea behind the partition step of quick sort.

Kth Largest Element in an Array (LeetCode 215)

Given an unsorted array nums and an integer k, return the kth largest element in sorted order. Duplicates count separately. For example, with nums = [3, 2, 1, 5, 6, 4] and k = 2, the answer is 5, because the values in descending order are 6, 5, 4, 3, 2, 1.

How to think about it

  1. Understand. You do not need the whole array in order, only one element. The value k is at least 1 and at most the length of the array.
  2. Brute force. Sort the array in descending order and take index k minus 1. Correct, and the cost is O(n log n) because of the sort.
  3. Find the waste. Sorting orders all n elements, but you only need the top k. Everything below the top k is wasted work.
  4. Optimise. Keep a min-heap of size k. A min-heap gives the smallest element in O(1) and inserts or removes in O(log k). Push each number; whenever the heap holds more than k items, pop the smallest. At the end the heap holds the k largest numbers, and its root is the smallest of them, which is the kth largest. The cost is O(n log k). Quickselect, a partition-based method, gives O(n) on average, and it is a good follow-up to mention.
  5. Dry run. With k = 2 and the values 3, 2, 1, 5, 6, 4 in order: push 3, then push 2 (the heap is 2, 3). Push 1, which makes three items, so pop 1 and keep 2, 3. Push 5 and pop 2, leaving 3, 5. Push 6 and pop 3, leaving 5, 6. Push 4 and pop 4, leaving 5, 6. The root, 5, is the answer.

Code

import heapq


def find_kth_largest(nums, k):
    """Return the kth largest value using a min-heap of size k."""
    heap = []                     # a min-heap: heap[0] is always the smallest item
    for x in nums:
        heapq.heappush(heap, x)
        if len(heap) > k:
            heapq.heappop(heap)   # drop the smallest, keeping only the k largest
    return heap[0]                # the smallest of the k largest is the kth largest


print(find_kth_largest([3, 2, 1, 5, 6, 4], 2))
print(find_kth_largest([3, 2, 3, 1, 2, 4, 5, 5, 6], 4))
print(find_kth_largest([7], 1))
5
4
7

Time O(n log k) · Space O(k)

Interviewers askCan you do better than O(n log k)? Quickselect runs in O(n) on average by partitioning like quick sort but recursing into only one side. Its worst case is O(n^2), which random pivots make very unlikely.

Pattern to rememberWhen you need the top k or the kth element and k is much smaller than n, keep a heap of size k rather than sorting everything.

Count of Smaller Numbers After Self (LeetCode 315)

Given an integer array nums, return an array counts where counts[i] is the number of elements to the right of position i that are strictly smaller than nums[i]. For example, with nums = [5, 2, 6, 1], the answer is [2, 1, 1, 0]. For the 5, the smaller numbers to its right are 2 and 1, so the count is 2. For the 2, only 1 is smaller, so the count is 1.

How to think about it

  1. Understand. "Strictly smaller" means equal values do not count. The answer has one number per position, and the array can be large, so the target is O(n log n).
  2. Brute force. For each i, scan every j after it and count the smaller values. This is O(n^2). It is simple and correct, and a good first answer to say out loud.
  3. Find the waste. Each comparison is repeated for many positions. If we could sort the right part as we go, the counts would come almost for free.
  4. Optimise. Use merge sort, and during each merge count the smaller values that the merge passes over. Suppose the merge places a left value a. Every right value already placed was strictly smaller than a, because we only place a right value when it is strictly smaller than the current left value. Those right values all sit to the right of a in the original array, so they are exactly the smaller elements after a. Add the number of right values placed so far to a's count. To keep track of original positions, the merge sorts indices rather than values. The cost is O(n log n).
  5. Dry run. Split [5, 2, 6, 1] into [5, 2] and [6, 1]. Merging [5, 2] places 2 first, then 5 is placed after one right value has gone, so 5 gets 1. Merging [6, 1] places 1 first, so 6 gets 1. Now merge [2, 5] with [1, 6]. The 1 is placed first, so it is counted as one right value taken. The 2 is placed next and gets 1 in this merge, and the 5 is placed and gets 1 more, so 5 has 2 in total. The 6 keeps the 1 from its own merge. Original order: 5 gets 2, 2 gets 1, 6 gets 1, 1 gets 0, giving [2, 1, 1, 0].

TrapPlace the left value when it is less than or equal to the right value, not strictly less. Placing the right value on a tie would count equal numbers as smaller, which the problem does not allow.

Code

def count_smaller_brute(nums):
    """O(n^2): for each position, scan everything to its right."""
    n = len(nums)
    result = []
    for i in range(n):
        result.append(sum(1 for j in range(i + 1, n) if nums[j] < nums[i]))
    return result


def count_smaller(nums):
    """O(n log n): merge sort on indices, counting right-side values during each merge."""
    n = len(nums)
    counts = [0] * n
    order = list(range(n))        # order holds original indices, sorted by their values

    def sort_range(lo, hi):
        if hi - lo <= 1:
            return
        mid = (lo + hi) // 2
        sort_range(lo, mid)
        sort_range(mid, hi)
        merged = []
        i, j = lo, mid
        right_taken = 0           # right-half values already placed before the current left value
        while i < mid or j < hi:
            take_left = j >= hi or (i < mid and nums[order[i]] <= nums[order[j]])
            if take_left:
                counts[order[i]] += right_taken
                merged.append(order[i])
                i += 1
            else:
                merged.append(order[j])
                j += 1
                right_taken += 1
        order[lo:hi] = merged

    sort_range(0, n)
    return counts


print(count_smaller_brute([5, 2, 6, 1]))
print(count_smaller([5, 2, 6, 1]))
print(count_smaller([2, 0, 1]))
print(count_smaller([1, 1, 1]))
[2, 1, 1, 0]
[2, 1, 1, 0]
[2, 0, 0]
[0, 0, 0]

Brute force: time O(n^2) · space O(n). Merge sort version: time O(n log n) · space O(n)

Interviewers askIs there another way? Yes. A Fenwick tree (binary indexed tree) over the compressed values counts smaller elements as you scan from right to left, also in O(n log n). Mentioning it shows you know more than one technique.

Pattern to rememberMerge sort is not only a sorting tool. Any question that counts pairs (i, j) with i before j and a comparison between their values can often be answered by counting during the merge.
