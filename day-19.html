Window functions: ranking and running totals

In the previous day you met GROUP BY, which collapses many rows into one row per group. A window function does something different. It looks at a set of related rows, called its window, and computes a value for each row, but it never collapses the rows. If you have 7 employees, a window function still returns 7 rows. Each row simply gets an extra column that depends on the rows around it.

Every window function is written with an OVER clause. The clause says which rows belong to the window. Two parts matter most. PARTITION BY splits the rows into independent groups, a bit like GROUP BY but without merging them. ORDER BY inside OVER sets the order of rows inside each partition, which matters for ranking and running totals.

Ranking inside each department

Suppose you want each employee's position by salary inside their own department. There are three ranking functions, and they differ only when two rows tie. Ben and Chen both earn 120000, so the tie is useful for seeing the difference.

  • ROW_NUMBER() numbers the rows 1, 2, 3, and so on. Ties still get different numbers. To make the result deterministic, add a unique column such as id as a tiebreaker.
  • RANK() gives tied rows the same number, then skips the next numbers. Two rows tied for 2nd place are both 2, and the next row is 4.
  • DENSE_RANK() gives tied rows the same number, but does not skip. Two rows tied for 2nd are both 2, and the next row is 3.
SELECT name, dept_id, salary,
  ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY salary DESC, id) AS row_num,
  RANK()       OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rnk,
  DENSE_RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS dense_rnk
FROM employees
ORDER BY dept_id, salary DESC, id;
 name  | dept_id | salary | row_num | rnk | dense_rnk
-------+---------+--------+---------+-----+-----------
 Asha  |       1 | 150000 |       1 |   1 |         1
 Ben   |       1 | 120000 |       2 |   2 |         2
 Chen  |       1 | 120000 |       3 |   2 |         2
 Gus   |       1 |  95000 |       4 |   4 |         3
 Dana  |       2 |  90000 |       1 |   1 |         1
 Eli   |       2 |  70000 |       2 |   2 |         2
 Farah |       3 |  65000 |       1 |   1 |         1
(7 rows)

Read the Engineering rows. Ben and Chen tie at 120000. RANK gives both a 2 and then jumps to 4 for Gus. DENSE_RANK gives both a 2 and then gives Gus a 3. ROW_NUMBER gives them 2 and 3 only because we added id as a tiebreaker. Without it, the order of tied rows is not guaranteed.

TrapWithout a unique tiebreaker, ROW_NUMBER() OVER (ORDER BY salary DESC) can give tied rows either number, and the answer can change between runs. Always add a unique column such as id when you need a stable result.

Running totals and the window frame

A running total adds up the values seen so far. Any aggregate function (SUM, AVG, COUNT, MIN, MAX) becomes a window function when you add OVER. The part of the partition that the function sees for each row is called the frame. 

SELECT name, salary,
       SUM(salary) OVER (ORDER BY id) AS running_total
FROM employees
ORDER BY id;
 name  | salary | running_total
-------+--------+---------------
 Asha  | 150000 |        150000
 Ben   | 120000 |        270000
 Chen  | 120000 |        390000
 Dana  |  90000 |        480000
 Eli   |  70000 |        550000
 Farah |  65000 |        615000
 Gus   |  95000 |        710000
(7 rows)

Here there is no PARTITION BY, so the window is the whole table. Because there is an ORDER BY, the default frame is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. In plain words: from the first row up to the current row, including every row that ties with the current row on the ORDER BY value.

That "including ties" part is easy to miss. Here is the running sum ordered by salary alone, for the three rows with salary of at least 120000. 

SELECT name, salary,
       SUM(salary) OVER (ORDER BY salary) AS running
FROM employees
WHERE salary >= 120000
ORDER BY salary, name;
 name | salary | running
------+--------+---------
 Ben  | 120000 |  240000
 Chen | 120000 |  240000
 Asha | 150000 |  390000
(3 rows)

Ben and Chen are tied on salary, so they are peers. Both see the same frame, which includes both salaries, so both show 240000. Only after the tied rows does the sum move on to 390000. If you want a strict row by row running total instead, write ROWS UNBOUNDED PRECEDING, which counts physical rows and ignores peers. Then the tied rows get different totals, which is why a tiebreaker is needed again.

Key ideaA window function computes a value for every row from a window of related rows, and never removes rows. The default frame with ORDER BY is RANGE, so tied rows share the same running value.

Looking at neighbours: LAG and LEAD

LAG(column) reads the value from the previous row in the window, and LEAD(column) reads the value from the next row. They are useful for comparing a row with its neighbour, for example to find salary changes between consecutive records. When there is no previous or next row, the result is NULL. 

SELECT name, salary,
       LAG(salary)  OVER (ORDER BY id) AS prev_salary,
       LEAD(salary) OVER (ORDER BY id) AS next_salary
FROM employees
ORDER BY id;
 name  | salary | prev_salary | next_salary
-------+--------+-------------+-------------
 Asha  | 150000 |             |      120000
 Ben   | 120000 |      150000 |      120000
 Chen  | 120000 |      120000 |       90000
 Dana  |  90000 |      120000 |       70000
 Eli   |  70000 |       90000 |       65000
 Farah |  65000 |       70000 |       95000
 Gus   |  95000 |       65000 |
(7 rows)

Asha has no previous row, so prev_salary is empty (NULL). Gus has no next row, so next_salary is empty.

Average per group without collapsing the rows

A common interview task is "show each employee next to the average salary of their department". A GROUP BY query would return one row per department and lose the names. A window function keeps the names and adds the average. ROUND keeps the output readable. 

SELECT name, dept_id,
       ROUND(AVG(salary) OVER (PARTITION BY dept_id)) AS dept_avg
FROM employees
ORDER BY id;
 name  | dept_id | dept_avg
-------+---------+----------
 Asha  |       1 |   121250
 Ben   |       1 |   121250
 Chen  |       1 |   121250
 Dana  |       2 |    80000
 Eli   |       2 |    80000
 Farah |       3 |    65000
 Gus   |       1 |   121250
(7 rows)

The Engineering average is (150000 + 120000 + 120000 + 95000) / 4 = 485000 / 4 = 121250, which is the value every Engineering row shows.

Interviewers askWhat is the difference between GROUP BY and a window function? GROUP BY reduces many rows to one row per group. A window function keeps every row and adds a value computed from its group or neighbours.

TipWindow functions run after WHERE, GROUP BY and HAVING. You cannot use a window function inside a WHERE clause. To filter on a window result, wrap the query in a subquery or a CTE and filter in the outer query, as the top-N example in the next unit shows.

Common table expressions and the classic interview queries

A common table expression, or CTE, is a named query defined with WITH. Think of it as a temporary result you can refer to by name in the main query. CTEs make long queries readable, because each step gets a name instead of being nested inside the one before it.

Plain CTEs

The next query first computes the total salary per department, then joins that result to the departments table to show the names. 

WITH dept_totals AS (
  SELECT dept_id, SUM(salary) AS total
  FROM employees
  GROUP BY dept_id
)
SELECT d.name, t.total
FROM dept_totals t
JOIN departments d ON d.id = t.dept_id
ORDER BY t.total DESC;
    name     | total
-------------+--------
 Engineering | 485000
 Sales       | 160000
 HR          |  65000
(3 rows)

In PostgreSQL 12 and later, a CTE that is used only once is usually folded into the main query, much like a subquery. A CTE used several times is computed once and stored. You can force either behaviour with MATERIALIZED or NOT MATERIALIZED. For readability, the more important point is that the query now reads top to bottom: first the totals, then the names.

Recursive CTEs: walking a tree

A recursive CTE refers to itself. It is the standard tool for hierarchies such as an organisation chart, folder trees, or bills of materials. A recursive CTE has two parts joined by UNION ALL.

  1. The anchor member. A query that returns the starting rows, for example the employee with no manager.
  2. The recursive member. A query that joins the CTE to the table to find the next level down. PostgreSQL runs it repeatedly, feeding in the rows produced by the previous round, until a round produces no new rows.

Here, the anchor is the employee with manager_id IS NULL, which is Asha. Each round finds the people who report to the people found in the previous round. The depth column counts the levels, and the path column builds a readable chain of names. 

WITH RECURSIVE chain AS (
  -- anchor: the top of the tree
  SELECT id, name, manager_id, 0 AS depth, name::text AS path
  FROM employees
  WHERE manager_id IS NULL
  UNION ALL
  -- recursive member: the direct reports of the rows found so far
  SELECT e.id, e.name, e.manager_id, c.depth + 1, c.path || ' > ' || e.name
  FROM employees e
  JOIN chain c ON e.manager_id = c.id
)
SELECT depth, name, path
FROM chain
ORDER BY depth, id;
 depth | name  |       path
-------+-------+-------------------
     0 | Asha  | Asha
     1 | Ben   | Asha > Ben
     1 | Chen  | Asha > Chen
     1 | Dana  | Asha > Dana
     1 | Farah | Asha > Farah
     2 | Eli   | Asha > Dana > Eli
     2 | Gus   | Asha > Ben > Gus
(7 rows)

Walk the rounds. Round 0 returns Asha. Round 1 finds everyone whose manager_id is 1 (Ben, Chen, Dana, Farah). Round 2 finds everyone whose manager is one of those four (Eli reports to Dana, Gus reports to Ben). Round 3 finds nobody, so the recursion stops.

TrapA recursive CTE that follows a cycle, such as A reports to B and B reports to A, never stops. Use UNION instead of UNION ALL if duplicate rows should be dropped, or add a depth limit such as WHERE depth < 20 in the recursive member.

Classic question: the second highest salary

The question "find the second highest salary" looks simple, but it hides a trap. If two people share the highest salary, "the second row when sorted" is not the second highest value. There are three standard answers.

Approach 1: a subquery for the maximum below the maximum. Find the largest salary, then find the largest salary that is smaller than it.

SELECT MAX(salary) AS second_highest
FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);
 second_highest
----------------
         120000
(1 row)

Approach 2: skip duplicates with OFFSET. Remove repeated values with DISTINCT, sort from highest to lowest, skip the first value, and take one.

SELECT DISTINCT salary
FROM employees
ORDER BY salary DESC
OFFSET 1 LIMIT 1;
 salary
--------
 120000
(1 row)

Approach 3: DENSE_RANK. Rank the salaries with no gaps and keep rank 2. Because tied salaries share a rank, several rows can have rank 2, so LIMIT 1 is needed.

SELECT salary
FROM (
  SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS r
  FROM employees
) ranked
WHERE r = 2
LIMIT 1;
 salary
--------
 120000
(1 row)

Interviewers askWhy not ORDER BY salary DESC LIMIT 1 OFFSET 1? Because it counts rows, not distinct values. Our data happens to work, since the second row is Ben at 120000. But if two people shared the top salary of 150000, the second row would repeat 150000, which is not the second highest value.

Top N per group

"Show the top two earners in each department" is another classic. The window approach numbers the rows inside each department, then the outer query keeps rows numbered 1 or 2. It needs a subquery because window functions cannot appear in WHERE. 

SELECT dept_id, name, salary
FROM (
  SELECT dept_id, name, salary,
         ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY salary DESC, id) AS rn
  FROM employees
) t
WHERE rn <= 2
ORDER BY dept_id, rn;
 dept_id | name  | salary
---------+-------+--------
       1 | Asha  | 150000
       1 | Ben   | 120000
       2 | Dana  |  90000
       2 | Eli   |  70000
       3 | Farah |  65000
(5 rows)

Note that HR has only one employee, so it returns one row. A LATERAL join is an alternative. It runs a small query once for each row of the outer table, which is efficient when an index supports the inner query. 

SELECT d.name AS dept, top.name, top.salary
FROM departments d
CROSS JOIN LATERAL (
  SELECT name, salary
  FROM employees e
  WHERE e.dept_id = d.id
  ORDER BY salary DESC, id
  LIMIT 2
) top
ORDER BY d.id, top.salary DESC;
    dept     | name  | salary
-------------+-------+--------
 Engineering | Asha  | 150000
 Engineering | Ben   | 120000
 Sales       | Dana  |  90000
 Sales       | Eli   |  70000
 HR          | Farah |  65000
(5 rows)

Key ideaSecond highest, top N per group, and running totals are all solved by one tool: a window function computed in a subquery, filtered in the outer query.

Views, procedures and triggers

These three objects store SQL inside the database. Each solves a different problem, and interviewers often ask you to explain when to use which.

Views: a saved query that looks like a table

A view is a named query. Querying the view runs the saved query. Views hide complexity, give a stable interface when the underlying tables change, and can restrict which columns a user sees. A view stores no data of its own, so it always shows current values. A materialized view is different: it stores the query result, so reading it is fast, but you must run REFRESH MATERIALIZED VIEW to update it. 

CREATE VIEW dept_summary AS
SELECT d.name AS dept, COUNT(e.id) AS headcount, SUM(e.salary) AS payroll
FROM departments d
LEFT JOIN employees e ON e.dept_id = d.id
GROUP BY d.name;

SELECT * FROM dept_summary ORDER BY dept;
CREATE VIEW
    dept     | headcount | payroll
-------------+-----------+---------
 Engineering |         4 |  485000
 HR          |         1 |   65000
 Sales       |         2 |  160000
(3 rows)

The view uses LEFT JOIN, so a department with no employees would still appear with a headcount of 0 and a payroll of NULL. Simple views on one table can also be used for INSERT, UPDATE and DELETE. Views built on joins and aggregates are generally read only.

Triggers: code that runs on every change

A trigger runs a function automatically when a row is inserted, updated or deleted. In PostgreSQL, a trigger calls a function written to return the special type trigger. Inside that function, NEW holds the row after the change and OLD holds the row before it. A typical use is an audit log. The example below records every salary change. 

CREATE TABLE salary_log (
  id serial PRIMARY KEY,
  emp_id int,
  old_salary int,
  new_salary int,
  changed_at timestamptz DEFAULT now()
);

CREATE OR REPLACE FUNCTION log_salary() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF NEW.salary IS DISTINCT FROM OLD.salary THEN
    INSERT INTO salary_log (emp_id, old_salary, new_salary)
    VALUES (OLD.id, OLD.salary, NEW.salary);
  END IF;
  RETURN NEW;
END;
$$;

CREATE TRIGGER trg_salary
AFTER UPDATE ON employees
FOR EACH ROW EXECUTE FUNCTION log_salary();

UPDATE employees SET salary = 72000 WHERE name = 'Eli';
SELECT emp_id, old_salary, new_salary FROM salary_log ORDER BY id;

--------+------------+------------

The function checks IS DISTINCT FROM rather than <> because IS DISTINCT FROM treats NULL correctly. A comparison such as NULL <> 5 gives NULL, not true, so it would skip the logging. IS DISTINCT FROM returns true when the values differ, including when one of them is NULL. The trigger fires after the update, so RETURN NEW is what the statement would have stored. For a BEFORE trigger, returning NEW lets you change the row before it is written.

TrapTriggers are hidden logic. A developer who updates a salary may not know a row was also written to another table. Keep triggers small, document them, and prefer explicit application code when the behaviour is complex.

Stored procedures: CALL and transactions

A stored procedure is a named block of procedural code that you run with CALL. Unlike a function, which is used inside a query and returns a value, a procedure is run as a statement and can control transactions. In PostgreSQL, procedures were added in version 11. The procedure below gives a raise to everyone in one department. 

CREATE OR REPLACE PROCEDURE give_raise(p_dept int, p_pct numeric)
LANGUAGE plpgsql AS $$
BEGIN
  UPDATE employees
  SET salary = ROUND(salary * (1 + p_pct / 100))
  WHERE dept_id = p_dept;
END;
$$;

CALL give_raise(3, 10);
SELECT name, salary FROM employees WHERE dept_id = 3;
CREATE PROCEDURE
CALL
 name  | salary
-------+--------
 Farah |  71500
(1 row)

Farah's salary was 65000. A 10 percent raise gives 65000 * 1.10 = 71500. Because the procedure runs in the caller's transaction, the same trigger we just wrote also logs the change to salary_log.

Interviewers askFunction or procedure? A function returns a value and can be used inside SELECT. A procedure is called with CALL, returns no value, and can contain COMMIT or ROLLBACK.

Indexes, query plans and EXPLAIN ANALYZE

An index is a separate data structure that lets the database find rows without reading the whole table. Without an index, PostgreSQL reads every row of the table, which is called a sequential scan. An index is like the index at the back of a book. It costs extra disk space and slows down writes, because every insert and update must also update the index, but it makes selective reads much faster.

You can see which access path the database chooses with EXPLAIN. It shows the query plan: the steps the planner intends to take, with cost and row estimates. The planner uses statistics collected by ANALYZE to decide between options.

The index types you need to know

  • B-tree is the default. It keeps values sorted in a balanced tree and supports equality, ranges (>, BETWEEN) and sorting. Use it for most columns, including primary and foreign keys.
  • GIN (generalized inverted index) maps each element inside a value to the rows that contain it. It suits JSONB containment (@>), array membership and full-text search. It is larger and slower to update than B-tree, but very fast for "contains" questions.
  • BRIN (block range index) stores only the minimum and maximum value for each group of physical pages. It is tiny, and it works well when the column's values follow the physical order of the table, such as an append-only timestamp. It works poorly when the values are scattered randomly across the table.
  • Partial index is any index with a WHERE clause. It indexes only the rows you query often, which keeps the index small. A partial index is used only when the query's own WHERE clause implies the index condition.

The next statements create one of each type on a table called events. The table has 20000 rows with an integer id primary key, a user_id from 0 to 49, a ts timestamp that increases by one minute per row, and a meta JSONB column. 

CREATE TABLE events AS
SELECT g AS id,
       (g % 50) AS user_id,

       '2026-01-01'::timestamptz + g * interval '1 minute' AS ts,
       CASE WHEN g % 10 = 0 THEN '{"plan":"pro","region":"eu"}'
            ELSE '{"plan":"free"}' END::jsonb AS meta
FROM generate_series(1, 20000) g;

Reading a query plan

Put EXPLAIN in front of any query to see its plan. Start with the innermost, most indented line, because that is the first thing the database does. Each line has three numbers in cost=start..total rows=estimate width=bytes. The cost is an abstract unit used only to compare plans, not milliseconds. The row estimate is the planner's guess, and a bad estimate is often the reason for a bad plan. 

EXPLAIN SELECT * FROM events WHERE id = 500;
                                QUERY PLAN
---------------------------------------------------------------------------
 Index Scan using events_pkey on events  (cost=0.29..8.30 rows=1 width=44)
   Index Cond: (id = 500)
(2 rows)

One row out of 20000 is very selective, so the planner uses the primary key index and reads one row. Now look at a condition that matches many rows, such as user_id = 7, which matches about 400 rows. 

EXPLAIN SELECT * FROM events WHERE user_id = 7;
                                   QUERY PLAN
--------------------------------------------------------------------------------
 Bitmap Heap Scan on events  (cost=7.39..204.39 rows=400 width=44)
   Recheck Cond: (user_id = 7)
   ->  Bitmap Index Scan on events_user_idx  (cost=0.00..7.29 rows=400 width=0)
         Index Cond: (user_id = 7)
(4 rows)

Now the planner uses a bitmap scan. It first uses the index to collect the locations of the matching rows, then reads those table pages in physical order. This is a middle path between one-row index lookups and a full sequential scan.

The GIN index is picked for the JSONB containment operator, and the BRIN index for a narrow time range. The partial index is picked only when the query repeats the partial index's condition. 

EXPLAIN SELECT * FROM events WHERE meta @> '{"plan":"pro"}';
EXPLAIN SELECT * FROM events WHERE ts >= '2026-01-10' AND ts < '2026-01-11';
EXPLAIN SELECT * FROM events WHERE kind = 'purchase' AND user_id = 7;

         Index Cond: (meta @> '{"plan": "pro"}'::jsonb)
(4 rows)

------------------------------------------------------------------------------------------------------------------------------------------------
 Bitmap Heap Scan on events  (cost=12.39..354.39 rows=1440 width=44)
   Recheck Cond: ((ts >= '2026-01-10 00:00:00+00'::timestamp with time zone) AND (ts < '2026-01-11 00:00:00+00'::timestamp with time zone))

The last plan is the one to study. The query asks for kind = 'purchase', which is exactly the partial index's condition, so the planner can use events_pro_partial. If the query had asked for kind = 'click', the partial index would be ignored.

TrapAn index is not used just because it exists. A function on the column, such as WHERE LOWER(name) = 'asha', cannot use a plain index on name. Either index the expression (CREATE INDEX ON employees (LOWER(name))) or compare the column directly.

EXPLAIN ANALYZE: the plan plus reality

EXPLAIN only estimates. EXPLAIN ANALYZE actually runs the query and adds the real time, the real row counts and the number of loops. When an estimate and the real count differ by a large factor, the planner was working from bad statistics, and running ANALYZE on the table is often the fix. 

EXPLAIN ANALYZE SELECT * FROM events WHERE id = 500;
                                                     QUERY PLAN
---------------------------------------------------------------------------------------------------------------------
 Index Scan using events_pkey on events  (cost=0.29..8.30 rows=1 width=44) (actual time=0.035..0.036 rows=1 loops=1)
   Index Cond: (id = 500)
 Planning Time: 0.021 ms
 Execution Time: 0.042 ms
(4 rows)

The timing values change from run to run and from machine to machine, so treat the numbers as an example. The useful part is the structure: the estimated rows (rows=1) match the actual rows (rows=1), so the statistics are good.

Key ideaEXPLAIN shows the plan the planner chose. EXPLAIN ANALYZE runs the query and shows what really happened. Because it executes the statement, wrap an UPDATE or DELETE in a transaction and roll it back when you only want to see the plan.

Interviewers askWhy might the planner ignore an index? Because a sequential scan can be cheaper when the query returns a large share of the table, when the estimate is wrong, or when the column has a function applied to it. An index is a tool the planner weighs against the alternatives, not a rule.

PostgreSQL features worth knowing

Standard SQL covers most of what you need, but PostgreSQL adds features that interviewers like to ask about. They fall into four groups: storing and querying JSON, writing rows and getting them back in one step, inserting or updating in one statement, and vector similarity for AI applications.

JSONB: JSON stored in binary form

PostgreSQL has two JSON types. json stores the text exactly as written. jsonb stores a decomposed binary form, which is slower to write but faster to query, and it supports indexes. Use jsonb in almost every case.

  • -> returns a JSON value (still JSON, so strings keep their quotes).
  • ->> returns the value as plain text.
  • @> tests containment: does the left side contain the right side?
  • ? tests whether a key exists at the top level.
SELECT id, meta->>'plan' AS plan, meta->'region' AS region
FROM events
WHERE id IN (10, 11)
ORDER BY id;
 id | plan | region
----+------+--------
 10 | pro  | "eu"
 11 | free |
(2 rows)

Row 10 has a region key, so meta->'region' returns the JSON string "eu", with quotes. Row 11 has no region key, so the result is NULL, which psql shows as an empty cell. 

SELECT id, meta
FROM events
WHERE meta ? 'region' AND id <= 20
ORDER BY id;

SELECT COUNT(*) FROM events WHERE meta @> '{"plan":"pro"}';
 id |              meta
----+---------------------------------
 10 | {"plan": "pro", "region": "eu"}
 20 | {"plan": "pro", "region": "eu"}
(2 rows)

 count
-------
  2000
(1 row)

Every tenth row has the pro plan, so 20000 / 10 = 2000 rows match the containment test.

RETURNING: get the new row back in one statement

Without RETURNING, you would insert a row and then query it again to learn its generated id. RETURNING returns the affected rows directly from INSERT, UPDATE or DELETE. It saves a round trip to the database and avoids a race where another session changes the row in between.

ON CONFLICT: upsert in one statement

An upsert means "insert the row, or update it if it already exists". PostgreSQL does this with INSERT ... ON CONFLICT. The conflict target is a unique or primary key column. DO NOTHING skips the row when there is a conflict. DO UPDATE changes the existing row, and EXCLUDED refers to the row that was proposed for insertion. 

CREATE TABLE products (sku text PRIMARY KEY, name text, stock int NOT NULL);

pgvector: similarity search for embeddings

An embedding is a list of numbers, a vector, that represents the meaning of a piece of text, an image or a product. Two similar things have vectors that point in similar directions. The pgvector extension adds a vector type, distance operators and approximate indexes to PostgreSQL, so you can store embeddings next to your normal data and search them with SQL. It is an extension, so it must be installed on the server and enabled per database with CREATE EXTENSION vector;.

  • <-> is Euclidean (L2) distance. Smaller means closer.
  • <=> is cosine distance, which compares direction and ignores length. Many text embedding models are designed for cosine similarity.
  • CREATE INDEX ... USING hnsw builds an approximate nearest neighbour index. It trades a little accuracy for much faster search on large tables.
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE docs (id bigserial PRIMARY KEY, body text, embedding vector(3));

-- the five nearest documents to a query embedding, by cosine distance
SELECT id, body
FROM docs
ORDER BY embedding <=> '[0.1, 0.9, 0.2]'
LIMIT 5;

This example has no output block because it needs the pgvector extension, which is not part of a default install. In real use the embedding comes from a model, and the vector dimension (3 here) must match that model.

Interviewers askWhy store embeddings in PostgreSQL instead of a dedicated vector database? Because you keep transactions, joins with normal tables and one backup strategy. A dedicated vector database can scale further and offers more index tuning, so the choice depends on data size and query load.

MVCC and VACUUM: how PostgreSQL handles concurrent work

Many people use the database at once. One session reads a report while another updates a salary. PostgreSQL lets them work without blocking each other for ordinary reads, using a technique called MVCC, which stands for multi-version concurrency control. The idea is simple: an UPDATE never overwrites a row in place. It writes a new version of the row and marks the old version as no longer current. Each transaction sees the versions that were current when it started.

Consider a three-row table. Watch where each row physically lives, using the hidden ctid column. The ctid is a row's physical address, written as (page, position). Do not use it in application code, because it changes. 

CREATE TABLE tv (id int, v text);
INSERT INTO tv VALUES (1,'a'), (2,'b'), (3,'c');
SELECT ctid, id, v FROM tv ORDER BY id;

UPDATE tv SET v = 'B' WHERE id = 2;
SELECT ctid, id, v FROM tv ORDER BY id;

DELETE FROM tv WHERE id = 1;
SELECT ctid, id, v FROM tv ORDER BY id;

The UPDATE moved row 2 from position (0,2) to a new position (0,4). The old version of row 2 is still on the page, but it is dead: no transaction that starts now can see it. The DELETE marks row 1 as dead in the same way, so it disappears from the results. Those dead versions still occupy space until something removes them.

Why does this matter for concurrency? Because a reader keeps seeing its own old version of a row while a writer creates a new one, neither waits for the other. Readers do not block writers, and writers do not block readers, for ordinary SELECT and UPDATE statements. Writers can still block each other when they change the same row, and locks are needed for those cases.

VACUUM: cleaning up dead row versions

VACUUM finds dead row versions that no active transaction can still need, and makes their space reusable for future rows. It also updates the visibility map and protects against transaction ID wraparound, a rare but serious failure when PostgreSQL's internal transaction counter runs out of room. ANALYZE refreshes the statistics the planner uses, as you saw with EXPLAIN. VACUUM ANALYZE does both.

  • Autovacuum runs VACUUM and ANALYZE in the background, based on how many rows have changed. In most systems you leave it on and tune it only when a busy table needs it.
  • Plain VACUUM makes space reusable inside the table but usually does not shrink the file. It does not block normal reads and writes.
  • VACUUM FULL rewrites the whole table into a new file and returns space to the operating system. It takes an exclusive lock, which blocks reads and writes while it runs.

TrapA long-running transaction holds back VACUUM. While an old transaction is open, the dead row versions it might still need cannot be removed, so tables grow and queries slow down. Keep transactions short, and never leave one open while you wait for user input.

Key ideaMVCC means an update writes a new row version instead of overwriting the old one. Readers see a consistent snapshot without blocking writers, and VACUUM later removes the dead versions.

Django: the framework that sits on PostgreSQL

Django is a Python web framework. It bundles a database layer (the ORM), an admin site, a URL router, form handling and a template language, so you can build a complete application with few outside libraries. Django does not run queries itself. It translates Python code into SQL and sends it to a database such as PostgreSQL. Django code in this unit cannot be run inside a single script, because it needs a project. Read it as a guide to what each file does, and check the behaviour with python manage.py shell once you have a project.

MTV: Model, Template, View

Django uses the MTV pattern, which is a variation of MVC. The Model defines the data and talks to the database. The Template is the HTML with placeholders that gets filled in. The View is a Python function or class that receives a request, asks the models for data, and returns a response. The URL configuration decides which view handles which address. The name "view" in Django means the controller in MVC terms, which surprises many people coming from other frameworks.

A project is the whole website and its settings, created with django-admin startproject. An app is a self-contained feature, such as a blog or a billing module, created with python manage.py startapp inside the project. A project lists its apps in INSTALLED_APPS. A reusable app can be moved into another project.

Models: Python classes that become tables

A model is a class that subclasses models.Model. Each class attribute that is a field becomes a column. Django creates the table, the primary key (an id column is added automatically), and the foreign key constraints from these definitions. A ForeignKey creates a column that points at another table. related_name sets the name you use to go backwards, from an author to their books. 

from django.db import models


class Author(models.Model):
    name = models.CharField(max_length=100)

    def __str__(self):
        return self.name


class Book(models.Model):
    title = models.CharField(max_length=200)
    author = models.ForeignKey(Author, on_delete=models.CASCADE, related_name="books")
    published = models.DateField(null=True, blank=True)
    meta = models.JSONField(default=dict, blank=True)

    class Meta:
        ordering = ["title"]

models.JSONField is stored as jsonb on PostgreSQL, so the JSON containment and indexing you learned earlier are available. on_delete=models.CASCADE means that deleting an author also deletes their books. Other options such as PROTECT stop the delete instead.

Migrations: versioned schema changes

A migration is a Python file that records one change to the schema, such as adding a column. You never edit the database by hand. Django compares your models with the migration history, writes a new migration file, and applies it. Migration files are committed to version control so that every developer and the production server make the same changes in the same order. 

python manage.py makemigrations blog   # write a migration file from model changes
python manage.py migrate              # apply pending migrations to the database
python manage.py sqlmigrate blog 0001 # show the SQL a migration will run
python manage.py createsuperuser      # create an admin login

TrapWhen you rename a field in a model, makemigrations asks whether you renamed it. If you answer no, Django drops the old column and adds a new one, which loses the data. Answer yes so the migration renames the column instead.

QuerySets: lazy, chainable queries

Book.objects is a manager, the entry point for queries on the model. Calling filter(), exclude() or order_by() returns a QuerySet. A QuerySet describes a query but does not run it. It runs when you iterate over it, call len(), convert it with list(), or call a method that returns a single value such as get(), count() or first(). Because it is lazy, you can keep adding conditions without running several queries. 

# Nothing is sent to PostgreSQL yet: this only builds the query.
recent = Book.objects.filter(published__year__gte=2000).order_by("-published")

# The SQL runs now, when the loop starts.
for book in recent:
    print(book.title, book.author.name)

# count() runs its own COUNT query, which is much cheaper than loading rows.
total = Book.objects.filter(author__name__startswith="L").count()

# get() returns one object, or raises Book.DoesNotExist or Book.MultipleObjectsReturned.
one = Book.objects.get(pk=1)

Notice author__name__startswith. Double underscores cross relationships and apply lookups. Django turns author__name__startswith="L" into a join with WHERE name LIKE 'L%'. The query published__year__gte becomes a comparison on the year part of the date.

For aggregates, use aggregate() for a single value over the whole queryset, and annotate() to add a computed value to each row: 

from django.db.models import Count

# one dictionary for the whole queryset, for example {'n': 42}
Book.objects.aggregate(n=Count("id"))

# one object per author, each with a books_count attribute
Author.objects.annotate(books_count=Count("books"))

The N+1 problem and select_related versus prefetch_related

The N+1 problem is the most common performance bug in ORM code. You run one query to load N objects, then one more query for each object to fetch a related object. The total is N+1 queries when you need one query. It hides easily, because each individual line of code looks innocent. 

# N+1: one query for all books, then one query per book to load its author.
for book in Book.objects.all():
    print(book.title, book.author.name)

# Fixed with select_related: one query with a SQL JOIN.
for book in Book.objects.select_related("author"):
    print(book.title, book.author.name)

# Fixed with prefetch_related: two queries, one for books and one for all their authors.
for author in Author.objects.prefetch_related("books"):
    print(author.name, [b.title for b in author.books.all()])

The two fixes do different jobs. select_related follows a ForeignKey or OneToOneField forward, and does it with a single SQL JOIN. prefetch_related handles relationships that point many ways, such as the reverse side of a foreign key (author to books) and many-to-many fields. It runs one extra query with an IN condition and joins the results in Python.

Key ideaUse select_related for "one" relationships (book to author) because it uses one JOIN. Use prefetch_related for "many" relationships (author to books) because it uses a second query instead of a huge join.

TipFind N+1 bugs in tests. Django's TestCase.assertNumQueries(n) fails when a block runs a different number of queries than expected, so you can lock in the fixed behaviour.

Interview questions

Test yourself before reading the answers. Each answer is a complete reply you could give in an interview.

What is a window function, and how does it differ from GROUP BY?

A window function computes a value for each row using a set of related rows defined by OVER, and it keeps every row in the result. GROUP BY collapses the rows into one row per group, so detail columns are lost. For example, AVG(salary) OVER (PARTITION BY dept_id) adds the department average to every employee row, while GROUP BY dept_id returns one row per department.

What is the difference between ROW_NUMBER, RANK and DENSE_RANK?

All three number rows inside a partition. ROW_NUMBER gives every row a unique number, even ties, so its order among ties is arbitrary unless you add a tiebreaker. RANK gives ties the same number and then skips numbers, so 2, 2, 4. DENSE_RANK gives ties the same number without skipping, so 2, 2, 3.

How do you find the second highest salary, and what is the trap?

Use the maximum of the salaries that are less than the overall maximum, or use DISTINCT with ORDER BY salary DESC OFFSET 1 LIMIT 1, or DENSE_RANK() = 2 with a LIMIT 1. The trap is ties. If two people share the top salary, "the second row" is still the top salary, so you must work with distinct values or dense ranks.

What is a recursive CTE, and what makes it stop?

A recursive CTE is a WITH RECURSIVE query made of an anchor member and a recursive member joined by UNION ALL. The recursive member refers to the CTE itself, and PostgreSQL repeats it, feeding in the rows from the previous round. It stops when a round returns no new rows. Cycles in the data can make it run forever, so guard against them with UNION or a depth limit.

What is the difference between a view, a materialized view and a table?

A view is a saved query with no data of its own, so it always reflects current table contents. A materialized view stores the query result, so reads are fast, but it is stale until you run REFRESH MATERIALIZED VIEW. A table stores data directly and is written to by INSERT, UPDATE and DELETE.

What is the difference between EXPLAIN and EXPLAIN ANALYZE?

EXPLAIN shows the plan the planner chose, with estimated costs and rows, without running the query. EXPLAIN ANALYZE runs the query and adds the actual time, rows and loops. Because it executes the statement, use it on UPDATE or DELETE only inside a transaction you roll back.

When would you choose a B-tree, a GIN, or a BRIN index?

B-tree is the default for equality, ranges and sorting, and it suits most columns. GIN suits values with many elements, such as JSONB containment with @>, arrays and full-text search. BRIN suits very large tables where a column follows the physical row order, such as an append-only timestamp, because it is tiny but only useful when the data is correlated with the physical order.

What is MVCC, and why does PostgreSQL need VACUUM?

MVCC (multi-version concurrency control) makes an update write a new row version instead of overwriting the old one, so readers keep a consistent snapshot without blocking writers. The old versions become dead once no transaction needs them. VACUUM removes dead versions so their space can be reused, updates the visibility map and protects against transaction ID wraparound.

What does INSERT ... ON CONFLICT do, and what does EXCLUDED refer to?

It inserts a row, but if a unique or primary key conflict occurs, it either does nothing (DO NOTHING) or updates the existing row (DO UPDATE). Inside the DO UPDATE clause, EXCLUDED refers to the row that was proposed for insertion, so you can write stock = products.stock + EXCLUDED.stock.

What is the N+1 problem, and how do select_related and prefetch_related fix it?

N+1 means one query loads N objects, then one query per object loads a related object. select_related fixes it for forward foreign keys and one-to-one fields by using a single SQL JOIN. prefetch_related fixes it for reverse foreign keys and many-to-many fields by running one extra query with an IN condition and joining in Python.

Why should you change a Django database schema with migrations instead of by hand?

Migrations are versioned files that record each change, so every developer and every environment applies the same changes in the same order. Editing the database by hand leaves the migration history out of step with the models, which breaks deployments and makes the schema impossible to reproduce.

DSA: topological sort and Dijkstra's algorithm

Today's patterns both work on graphs, which are collections of nodes joined by edges. A directed graph has edges with a direction, such as "course B must come before course A". A weighted graph gives each edge a cost, such as the time a message takes to travel along a link.

Topological sort orders the nodes of a directed graph so that every edge points forward. It is possible only when the graph has no cycle. The standard method is Kahn's algorithm: count the incoming edges of each node, then repeatedly take a node with no incoming edges left, output it, and remove its outgoing edges.

Dijkstra's algorithm finds the shortest distance from one source node to every other node when all edge weights are zero or positive. It always settles the unsettled node with the smallest known distance, using a min-heap to find it quickly. Once a node is settled, its distance never changes, because any other path would have to go through a node that is already at least as far away.

Python's heapq module provides a binary min-heap on a plain list. heapq.heappush(heap, item) adds an item, and heapq.heappop(heap) removes and returns the smallest. Tuples compare by their first element, so (distance, node) pairs come out in distance order.

Course Schedule II (LeetCode 210)

There are numCourses courses labelled 0 to numCourses-1. Each pair [a, b] in prerequisites means you must take course b before course a. Return an order in which you can finish all courses, or an empty list if it is impossible. Example: numCourses = 4, prerequisites = [[1,0],[2,0],[3,1],[3,2]] gives one valid answer, [0,1,2,3]. Example: numCourses = 2, prerequisites = [[1,0],[0,1]] gives [] because each course waits for the other.

How to think about it

  1. Understand. Treat each prerequisite as a directed edge from b to a. The answer is a topological order, where every edge goes from an earlier course to a later one. If the graph has a cycle, no order exists, so return an empty list. A course with no prerequisites can go first.
  2. Brute force. Try every permutation of the courses and check each one against the prerequisites. With n courses there are n! permutations, which is far too many for n of 2000.
  3. Find the waste. The brute force keeps rebuilding the same answer from scratch. What we really need is to know, at each moment, which courses have all their prerequisites finished.
  4. Optimise. Keep an indegree count for each course, which is the number of prerequisites still unfinished. Put every course with indegree 0 in a queue. Pop one, add it to the answer, and for each course that depends on it, subtract one from its indegree. When a course's indegree reaches 0, it joins the queue. If the answer ends up with all n courses, the order is valid. Otherwise a cycle blocked some courses forever. This is O(V + E) time.
  5. Dry run. Use numCourses = 4 with [[1,0],[2,0],[3,1],[3,2]]. The starting indegrees are 0:0, 1:1, 2:1, 3:2.

from collections import deque


def find_order(num_courses, prerequisites):
    graph = [[] for _ in range(num_courses)]
    indegree = [0] * num_courses
    for course, prereq in prerequisites:
        graph[prereq].append(course)
        indegree[course] += 1

    queue = deque(c for c in range(num_courses) if indegree[c] == 0)
    order = []
    while queue:
        c = queue.popleft()
        order.append(c)
        for nxt in graph[c]:
            indegree[nxt] -= 1
            if indegree[nxt] == 0:
                queue.append(nxt)

    return order if len(order) == num_courses else []


print(find_order(2, [[1, 0]]))
print(find_order(4, [[1, 0], [2, 0], [3, 1], [3, 2]]))
print(find_order(2, [[1, 0], [0, 1]]))
print(find_order(1, []))

Network Delay Time (LeetCode 743)

A network has n nodes labelled 1 to n. Each entry [u, v, w] in times is a directed link: a signal from u reaches v after w time units. A signal starts at node k. Return the time at which every node has received the signal, or -1 if some node never receives it. Example: times = [[2,1,1],[2,3,1],[3,4,1]], n = 4, k = 2 gives 2, because the signal reaches node 4 via 2 to 3 to 4 at time 2.

How to think about it

  1. Understand. We need the shortest-path distance from k to every node, then the largest of those distances. If any node is unreachable, return -1. All weights are positive, so Dijkstra applies.
  2. Brute force. Explore every path from k with depth-first search, record the arrival time at each node, and keep the minimum. The number of paths can grow exponentially in a dense graph.
  3. Find the waste. The same node is reached again and again through different paths, and every path is explored even when a shorter one has already been found.
  4. Optimise. Dijkstra fixes the order. Always pop the unsettled node with the smallest distance, settle it, and relax its outgoing edges by pushing new candidate distances onto the heap. A node popped a second time is ignored. Stop when no more nodes can be reached. The answer is the largest settled distance, or -1 if fewer than n nodes were settled. Time is O(E log E) with a heap.
  5. Dry run. Start at node 2 with distance 0. Settling 2 pushes (1, 1) and (3, 1). Settling 1 finds nothing new. Settling 3 pushes (4, 2). Settling 4 finishes. The largest distance is 2.

import heapq


def network_delay_time(times, n, k):
    graph = {i: [] for i in range(1, n + 1)}
    for u, v, w in times:
        graph[u].append((v, w))

    dist = {}                      # settled nodes and their final distances
    heap = [(0, k)]                # (distance so far, node)
    while heap:
        d, node = heapq.heappop(heap)
        if node in dist:           # a shorter route was already settled
            continue
        dist[node] = d
        for nxt, w in graph[node]:
            if nxt not in dist:
                heapq.heappush(heap, (d + w, nxt))

    if len(dist) < n:
        return -1
    return max(dist.values())

print(network_delay_time([[1, 2, 1]], 2, 1))

Swim in Rising Water (LeetCode 778)

You are given an n by n grid of elevations. At time t, the water level is t, and you can stand on any cell whose elevation is at most t. You start at the top-left cell (0, 0) and want to reach the bottom-right cell (n-1, n-1). You can move up, down, left or right, and you can move instantly between cells at any time. Return the smallest t that makes the trip possible. Example: [[0,2],[1,3]] gives 3. You have to wait until the water reaches 3 to enter the cell with elevation 3, because the only route goes through it.

How to think about it

  1. Understand. The answer is a bottleneck: the highest elevation on the path you choose, minimised over all paths. The start cell is already occupied at time grid[0][0], so the answer is at least that. The grid has n squared cells, so n can be up to about 50.
  2. Brute force. For each time t from grid[0][0] upward, run a breadth-first search from (0, 0) that only enters cells with elevation at most t. The first t that reaches (n-1, n-1) is the answer. This is simple and correct, but it may repeat the whole search for up to n squared values of t.
  3. Find the waste. Each time step redoes the search from scratch. Most of the cells explored at time t were already explored at time t minus 1. The search should instead remember how cheap each cell is to reach.
  4. Optimise. Define the cost of a path as its highest elevation so far. Use a Dijkstra-style search that always expands the cell with the smallest path cost. The cost can only stay the same or rise as you walk, so the first time we pop the bottom-right cell, its cost is the best possible. Each cell is pushed at most once if we mark it as seen when it is pushed, which is valid because pops come out in nondecreasing cost order. This gives O(n squared log n) time.
  5. Dry run. On [[0,2],[1,3]], start with (0, 0, cost 0). Push (0, 1) with cost max(0, 2) = 2, and (1, 0) with cost max(0, 1) = 1. Pop (1, 0) at cost 1. Push (1, 1) with cost max(1, 3) = 3. Pop (0, 1) at cost 2, which finds nothing new because (1, 1) is already seen. Pop (1, 1) at cost 3 and return 3.

Code

from collections import deque
import heapq

grid_a = [[0, 2], [1, 3]]
grid_b = [[0, 1, 2, 3, 4], [24, 23, 22, 21, 5], [12, 13, 14, 15, 16],
          [11, 17, 18, 19, 20], [10, 9, 8, 7, 6]]


# Brute force: try each time t and check reachability with BFS.
def swim_brute_force(grid):
    n = len(grid)
    t = grid[0][0]
    while True:
        seen = {(0, 0)}
        queue = deque([(0, 0)])
        while queue:
            r, c = queue.popleft()
            for dr, dc in ((1, 0), (-1, 0), (0, 1), (0, -1)):
                nr, nc = r + dr, c + dc
                if 0 <= nr < n and 0 <= nc < n and (nr, nc) not in seen and grid[nr][nc] <= t:
                    seen.add((nr, nc))
                    queue.append((nr, nc))
        if (n - 1, n - 1) in seen:
            return t
        t += 1


# Optimised: Dijkstra where the cost of a path is its highest elevation.
def swim_in_water(grid):
    n = len(grid)
    heap = [(grid[0][0], 0, 0)]          # (cost so far, row, col)
    seen = {(0, 0)}
    while heap:
        t, r, c = heapq.heappop(heap)
        if r == n - 1 and c == n - 1:
            return t
        for dr, dc in ((1, 0), (-1, 0), (0, 1), (0, -1)):
            nr, nc = r + dr, c + dc
            if 0 <= nr < n and 0 <= nc < n and (nr, nc) not in seen:
                seen.add((nr, nc))
                heapq.heappush(heap, (max(t, grid[nr][nc]), nr, nc))
    return -1


print(swim_brute_force(grid_a))
print(swim_brute_force(grid_b))
print(swim_in_water(grid_a))
print(swim_in_water(grid_b))

Brute force: time O(n^4) · Optimised: time O(n^2 log n) · Space O(n^2)

TrapDo not treat the cost as a sum. Here the cost of a path is the largest value on it, so each step uses max(t, grid[nr][nc]), not t + grid[nr][nc]. Using a sum solves a different problem and gives wrong answers.

Pattern to rememberWhen you need the path that minimises its worst step (a bottleneck), run Dijkstra with the combining rule changed from addition to max. Another route to the same answer is a binary search on t combined with a reachability check.

Summary

Window function
A function with an OVER clause that computes a value for each row from a related set of rows, without removing rows.
PARTITION BY
Splits the rows of a window into independent groups, without collapsing them.
Frame
The subset of a partition that an aggregate window function sees for the current row.
RANK and DENSE_RANK
Rank functions where ties share a number; RANK skips numbers after ties, DENSE_RANK does not.
LAG and LEAD
Window functions that read a value from the previous or next row in the window.
CTE
A named query defined with WITH that the main query can refer to by name.
Recursive CTE
A CTE that refers to itself, used to walk trees and hierarchies, with an anchor and a recursive member.
Second highest pattern
Use the maximum below the maximum, or DISTINCT with OFFSET, or DENSE_RANK equal to 2.
Top N per group
Number rows with ROW_NUMBER inside each group in a subquery, then keep rank 1 to N, or use LATERAL with LIMIT.
View
A saved query that runs each time it is read and stores no data of its own.
Materialized view
A view that stores its result and must be refreshed to reflect changes.
Trigger
A function that runs automatically before or after a row is inserted, updated or deleted.
Stored procedure
A named block of code run with CALL, which returns no value and can control transactions.
EXPLAIN
Shows the plan the planner would use, with estimated costs and rows, without running the query.
EXPLAIN ANALYZE
Runs the query and shows actual times and row counts beside the estimates.
Sequential scan
Reading every row of a table, used when no index helps or most rows are needed.
B-tree index
The default index type, for equality, ranges and sorting.
GIN index
An index for values with many elements, such as JSONB containment and arrays.
BRIN index
A very small index that works when column values follow the physical row order.
Partial index
An index built only on rows matching a WHERE condition, used when a query implies that condition.
JSONB
PostgreSQL's binary JSON type, which supports indexing and containment operators.
RETURNING
A clause that returns the rows changed by INSERT, UPDATE or DELETE in the same statement.
Upsert
Insert a row, or update the existing row if it conflicts, using INSERT ... ON CONFLICT.
DISTINCT ON
PostgreSQL clause that keeps the first row for each listed value, according to ORDER BY.
pgvector
An extension that stores embedding vectors and searches them by distance inside PostgreSQL.
MVCC
Multi-version concurrency control: updates write new row versions so readers and writers do not block each other.
VACUUM
Removes dead row versions so their space can be reused, and protects against transaction ID wraparound.
Django MTV
Model, Template, View: Django's pattern, where the view is the controller in MVC terms.
Project and app
A project is the whole site and its settings; an app is one reusable feature inside it.
Migration
A versioned file that applies one schema change, so every environment changes in the same order.
QuerySet
A lazy description of a database query that runs when iterated, counted or evaluated.
N+1 problem
One query for N objects followed by one query per object for a related value.
select_related
Loads a forward foreign key or one-to-one field in the same query using a SQL JOIN.
prefetch_related
Loads many-side relationships in a second query and joins them in Python.
Django REST Framework
A library that builds JSON APIs from serializers, viewsets and routers.
Topological sort
An ordering of a directed acyclic graph where every edge points forward; Kahn's algorithm builds it with indegree counts.
Dijkstra's algorithm
Shortest paths from one source with non-negative weights, using a min-heap to settle the closest node next.
