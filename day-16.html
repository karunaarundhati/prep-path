Database fundamentals and the relational model

A database is an organised collection of data. A database management system (DBMS) is the software that stores that data and lets many programs and people read and write it safely. PostgreSQL, MySQL, Oracle and SQL Server are all DBMSs. The ones that organise data as tables and use SQL to query them are called relational database management systems (RDBMSs).

Before databases, each program kept its own data files. Every program had its own file format, the same facts were copied into many files, and a change made in one file was easy to forget in another. A DBMS solves this by keeping one shared, managed copy of the data. A good DBMS gives you four things, and interviewers like it when you name them:

  • Data independence. A program asks for the data it needs by name, not by its position on disk. Administrators can change how the bytes are stored, or add a new column to a table, without rewriting every program. The schema (the logical design) and the storage (the physical design) can change separately.
  • Integrity. Rules such as "every order must belong to a customer" are enforced by the database itself, so a buggy program cannot quietly break them.
  • Concurrency. Many users can read and write at the same time without destroying each other's work. Day 17 covers how this is done.
  • Recovery and security. The database can come back to a correct state after a crash, and permissions decide which user may read or change which table.

The relational model

In 1970 Edgar F. Codd proposed the relational model. Its single idea is that all data is stored in tables, and each table is a mathematical relation. Because the idea is so precise, you can reason about correctness, and that is why SQL, the language built on it, has lasted for decades.

Interviewers use the formal words, so learn them exactly:

  • Relation is the formal word for a table.
  • Tuple is a row. A table with five rows has five tuples.
  • Attribute is a column. The column names form the header of the relation.
  • Domain is the set of values an attribute is allowed to take, such as whole numbers, dates, or text. Every value in a column must come from that column's domain.
  • Degree is the number of attributes. Cardinality is the number of tuples.
  • Schema is the structure: table names, column names, data types and rules. It changes rarely. Instance is the data stored at one moment. It changes all the time.

Key ideaIn the formal model a relation is a set of tuples: no duplicate rows, and no meaningful row order. SQL tables are looser. They are bags (multisets) and can hold duplicate rows unless you declare a key, so expect an interviewer to ask about this difference.

Why schema design matters

A badly designed table does not fail at once. It works for a while, then produces wrong answers. Two copies of the same fact drift apart. A new row cannot be added without inventing data for an unrelated column. Deleting one fact silently deletes another. Those failures are called anomalies, and this day is about preventing them. The tools are the ER model (to decide which tables exist), keys and constraints (to decide which rows are allowed), and normalization (to decide which columns belong together). We will work through all three, in that order.

The entity-relationship model and its mapping to tables

Before writing CREATE TABLE, most designers draw an entity-relationship (ER) diagram. It is a sketch of the things you care about and how they connect. It is not a database, but every ER diagram maps to tables with a fixed set of rules.

Entities and attributes

An entity is a thing that can be told apart from other things, such as a student, a course or a department. An entity type (or entity set) is the category, such as all students. Each member of the category is an entity instance. An attribute describes an entity, such as a student's name. Attributes come in four kinds:

  • Simple attributes cannot be split further, such as roll_no.
  • Composite attributes are made of smaller parts, such as an address made of street, city and postal code.
  • Derived attributes are computed from other data, such as age computed from a date of birth. They are usually not stored.
  • Multivalued attributes can hold several values for one entity, such as several phone numbers for one employee.

A strong entity has its own key. A weak entity cannot be identified by its own attributes alone. It needs an owner. For example, a dependant of an employee is identified by the employee's ID together with the dependant's first name. Weak entities are drawn with a double rectangle in most notations.

Relationships, cardinality and participation

A relationship connects entities. A student enrolls in a course. The degree of a relationship is the number of entity types it connects: binary (two) is by far the most common, and ternary (three) appears in some designs.

The cardinality ratio says how many entities on each side can be linked:

  • One to one (1:1). A person has one passport and a passport belongs to one person.
  • One to many (1:N). One department has many employees, and each employee works in one department.
  • Many to many (M:N). A student takes many courses, and a course has many students.

The participation says whether every entity must take part. Total participation means every employee must belong to a department. Partial participation means some entities may take no part, such as a department with no employees yet.

A relationship can have its own attributes. In a student and course example, the grade a student receives is not a property of the student alone or of the course alone. It belongs to the pair, so it is an attribute of the enrolls in relationship.

Mapping the diagram to tables

The mapping rules are mechanical, and interviewers often ask you to apply them to a diagram. Here they are in order:

  1. Strong entity. Make one table. Its columns are the simple attributes, and its primary key is the entity's key.
  2. Composite attribute. Flatten it into several columns, such as street, city and postal_code.
  3. Derived attribute. Do not store it, or store it deliberately in a view, because storing a computed value can go stale.
  4. Multivalued attribute. Make a separate table with one row per value. Its key is the owner's key plus the value, so one employee can have many phone rows.
  5. One to many (1:N). Put a foreign key on the many side, which points to the one side. Any attribute of the relationship also goes on the many side.
  6. Many to many (M:N). Make a new junction (or associative) table. It has a foreign key to each participant, and its primary key is both foreign keys together. Relationship attributes such as grade live in this table.
  7. One to one (1:1). Put a foreign key on one side, preferably the side with total participation, and add a UNIQUE constraint so that each row is paired with at most one row on the other side.
  8. Weak entity. Make a table whose primary key is the owner's key plus the weak entity's partial key. The owner's key is also a foreign key.

Here is the mapping applied to two relationships. Employees and departments form a 1:N relationship. Students and courses form an M:N relationship with a grade attribute:

CREATE TABLE department (
    dept_id   INTEGER PRIMARY KEY,
    dept_name VARCHAR(50) NOT NULL UNIQUE
);

CREATE TABLE employee (

    full_name VARCHAR(100) NOT NULL,
    dept_id   INTEGER REFERENCES department (dept_id)   -- the 'many' side holds the foreign key
);

    student_id INTEGER PRIMARY KEY,
    name       VARCHAR(100) NOT NULL
);

    grade      CHAR(2),

);

TrapStudents often put the foreign key for a many to many relationship on one of the entity tables. That can hold only one course per student. The fix is always the junction table.

A department has many employees. Where does the foreign key go?

On the employee table, the many side. The foreign key dept_id points to the one side, the department. Putting it on the department table would allow only one employee per department.

Keys and constraints

A key identifies a row. Keys are the most tested idea in relational design, so it helps to build them from the bottom up.

From superkey to primary key

  • Superkey. A set of attributes whose values are unique across all rows. Any set that contains a superkey is also a superkey. The full set of all columns is always a superkey, but it is usually too big to be useful.
  • Candidate key. A minimal superkey: a superkey from which no attribute can be removed while keeping it unique. A table can have several candidate keys.
  • Primary key. The one candidate key chosen to identify rows. It must be unique and cannot contain NULL.
  • Alternate key. A candidate key that was not chosen as the primary key. Its columns are often declared UNIQUE.
  • Prime attribute. An attribute that belongs to at least one candidate key. Other attributes are called non-prime. This term is needed in the normal forms below.

Take a table of students with columns roll_no, email and name. Both roll_no and email are unique, so each is a candidate key. The set {roll_no, email} is a superkey, but it is not a candidate key, because roll_no alone already works and so the pair is not minimal. The designer picks roll_no as the primary key and makes email an alternate key.

Interviewers askWhat is the difference between a superkey and a candidate key? A superkey only has to be unique. A candidate key is a superkey with no unnecessary attributes, so removing any column breaks the uniqueness.

Foreign keys and referential integrity

A foreign key is a column (or set of columns) whose values must match a primary key value in another table, or be NULL when NULL is allowed. The rule that every foreign key value has a matching row is called referential integrity. It stops the database from holding an employee whose department does not exist.

What should happen when the parent row is deleted? The foreign key clause answers this:

  • NO ACTION (the default in PostgreSQL) and RESTRICT refuse the delete while child rows still point to the parent. The difference is timing: RESTRICT is checked at once, while NO ACTION can be deferred to the end of the transaction if the constraint is declared DEFERRABLE.
  • CASCADE deletes the child rows too. Deleting a department would delete all of its employees.
  • SET NULL keeps the child rows and sets their foreign key to NULL.
  • SET DEFAULT sets the foreign key to its default value, which must itself exist in the parent.

Column constraints

Constraints are rules the DBMS enforces on every insert and update:

  • NOT NULL means a value must be supplied. NULL means "unknown or not applicable", not zero and not an empty string.
  • UNIQUE means no two rows can have the same value. In PostgreSQL, several rows may hold NULL in a UNIQUE column, because two unknown values are not considered equal.
  • CHECK means a condition that every row must satisfy, such as salary > 0.
  • DEFAULT supplies a value when the insert does not mention the column.
  • PRIMARY KEY combines NOT NULL and UNIQUE for one set of columns, and a table can have only one.

The next block declares the constraints for a small employee table. Read each line as a rule the database will enforce:

CREATE TABLE department (
    dept_id   INTEGER PRIMARY KEY,
    dept_name VARCHAR(50) NOT NULL UNIQUE
);

CREATE TABLE employee (
    emp_id    INTEGER PRIMARY KEY,
    email     VARCHAR(120) NOT NULL UNIQUE,
    full_name VARCHAR(100) NOT NULL,
    salary    NUMERIC(10, 2) CHECK (salary > 0),
    dept_id   INTEGER REFERENCES department (dept_id) ON DELETE SET NULL
);

With these rules in place, the database rejects an insert with a negative salary (CHECK), a second employee with the same email (UNIQUE), and an employee whose dept_id names a department that does not exist (the foreign key). Deleting a department sets its employees' dept_id to NULL instead of deleting them, because of ON DELETE SET NULL.

TipPut a constraint in the database even when your application already checks it. Applications have bugs, scripts run directly against the database, and other applications may share the same tables.

Why can a UNIQUE column hold several NULLs in PostgreSQL, while a PRIMARY KEY column cannot?

A primary key must be NOT NULL. A UNIQUE constraint does not require values, and by default NULL is treated as unknown, so two NULLs are not considered equal to each other and the uniqueness check passes. Each NULL is a different unknown value.

Relational algebra: the formal core of SQL

Relational algebra is a small set of operators that take relations as input and produce a new relation as output. SQL is a practical language built on the same ideas. Learning the algebra makes SQL queries easy to plan, and interviewers often ask you to write an expression in symbols and then in SQL.

Each operator produces a relation, and operators can be nested like arithmetic. These are the core operators:

  • Selection, sigma (σ). Keeps the rows that satisfy a condition. Written σdept='Sales'(Emp). It corresponds to WHERE.
  • Projection, pi (π). Keeps only the listed attributes, and removes duplicate rows because a relation is a set. Written πname(Emp). It corresponds to choosing columns in SELECT, with DISTINCT behaviour.
  • Union (∪). All rows in either relation. The two inputs must have the same attributes.
  • Difference (−). Rows in the first relation that are not in the second. The inputs must be union-compatible.
  • Cartesian product (×). Every row of one relation paired with every row of the other. A relation with 3 rows times one with 4 rows gives 12 rows.
  • Natural join (⋈). A product followed by a selection that keeps only pairs with equal values in every attribute name the two relations share, followed by a projection that removes the duplicate shared columns. In SQL it is a join on the shared column names.
  • Rename (ρ). Gives a relation or attribute a new name. It is needed when a join must compare columns with different names.

Functional dependencies and attribute closure

So far we have looked at keys. Normalization needs something more general: rules about which attributes determine which others. Those rules are functional dependencies.

Definition

A functional dependency (FD) written X → Y means: for any two rows in the relation, if they agree on every attribute in X, they must also agree on every attribute in Y. X determines Y. Some examples:

  • emp_id → name. Two rows with the same employee ID must have the same name.
  • {student, course} → grade. A student has one grade in each course.
  • dept_id → dept_name. A department ID identifies one department name.

An FD is a statement about the meaning of the data, not something you can discover by looking at a small sample. Sample rows can only show that an FD is violated, never prove that it holds. The designer decides which FDs are true of the real world, and the rules are written into the schema.

An FD X → Y is trivial when Y is a subset of X, because then it always holds. For example {A, B} → A is trivial.

Armstrong's axioms

William Armstrong showed that three rules are enough to derive every FD that follows from a given set. They are sound (they never derive a false FD) and complete (they derive every FD that must hold):

  1. Reflexivity. If Y is a subset of X, then X → Y.
  2. Augmentation. If X → Y, then XZ → YZ for any set Z.
  3. Transitivity. If X → Y and Y → Z, then X → Z.

Three convenient rules follow from them. Union: if X → Y and X → Z, then X → YZ. Decomposition: if X → YZ, then X → Y and X → Z. Pseudotransitivity: if X → Y and WY → Z, then WX → Z.

Attribute closure

Checking derivations by hand is slow. The standard tool is the closure of a set of attributes. The closure of X, written X+, is the set of every attribute that X determines under the given FDs. The algorithm is short:

  1. Start with the result set equal to X.
  2. Look at each FD A → B. If every attribute of A is already in the result, add all of B to the result.
  3. Repeat step 2 until nothing new is added.

Take the relation R(A, B, C, D, E) with the FDs AB → C, C → D and D → E. Compute the closure of {A, B}:

StepFD usedLeft side in result?Result after step
0(start)—{A, B}
1AB → CYes, A and B are both there{A, B, C}
2C → DYes, C was just added{A, B, C, D}
3D → EYes, D was just added{A, B, C, D, E}

So {A, B}+ is all five attributes. Now compute the closure of {A} alone. No FD has a left side that is contained in {A}, because AB → C needs B too. So {A}+ = {A}.

Closure answers the main design questions:

  • Is X a superkey? Yes exactly when X+ contains every attribute of the relation.
  • Does X → Y follow from the FDs? Yes exactly when Y is a subset of X+.
  • Is X a candidate key? It is a superkey, and removing any single attribute gives a set whose closure is not everything.

In the example above, {A, B} is a superkey. Because {A} and {B} are not superkeys (the closure of {B} is just {B}), {A, B} is the only candidate key.

Key ideaThe closure of X is the set of everything X can reach by repeatedly applying the FDs. X is a superkey exactly when the closure covers the whole relation.

Closure in code

The next program implements the closure algorithm and finds every candidate key by brute force. It is pure Python, so the output is exact. Attributes are single letters, and an FD is a pair of strings.

from itertools import combinations


def closure(attrs, fds):
    """Return the attribute closure of attrs under the functional dependencies fds."""
    result = set(attrs)
    changed = True
    while changed:
        changed = False
        for lhs, rhs in fds:
            if set(lhs) <= result and not set(rhs) <= result:
                result |= set(rhs)
                changed = True
    return "".join(sorted(result))


def candidate_keys(all_attrs, fds):
    """Return all minimal superkeys, smallest first."""
    everything = "".join(sorted(all_attrs))
    keys = []
    for size in range(1, len(all_attrs) + 1):
        for combo in combinations(all_attrs, size):
            candidate = "".join(combo)
            if closure(candidate, fds) != everything:
                continue                      # not a superkey
            if any(set(k) <= set(candidate) for k in keys):
                continue                      # contains a smaller key, not minimal
            keys.append(candidate)
    return keys


fds = [("AB", "C"), ("C", "D"), ("D", "B")]
print("closure of A:", closure("A", fds))
print("closure of C:", closure("C", fds))
print("closure of AB:", closure("AB", fds))
print("candidate keys:", candidate_keys("ABCD", fds))
closure of A: A
closure of C: BCD
closure of AB: ABCD
candidate keys: ['AB', 'AC', 'AD']

The closure of C is BCD because C gives D, and D gives B. The three candidate keys are AB, AC and AD. Each one reaches all four attributes, and none of them contains another key. All four attributes are prime, because each appears in at least one key. Attribute A appears in all three keys, while C appears only in AC.

TrapDo not infer FDs from sample data. Two rows with different names can have the same department, which is fine. Only the business rules say whether an FD is true, and the answer decides the normal form.

Given R(A, B, C) with FDs A → B and B → C, what is the only candidate key?

A. The closure of A is {A, B, C} because A gives B and B gives C. No other single attribute works: the closure of B is {B, C} and the closure of C is {C}. So A is the only candidate key.

Anomalies and normalization from 1NF to BCNF

Normalization is the process of decomposing a relation into smaller relations so that each fact is stored in one place. It is driven by functional dependencies. The goal is to avoid the three anomalies introduced earlier, which are the failures a poorly designed table causes when you insert, delete or update data.

An unnormalized table with all three anomalies

Consider one table that records which student took which course and what grade they got. The key is the pair {StudentID, CourseID}:

The table has these problems:

  • Update anomaly. The title "Databases" is stored three times. If the course is renamed to "Database Systems", all three rows must change. If one is missed, the table disagrees with itself.
  • Insert anomaly. Suppose the college adds course CS103, "Operating Systems", before any student enrolls. Where do you store it? A row needs a StudentID, and StudentID is part of the key, so you would have to invent a student or store NULL in a key column, which is not allowed.
  • Delete anomaly. If Chen drops his only course, the row that holds his name disappears with it. If the last student leaves CS102, the title "Compilers" disappears too, even though the course still exists.

Each anomaly happens because one table stores facts about different things: students, courses and enrollments. Normalization separates them.

First normal form (1NF)

A relation is in 1NF when every attribute holds atomic values, meaning single indivisible values, and there are no repeating groups. A cell that contains Databases, Compilers breaks the rule, because the cell holds two values. The fix is to store one row per value. A well-designed table should always be in 1NF. SQL cannot stop you from putting a list into one text column, so 1NF is a design rule you must follow yourself.

Second normal form (2NF)

A partial dependency exists when a non-prime attribute depends on only part of a candidate key. A relation is in 2NF when it is in 1NF and there are no partial dependencies. Only relations with composite keys can violate 2NF.

Third normal form (3NF)

A transitive dependency exists when X → Y and Y → Z hold, Y is not a superkey, and Z is a non-prime attribute. A relation is in 3NF when it is in 2NF and has no transitive dependencies. A commonly used equivalent statement: for every non-trivial FD X → Y, either X is a superkey, or every attribute in Y is prime.

Boyce-Codd normal form (BCNF)

A relation is in BCNF when, for every non-trivial FD X → Y, X is a superkey. BCNF is stricter than 3NF. The 3NF definition allowed an FD whose right side is prime, and BCNF does not. Here is the classic case where 3NF holds but BCNF does not.

Take R(Student, Course, Instructor) with these FDs. Each student has one instructor per course, and each instructor teaches one course:

  • {Student, Course} → Instructor
  • Instructor → Course

The candidate keys are {Student, Course} and {Student, Instructor}, since the second pair determines Course through the second FD. Every attribute is prime, so the relation is in 3NF. But Instructor → Course has a left side that is not a superkey, so the relation is not in BCNF. The fix is to decompose on that FD:

  • R1(Instructor, Course) holds Instructor → Course, and Instructor is its key.
  • R2(Student, Instructor) holds the rest of the information.

A quick test for a two-table split: it is lossless when the attributes the two tables share form a key of at least one of them. Here the shared attribute is Instructor, and it is the key of R1.

TrapBCNF can lose an FD. The original rule {Student, Course} → Instructor is no longer inside one table, so checking it means joining the two tables. A 3NF decomposition always keeps every FD, but it may keep some redundancy. Designers choose between the two based on the workload.

Choosing a normal form

Work through the checks in order. Find the candidate keys with closure. List the FDs. Look for a partial dependency (2NF), a transitive dependency (3NF) and a determinant that is not a superkey (BCNF). Decompose on the violating FD and check that the result is lossless. In practice most OLTP schemas target 3NF or BCNF, and a read-heavy reporting schema may deliberately denormalise, that is, store a duplicated value to avoid a join. Denormalising is a conscious trade-off, not a mistake.

Interviewers askWhat is the difference between 3NF and BCNF? Both forbid transitive dependencies on non-prime attributes. BCNF also forbids any FD whose left side is not a superkey, even when the right side is prime. 3NF always allows a dependency-preserving, lossless decomposition, while BCNF is lossless but may not preserve every FD.

Why is a relation with the key {A, B} and the FD B → C not in 2NF?

The FD B → C depends only on part of the key {A, B}, because B alone determines C. C is non-prime, so the dependency is partial and the relation violates 2NF. Splitting it into R1(B, C) and R2(A, B) fixes the problem.

Can a relation be in BCNF but still have an anomaly?

BCNF removes the anomalies that come from FDs. A relation can still have anomalies caused by multivalued dependencies, which are a separate concept handled by 4NF. Ordinary FDs are the main concern for interviews.

Interview questions

What is the difference between a relation and a table?

A relation is the formal mathematical object. A table is its common implementation. The main differences are that a relation is a set (no duplicate rows, no row order), while an SQL table is a bag that can hold duplicates unless constrained, and SQL adds features such as NULL that the pure model does not have.

Define degree and cardinality with an example.

Degree is the number of attributes (columns). Cardinality is the number of tuples (rows). A table of students with columns id, name and city, holding 40 rows, has degree 3 and cardinality 40.

What is the difference between a superkey, a candidate key and a primary key?

A superkey is any set of attributes that is unique across rows. A candidate key is a superkey with no unnecessary attributes. The primary key is the one candidate key the designer chooses to identify rows, and it must not contain NULL.

How do you map a many to many relationship to tables?

Create a junction table with a foreign key to each participating entity. Make the primary key the combination of those two foreign keys. Any attribute of the relationship, such as a grade, is stored as a column in the junction table.

What does ON DELETE CASCADE do, and when would you avoid it?

It deletes child rows automatically when the parent row is deleted. It is convenient for owned data, such as order lines of an order. Avoid it when child rows have a life of their own, because a single delete can remove much more data than intended.

What is referential integrity?

It is the rule that every non-NULL foreign key value must match an existing primary key value in the referenced table. The DBMS enforces it on inserts, updates and deletes, so the database never contains dangling references.

Explain the three anomalies with a one-line example each.

Update: a course title stored in many rows must be changed in every row. Insert: you cannot record a course that has no students, because the key requires a student. Delete: removing a student's last enrollment also removes the student's name if both are stored in one row.

Given R(A, B, C, D) with FDs A → B and C → D, is AC a key?

Yes. The closure of {A, C} is {A, B, C, D}, because A gives B and C gives D. Neither A nor C alone is a superkey, because the closure of A is {A, B} and the closure of C is {C, D}. So AC is a candidate key, and it is the only one.

Is a table in 3NF automatically in BCNF?

No. 3NF allows an FD whose left side is not a superkey when the right side is prime. The classic example is the Student, Course, Instructor table, where Instructor determines Course and the relation is in 3NF but not BCNF.

What does lossless decomposition mean and why does it matter?

A decomposition is lossless when joining the parts gives back exactly the original rows, with no extra rows and no missing rows. A lossy split would invent false combinations of facts. Lossless decomposition is mandatory when normalising.

DSA: binary search trees

A binary tree is a tree where each node has at most two children, called left and right. A binary search tree (BST) adds an ordering rule: for every node, every value in its left subtree is smaller than the node's value, and every value in its right subtree is larger. Duplicates are either forbidden or sent to one side, depending on the problem statement.

The BST rule gives two powerful consequences. First, searching can discard half the tree at each step, just as binary search discards half of a sorted array. Second, an inorder traversal (visit left subtree, then the node, then the right subtree) visits the values in sorted order. Most BST interview problems use one of these two facts.

The tree is always built from a level-order list in the examples. Each list entry is a node value, and None marks a missing child. The list [4, 2, 7, 1, 3] describes a root of 4, with children 2 and 7, and 2 has children 1 and 3. The helper functions below build such trees and turn them back into lists, so every answer can be printed and checked.

Search in a Binary Search Tree (LeetCode 700)

Given the root of a binary search tree and an integer val, return the subtree rooted at the node whose value is val. If no node has that value, return null. For the tree [4, 2, 7, 1, 3] and val = 2, the answer is the subtree [2, 1, 3].

How to think about it

  1. Understand. The answer is a whole subtree, not just a value. If the value is missing, the answer is null. Values are unique in this problem.
  2. Brute force. Visit every node with any traversal and compare values. That works, but it ignores the BST rule, so it costs O(n) time even when the target is near the top.
  3. Find the waste. The brute force looks at the whole tree. The BST rule says that at each node, the target is either this node, or it is in exactly one subtree. Half the tree never needs a look.
  4. Optimise. Start at the root. If the target equals the node, stop. If the target is smaller, move left. If it is larger, move right. Each step goes one level deeper, so the work is the height of the tree.
  5. Dry run. Search for 2 in [4, 2, 7, 1, 3]. The steps are shown below.
Current nodeCompareDecision
4 (root)2 < 4Move left
22 = 2Found, return this node

from collections import deque


class TreeNode:
    def __init__(self, val=0, left=None, right=None):
        self.val = val
        self.left = left
        self.right = right


def build_tree(values):
    """Build a tree from a level-order list; None marks a missing child."""
    if not values or values[0] is None:
        return None
    root = TreeNode(values[0])
    queue = deque([root])
    i = 1
    while queue and i < len(values):
        node = queue.popleft()
        if i < len(values) and values[i] is not None:
            node.left = TreeNode(values[i])
            queue.append(node.left)
        i += 1
        if i < len(values) and values[i] is not None:
            node.right = TreeNode(values[i])
            queue.append(node.right)
        i += 1
    return root


def to_list(root):
    """Turn a tree back into a level-order list, with trailing None values removed."""
    if root is None:
        return []
    out = []
    queue = deque([root])
    while queue:
        node = queue.popleft()
        if node is None:
            out.append(None)
            continue
        out.append(node.val)
        queue.append(node.left)
        queue.append(node.right)
    while out and out[-1] is None:
        out.pop()
    return out


def search_bst(root, val):
    node = root
    while node is not None and node.val != val:
        node = node.left if val < node.val else node.right
    return node


root = build_tree([4, 2, 7, 1, 3])
print(to_list(search_bst(root, 2)))
print(to_list(search_bst(root, 7)))
print(to_list(search_bst(root, 5)))
print(search_bst(root, 5) is None)

Pattern to rememberIn a BST, each comparison tells you which subtree can be ignored. Walk down one path, and the cost is the height, not the size.

Validate Binary Search Tree (LeetCode 98)

Given the root of a binary tree, decide whether it is a valid BST. Every node's left subtree must hold values strictly smaller than the node, and its right subtree must hold values strictly larger, and the same must hold for every node below. The tree [5, 1, 4, null, null, 3, 6] is not valid, even though each node is larger than its own left child, because 3 sits in the right subtree of 5 and is smaller than 5.

How to think about it

  1. Understand. The rule applies to all descendants, not only to direct children. Values are strict, so equal values are invalid. An empty tree is valid.
  2. Brute force. Check each node against every value in its left and right subtrees. That is correct but repeats work, because the same nodes are scanned again for each ancestor.
  3. Find the waste. Each node has a valid range of values, and the range is set by its ancestors. The root allows anything. A left child of the root must be below the root. A right grandchild must be above its parent and also above the root. Checking only parent and child is not enough, as the example shows: 3 is a valid child of 4, but 3 is not valid under 5.
  4. Optimise. Pass the allowed range down the recursion. At node v with range (low, high), require low < v < high. Going left narrows high to v. Going right raises low to v. Each node is checked once, in O(n) time.
  5. Dry run. The steps for [5, 1, 4, null, null, 3, 6] are shown below.
NodeAllowed range (low, high)CheckResult
5 (root)(-inf, inf)-inf < 5 < infOK, recurse on both children
1 (left of 5)(-inf, 5)-inf < 1 < 5OK, no children
4 (right of 5)(5, inf)5 < 4 is falseInvalid, return False

def is_valid_bst(root):
    def check(node, low, high):
        if node is None:
            return True
        if not (low < node.val < high):
            return False
        return check(node.left, low, node.val) and check(node.right, node.val, high)

    return check(root, float("-inf"), float("inf"))

Kth Smallest Element in a BST (LeetCode 230)

Given the root of a BST and an integer k, return the k-th smallest value in the tree, counting from 1. For [3, 1, 4, null, 2] and k = 1, the answer is 1. For k = 3 the answer is 3.

How to think about it

  1. Understand. "k-th smallest" is the same as the k-th value in sorted order. Count the values from smallest to largest and stop at the k-th one.
  2. Brute force. Collect every value into a list, sort it, and index position k. That is O(n log n) time and O(n) space, and it ignores the tree's structure completely.
  3. Find the waste. The BST property means an inorder traversal already produces the values in sorted order. The brute force sorts a list that is already sorted.
  4. Optimise. Run an inorder traversal and count. Stop as soon as the count reaches k, so the work is proportional to the number of nodes visited, not the whole tree. An explicit stack gives an iterative version that can stop early without an exception.
  5. Dry run. For [3, 1, 4, null, 2] and k = 1, the stack holds 3 and 1 when we reach the leftmost node. Pop 1, count it as the first value, and return 1.

        self.left = left
        self.right = right

        if i < len(values) and values[i] is not None:
            node.left = TreeNode(values[i])
            queue.append(node.left)
        i += 1
        if i < len(values) and values[i] is not None:
            node.right = TreeNode(values[i])
            queue.append(node.right)
        i += 1
    return root


def kth_smallest(root, k):
    stack = []
    node = root
    while stack or node is not None:
        while node is not None:          # go as far left as possible
            stack.append(node)
            node = node.left
        node = stack.pop()               # next value in sorted order
        k -= 1
        if k == 0:
            return node.val
        node = node.right
    return None


print(kth_smallest(build_tree([3, 1, 4, None, 2]), 1))
print(kth_smallest(build_tree([5, 3, 6, 2, 4, None, None, 1]), 3))
print(kth_smallest(build_tree([5, 3, 6, 2, 4, None, None, 1]), 6))

3

Time O(h + k) · Space O(h) for the stack, where h is the height

Interviewers askWhat if the tree is modified often and you must answer many k queries quickly? Keep a count of nodes in each subtree. Then you can walk down from the root, going left or right according to the size of the left subtree, in O(h) time per query.

Pattern to rememberInorder traversal of a BST gives sorted order. Any "k-th smallest" or "sorted order" question on a BST is an inorder traversal with an early stop.

Serialize and Deserialize Binary Tree (LeetCode 297)

Design a way to turn a binary tree into a string (serialize) and turn that string back into the same tree (deserialize). You choose the format. For the tree [1, 2, 3, null, null, 4, 5], one valid string is 1,2,#,#,3,4,#,#,5,#,#, where # marks a missing child. The round trip must give back the same shape and values.

How to think about it

  1. Understand. The string must contain enough information to rebuild the shape, not only the values. Empty trees and single nodes must work. Values can be negative or repeated.
  2. Brute force. Try to store only the values, in inorder or preorder, with no markers. This fails: the values alone do not fix the shape. The root 1 with a right child 2, and the root 2 with a left child 1, both have inorder sequence 1, 2. A correct encoding must record where the missing children are.
  3. Find the waste. The real need is a marker for each missing child. Without markers the decoder cannot tell where one subtree ends and the next begins. A marker lets the decoder read the string once, in the same order the encoder wrote it.
  4. Optimise. Use preorder (node, left subtree, right subtree) with # for each missing child. Serialize with a recursive walk. Deserialize with the same recursive order: read the next token, and if it is # return null, otherwise create a node and read its left subtree and then its right subtree. An iterator over the tokens keeps the position between recursive calls. Both directions are O(n) time.
  5. Dry run. Read the tokens of 1,2,#,#,3,4,#,#,5,#,# in order. The table shows what the decoder does with each one.
Token readActionNode created
1Create the root, then build its left subtree1
2Create the left child of 1, then build its left subtree2
#Left child of 2 is missing, return nullnone
#Right child of 2 is missing, so 2 is complete, return to 1none
3Create the right child of 1, then build its left subtree3
4Create the left child of 3, then build its left subtree4
#, #Both children of 4 are missing, so 4 is completenone
5Create the right child of 3, then its two markers finish it5

class TreeNode:

        self.val = val
        self.left = left
        self.right = right

    if not values or values[0] is None:
        return None
    root = TreeNode(values[0])
    queue = deque([root])
    i = 1
    while queue and i < len(values):
        node = queue.popleft()
        if i < len(values) and values[i] is not None:
            node.left = TreeNode(values[i])
            queue.append(node.left)
        i += 1
        if i < len(values) and values[i] is not None:
            node.right = TreeNode(values[i])
            queue.append(node.right)
        i += 1
    return root


def to_list(root):
    """Turn a tree back into a level-order list, with trailing None values removed."""
    if root is None:
        return []
    out = []
    queue = deque([root])
    while queue:
        node = queue.popleft()
        if node is None:
            out.append(None)
            continue
        out.append(node.val)
        queue.append(node.left)
        queue.append(node.right)
    while out and out[-1] is None:
        out.pop()
    return out


class Codec:
    def serialize(self, root):
        parts = []

        def dfs(node):
            if node is None:
                parts.append("#")
                return
            parts.append(str(node.val))
            dfs(node.left)
            dfs(node.right)

        dfs(root)
        return ",".join(parts)

    def deserialize(self, data):
        tokens = iter(data.split(","))

        def build():
            token = next(tokens)
            if token == "#":
                return None
            node = TreeNode(int(token))
            node.left = build()
            node.right = build()
            return node

        return build()


codec = Codec()
root = build_tree([1, 2, 3, None, None, 4, 5])
text = codec.serialize(root)
print(text)
print(to_list(codec.deserialize(text)))
print(codec.serialize(None))

TrapForgetting the marker for a missing child is the usual bug. Without the second # after 2, the decoder would attach 3 as the right child of 2 instead of the right child of 1.

Pattern to rememberTo rebuild a tree from a sequence, record the shape with null markers in a fixed traversal order. Then decode with the same traversal, reading one token at a time.

Summary

Relation
The formal name for a table: a set of tuples over named attributes.
Tuple
One row of a relation.
Attribute
A named column of a relation.
Domain
The set of allowed values for an attribute.
Degree and cardinality
Degree is the number of attributes; cardinality is the number of tuples.
Schema and instance
The schema is the structure; the instance is the data at one moment.
Entity and weak entity
A thing we model; a weak entity needs an owner entity to be identified.
Relationship
An association between entities, which can have its own attributes.
Cardinality ratio
How many entities on each side may be linked: 1:1, 1:N or M:N.
Participation
Total means every entity must take part; partial means some need not.
Junction table
The table that represents a many to many relationship.
Superkey
A set of attributes that is unique across all rows.
Candidate key
A minimal superkey: removing any attribute breaks uniqueness.
Primary key
The candidate key chosen to identify rows; it cannot be NULL.
Alternate key
A candidate key that is not the primary key.
Prime attribute
An attribute that belongs to at least one candidate key.
Foreign key
A column whose values must match a primary key in another table.
Referential integrity
Every non-NULL foreign key value refers to an existing row.
Selection (sigma)
Keeps the rows that satisfy a condition; the WHERE clause.
Projection (pi)
Keeps chosen attributes and removes duplicate rows.
Natural join
Pairs rows that agree on all shared attribute names.
Functional dependency
X determines Y when rows agreeing on X always agree on Y.
Trivial dependency
An FD whose right side is contained in its left side; it always holds.
Armstrong's axioms
Reflexivity, augmentation and transitivity: sound and complete rules for deriving FDs.
Attribute closure
The set of attributes that X determines, computed by repeatedly applying FDs.
Anomaly
An insert, update or delete problem caused by redundant or mixed data.
Partial dependency
A non-prime attribute depends on part of a composite key; violates 2NF.
Transitive dependency
X determines Y, Y determines a non-prime Z, and Y is not a key; violates 3NF.
1NF, 2NF, 3NF
Atomic values; no partial dependencies; no transitive dependencies.
BCNF
Every non-trivial FD has a superkey on its left side.
Lossless decomposition
Splitting a relation so that joining the parts returns exactly the original rows.
Dependency preservation
Every FD can still be checked inside one of the decomposed tables.
Binary search tree
A binary tree where left values are smaller and right values larger than each node.
Inorder traversal
Left, node, right; visits a BST in sorted order.
