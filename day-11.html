Concurrency vs parallelism

These two words are used interchangeably by many developers, and interviewers notice when you do. They describe different things.

Concurrency means dealing with several tasks at once: the tasks are in progress during the same period, and their steps can interleave. A single CPU core can be concurrent by switching quickly between tasks. Concurrency is about structure: how a program is organized so that waiting on one thing does not block everything else.

Parallelism means doing several things at the same instant, which requires more than one processing unit, such as multiple cores. Parallelism is about execution: the work really runs side by side.

You can have concurrency without parallelism (one core, many threads taking turns), parallelism without much concurrency (a single job split across cores), or both. A web server that handles many connections while waiting for a database is concurrent. A matrix multiplication split across eight cores is parallel.

Key ideaConcurrency is a way of structuring a program around independent tasks. Parallelism is running those tasks at the same time on hardware that can do so.

I/O-bound vs CPU-bound work

The right tool depends on what the work spends its time doing. I/O-bound work spends most of its time waiting for disks, networks or users. Threads or async tasks help a lot here, because while one task waits, another can run. CPU-bound work spends its time computing. Extra threads help only if they can truly run in parallel on separate cores, and in CPython they often cannot, as explained later in this day.

A thread is a flow of execution inside a process that shares its memory. A process has separate memory. Creating a thread is cheaper than creating a process, which is why thread pools exist. Sharing memory is what makes threads useful and also what makes them dangerous, as the previous day showed.

A program runs 8 threads that each spend 99 percent of their time waiting for a web response. Is it concurrency, parallelism, or both?

It is concurrency. The threads overlap their waiting, so many requests are in progress at once. Parallelism would need the threads to run computations at the same instant on several cores, and that is not what the waiting-heavy work needs.

Locks, read-write locks, semaphores and atomics

Day 10 introduced the theory. Here are the tools as you would use them in code. Each one solves a slightly different problem, and choosing the right one is a common interview question.

Locks (mutexes)

A lock allows one thread at a time to enter a critical section. In Python, threading.Lock is the basic mutex, and with lock: is the safe way to use it. Java has synchronized blocks and the ReentrantLock class, which adds features such as try-lock and fairness settings. A reentrant lock can be acquired again by the thread that already holds it, which is convenient when one locked method calls another.

Keep critical sections short. The longer a thread holds a lock, the longer every other thread waits for it. Never call slow operations, such as network requests, while holding a lock unless there is no alternative.

Read-write locks

A read-write lock (also written RW lock) allows many readers at once or one writer at a time, the same rule as the readers-writers problem. It helps when reads are far more common than writes, such as a configuration table read on every request and updated once a day. Java provides it as ReentrantReadWriteLock. The Python standard library does not include one, so Python programs usually use a plain lock or redesign the data.

The trade-off is overhead. An RW lock does more bookkeeping than a plain lock, so when writes are common or critical sections are tiny, a plain lock is often faster.

Semaphores

A semaphore is a counter of permits. A thread takes a permit with acquire and gives it back with release. A semaphore with five permits allows five threads into a region at once, which is the right tool for limiting concurrent use of a resource such as a connection pool or a rate limit. A binary semaphore with one permit behaves like a lock, but without ownership.

import threading

sem = threading.BoundedSemaphore(1)  # a bounded semaphore refuses extra releases
sem.acquire()
sem.release()
try:
    sem.release()                    # releasing more than was acquired
except ValueError as e:
    print("error:", type(e).__name__)
error: ValueError

In the example, the semaphore starts with one permit. The first acquire takes it and the first release gives it back. The second release would make the count two, which a bounded semaphore refuses with a ValueError. A plain semaphore would silently accept it, and the extra permit would let two threads into a region that should hold only one. That silent corruption is why bounded versions are recommended for locking-style use.

Atomics

An atomic operation happens as one indivisible step. No other thread can see it half done. Atomic reads, writes, and read-modify-write operations are provided by the hardware, usually as an instruction such as compare-and-swap (CAS). CAS takes three values: an address, the value you expect to find there, and a new value. It writes the new value only if the current value matches the expected one, and it reports whether it succeeded. Look at the pattern below, which is how a lock-free increment is written:

do {
    old = counter;                 // read the current value
    new = old + 1;                 // compute the new value
} while (!compare_and_swap(&counter, old, new));   // retry if someone changed it first

If another thread changes counter between the read and the CAS, the CAS fails, and the loop reads again. No lock is held, so no thread can block another one while it sleeps. Java exposes this idea through classes such as AtomicInteger, whose incrementAndGet() method is atomic. C and C++ provide atomic types for the same purpose.

Atomics are fast for a single variable, but they do not solve multi-variable invariants. If two counters must always change together, one atomic per counter is not enough, and you need a lock.

TrapPython has no atomic integer. The statement counter += 1 is several bytecode steps, and a thread switch can occur between them, so it is not atomic even though the interpreter has a global lock. Protect it with a lock, or use a class that documents atomicity.

What does "atomic" mean, and why does a volatile variable in Java not make count++ safe?

Atomic means an operation completes as a single indivisible step, so no thread can observe it half done. A volatile variable guarantees that every read sees the latest written value and that writes become visible to other threads. It does not make a read-modify-write like count++ atomic, because the read and the write are still two steps that can interleave. Use AtomicInteger or a lock for that.

Condition variables and blocking queues

Most real systems do not hand-write producer-consumer logic. They use a blocking queue: a thread-safe container where put waits when the queue is full, and get waits when it is empty. Python provides queue.Queue, and Java provides ArrayBlockingQueue and LinkedBlockingQueue. Internally they use the same condition variables you met on day 10.

Two details matter. First, the queue has a capacity, so producers are slowed down when consumers fall behind, which is called backpressure. Second, a consumer needs a way to stop. A common trick is a sentinel, a special value such as None that the producer sends last, telling consumers to finish.

import queue
import threading

tasks = queue.Queue(maxsize=2)     # bounded: put() blocks while 2 items wait
results = []
STOP = None                        # sentinel: tells the consumer to finish

def producer():
    for i in range(1, 6):
        tasks.put(i)               # blocks if the queue is full
    tasks.put(STOP)

def consumer():
    while True:
        item = tasks.get()         # blocks if the queue is empty
        if item is STOP:
            break
        results.append(item * item)

p = threading.Thread(target=producer)
c = threading.Thread(target=consumer)
p.start()
c.start()
p.join()
c.join()
print("squares:", results)
squares: [1, 4, 9, 16, 25]

The output order is fixed because there is one producer and one consumer, and the queue is first-in, first-out. Even if the producer is much faster, the queue never holds more than two items, so the producer waits at the full queue, and the consumer waits at the empty queue when it catches up.

Odd-even printing with two threads

This is a favourite interview exercise. Two threads share one counter. One thread must print the odd numbers and the other the even numbers, so that the output is 1, 2, 3, 4, and so on, in order. The solution needs a shared variable saying whose turn it is, a lock, and a condition variable so a thread can sleep until it is its turn.

The rule each thread follows is simple: take the lock, wait while the shared turn value is not mine, print my number, advance the turn, and wake the others. The while loop around wait() matters for the same reason as on day 10: when the thread wakes, it must re-check whether the turn is really its own.

import threading

LIMIT = 6
turn = 1                           # the next number that may be printed
cond = threading.Condition()
printed = []

def printer(start):
    global turn
    n = start
    while n <= LIMIT:
        with cond:
            while turn != n:       # not my number yet, so sleep
                cond.wait()
            printed.append(n)      # "print" the number
            turn += 1
            cond.notify_all()      # wake the other thread so it can check its turn
        n += 2                     # my next number is two higher

odd = threading.Thread(target=printer, args=(1,))
even = threading.Thread(target=printer, args=(2,))
odd.start()
even.start()
odd.join()
even.join()
print(*printed)
1 2 3 4 5 6

Trace the first steps. The odd thread starts with n equal to 1 and finds turn equal to 1, so it records 1, sets turn to 2, and moves its n to 3. The even thread waits until turn is 2, records 2, sets turn to 3, and moves its n to 4. The odd thread wakes, sees turn equal to 3, and records 3. Each thread sleeps whenever it is not its turn, so the sequence is forced, and the program cannot print out of order no matter how the operating system schedules them.

When the printer thread's n passes the limit, it leaves the loop and ends. The loop bound must be checked on the thread's own n, which is why each thread steps by two.

Interviewers askWhy use notify_all instead of notify here? With only two threads, notify would also work, because only the other thread can be waiting. The habit of notify_all is safer when more threads wait on the same condition, because notify might wake a thread that is not the one whose turn it is, and that thread would simply wait again. Mention this trade-off and explain that correctness comes from the while loop.

Why must the producer call put on a bounded queue instead of checking the size and appending?

Checking the size and then appending is two steps. Another producer can add an item between them, and the queue can exceed its capacity. A blocking put performs the check and the insert under one lock, and it waits on a condition variable when the queue is full.

Deadlock prevention in code

Day 10 explained the four conditions for deadlock. In application code the practical rule is almost always the same: break circular wait by agreeing on a global lock order. The next program shows the pattern on bank accounts, where a transfer must lock two accounts.

Suppose one thread transfers money from A to B and another transfers from B to A. If the first thread locks A and then B while the second locks B and then A, each can hold one lock and wait for the other. That is the classic deadlock. The fix is to sort the two names, so that every thread locks the account with the smaller name first, no matter which direction the money moves.

import threading

balances = {"A": 1000, "B": 1000}
locks = {"A": threading.Lock(), "B": threading.Lock()}

def transfer(src, dst, amount):
    # Always lock the accounts in sorted name order, whatever the direction.
    first, second = sorted([src, dst])
    with locks[first]:
        with locks[second]:
            balances[src] -= amount
            balances[dst] += amount

def worker_ab():
    for _ in range(500):
        transfer("A", "B", 1)

def worker_ba():
    for _ in range(500):
        transfer("B", "A", 2)

threads = [threading.Thread(target=worker_ab), threading.Thread(target=worker_ba)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print(balances)
{'A': 1500, 'B': 500}

Both threads finish, and the totals are the same no matter how the threads interleave: A gives 1 unit 500 times and receives 2 units 500 times, so A ends at 1000 minus 500 plus 1000, which is 1500. The sum of the balances stays 2000 throughout, because each transfer subtracts and adds the same amount.

Other prevention techniques exist, and they are worth naming in an interview:

  • Try-lock with back-off. Take the first lock, then try the second without waiting (for example acquire(blocking=False) in Python, or tryLock() in Java). If it fails, release the first lock, wait a little, and retry. This breaks hold and wait. Be careful: two threads that keep backing off in lockstep can livelock, where both run forever and make no progress, so add a random delay.
  • One coarse lock. Use a single lock for all accounts. It cannot deadlock with itself, but it removes concurrency, so it is only sensible for small or rarely contended data.
  • Lock-free or message passing. Give each account to one thread, and send transfer requests as messages. No shared locks means no lock-order bugs.

TrapA lock order is only useful if it is followed everywhere. One function that takes the locks in a different order can reintroduce the deadlock. Document the order next to the locks, and review every function that takes more than one.

Two threads each take lock X then lock Y. Can they deadlock?

No. Both threads acquire the locks in the same order, so neither can hold Y while waiting for X in a way that forms a cycle. The first thread to get X also gets Y before the second thread can get X, so the second thread waits without holding anything the first needs.

Thread pools, futures and async

Creating a thread for every small task is wasteful: starting a thread has a cost, and too many threads compete for memory and cache. A thread pool creates a fixed set of worker threads once, and sends tasks to them through a queue. An executor is the object that runs tasks, and a future is the handle you get back for a task that may still be running. Calling result() on a future waits for the answer and returns it, or raises the task's exception.

Python provides concurrent.futures.ThreadPoolExecutor. Its map method returns results in input order, even when tasks finish in a different order. Its submit method returns a future for each task, which is useful when tasks have different shapes.

from concurrent.futures import ThreadPoolExecutor

def square(n):
    return n * n

with ThreadPoolExecutor(max_workers=3) as pool:
    print(list(pool.map(square, range(1, 8))))

with ThreadPoolExecutor(max_workers=2) as pool:
    futures = [pool.submit(square, n) for n in (4, 5)]
    print([f.result() for f in futures])
[1, 4, 9, 16, 25, 36, 49]
[16, 25]

The with block waits for all submitted tasks to finish when it ends, and it shuts the pool down. That makes the example safe: no thread is left running after the block.

Async tasks on one thread

Async programming, in Python with asyncio, runs many tasks on one thread. A task runs until it reaches an await, which means it is waiting for something. At that point it gives control back to the event loop, which runs another ready task. There is no preemption: a task that never awaits blocks everyone. This is cooperative multitasking.

import asyncio

async def job(name, steps):
    total = 0
    for i in range(steps):
        await asyncio.sleep(0)     # hand control back to the event loop
        total += i
    return f"{name} finished with {total}"

async def main():
    results = await asyncio.gather(job("A", 3), job("B", 4), job("C", 2))
    for line in results:
        print(line)

asyncio.run(main())
A finished with 3
B finished with 6
C finished with 1

asyncio.gather runs the three jobs concurrently and returns their results in the order you passed them, not the order they finished. The await asyncio.sleep(0) line is the only point where control switches. Real programs await network or file operations at the same points.

TipA useful interview answer: threads are preemptive and the OS switches them, so you must lock shared data. Async tasks switch only at await points, so they still need care, but the places where state can change are visible in the code.

What happens in asyncio if one task runs a long loop with no await?

Nothing else runs on that event loop until the loop finishes or reaches an await. The event loop cannot preempt the task. This is why CPU-heavy code and blocking calls, such as a plain time.sleep, should be moved into a thread or process pool.

The Python GIL and Java concurrency utilities

The Python GIL

The Global Interpreter Lock (GIL) is a lock inside the standard CPython interpreter. Only one thread at a time executes Python bytecode. Threads switch regularly, so they still take turns, but two threads never run Python code at the same instant, even on a machine with eight cores.

The GIL has two practical consequences. First, CPU-bound Python code gets no speed-up from threads, because the threads queue for the GIL. Second, I/O-bound code benefits from threads, because a thread waiting for a network or disk operation releases the GIL, letting another thread run. For CPU work, use multiprocessing, which starts separate processes with separate interpreters and GILs, or push the work into a native extension that releases the GIL.

The GIL does not make your program thread safe. As the atomics section showed, counter += 1 can still lose updates, because the thread can be switched out between bytecode steps. Python 3.13 introduced an optional, experimental build without the GIL, but the default build still has it, so do not assume it in an interview answer.

Interviewers askAre Python threads useless? No. They are good for I/O-bound work, such as many downloads or database calls, and they are simple to use. They are not a way to make pure Python arithmetic faster on several cores.

Java concurrency utilities

Java's java.util.concurrent package provides most of what this day covers, with stronger tools than the basic synchronized keyword: ExecutorService for thread pools, Future and CompletableFuture for results, ConcurrentHashMap for shared maps, CountDownLatch for waiting until several tasks finish, Semaphore, the locks package for ReentrantLock and ReentrantReadWriteLock, blocking queues, and the atomic classes. The program below uses several of them. Its output is fixed because it reads results in a known order and waits for every task.

import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.Callable;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.atomic.AtomicInteger;
import java.util.concurrent.locks.ReentrantReadWriteLock;

public class ConcurrencyDemo {
    static int shared = 0;
    static final ReentrantReadWriteLock rw = new ReentrantReadWriteLock();

    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newFixedThreadPool(4);

        // 1. An atomic counter: four tasks each add 1000 times.
        AtomicInteger counter = new AtomicInteger();
        List<Future<?>> futures = new ArrayList<>();
        for (int t = 0; t < 4; t++) {
            futures.add(pool.submit(() -> {
                for (int i = 0; i < 1000; i++) {
                    counter.incrementAndGet();
                }
            }));
        }
        for (Future<?> f : futures) {
            f.get();                       // wait for each task to finish
        }
        System.out.println("atomic counter: " + counter.get());

        // 2. Callables return values, and invokeAll keeps submission order.
        List<Callable<Integer>> jobs = new ArrayList<>();
        for (int n = 1; n <= 4; n++) {
            final int k = n;
            jobs.add(() -> k * k);
        }
        int total = 0;
        for (Future<Integer> f : pool.invokeAll(jobs)) {
            total += f.get();
        }
        System.out.println("sum of squares: " + total);

        // 3. Read-write lock: one writer updates, then a reader reads.
        rw.writeLock().lock();
        try {
            shared = 42;
        } finally {
            rw.writeLock().unlock();
        }
        rw.readLock().lock();
        try {
            System.out.println("read under lock: " + shared);
        } finally {
            rw.readLock().unlock();
        }

        // 4. CompletableFuture chains steps without blocking the caller.
        CompletableFuture<String> answer = CompletableFuture
                .supplyAsync(() -> 21, pool)
                .thenApply(x -> x * 2)
                .thenApply(x -> "answer=" + x);
        System.out.println(answer.get());

        pool.shutdown();
    }
}
atomic counter: 4000
sum of squares: 30
read under lock: 42
answer=42

Read the program in four parts. Part 1 uses an AtomicInteger, so four threads can increment it without a lock, and the total is exactly 4000. Part 2 submits four callables and collects their results with invokeAll, which returns futures in the order the tasks were submitted, so summing them is safe. Part 3 takes the write lock to update a shared value and the read lock to read it, releasing both in finally blocks so an exception cannot leave a lock held. Part 4 chains three steps with CompletableFuture, and get() waits for the final result.

Notice the finally blocks. A lock acquired without a matching release in finally is a classic source of hangs. Python's with statement and Java's try-finally play the same role.

Why would you pick a read-write lock over a plain lock for a configuration table that is read thousands of times a second and changed once a day?

Many readers can hold the read lock at the same time, so reads do not queue behind each other. Only the rare writer takes the exclusive write lock. A plain lock would make every reader wait for every other reader, which costs throughput for no safety benefit.

Interview questions

Answer each question out loud before opening the answer. Good answers name the trade-off, not just the definition.

What is the difference between concurrency and parallelism?

Concurrency is structuring a program so that many tasks are in progress and can interleave, even on one core. Parallelism is executing tasks at the same instant on several cores. Concurrency is about design, parallelism is about hardware use.

When would you use a read-write lock, and when is it a bad idea?

Use it when reads greatly outnumber writes and the critical section is long enough that reader parallelism matters. It is a bad idea when writes are frequent or the sections are tiny, because its bookkeeping costs more than a plain lock. It can also starve writers if readers keep arriving, depending on the policy.

How is a semaphore different from a lock?

A lock allows one holder and has an owner who must release it. A semaphore has a count of permits and no owner, so it can limit concurrent use to N threads, and any thread may release a permit. Use a lock for exclusive access and a semaphore for limiting.

Why does a condition variable wait need a while loop?

When a thread wakes, another thread may have changed the state again, or the wake-up may have come without a notify. The loop re-checks the condition after each wake-up and waits again if it is still false.

How do you prevent deadlock when two threads need the same two locks?

Always acquire the two locks in one global order, such as by sorted name or by ID. The circular wait then cannot form. Alternatively use try-lock with back-off, though that needs randomness to avoid livelock.

What is a thread pool, and why is it better than creating a thread per task?

A thread pool creates a fixed set of worker threads once and reuses them for many tasks through a queue. Creating and destroying threads has a cost, and too many threads compete for memory and CPU. The pool bounds the concurrency and amortizes the setup cost.

What does the Python GIL mean for CPU-bound and I/O-bound code?

Only one thread runs Python bytecode at a time in CPython, so CPU-bound threads do not run faster on more cores. I/O-bound threads still help, because a thread waiting on I/O releases the GIL. For CPU-bound work use multiprocessing.

Why are async tasks not automatically safe from race conditions?

Async tasks switch only at await points, which reduces surprise, but a task can still read a value, await, and then write a stale result. Two tasks can interleave across an await, so shared state needs care too. Also, one task that never awaits blocks the whole event loop.

What does an atomic operation guarantee, and when is one not enough?

It guarantees the operation completes as one indivisible step, so no thread sees it half done. One atomic is not enough when several variables must change together consistently, because each atomic protects only itself. Use a lock for multi-variable invariants.

Why does notify_all plus a while loop make odd-even printing correct?

Each thread sleeps until the shared turn equals its own number. Every time the turn changes, all waiters are woken, and each re-checks the turn in its loop. Only the thread whose turn it is proceeds, so the order is forced.

DSA: recursion and backtracking

Recursion is a function that calls itself on a smaller version of the problem. Every recursive function needs a base case that stops the calls, and a recursive case that makes progress toward the base case. If either is missing, the function runs forever or until the stack overflows. Python's default recursion limit is 1000 calls, so keep recursion depth modest or convert to a loop.

Backtracking is recursion that builds a solution one choice at a time and undoes the last choice when a branch fails or is complete. Picture a decision tree. Each node is a partial solution, each edge is a choice, and you walk the tree depth-first. Three steps repeat at each node:

  1. Choose. Add one option to the current partial solution.
  2. Explore. Recurse to extend that partial solution.
  3. Un-choose. Remove the option, so the next sibling branch starts from the same state.

The un-choose step is what makes backtracking efficient. You share one mutable list across the whole search and restore it as you return, instead of copying it at every node. When you need to keep a result, copy it at that moment, for example with path[:].

Key ideaBacktracking is a depth-first walk of a decision tree, where each step adds a choice, recurses, and removes the choice. Pruning, which skips branches that cannot succeed, is what makes it fast.

Memoization for repeated subproblems

Some recursive problems solve the same subproblem many times. Memoization stores each answer the first time it is computed, and returns the stored answer later. Python's functools.lru_cache decorator does this for you. It is the simplest way to turn an exponential recursion into a linear one.

Climbing Stairs (LeetCode 70)

You are climbing a staircase with n steps. Each time you can climb 1 step or 2 steps. Return the number of distinct ways to reach the top. For example, with n = 3 there are three ways: 1 plus 1 plus 1, 1 plus 2, and 2 plus 1.

How to think about it

  1. Understand. n can be large, so the answer can be large too. We count ways, not list them.
  2. Brute force. Recurse: the ways to reach step n are the ways to reach n minus 1 (take one step) plus the ways to reach n minus 2 (take two steps). This is correct, but it recomputes the same values many times, so it takes exponential time.
  3. Find the waste. The subproblems overlap heavily. Step 5 is needed by both step 6 and step 7, and so on.
  4. Optimise. Memoize the recursion with a cache, so each step is computed once. The base cases are one way for step 0 and one way for step 1, and the same formula then gives 2 for step 2.
  5. Dry run. Starting from the bottom: ways(0) = 1, ways(1) = 1, ways(2) = 1 plus 1 = 2, ways(3) = 2 plus 1 = 3, ways(4) = 3 plus 2 = 5, ways(5) = 5 plus 3 = 8. The answer for 5 is 8.

Code

from functools import lru_cache

@lru_cache(maxsize=None)
def climb(n):
    # Ways to reach step n: the last move was 1 step or 2 steps.
    if n <= 1:
        return 1
    return climb(n - 1) + climb(n - 2)

print(climb(5))
print(climb(10))
8
89

Time O(n) · Space O(n) for the cache and recursion stack

Pattern to rememberWhen a count depends on smaller counts in a fixed way, write the recurrence, add base cases, and cache. This is dynamic programming in its top-down form.

Subsets (LeetCode 78)

Given an array of distinct integers nums, return all possible subsets (the power set). The answer may be in any order and must not contain duplicate subsets. For example, nums = [1, 2, 3] gives eight subsets, from the empty set to [1, 2, 3].

How to think about it

  1. Understand. A subset is any selection of elements, including the empty one. With n elements there are 2 to the power n subsets, so the output itself is exponential, and that is fine.
  2. Brute force. Loop over all 2 to the power n bit masks and build the subset each mask describes. This works, but it is harder to extend to other problems.
  3. Find the structure. Each element is either in or out. Decide element by element, and each full decision gives one subset.
  4. Optimise. Backtrack with a start index. At each node, the current path is already a valid subset, so record it. Then for each i from the start index onward, choose nums[i], recurse with start i plus 1 so that no subset is produced twice in a different order, and un-choose.
  5. Dry run for [1, 2, 3]. Record [] first. Choose 1 and record [1]. Choose 2 and record [1, 2]. Choose 3 and record [1, 2, 3]. Un-choose 3, then 2, back to [1]. Choose 3 and record [1, 3]. Un-choose to []. Choose 2 and record [2], then [2, 3]. Finally choose 3 and record [3]. That is 8 subsets.

Code

def subsets(nums):
    result = []
    path = []

    def backtrack(start):
        result.append(path[:])          # every partial path is a valid subset
        for i in range(start, len(nums)):
            path.append(nums[i])        # choose nums[i]
            backtrack(i + 1)            # explore with it included
            path.pop()                  # un-choose it

    backtrack(0)
    return result

print(subsets([1, 2, 3]))
[[], [1], [1, 2], [1, 2, 3], [1, 3], [2], [2, 3], [3]]

Time O(n times 2 to the power n) · Space O(n) for the recursion, plus the output

Pattern to rememberFor every combination or subset problem, use a start index so each element is considered only once, forward from where you are. This avoids duplicates such as [1, 2] and [2, 1].

Combination Sum (LeetCode 39)

Given an array of distinct positive integers candidates and a target integer, return all unique combinations of candidates that sum to the target. The same number may be chosen any number of times. For example, candidates = [2, 3, 6, 7] and target = 7 give [2, 2, 3] and [7].

How to think about it

  1. Understand. Order inside a combination does not matter, so [2, 2, 3] and [3, 2, 2] count once. Reuse of the same number is allowed, which changes the recursion: we stay at the same index after choosing.
  2. Brute force. Generate every multiset of candidates up to the target and filter by sum. The search space is huge without pruning.
  3. Find the waste. Once the remaining amount is negative, the branch is hopeless. Sorting the candidates lets us stop a loop early: if one candidate is too big, every larger one is too big too.
  4. Optimise. Sort the candidates. Backtrack with a start index and the remaining amount. Record the path when the remainder is zero. For each candidate from the start index on, stop the loop when the candidate exceeds the remainder. Recurse with the same index, because reuse is allowed.
  5. Dry run for target 7. Sorted candidates are [2, 3, 6, 7]. Choose 2 (remaining 5), choose 2 again (remaining 3), choose 2 again (remaining 1). Now every candidate is bigger than 1, so this branch ends. Back at remaining 3, the next candidate 3 fits exactly and leaves remaining 0, so [2, 2, 3] is recorded. The branch starting with 6 leaves remaining 1, which no candidate can fill, so it ends. The branch starting with 7 gives [7] at once.

Code

def combination_sum(candidates, target):
    candidates = sorted(candidates)
    result = []
    path = []

    def backtrack(start, remaining):
        if remaining == 0:
            result.append(path[:])
            return
        for i in range(start, len(candidates)):
            if candidates[i] > remaining:    # sorted, so no later value fits either
                break
            path.append(candidates[i])
            backtrack(i, remaining - candidates[i])    # same index: reuse is allowed
            path.pop()

    backtrack(0, target)
    return result

print(combination_sum([2, 3, 6, 7], 7))
print(combination_sum([2, 3, 5], 8))
[[2, 2, 3], [7]]
[[2, 2, 2, 2], [2, 3, 3], [3, 5]]

Time grows exponentially with the target divided by the smallest candidate · Space O(target / smallest candidate) for the recursion

TrapPassing i + 1 instead of i is the most common bug here. That version forbids reuse, so it solves a different problem (Combination Sum II). Read the statement for the word "any number of times".

Expression Add Operators (LeetCode 282)

Given a string num of digits and an integer target, insert the binary operators plus, minus, or multiply between the digits, and return every expression that evaluates to target. Numbers cannot have leading zeros, so "05" is not allowed, though "0" alone is. For example, num = "123" and target = 6 give "1+2+3" and "1*2*3". Multiplication binds tighter than addition, so "2+3*2" is 8, not 10.

How to think about it

  1. Understand. Between each pair of digits there are three choices (plus, minus, multiply) or none, so the search space grows very fast. The hard part is precedence: multiplication must be applied before addition, which a left-to-right evaluator would get wrong.
  2. Brute force. Try every way to split the digits into numbers and every operator between them, then evaluate each expression with proper precedence. That is correct but slow, and evaluation is awkward.
  3. Find the waste. We can evaluate while building the expression, so we never need to parse it again. The only problem is precedence, and it has a neat fix. Keep the value so far and the last operand. When we see multiplication, undo the last operand's addition and add the product instead.
  4. Optimise. Backtrack over split points. For the first number, start the value at that number. For each later number, try three operators. Plus adds the operand. Minus subtracts it, and remembers the operand as negative so that a later multiplication can undo it. Multiply replaces the last operand's contribution, computed as value minus last plus last times operand. Stop extending a token when it has a leading zero.
  5. Dry run for "105" with target 5. Start with token "1", value 1, last 1. Next token "0": plus gives value 1, last 0, while multiply gives value 1 minus 1 plus 0 equals 0, last 0. Then token "5" from "1*0" gives 0 plus 5 = 5, which matches, so "1*0+5" is recorded. Starting from the single token 10 gives value 10, and then minus 5 gives 5, which is recorded as "10-5".

Code

def add_operators(num, target):
    result = []

    def backtrack(index, expr, value, last):
        # value: the result of the expression so far
        # last: the most recent operand, so that * can undo its addition
        if index == len(num):
            if value == target:
                result.append(expr)
            return
        for end in range(index + 1, len(num) + 1):
            token = num[index:end]
            if len(token) > 1 and token[0] == "0":     # no leading zeros allowed
                break
            operand = int(token)
            if index == 0:
                backtrack(end, token, operand, operand)
            else:
                backtrack(end, expr + "+" + token, value + operand, operand)
                backtrack(end, expr + "-" + token, value - operand, -operand)
                backtrack(end, expr + "*" + token,
                          value - last + last * operand, last * operand)

    backtrack(0, "", 0, 0)
    return result

print(add_operators("123", 6))
print(add_operators("232", 8))
print(add_operators("105", 5))
['1+2+3', '1*2*3']
['2+3*2', '2*3+2']
['1*0+5', '10-5']

Time O(4 to the power n) in the worst case, with extra work per expression · Space O(n) for the recursion

Pattern to rememberWhen an expression must respect operator precedence while you build it left to right, keep the running value and the last operand. Multiplication can then correct the previous addition in constant time, and no parsing is needed.

Summary

Use this as a quick reference. Each line should be something you can say in one breath.

Concurrency
Structuring a program around tasks that are in progress together and may interleave.
Parallelism
Running tasks at the same instant on several processing units.
I/O-bound
Work that spends most of its time waiting for disks, networks or users.
CPU-bound
Work that spends most of its time computing.
Lock
A mutual exclusion primitive that lets one thread at a time into a critical section.
Reentrant lock
A lock that the owning thread may acquire again without deadlocking itself.
Read-write lock
A lock that allows many readers or one writer at a time.
Semaphore
A permit counter that limits how many threads may use a resource at once.
Bounded semaphore
A semaphore that refuses a release beyond its initial count.
Atomic operation
An operation that completes as one indivisible step.
Compare-and-swap
An atomic instruction that writes a new value only if the current value matches the expected one.
Condition variable
A wait queue that lets a thread sleep until another thread signals that a condition may have changed.
Blocking queue
A thread-safe queue whose put waits when full and whose get waits when empty.
Backpressure
Slowing producers down when a bounded queue is full, so consumers can catch up.
Sentinel
A special value that tells a consumer to stop.
Lock ordering
Acquiring several locks in one agreed global order, which prevents circular wait.
Livelock
Threads keep changing state in response to each other and make no progress.
Thread pool
A fixed set of worker threads that run tasks taken from a queue.
Future
A handle to a result that will be available later.
Async task
A coroutine that runs on an event loop and yields control at each await.
Event loop
The scheduler that runs ready async tasks on one thread.
Cooperative multitasking
Tasks switch only when they voluntarily yield, such as at an await.
GIL
The lock in CPython that lets only one thread run Python bytecode at a time.
Recursion
A function that calls itself on a smaller problem, with a base case that stops it.
Backtracking
A depth-first search that adds a choice, recurses, and removes the choice.
Pruning
Skipping branches of the search tree that cannot lead to a valid answer.
Memoization
Caching the result of a subproblem so it is computed only once.
