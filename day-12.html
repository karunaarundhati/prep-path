Paging, the page table and the TLB

Every program believes it owns a clean, private range of memory, usually starting at address 0. The physical RAM is shared by every running process and is not laid out that way. The operating system and the hardware bridge the gap by translating each logical address (the address the program uses) into a physical address (the real location in RAM). Paging is the most common way to do this translation.

With paging, the logical address space is cut into equal fixed-size blocks called pages, and physical memory is cut into blocks of the same size called frames. Typical sizes are 4 KB (4096 bytes). Any page can sit in any free frame, so the pages of one process do not need to be next to each other in RAM.

A logical address is split into two parts. The high part is the page number and the low part is the offset within the page. The offset is the same in the logical and physical address, because a page and its frame are the same size. Only the page number changes. The page table is a per-process table that maps each page number to a frame number.

Key ideaTranslation keeps the offset and swaps the page number for a frame number. physical = frame times page size, plus offset.

A worked example

Take a page size of 4096 bytes and a page table that says page 0 is in frame 5, page 1 is in frame 9, page 2 is in frame 3, and page 3 is in frame 7. To translate the logical address 8200, first find the page number and the offset. 8200 divided by 4096 is 2 with a remainder of 8, so the page is 2 and the offset is 8. Page 2 is in frame 3, so the physical address is 3 times 4096 plus 8, which is 12296. The program below does the same calculation, and it also shows what happens when the page is not in the table.

PAGE_SIZE = 4096
page_table = {0: 5, 1: 9, 2: 3, 3: 7}      # page number -> frame number

def translate(logical):
    page = logical // PAGE_SIZE            # which page
    offset = logical % PAGE_SIZE           # where inside the page
    if page not in page_table:
        return f"page fault: page {page} is not in memory"
    frame = page_table[page]
    physical = frame * PAGE_SIZE + offset  # frame base plus the same offset
    return f"logical {logical}: page {page}, offset {offset}, frame {frame}, physical {physical}"

print(translate(8200))
print(translate(4100))
print(translate(20000))
logical 8200: page 2, offset 8, frame 3, physical 12296
logical 4100: page 1, offset 4, frame 9, physical 36868
page fault: page 4 is not in memory

The third call uses address 20000. Its page is 4, because 4 times 4096 is 16384 and 20000 lies between 16384 and 20480. The page table has no entry for page 4, so the hardware raises a page fault, a trap to the operating system. The next unit explains what the OS does next.

Internal fragmentation

Fragmentation is memory that is allocated but cannot be used. With paging, the only waste is inside the last page of each process. Suppose a process needs 10,000 bytes. It needs three pages of 4096 bytes, which is 12,288 bytes. The last frame has 2,288 bytes that nobody can use. This waste is called internal fragmentation, because it is inside an allocated unit. On average each process wastes about half a page, which is the price paid for fixed-size frames.

The TLB: making translation fast

Paging has a cost. The page table itself lives in memory, so every translation would need one extra memory access before the real access. That would double the time for every read and write. The fix is the TLB, the translation lookaside buffer. It is a small, very fast cache of recent page-to-frame entries, built into the CPU. A TLB hit gives the frame at once. A TLB miss makes the hardware or OS walk the page table in memory, and then the new entry is loaded into the TLB, usually replacing an old one.

Programs tend to reuse the same pages for a while (this is called locality), so the hit ratio is usually high. We can measure the benefit with the effective access time (EAT), the average time per memory access. Assume a TLB lookup takes 20 ns, a memory access takes 100 ns, and the hit ratio is 0.80. A hit costs the TLB check plus one memory access, which is 20 plus 100, or 120 ns. A miss costs the TLB check, one access to read the page table, and one access for the data, which is 20 plus 100 plus 100, or 220 ns. The average is 0.80 times 120 plus 0.20 times 220, which is 96 plus 44, or 140 ns. Without the TLB every access would cost at least 200 ns.

Interviewers askWhat is the TLB, and why does it matter? It is a small hardware cache of page translations. Without it, every memory access would pay for a page table lookup in RAM. With a high hit ratio, the average translation cost stays close to the cost of one TLB check.

TrapThe TLB is per CPU and is flushed or tagged when the process changes. Address space switches therefore have a cost, which is one reason context switches are not free.

A page size is 4 KB and a process uses 9,000 bytes. How many bytes are wasted by internal fragmentation?

9,000 bytes need three pages, because two pages give only 8,192 bytes. Three pages hold 12,288 bytes, so 3,288 bytes are wasted in the last page. The waste is always less than one page per allocation.

Segmentation and external fragmentation

Segmentation divides a process's address space into logical pieces called segments: the code, the global data, the stack, the heap, and so on. Each segment has its own length, which may differ from the others. A logical address is a pair: a segment number and an offset within that segment.

The segment table holds, for each segment, a base (the physical start address) and a limit (the length). Translation has two steps. First, check that the offset is less than the limit. If it is not, the hardware traps, because the program has referred outside its segment. Second, add the offset to the base. Segment protection is a major benefit: each segment can be marked read-only or executable, and the hardware enforces it.

The program below uses a small segment table in the style of the textbook examples. Segment 2 starts at physical address 4300 and has length 400, so offset 53 maps to 4353. Segment 1 has length 400, so offset 500 is out of range.

SEGMENT_TABLE = {0: (1400, 1000), 1: (6300, 400), 2: (4300, 400), 3: (3200, 1100)}   # segment -> (base, limit)

def translate(segment, offset):
    base, limit = SEGMENT_TABLE[segment]
    if offset >= limit:                     # outside the segment: the hardware traps
        return f"trap: offset {offset} is beyond the limit {limit}"
    return base + offset                   # physical address

print(translate(2, 53))
print(translate(1, 500))
4353
trap: offset 500 is beyond the limit 400

External fragmentation

Segments have different lengths, so they must be placed in free memory of matching size. Over time, allocating and freeing segments leaves many small gaps between live segments. The total free memory may be large, yet no single gap is big enough for a new segment. This is external fragmentation, because the waste lies outside every allocated unit.

Allocators choose gaps with a policy. First fit takes the first gap that is big enough, and it is fast. Best fit takes the smallest gap that is big enough, which leaves small remnants that are hard to use. Worst fit takes the largest gap, which leaves larger remnants. None of them eliminates the problem. The classic cure is compaction, which slides live segments together to merge the gaps, but it costs time and needs relocation support.

Modern systems usually combine the two ideas, or use paging alone with protection bits per page. Mention this in an interview, because it shows you know the trade-off is about where the waste lands.

Why does paging avoid external fragmentation, while segmentation does not?

Every frame is the same size, so any free frame fits any page. The free frames never need to be contiguous for one allocation. Segments have variable sizes, so the free gaps may be too small for a new segment even when the total free memory is large.

Virtual memory and demand paging

Virtual memory lets a process use more address space than the physical RAM installed, and lets the OS keep only the pages that are actively used in memory. The rest live on disk, in a swap area or in the program's own file. The program does not know; it just uses addresses.

The usual technique is demand paging: a page is loaded only when a program first touches it. Each page-table entry has a valid bit. If the bit says the page is in memory, the translation proceeds normally. If not, the access causes a page fault. The hardware raises a trap, and the OS handles it with these steps:

  1. The trap enters the kernel and the OS checks whether the address is legal. An address outside the process's regions is a real error, and the process gets a segmentation fault.
  2. If the address is legal, the OS finds a free frame. If none is free, it picks a victim page using a page replacement algorithm. If the victim was modified, it is written to disk first. A dirty bit records whether a page has changed since it was loaded, so clean pages can be dropped without writing.
  3. The OS schedules a disk read to bring the needed page into the frame. The process sleeps during the read, and the CPU runs other processes.
  4. When the read completes, the OS updates the page table and sets the valid bit.
  5. The faulting instruction is restarted, and this time the translation succeeds.

Key ideaA page fault is not an error in the normal case. It is how the OS loads a page on demand, and it is expensive only because the disk is slow.

How much do faults cost?

Let p be the probability that an access causes a fault. The effective access time is the normal access time times (1 minus p), plus the fault service time times p. Suppose a normal memory access takes 200 ns and a page fault takes 8 ms, which is 8,000,000 ns. If one access in a thousand faults, p is 0.001, and the average is 0.999 times 200 plus 0.001 times 8,000,000, which is 199.8 plus 8000, about 8200 ns. One fault in a thousand accesses makes memory about 41 times slower. That is why the OS works hard to keep the fault rate tiny.

Copy-on-write

Creating a process with fork in Unix-like systems would be slow if every page were copied at once. Modern systems use copy-on-write: parent and child share the same frames, marked read-only. Only when one of them writes does the OS copy that single page. Most forked processes call exec soon after, so most copies never happen.

Why is a page fault for a page that is stored on disk much more costly than a TLB miss?

A TLB miss reads the page table in RAM, which takes about one memory access, around 100 ns in the example. A page fault waits for a disk read, which takes milliseconds, roughly tens of thousands of times longer. The disk is the bottleneck.

Page replacement, fault counts and thrashing

When a page fault occurs and no frame is free, the OS must evict a page. The choice is made by a page replacement algorithm, and good choices reduce faults. Three algorithms are the standard reference:

  • FIFO. Evict the page that was loaded earliest. It is simple, but it ignores how often a page is used, so it may evict a busy page.
  • LRU (least recently used). Evict the page that has gone unused for the longest time. It matches the locality of real programs well, but exact LRU needs bookkeeping on every access, which is expensive, so real systems approximate it.
  • Optimal (OPT). Evict the page whose next use is farthest in the future. It gives the fewest possible faults, but it needs knowledge of the future, so it cannot be built into a real OS. It serves as a benchmark: no algorithm can beat it.

To compare the algorithms, we use a reference string, the sequence of page numbers a program touches, and count the faults for a given number of frames. Consider this string with 3 frames: 1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5. The table traces FIFO. A fault happens when the page is not in memory, and the page list shows the frames in the order they were loaded.

def fifo(refs, frames):
    memory, faults = [], 0
    for page in refs:
        if page in memory:
            continue                        # a hit changes nothing for FIFO
        faults += 1
        if len(memory) == frames:
            memory.pop(0)                   # evict the page that arrived first
        memory.append(page)
    return faults

def lru(refs, frames):
    memory, faults = [], 0                  # front of the list = least recently used
    for page in refs:
        if page in memory:
            memory.remove(page)             # a hit makes this page the most recent
            memory.append(page)
            continue
        faults += 1
        if len(memory) == frames:
            memory.pop(0)                   # evict the least recently used page
        memory.append(page)
    return faults

def optimal(refs, frames):
    memory, faults = [], 0
    for i, page in enumerate(refs):
        if page in memory:
            continue
        faults += 1
        if len(memory) == frames:
            future = refs[i + 1:]
            def next_use(p):
                # distance to the next use of p, or infinity if it is never used again
                return future.index(p) if p in future else float("inf")
            memory.remove(max(memory, key=next_use))   # evict the farthest next use
        memory.append(page)
    return faults

belady = [1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5]
for frames in (3, 4):
    print(frames, "frames: FIFO", fifo(belady, frames), "LRU", lru(belady, frames), "OPT", optimal(belady, frames))
3 frames: FIFO 9 LRU 10 OPT 7
4 frames: FIFO 10 LRU 8 OPT 6

Read the results carefully. With 3 frames, the order of quality is OPT (7 faults), then FIFO (9), then LRU (10). OPT is the best, as expected. Here FIFO beats LRU, which shows that "LRU is always best" is false. Both numbers depend on this particular string.

With 4 frames, FIFO gets worse: 10 faults instead of 9. Adding memory made FIFO slower on this string. This is Belady's anomaly, named after the researcher who found it. LRU and OPT never suffer from it, because they keep a stack property: the pages held with n frames are always a subset of the pages held with n plus 1 frames. FIFO does not have this property.

TrapCounting faults by eye is error-prone. Count the misses for each algorithm separately, and remember that a hit does not change FIFO's queue, but it does change LRU's recency order.

Thrashing and the working set

Thrashing is the collapse that happens when a system spends most of its time moving pages in and out of memory and very little time running the program. It starts when the processes together need more frames than memory holds. Each process faults, waits for the disk, and the OS responds by swapping more processes out and in. The CPU sits idle, the load average climbs, and throughput falls sharply.

The working set of a process is the set of pages it has referenced in a recent window of time. If each process keeps its working set in memory, faults are rare. The OS can estimate working sets, or watch the page-fault frequency: give a process more frames when its fault rate is high, and take frames away when it is low. When the total demand is too high, the OS lowers the degree of multiprogramming, meaning fewer processes run, so the rest can work efficiently.

Interviewers askHow do you fix thrashing? Reduce the number of active processes, add memory, or make each process use fewer pages at a time. Explain that adding CPU does not help, because the CPU is already waiting on the disk.

With 3 frames and the reference string 7, 0, 1, 2, 0, 3, 0, 4, which page does LRU evict when page 3 is requested?

Trace the frames: after 7, 0, 1 the memory holds 7, 0, 1. Page 2 evicts 7 (least recently used), so memory is 0, 1, 2. Page 0 is a hit and becomes most recent, so the order is 1, 2, 0. Page 3 is a fault, and LRU evicts 1, the least recently used page.

File systems and RAID

A file system turns a raw disk, which is just numbered blocks, into named files and directories. Each file has metadata (size, owner, permissions and timestamps) and a list of the disk blocks that hold its data. In Unix-like systems the metadata lives in an inode, identified by an inode number. A directory is a special file that maps names to inode numbers. Two names that point to the same inode are hard links, and deleting one name does not delete the file until the last link goes.

How the blocks are allocated

  • Contiguous. The file occupies consecutive blocks. Reading is fast, but the file is hard to grow, and free space fragments just as memory does.
  • Linked. Each block holds a pointer to the next. Growing is easy, but random access requires walking the chain, and losing one pointer can lose the rest of the file.
  • Indexed. An index block lists the data blocks. Unix inodes use direct pointers for the first blocks, and indirect pointers that point to blocks of pointers for large files. Modern systems such as ext4 use extents, which describe runs of contiguous blocks compactly.

The FAT family keeps a table of links in one place, so the chain can be followed without reading the data blocks. This is simple and was widely used on removable media.

Crashes are a central concern. A write can be interrupted halfway, leaving a directory that points to a half-written inode. Journaling solves this by writing the intended changes to a journal first, then applying them. After a crash, the file system replays or discards the journal entries, so it returns to a consistent state. Tools such as fsck check and repair file systems.

RAID

RAID (originally Redundant Array of Inexpensive Disks, now often called Independent) combines several disks into one logical device. It serves two goals: speed, by spreading data across disks so they work in parallel, and reliability, by storing redundant information so a failed disk does not lose data. RAID is not a backup. It protects against hardware failure, not against deleted files, bugs, or ransomware.

LevelHow it worksUsable capacity (N disks)Survives one disk failure
RAID 0Striping: data split across disks, no redundancyN disksNo
RAID 1Mirroring: each block written to two disksN divided by 2 (for a mirror pair)Yes

RAID 6Striping with two parity blocks per stripeN minus 2Yes, and two failures too (needs at least 4 disks)
RAID 10Mirrored pairs, then striped across the pairsN divided by 2Yes, one per mirror pair

Parity works with the XOR operation. The parity block is the XOR of the data blocks in its stripe. If one disk is lost, its block equals the XOR of all the surviving blocks in that stripe. RAID 5 and RAID 6 spread the parity across all disks so no single disk is a bottleneck for writes. Writes are slower than reads in these levels because parity must be updated.

Five disks are arranged as RAID 5. How many disks' worth of capacity is usable, and how many can fail?

RAID 5 uses one disk's worth of space for parity, so 4 disks of 5 are usable. One disk can fail, and the data is rebuilt from the surviving disks. A second failure before the rebuild finishes loses data.

Disk scheduling: FCFS, SSTF, SCAN and C-SCAN

A hard disk has a spinning platter and a moving arm with a head. To read a block, the head must first move to the right track, called a cylinder. This movement, the seek time, is usually the largest part of the delay. After the seek, the disk must wait for the sector to rotate under the head (rotational latency), and then transfer the data. The disk scheduler chooses the order in which pending requests are served to reduce seek time.

Assume a disk with cylinders numbered 0 to 199. The head starts at cylinder 53, and the queue of pending requests, in arrival order, is 98, 183, 37, 122, 14, 124, 65, 67. The measure of quality is the total head movement: the number of cylinders the head crosses in total.

  • FCFS (first come, first served). Serve requests in arrival order. It is fair and simple, but the head jumps back and forth across the disk.
  • SSTF (shortest seek time first). Always serve the pending request nearest to the current head position. It moves the head much less, but a request far from the current area can be postponed indefinitely (starvation).
  • SCAN (the elevator algorithm). The head sweeps in one direction to the end of the disk, serving requests on the way, then reverses. Requests at the edges wait a long time after a sweep passes, but no request waits forever.
  • C-SCAN (circular SCAN). The head sweeps in one direction only. At the end it jumps back to the start without serving requests, then sweeps again. Waiting times are more uniform than with SCAN.

The program below computes the order and total movement for each policy on this queue. It makes one convention explicit. SCAN is assumed to sweep up to cylinder 199 before reversing, even though there is no request there. C-SCAN counts its return jump from 199 to 0 as head movement, so the total includes that jump. Many textbooks use the same convention, and you should always state yours in an interview.

HEAD = 53
REQUESTS = [98, 183, 37, 122, 14, 124, 65, 67]
END = 199                                     # the last cylinder; cylinders run 0 to 199

def fcfs(head, reqs):
    order, cur, moved = [], head, 0
    for r in reqs:
        moved += abs(r - cur)                 # distance crossed for this request
        cur = r
        order.append(r)
    return order, moved

def sstf(head, reqs):
    pending, order, cur, moved = list(reqs), [], head, 0
    while pending:
        nxt = min(pending, key=lambda r: abs(r - cur))   # nearest request first
        moved += abs(nxt - cur)
        cur = nxt
        order.append(nxt)
        pending.remove(nxt)
    return order, moved

def scan(head, reqs):
    up = sorted(r for r in reqs if r >= head)                     # served on the way up
    down = sorted((r for r in reqs if r < head), reverse=True)    # served on the way back
    lowest = down[-1] if down else head
    moved = (END - head) + (END - lowest)     # up to the end, then back down to the lowest
    return up + down, moved

def c_scan(head, reqs):
    up = sorted(r for r in reqs if r >= head)
    low = sorted(r for r in reqs if r < head)                     # served after the jump
    moved = (END - head) + END + (low[-1] if low else 0)    # up, jump 199 to 0, then up again
    return up + low, moved

for name, (order, moved) in [("FCFS", fcfs(HEAD, REQUESTS)),
                             ("SSTF", sstf(HEAD, REQUESTS)),
                             ("SCAN", scan(HEAD, REQUESTS)),
                             ("C-SCAN", c_scan(HEAD, REQUESTS))]:
    print(name, "order", order, "movement", moved)
FCFS order [98, 183, 37, 122, 14, 124, 65, 67] movement 640
SSTF order [65, 67, 37, 14, 98, 122, 124, 183] movement 236
SCAN order [65, 67, 98, 122, 124, 183, 37, 14] movement 331
C-SCAN order [65, 67, 98, 122, 124, 183, 14, 37] movement 382

Trace FCFS by hand to be sure you understand it. The head goes 53 to 98 (45 cylinders), then to 183 (85), then back to 37 (146), then to 122 (85), to 14 (108), to 124 (110), to 65 (59), and finally to 67 (2). Add them: 45 plus 85 plus 146 plus 85 plus 108 plus 110 plus 59 plus 2 is 640.

SSTF is much shorter. From 53 the nearest request is 65 (12 away), then 67 (2), then 37 (30), then 14 (23), then 98 (84), then 122 (24), then 124 (2), then 183 (59). The total is 236. The price is that the far requests at 183 are served last, after the head has been in the middle of the disk for a long time.

SCAN moves up from 53 to the end at 199, which is 146 cylinders. It serves 65, 67, 98, 122, 124 and 183 on the way up, then reverses and travels from 199 down to 14, which is 185 cylinders, and serves 37 and 14 on the way back. The total is 146 plus 185, or 331. C-SCAN also travels up to 199 (146), jumps back to 0 (199), and then climbs from 0 to 37 (37), serving 14 and 37 on that final climb. The total is 146 plus 199 plus 37, or 382. C-SCAN costs more movement than SCAN here, but it makes the wait for each request more even, because the head never reverses across the middle of the disk.

Key ideaSSTF minimizes movement at the risk of starvation. SCAN and C-SCAN trade some movement for fairness. FCFS is fair but wasteful.

Why can SSTF starve a request, and how does SCAN avoid that?

SSTF always picks the nearest request. If new requests keep arriving near the head, a request far away is never the nearest, so it waits forever. SCAN sweeps across the whole disk, so every request is reached within one sweep, which bounds the wait.

Linux commands for memory and storage

Interviewers like to ask what you would run to investigate a slow machine. The commands below read the kernel's counters. None of them change the system, so they are safe to run. Commands that print samples over time, such as vmstat 1 5, stop after the count you give.

free -h                      # memory and swap in human units (see "available")
cat /proc/meminfo            # every memory counter the kernel tracks
vmstat 1 5                   # five samples, one per second; si and so are swap in and out
swapon --show               # swap devices and how full each one is
sysctl vm.swappiness         # how eagerly the kernel swaps; the usual default is 60
lsblk                        # block devices and partitions as a tree
findmnt                      # mounted file systems as a tree
df -h                        # free space on each file system
du -sh /var/log              # total size of one directory
ls -li notes.txt             # -i adds the inode number of each file
stat notes.txt               # inode, size, blocks and timestamps of one file
ps -eo pid,stat,comm         # process ID, state (D = waiting on I/O, Z = zombie), name
pmap -x 1234                 # memory map of process 1234 (replace 1234 with a real PID)
iostat -x 1 3                # per-disk utilization and wait times (needs the sysstat package)
ulimit -a                    # per-process resource limits for this shell

Read the output of free with care. The Linux kernel uses spare RAM as a page cache, so "free" memory is often small even on a healthy machine. The useful number is available, which estimates how much memory could be given to new programs without swapping. MemAvailable in /proc/meminfo is the same estimate.

In vmstat, the si and so columns show pages swapped in and out per second. Sustained nonzero values with a high wa (CPU time waiting on I/O) suggest memory pressure or thrashing. In ps, a state of D means a process is in uninterruptible sleep, usually waiting on disk, and a state of Z means a zombie: a finished process whose parent has not yet collected its exit status.

TipWhen someone reports that a server is slow, check in this order: memory (free, vmstat), disk (iostat, df), then the busiest processes (ps). This order narrows the problem quickly.

Why does free often show little free memory on a healthy Linux machine?

The kernel uses otherwise unused RAM as a page cache for files, so that disk reads are fast. That memory is reclaimable when a program needs it. The "available" column counts this reclaimable cache, so it shows how much new programs could get without swapping.

Interview questions

Answer each question out loud before opening the answer. Strong answers name the trade-off and one concrete number.

What is the difference between internal and external fragmentation?

Internal fragmentation is waste inside an allocated unit, such as the unused part of the last page. External fragmentation is free memory split into gaps too small to be used, between allocated units. Paging causes internal fragmentation, and variable-size segments cause external fragmentation.

What does the TLB do, and what happens on a miss?

The TLB caches recent page-to-frame translations in fast hardware. On a hit, the frame is known immediately. On a miss, the page table in memory is read, and the entry is loaded into the TLB for future use.

List the steps of handling a page fault.

Trap to the kernel, check the address is legal, find a free frame or evict a victim (writing it out if dirty), read the needed page from disk, update the page table and valid bit, and restart the faulting instruction.

Which page replacement algorithm gives the fewest faults, and can a real OS use it?

Optimal replacement gives the fewest faults, because it evicts the page whose next use is farthest away. A real OS cannot use it, since it needs to know future accesses. It is used as a benchmark for other algorithms.

What is Belady's anomaly?

It is the effect where adding frames increases the number of page faults. FIFO can show it, as the 3-frame and 4-frame results for the string 1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5 show (9 faults versus 10). LRU and OPT do not suffer from it.

What is thrashing, and how is it fixed?

Thrashing is when processes together need more frames than memory holds, so the system spends most of its time paging and little time computing. It is fixed by reducing the number of active processes, giving each one its working set, or adding memory.

What is the difference between a hard link and a symbolic link, at a high level?

A hard link is another directory entry pointing to the same inode, so both names are equal and the data is freed only after the last link is removed. A symbolic link is a small file that stores a path to another name, and it can dangle if the target is removed.

Why does RAID 5 need at least three disks, and what does its parity let it do?

A RAID 5 stripe needs at least two data blocks plus one parity block, and the parity must sit on a different disk from its data, so the array needs three disks to be a real distributed-parity layout. With parity, any single lost block equals the XOR of the others in its stripe, so one disk can fail without losing data.

Which disk scheduling policy minimizes total head movement, and what is its drawback?

SSTF minimizes movement in simple cases by always serving the nearest request. Its drawback is starvation: requests far from the head can wait indefinitely while nearby requests keep arriving.

Why does SCAN have a more uniform wait time than SSTF?

SCAN sweeps the whole disk in each pass, so every pending request is reached within one sweep. SSTF can keep serving one busy area and postpone far requests indefinitely, which gives a much wider spread of waits.

DSA: binary search

Binary search finds a value in a sorted array in O(log n) time by discarding half of the remaining range at every step. For an array of one million items, about 20 comparisons are enough, because 2 to the power 20 is about one million.

The pattern is wider than sorted arrays. Binary search works on any monotonic question: a yes-or-no test whose answer changes only once as the input grows, such as "is speed k fast enough?" The key is to keep an invariant that the answer always lies inside a range [left, right], and to shrink that range each step.

Most bugs come from the loop boundaries. The version used below is the most reliable template. Use while left <= right when you search for an exact value. Compute the middle with left + (right - left) // 2, which avoids overflow in languages with fixed-size integers. After comparing, move the boundary past the middle (mid + 1 or mid - 1), so the range always shrinks and the loop always ends. A common bug is setting left = mid, which can loop forever when the range has two items.

Key ideaEach step must shrink the range, and the boundary must move past mid. If you cannot say what the invariant is, your loop boundaries are probably wrong.

Binary Search (LeetCode 704)

Given a sorted array of distinct integers nums and a target, return the index of target, or -1 if it is not present. You must run in O(log n) time. For example, nums = [-1, 0, 3, 5, 9, 12] and target = 9 gives 4, and target = 2 gives -1.

How to think about it

  1. Understand. The array is sorted and has distinct values, so there is at most one answer. The time bound rules out a linear scan.
  2. Brute force. Loop through the array and compare each value with the target. That is O(n).
  3. Find the waste. Comparing with the middle tells us which half can contain the target, so the other half can be discarded without looking at it.
  4. Optimise. Keep left and right bounds. Look at the middle. If it equals the target, return its index. If the middle is smaller, the target must be to the right. If larger, it must be to the left. Stop when the bounds cross.
  5. Dry run for target 9. left = 0, right = 5, mid = 2, value 3, which is smaller than 9, so left becomes 3. Now mid = (3 + 5) // 2 = 4, value 9, which matches. Return 4.

Code

def search(nums, target):
    left, right = 0, len(nums) - 1
    while left <= right:
        mid = left + (right - left) // 2     # safe form of (left + right) // 2
        if nums[mid] == target:
            return mid
        if nums[mid] < target:
            left = mid + 1                   # the target can only be to the right
        else:
            right = mid - 1                  # the target can only be to the left
    return -1

print(search([-1, 0, 3, 5, 9, 12], 9))
print(search([-1, 0, 3, 5, 9, 12], 2))
4
-1

Time O(log n) · Space O(1)

Pattern to rememberIn a sorted array, compare with the middle and discard the half that cannot contain the answer. Always move the boundary past mid.

Search in Rotated Sorted Array (LeetCode 33)

An ascending array of distinct integers has been rotated at an unknown pivot, so [0, 1, 2, 4, 5, 6, 7] might become [4, 5, 6, 7, 0, 1, 2]. Given such an array and a target, return its index or -1, in O(log n) time. For example, [4, 5, 6, 7, 0, 1, 2] with target 0 gives 4, and with target 3 gives -1.

How to think about it

  1. Understand. The array is no longer fully sorted, but it is made of two sorted pieces. At any split point, at least one of the two halves is sorted.
  2. Brute force. Scan the array for the target, which is O(n).
  3. Find the waste. If we know which half is sorted, we can check whether the target lies inside that sorted half by comparing with its ends. If it does, search there. If not, it must be in the other half.
  4. Optimise. At each middle, test whether the left half is sorted by comparing nums[left] with nums[mid]. If it is sorted and the target is within its range, move right to mid minus 1. If it is sorted and the target is not in range, move to mid plus 1. If the right half is sorted, do the mirror-image test.
  5. Dry run for target 0. left = 0, right = 6, mid = 3 (value 7). The left half [4, 5, 6, 7] is sorted, and 0 is not in [4, 7], so left becomes 4. Now mid = 5 (value 1). The left half [0, 1] is sorted, and 0 lies in [0, 1), so right becomes 4. Now mid = 4 holds 0, so return 4.

Code

def search_rotated(nums, target):
    left, right = 0, len(nums) - 1
    while left <= right:
        mid = (left + right) // 2
        if nums[mid] == target:
            return mid
        if nums[left] <= nums[mid]:                       # the left half is sorted
            if nums[left] <= target < nums[mid]:           # target lies in that sorted half
                right = mid - 1
            else:
                left = mid + 1
        else:                                             # the right half is sorted
            if nums[mid] < target <= nums[right]:          # target lies in that sorted half
                left = mid + 1
            else:
                right = mid - 1
    return -1

print(search_rotated([4, 5, 6, 7, 0, 1, 2], 0))
print(search_rotated([4, 5, 6, 7, 0, 1, 2], 3))
print(search_rotated([1], 0))
4
-1
-1

Time O(log n) · Space O(1)

TrapUsing nums[left] < nums[mid] instead of <= fails when left equals mid, which happens when the range has one or two items. The equality matters.

Pattern to rememberWhen the array is sorted in pieces, first find which half is sorted, then test whether the target falls inside that sorted half.

Koko Eating Bananas (LeetCode 875)

Koko has piles of bananas and h hours. She eats at a speed of k bananas per hour, and in each hour she eats from one pile only. If a pile has fewer than k bananas, she finishes it in that hour and does not eat more. Return the minimum integer k that lets her finish within h hours. For example, piles = [3, 6, 7, 11] and h = 8 give 4.

How to think about it

  1. Understand. The answer is a speed, not an index in an array. Speeds are integers from 1 up to the largest pile.
  2. Brute force. Try k = 1, 2, 3 and so on, and stop at the first speed that works. That can take up to the size of the largest pile steps, each costing a pass over the piles.
  3. Find the structure. If speed k finishes in time, any faster speed also does. So the set of working speeds is a range that starts at some minimum and goes to infinity. We need the first value in that range, which is a monotonic yes-or-no question.
  4. Optimise. Binary search on the speed. For a candidate k, compute the hours needed: each pile of p bananas takes ceil(p / k) hours. If the total is at most h, k works, and we look for something smaller. If not, we need something faster.
  5. Dry run for piles [3, 6, 7, 11] and h = 8. The search range is 1 to 11. Try mid = 6: hours are 1 + 1 + 2 + 2 = 6, which fits, so right = 6. Try mid = 3: hours are 1 + 2 + 3 + 4 = 10, too many, so left = 4. Try mid = 5: hours are 1 + 2 + 2 + 3 = 8, which fits, so right = 5. Try mid = 4: hours are 8, which fits, so right = 4. Now left equals right, and the answer is 4.

Code

import math

def min_eating_speed(piles, h):
    def can_finish(k):
        hours = 0
        for p in piles:
            hours += math.ceil(p / k)     # a partial hour still counts as a full hour
        return hours <= h

    left, right = 1, max(piles)           # the answer is between 1 and the largest pile
    while left < right:
        mid = (left + right) // 2
        if can_finish(mid):
            right = mid                   # mid works, so look for something smaller
        else:
            left = mid + 1                # mid is too slow, so go faster
    return left

print(min_eating_speed([3, 6, 7, 11], 8))
print(min_eating_speed([30, 11, 23, 4, 20], 5))
print(min_eating_speed([30, 11, 23, 4, 20], 6))
4
30
23

Time O(n log m), where m is the largest pile · Space O(1)

Pattern to rememberWhen you need the smallest value that satisfies a monotonic test, binary search on the answer itself. The search range is the set of possible answers, not an array.

Median of Two Sorted Arrays (LeetCode 4)

Given two sorted arrays a and b of sizes m and n, return the median of the combined elements. The overall run time must be O(log(m + n)). For example, a = [1, 3] and b = [2] give 2.0, and a = [1, 2] and b = [3, 4] give 2.5.

How to think about it

  1. Understand. The median splits the combined data into two halves of equal size (or differing by one). Everything in the left half is at most everything in the right half. We never need to merge the arrays.
  2. Brute force. Merge the two sorted arrays and pick the middle. That is O(m + n), which is too slow for the required bound.
  3. Find the waste. We only need to find the split point. If we take i elements from a for the left half, the number of elements taken from b is fixed, because the left half has a known size. So the whole problem is to find one number i.
  4. Optimise. Binary search on i, which ranges from 0 to m. For each i, the left half holds a[0 to i-1] and b[0 to j-1], where j is the leftover needed. The split is correct when the largest value on the left is at most the smallest value on the right, for both arrays. If a's left boundary is too big, move i left. If it is too small, move i right. Use plus and minus infinity to handle empty sides.
  5. Dry run for a = [1, 3] and b = [2]. Swap so that a is the shorter array: a = [2], b = [1, 3]. The total is 3, so the left half has 2 elements. Try i = 0: the left side of a is empty, and the right side of b starts at 3, but b's left value 3 is larger than a's right value 2, so i must increase. Try i = 1: a's left value is 2, and b takes j = 1 element, value 1. Both left values are at most both right values, and the total is odd, so the answer is the largest left value, max(2, 1), which is 2.0.

Code

def find_median_sorted_arrays(a, b):
    if len(a) > len(b):
        a, b = b, a                              # binary search the shorter array
    m, n = len(a), len(b)
    left_size = (m + n + 1) // 2                 # how many elements belong to the left half
    lo, hi = 0, m
    while lo <= hi:
        i = (lo + hi) // 2                       # elements taken from a for the left half
        j = left_size - i                        # elements taken from b for the left half
        a_left = a[i - 1] if i > 0 else float("-inf")
        a_right = a[i] if i < m else float("inf")
        b_left = b[j - 1] if j > 0 else float("-inf")
        b_right = b[j] if j < n else float("inf")
        if a_left <= b_right and b_left <= a_right:    # a valid split was found
            if (m + n) % 2 == 1:
                return float(max(a_left, b_left))
            return (max(a_left, b_left) + min(a_right, b_right)) / 2
        if a_left > b_right:
            hi = i - 1                           # too many from a, move left
        else:
            lo = i + 1                           # too few from a, move right

print(find_median_sorted_arrays([1, 3], [2]))
print(find_median_sorted_arrays([1, 2], [3, 4]))
2.0
2.5

Time O(log(min(m, n))) · Space O(1)

TrapSearching the longer array, or merging the arrays first, loses the required time bound. Also forget the sentinel values (infinity) at the edges, and the code indexes out of range on empty halves.

Pattern to rememberTo split two sorted arrays into equal halves, binary search for the cut in the shorter array. The other cut follows from the total size.

Summary

Use this as a quick reference before the interview. Each line should be something you can say in one breath.

Logical address
The address a program uses, translated by the hardware to a physical address.
Page and frame
Equal-sized blocks of the logical address space (pages) and of physical RAM (frames).
Page table
A per-process table that maps each page number to a frame number.
Offset
The position inside a page or segment, which stays the same after translation.
Internal fragmentation
Waste inside an allocated unit, such as the unused end of the last page.
External fragmentation
Free memory split into gaps too small to use, between allocated units.
Segment table
A table of base and limit pairs, one per segment, used to check offsets and translate them.
TLB
A small hardware cache of recent page translations that avoids most page table lookups.
Effective access time
The average memory access time, weighted by hit and miss ratios or fault probability.
Virtual memory
Address space larger than RAM, with pages loaded from disk on demand.
Demand paging
Loading a page only when a program first touches it.
Valid bit and dirty bit
The valid bit says a page is in memory. The dirty bit says it was modified and must be written before eviction.
Page fault
A trap raised when a referenced page is not in memory, handled by the OS.
Copy-on-write
Sharing pages after fork until one process writes, then copying only that page.
FIFO, LRU, Optimal
Replacement policies that evict the oldest, least recently used, or farthest-needed page.
Belady's anomaly
More frames causing more faults, which FIFO can show but LRU and OPT never do.
Thrashing
A state where processes need more frames than memory holds, so the system mostly pages.
Working set
The pages a process has used recently, which should stay in memory.
Inode
The Unix structure holding a file's metadata and the locations of its data blocks.
Journaling
Recording intended changes before applying them, so a crash can be recovered cleanly.
RAID 0, 1, 5, 6, 10
Striping, mirroring, striping with parity, double parity, and mirrored stripes.
Parity
The XOR of the data blocks in a stripe, which rebuilds one lost block.
Seek time and rotational latency
Time to move the head to a cylinder, and time to wait for the sector to rotate under it.
FCFS, SSTF, SCAN, C-SCAN
Disk policies: arrival order, nearest request, elevator sweep, and one-way sweep with a jump back.
Binary search
Repeatedly halving a range that is known to contain the answer, in O(log n) steps.
Binary search on the answer
Searching a range of possible answers using a monotonic yes-or-no test.
