Data warehouse modelling: schema types

A data warehouse stores years of history so that managers can ask big questions, such as which product sold best in which region. This topic explains how a warehouse differs from an ordinary database, how its tables are arranged as star, snowflake or fact constellation schemas, and the OLAP operations used to explore the data.

The idea in plain words

Think of a shop with two kinds of records. The till records each sale as it happens: "one phone, Pune, paid 500". That is the daily work of the shop. The owner also wants to know, "which city bought the most phones over the last three years?" That question needs millions of old sales added together, and it should not slow down the till.

A data warehouse is a separate store built for questions like the owner's. It collects data from many operational systems, cleans it, and keeps history. A normal database is built for the till: it records and changes single transactions quickly. The two jobs need different designs.

GATE Data Science and AI (paper DA) asks conceptual questions on this topic. Typical questions ask you to:

  • tell an OLTP system from an OLAP system,
  • identify a star, snowflake or fact constellation from a diagram or a description,
  • name the OLAP operation that changes a view in a given way, and
  • count rows or columns in a fact or dimension table for a small example.

We will use one running example. A company sells products in several cities. Each sale is recorded with a time, a product, a location, the units sold and the dollars earned.

Key ideaA data warehouse is designed for reading large amounts of history quickly. An operational database is designed for writing and changing small amounts of current data quickly.

Key terms

Data warehouse
A subject-oriented, integrated, time-variant and non-volatile collection of data for analysis. Plain meaning: a store of history built for questions.
OLTP
Online transaction processing. Plain meaning: the everyday systems that record each transaction. Short, frequent reads and writes of current data.
OLAP
Online analytical processing. Plain meaning: systems that answer analysis questions over large history. Few writes, large reads, often summarized.
Fact table
A central table that stores the measurements of events, such as sales. Plain meaning: one row per event, with numbers to add up.
Dimension table
A table that describes the context of a fact, such as product, time or location. Plain meaning: the who, what, when and where.
Measure
A numeric value stored in a fact table, such as units sold or dollars. Plain meaning: a number you add up or average.
Dimension attribute
A column of a dimension table, such as city or category.
Surrogate key
An artificial key, usually an integer, used as the primary key of a dimension table. Plain meaning: a simple id made for the warehouse.
Star schema
One fact table joined directly to several dimension tables, each stored in one flat table. Plain meaning: a star shape with the fact table in the middle.
Snowflake schema
A star schema where dimension tables are normalized into several linked tables. Plain meaning: the star's points split into smaller branches.
Fact constellation
A schema with more than one fact table that shares some dimension tables. Plain meaning: several stars that share some points.
Data cube
A multidimensional view of measures indexed by dimension values. Plain meaning: a block of numbers you can slice in several directions.
Concept hierarchy
An ordering of attribute values from detailed to general, such as city, state, country.
Roll-up
Moving up a concept hierarchy, or removing a dimension, to see coarser totals.
Drill-down
Moving down a concept hierarchy to see finer detail. The opposite of roll-up.
Slice
Fixing one dimension to a single value, which reduces the cube by one dimension.
Dice
Selecting a range or set of values on two or more dimensions to form a smaller sub-cube.
Pivot
Rotating the cube so that different dimensions appear as rows and columns. Also called rotate.

Concept 1: Data warehouse versus database, OLTP and OLAP

Two kinds of work

Operational systems do the daily work of an organization. They are called OLTP systems. Each transaction is small: create an order, update a balance, cancel a booking. Many users work at once, so each transaction must be fast and must not disturb the others.

Analytical systems answer questions over large history. They are called OLAP systems, and a data warehouse is their usual home. A typical analyst query reads millions of rows and summarizes them, for example "total dollars per city per quarter".

The differences

FeatureOLTP (operational database)OLAP (data warehouse)
Main purposeRun daily transactionsSupport analysis and decisions
Typical operationInsert, update, delete a few rowsRead and summarize many rows
DataCurrent, detailedHistory, summarized where useful
DesignNormalized, to avoid redundancyDenormalized, for fast reading
Update frequencyContinuousPeriodic loads
Query speed priorityShort transactionsLarge scans and aggregates

The four properties usually listed for a data warehouse are:

  • Subject-oriented: organized around topics such as sales, not around applications.
  • Integrated: data from many sources is cleaned and given one consistent format.
  • Time-variant: data carries a time dimension, so history can be compared.
  • Non-volatile: data is loaded and read, not changed row by row once stored.

TrapA normalized design is good for OLTP, because it avoids repeated data. A warehouse often accepts repeated data on purpose, because joins are costly when the table is large and the question is read-only.

Question: Which system is more likely to be normalized, an OLTP database or a data warehouse?

The OLTP database. Normalization avoids repeated data during frequent updates. A warehouse is often denormalized for faster reading.

Question: Why does a warehouse keep history?

Analysis needs comparisons over time, such as this quarter against last quarter. An operational system often keeps only current values.

Concept 2: Fact tables and dimension tables

The fact table

A fact table records events. Each row is one event, such as one sale. A fact table has two kinds of column:

  • Foreign keys that point to each dimension table, such as time_id, item_id and location_id.
  • Measures, the numbers we add up, such as units_sold and dollars_sold.

Six fact rows and two item rows. Each fact row is one summarized sale record, and each item appears once.

Question: Is a measure such as dollars_sold stored in a fact table or in a dimension table?

In the fact table. Measures are the numbers that are added up, and they belong to each event.

Concept 3: Star, snowflake and fact constellation schemas

Star schema

In a star schema, the fact table sits in the middle and each dimension table is joined to it directly. Each dimension is stored as one flat table, even if it has repeated values such as state and country next to city.

The shape looks like a star: a centre with rays. For the example, the star has the Sales fact table in the middle and the Time, Item and Location tables around it. A query joins the fact table with one or more dimensions, then groups.

Snowflake schema

A snowflake schema normalizes the dimension tables. The Location dimension is split into smaller tables:

Location(location_id, city, state_id) → State(state_id, state, country_id) → Country(country_id, country)

Read the arrows as "refers to". The branches look like a snowflake. The benefit is less repetition, and the cost is more joins. To find the country of a sale, a query joins Sales, Location, State and Country.

TrapA snowflake schema is not the same as a normalized OLTP design. It normalizes only the dimension tables. The fact table is still one central table.

Fact constellation schema

A fact constellation has two or more fact tables that share some dimension tables. For example, Sales and Shipments might both use Time and Location, but each has its own measures. The shape looks like several stars that share points. It is also called a galaxy schema.

Comparing the three

SchemaFact tablesDimension tablesJoins for a typical queryRedundancy
StarOneFlat, may repeat valuesFewestHighest in dimensions
SnowflakeOneNormalized into sub-tablesMoreLower
Fact constellationTwo or moreShared by factsDepends on the queryDepends on the design

GATE loves thisA common question asks which schema gives the fewest joins for a simple query. The answer is the star schema. Another asks which schema has the most normalized dimensions. The answer is the snowflake.

Question: How many joins does a star query need to get the country of a sale?

One join, from Sales to Location, because Location stores country directly.

Question: Two fact tables share the Time and Location dimensions. Which schema is this?

A fact constellation schema.

Concept 4: The multidimensional data model and the data cube

From tables to a cube

The star schema suggests a multidimensional view. Each dimension is an axis, and each cell holds a measure value. With three dimensions (time, item and location), the view is a cube. Each cell is the total for one combination, such as "Q1, Phone, Pune".

Cubes can have more than three dimensions, but they are hard to draw. A four-dimensional cube is a set of cubes, and the same idea holds.

Cells and totals

Some cells are empty when no sale happened. The cube also holds totals along each axis. For example, the total dollars for Electronics across all cities and quarters is one aggregate cell. Warehouses precompute many of these totals so that queries are fast.

Key ideaA data cube is a way of organizing the same fact table, not a new kind of storage. Each combination of dimension values gives one cell.

Question: A cube has three dimensions with 4, 5 and 3 values. How many base cells does it have?

4 × 5 × 3 = 60 cells, some of which may be empty.

Question: What is an aggregate cell?

A cell that holds a total over some values of a dimension, such as the total for all cities.

Concept 5: OLAP operations: roll-up, drill-down, slice, dice and pivot

Why operations on the cube

An analyst moves through the cube by changing the view. The standard operations are roll-up, drill-down, slice, dice and pivot. Each one takes a view and returns another view.

Roll-up

Roll-up moves up a concept hierarchy, so the detail becomes coarser. Moving from city to country in the Location dimension is a roll-up. The totals are now per country, and there are fewer cells.

Drill-down

Drill-down is the opposite. It moves down a hierarchy to finer detail, such as from country to city. Drill-down needs the detailed data to be present.

Slice

Slice fixes one dimension to one value. Fixing category to Electronics gives a two-dimensional view, with time and location still free. The cube loses one dimension.

Dice

Dice picks values on two or more dimensions. For example, category is Electronics and city is Pune or Delhi. The result is a smaller sub-cube, with all dimensions still present but fewer values.

Pivot

Pivot rotates the view. If the table has quarters down the side and categories across the top, pivoting swaps them. Pivot does not change the numbers. It only changes which dimension is shown on which axis.

TrapA restriction on one dimension to a single value is a slice. A restriction on two or more dimensions at once, such as category Electronics and city Pune or Delhi, is a dice.

A worked example with the cube

Start from the six sales rows. Roll-up to country, slice to Electronics, dice to Electronics in Pune or Delhi, and pivot to quarter by category. The program below computes each view from the fact rows.

# (quarter, category, city, country, units, dollars)
facts = [
    ("Q1", "Electronics", "Pune", "India", 10, 5000),
    ("Q1", "Electronics", "Delhi", "India", 4, 2000),
    ("Q1", "Clothing", "Pune", "India", 6, 900),
    ("Q2", "Electronics", "Pune", "India", 7, 3500),
    ("Q2", "Clothing", "Delhi", "India", 3, 450),
    ("Q2", "Electronics", "Dhaka", "Bangladesh", 5, 2600),
]

# Roll-up: city to country, total dollars
by_country = {}
for q, cat, city, country, units, dollars in facts:
    by_country[country] = by_country.get(country, 0) + dollars
print("roll-up to country:", by_country)

# Slice: category fixed to Electronics, total units
print("slice Electronics units:", sum(f[4] for f in facts if f[1] == "Electronics"))

# Dice: category Electronics and city in Pune or Delhi, total dollars
dice = [f for f in facts if f[1] == "Electronics" and f[2] in ("Pune", "Delhi")]
print("dice dollars:", sum(f[5] for f in dice))

# Pivot: quarter (rows) by category (columns), dollars
table = {}
for q, cat, city, country, units, dollars in facts:
    table[(q, cat)] = table.get((q, cat), 0) + dollars
for q in ("Q1", "Q2"):
    print("pivot", q, [table.get((q, c), 0) for c in ("Electronics", "Clothing")])

# Average is algebraic: sum and count combine, so the average is sum / count
india = [f[5] for f in facts if f[3] == "India"]
print("average dollars India:", sum(india) / len(india))

roll-up to country: {'India': 11850, 'Bangladesh': 2600}
slice Electronics units: 26
dice dollars: 10500
pivot Q1 [7000, 900]
pivot Q2 [6100, 450]
average dollars India: 2370.0

GATE loves thisTo name an OLAP operation, ask two questions. First, did the number of dimensions change? A slice or a roll-up that removes a dimension does. Second, did the detail level change? Roll-up and drill-down do.

Question: Which operation moves from Pune to India as a location?

Roll-up, along the location hierarchy city, state, country.

Question: Which operation changes only the layout of the table and not the numbers?

Pivot.

Solved GATE-style problems

These problems are original, written in the GATE style. They are not past exam questions.

OLTP or OLAP

A system records each bank transfer as it happens and updates two account balances. Is this an OLTP or an OLAP system?

How to think about it

  1. What is asked. The type of system.
  2. Which idea applies. OLTP handles short transactions that change current data. OLAP summarizes large history.
  3. Work it out. A transfer is one short transaction that updates two balances. That matches OLTP.
  4. Check. No summary over many years is involved, so OLAP does not fit.

Answer: OLTP.

Rows in a star

A star schema has one fact table and three dimension tables. How many joins does a query that uses all three dimensions need?

How to think about it

  1. What is asked. The joins for one query.
  2. Which idea applies. In a star, each dimension joins directly to the fact table.
  3. Work it out. Three dimensions, each joined once to the fact table, give three joins.
  4. Check. A snowflake would need more joins, so the star gives the minimum.

Answer: 3.

Statements about schemas

Select all that apply. Which statements about data warehouse schemas are true?

(A) A snowflake schema normalizes the dimension tables.

(B) A star schema has more than one fact table.

(C) A fact constellation can share dimension tables between fact tables.

(D) In a star schema, the dimension tables are always normalized.

How to think about it

  1. What is asked. Which statements are true.
  2. Which idea applies. Recall the defining feature of each schema.
  3. Work it out. (A) True, that is the definition of snowflake. (B) False, a star has one fact table. (C) True, that is the point of a constellation. (D) False, star dimensions are flat tables.
  4. Check. Two statements are true, one describing snowflake and one describing constellation.

Answer: (A) and (C).

Cells in a cube

A data cube has dimensions time (8 values), item (5 values) and location (6 values). How many base cells does it have?

How to think about it

  1. What is asked. The number of base cells.
  2. Which idea applies. Each cell is one combination of one value from each dimension.
  3. Work it out. 8 × 5 × 6 = 240.
  4. Check. The number of cells is the product of the sizes, not the sum.

Answer: 240.

Which operation is it

An analyst starts with sales by city and asks for sales by country. Which OLAP operation is this?

How to think about it

  1. What is asked. The name of the operation.
  2. Which idea applies. Moving from detailed to general along a concept hierarchy.
  3. Work it out. City is below country in the location hierarchy. Going from city up to country is moving up.
  4. Check. The level got coarser, so it is not drill-down.

Answer: roll-up.

Joins in a snowflake

A snowflake schema stores the Location dimension as Location(location_id, city, state_id), State(state_id, state, country_id) and Country(country_id, country). A query needs the country of every sale in the Sales fact table. How many joins does it need, counting joins between Sales and each table on the path?

How to think about it

  1. What is asked. The number of joins on the path from Sales to Country.
  2. Which idea applies. Each link in the snowflake is one join.
  3. Work it out. Sales joins Location (1). Location joins State (2). State joins Country (3).
  4. Check. In a star, the same answer needs only one join, so the snowflake needs two more.

Answer: 3.

Identify the operation chain

Select all that apply. Which of these changes the cube so that it has fewer dimensions than before?

(A) Slice on item fixed to one value

(B) Roll-up from city to country

(C) Dice on item and location

(D) Pivot that swaps time and location

How to think about it

  1. What is asked. Which operations reduce the number of dimensions.
  2. Which idea applies. Slice fixes one dimension, which removes it from the view. Roll-up changes the level of detail, but keeps the dimension. Dice selects values, and pivot only rotates.
  3. Work it out. (A) Fixing item to one value removes item from the view, so the view has fewer dimensions. True. (B) Roll-up keeps location as a dimension, only coarser. False. (C) Dice keeps both dimensions. False. (D) Pivot keeps all dimensions. False.
  4. Check. Only the slice removes a dimension in this list.

Answer: (A) only.

Dollars for a dice

Using the six sales rows in the worked example, what is the total dollars for category Clothing in any city? Then state which OLAP operation produces this view from the full cube.

How to think about it

  1. What is asked. A total and an operation name.
  2. Which idea applies. Fixing one dimension to a single value is a slice. Summing the measure gives the total.
  3. Work it out. Clothing rows: Pune in Q1 with 900 dollars, and Delhi in Q2 with 450 dollars. Total 900 + 450 = 1350. Fixing category to one value is a slice.
  4. Check. The full total is 5000 + 2000 + 900 + 3500 + 450 + 2600 = 14450. Electronics is 5000 + 2000 + 3500 + 2600 = 13100, and 13100 + 1350 = 14450, which matches.

Answer: 1350 dollars, produced by a slice on category.

Exam-level 1: cells in a full data cube (NAT, 2 marks)

A sales cube has three dimensions. Time has 4 quarters, Product has 5 products and Region has 3 regions. Every dimension also has an ALL value, which means all of its members are grouped together. A cell is one combination of one value from each dimension, where a value can be ALL. How many cells does the full data cube have?

How to think about it

  1. What is asked. The total number of cells, counting ALL.
  2. Which idea applies. Each dimension gives its own values plus ALL, and the cube is every combination of one choice per dimension.
  3. Work it out. Time has 4 + 1 = 5 choices, Product has 5 + 1 = 6, and Region has 3 + 1 = 4. Multiply: 5 × 6 × 4 = 120.
  4. Check. Leaving out ALL would give 4 × 5 × 3 = 60 cells, which are only the ungrouped cells. So 120 is the size of the full cube.

Answer: 120 cells.

time=4+1
product=5+1
region=3+1
print(time, product, region, time*product*region)
5 6 4 120

Exam-level 2: star, snowflake and constellation (MSQ, 2 marks)

A warehouse has a fact table Sales that refers to dimension tables Product and Store. A query needs the product Category and the store State. In a star schema, each dimension is one flat table. In a snowflake schema, each dimension is normalized into linked tables, such as Product to Category and Store to City to State. Select all that apply. Which of these statements are true?

(A) The snowflake version needs more joins than the star version for this query.

(B) A star schema normalizes each dimension into a chain of tables.

(C) A fact constellation has two or more fact tables that share dimension tables.

(D) Fact tables usually store descriptive text, such as a city name.

How to think about it

  1. What is asked. Which statements about schema types are true.
  2. Which idea applies. A star keeps dimensions flat, a snowflake normalizes them, and a constellation uses several fact tables that share dimensions.
  3. Work it out. Star: Sales joins Product and Store, so there are 2 joins, and Category and State are columns in those flat tables. Snowflake: Sales to Product, Product to Category, Sales to Store, Store to City, City to State. That is 5 joins, 3 more than the star. So (A) is true.
  4. Check. (C) is the definition of a constellation. (B) and (D) reverse the rules, since a snowflake normalizes dimensions and fact tables hold keys and measures, not descriptive text.

Answer: (A) and (C). Why the others fail: (B) is the snowflake idea, while a star keeps each dimension flat; (D) descriptive attributes belong in dimension tables, while fact tables hold keys and measures.

star_joins=['Sales-Product','Sales-Store']
snow_joins=['Sales-Product','Product-Category','Sales-Store','Store-City','City-State']
print(len(star_joins), len(snow_joins))
print(len(snow_joins)-len(star_joins))

Exam-level 3: cuboids in the lattice (NAT, 2 marks)

A cube has three dimensions with hierarchies. Time has three levels: day, month and year. Location has two levels: city and state. Product has one level, product. Each dimension can also roll up to ALL. A cuboid is one choice of level in each dimension. How many cuboids does the full lattice contain?

How to think about it

  1. What is asked. The number of cuboids in the lattice.
  2. Which idea applies. Count the choices for each dimension, including ALL, then multiply, because each dimension is chosen independently.
  3. Work it out. Time has 3 + 1 = 4 choices. Location has 2 + 1 = 3 choices. Product has 1 + 1 = 2 choices. Multiply: 4 × 3 × 2 = 24.
  4. Check. Forgetting ALL would give 3 × 2 × 1 = 6, which is too few, because the top of each dimension would be missing.

Answer: 24 cuboids.

dims={'Time':3,'Location':2,'Product':1}
total=1
for name,levels in dims.items():
    total*=(levels+1)
    print(name, levels+1)
print(total)
Time 4
Location 3
Product 2
24

Exam-level 4: fact table size (NAT, 2 marks)

A retailer sells 30 products in 12 months across 10 stores. Each product, month and store combination is a slot. Nine out of every ten slots have sales, and each slot with sales has exactly 2 rows in the fact table. How many fact rows are there in total?

How to think about it

  1. What is asked. The total number of fact rows.
  2. Which idea applies. Count the slots, keep only the slots with sales, then multiply by the rows per slot.
  3. Work it out. 30 × 12 × 10 = 3600 slots. Nine in ten have sales: 3600 × 9 / 10 = 3240. Each has 2 rows: 3240 × 2 = 6480.
  4. Check. 6480 is 1.8 times 3600, which matches 2 rows on 90 percent of the slots.

Answer: 6480 rows.

combos=30*12*10
active=combos*9//10
print(combos, active, active*2)
3600 3240 6480
