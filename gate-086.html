ER-Model

Before you build a database, you sketch what it must store. The Entity-Relationship (ER) model is the standard sketch. This topic teaches entities, attributes, keys, relationships, cardinality, participation, weak entities, and how to turn an ER diagram into tables, which GATE asks about both as concepts and as diagram-to-schema questions.

The idea in plain words

Imagine you are asked to build a system for a small school. Before you buy any cabinets, you talk to the staff and write down the important things. There are students, teachers and courses. Each student has a name and a roll number. Each student enrols in several courses, and each course has many students. Writing this down as a picture first is much cheaper than rebuilding a database later.

The Entity-Relationship model, usually called the ER model, is that picture. It was designed to describe what data a database must hold and how the pieces connect, before any table is created. It has three main building blocks:

  • Entities, which are the things we store information about, such as a student or a course.
  • Attributes, which are the facts we store about each entity, such as a student's name.
  • Relationships, which are the links between entities, such as "student enrols in course".

Once the ER diagram is right, a simple set of rules turns it into tables, which is the form a relational database uses. GATE tests both the meaning of the diagram and the conversion rules, so this page covers both.

Why this matters for GATE: questions in the database part of GATE DA often give a short description of a situation and ask for the cardinality, the number of tables, or the primary key of a table that results. Careful reading of the words "each", "at most", "at least" and "may" decides the answer.

Key terms

Read these now. Each one is used in the explanations that follow.

Entity
A thing about which we store data. Plain meaning: a "noun" in the problem, such as Student. Precisely: an object that can be distinguished from others and has attributes.
Entity set
The collection of all entities of one kind, such as all the students in the school.
Attribute
A property of an entity, such as the name of a student. Precisely: a function that gives a value for each entity in an entity set.
Simple attribute
An attribute that cannot be split further, such as a roll number.
Composite attribute
An attribute made of smaller parts, such as an address made of street, city and postcode.
Derived attribute
An attribute whose value can be calculated from other data, such as age calculated from date of birth.
Multivalued attribute
An attribute that can hold several values for one entity, such as several phone numbers.
Key
An attribute, or set of attributes, whose values identify each entity uniquely.
Weak entity
An entity that cannot be identified by its own attributes. It needs a related owner entity to be identified.
Relationship
An association between two or more entities, such as "enrols".
Cardinality
How many entities on one side can be linked to entities on the other side. Typical values are one and many.
Participation
Whether every entity in a set must take part in a relationship (total) or not necessarily (partial).
Foreign key
An attribute in one table whose value must match a primary key value in another table.
Primary key
The key chosen to identify rows in one table. It must be unique and must not be empty.

Entities, entity sets and attributes

An entity is one specific thing. Ravi, a student with roll number 101, is one entity. The set of all students is the entity set Student. In diagrams, an entity set is drawn as a rectangle with its name inside.

Attributes are the facts about each entity. For Student we may store roll number, name, and date of birth. In diagrams, each attribute is an oval joined by a line to its entity rectangle.

Attributes come in four kinds. Learn each one with an example.

Key ideaA derived attribute is not normally stored in a table, because it can be recalculated. A multivalued attribute cannot be stored in the same row as a single value without breaking the rules of a table, so it needs its own table when converted.

Take the entity Student with these attributes: roll number, name (composite: first name and last name), date of birth, age (derived), and phone numbers (multivalued). In a table, the composite name would become two columns. The derived age would usually be left out, and the multivalued phone numbers would move to a separate table. These conversion steps come later on this page.

TrapA composite attribute is not the same as a multivalued attribute. Composite means one value made of parts, such as one full address. Multivalued means several values of the same kind, such as several addresses.

Is the age of a student a simple, derived or multivalued attribute?

Derived. Age can be calculated from the date of birth and today's date, so it does not need to be stored.

A person has three email addresses. What kind of attribute is email?

Multivalued, because one person can have several values of the same kind.

Keys and weak entities

A key is an attribute, or a group of attributes, whose value identifies one entity. Two students must never share the same key. Roll number is a good key for Student, because each roll number belongs to one student. Name is a poor key, because two students may have the same name.

In ER diagrams, a key attribute is drawn with its name underlined. A candidate key is any attribute set that could be a key. The one chosen to identify rows is the primary key. For a set of attributes to be a key, it must be unique for every entity, and a smaller set of it must not still be unique. This second condition is called minimality.

Weak entities

Some entities cannot be identified by their own attributes. Consider Dependent, which records the children of an employee. Two employees may each have a child called Asha. The name Asha does not identify the dependent. The dependent is identified only together with the employee who is the parent. Such an entity is a weak entity.

A weak entity has a partial key, which is the set of attributes that separates it from other dependents of the same owner. For Dependent, the partial key is the dependent's name. The full key is the owner's key plus the partial key. In diagrams, a weak entity is drawn as a double rectangle, its partial key is drawn with a dashed underline, and its link to the owner is a double diamond.

Key ideaThe key of a weak entity is the owner's key together with its own partial key. Without the owner, the weak entity cannot be identified.

Example. Employee E101 has dependents Asha and Ravi. Employee E202 also has a dependent called Asha. The dependent rows are identified as (E101, Asha), (E101, Ravi) and (E202, Asha). The name Asha appears twice, but the pair is unique.

TrapA weak entity's partial key alone is not a primary key. The primary key of the weak entity's table is the owner's key together with the partial key.

What is the primary key of the Dependent table in the example above?

The pair (emp_id, dep_name), because the owner's key emp_id plus the partial key dep_name identifies each dependent.

Why is name a poor key for Student?

Two different students can share a name, so a name value does not always identify one student.

Relationships and cardinality

A relationship links entities. Students enrol in courses. Employees work in departments. In diagrams, a relationship is drawn as a diamond joined to the entity rectangles it connects.

Cardinality describes how many entities on each side may take part. It is one of three patterns.

  • One to one (1:1). One entity on the left links to at most one on the right, and the reverse also holds. Example: each person has at most one passport, and each passport belongs to one person.
  • One to many (1:N). One entity on the left can link to many on the right, but each entity on the right links to only one on the left. Example: one department has many employees, and each employee works in one department.
  • Many to many (M:N). An entity on either side can link to many on the other side. Example: a student enrols in many courses, and each course has many students.

A simple way to check the type is to ask two questions: "how many courses can one student take?" and "how many students can one course have?" If the answer to both is "many", the relationship is M:N. If one side says "one", check the other side.

RelationshipQuestion askedAnswerType
Department to EmployeeHow many employees per department?Many1:N, since an employee has one department
Person to PassportHow many passports per person?At most one1:1
Student to CourseHow many courses per student?ManyM:N, since a course also has many students

Relationships can carry their own attributes. For example, the enrolment of a student in a course may have a grade. The grade belongs to the pair, not to the student alone or the course alone. So it is drawn on the relationship diamond.

GATE loves thisRead cardinality from the meaning in the question, not from the names. The phrase "each employee works in exactly one department" fixes one side as one. The phrase "a department may have many employees" fixes the other side as many.

A teacher teaches many subjects, and each subject is taught by one teacher. What is the cardinality?

One to many, with the teacher on the one side and the subject on the many side.

Which relationship type needs its own table when converted to tables?

The many to many relationship, which needs a separate table to hold the pairs.

Participation constraints

Cardinality says how many. Participation says whether every entity must take part at all. There are two kinds.

  • Total participation. Every entity in the set must be linked. In diagrams it is a double line from the entity to the relationship.
  • Partial participation. An entity may or may not be linked. In diagrams it is a single line.

Example. Every employee must work in a department, so the Employee side of "works in" is total. A department may exist with no employees yet, so the Department side is partial.

Cardinality and participation can be stated together with a pair of numbers, the (min, max) notation. The minimum is 1 for total participation and 0 for partial. The maximum is 1 or N, where N means many. For "works in", Employee has (1, 1), because each employee works in exactly one department. Department has (0, N), because a department may have no employees, and it may have many.

(min, max) = (1, 1) means total and at most one
(min, max) = (0, N) means partial and many

TrapStudents often read the (min, max) pair in the wrong place. In the notation used here, the pair beside an entity states how many relationship instances that one entity can take part in. For "works in", the pair beside Employee is (1, 1), not the pair beside Department.

What is the participation of Employee in "works in" if every employee must have a department?

Total. Every employee must take part in the relationship.

A pair (0, 1) appears beside Person in "has passport". What does it mean?

A person may have no passport, and at most one passport. Participation is partial and the maximum is one.

A weak entity with its owner

Earlier we saw Dependent as a weak entity. Its link to Employee is an identifying relationship, and it is drawn with a double diamond. The relationship is always one to many, from the owner Employee to the weak entity Dependent. Each dependent belongs to exactly one employee, so the Dependent side is total.

Think of it as a rule: a weak entity cannot exist without its owner. If an employee leaves and the company deletes that employee, the dependents must also go, or they would have no owner. This is why the link is total on the weak side.

Key ideaA weak entity always has total participation in its identifying relationship, and that relationship is one to many from the owner.

Why is the participation of Dependent in the identifying relationship total?

Because every dependent must belong to an employee. A dependent with no owner cannot be identified.

What does a double rectangle mean in an ER diagram?

A weak entity.

Converting an ER diagram to tables

A relational database stores each entity set, and some relationships, as tables. Each row is one entity, and each column is one attribute. The conversion follows fixed rules. Learn them in this order, and check each part of the diagram once.

  1. Strong entity. Make one table. Its columns are its simple attributes. Split each composite attribute into its parts. Leave out derived attributes. The primary key is the entity's key.
  2. Multivalued attribute. Make a new table with two columns: the entity's key and the value. The primary key is both columns together.
  3. Weak entity. Make one table. Its columns are its own attributes, plus the owner's key as a foreign key. The primary key is the owner's key together with the partial key.
  4. One to many relationship (1:N). Do not make a new table. Copy the primary key of the "one" side into the table of the "many" side as a foreign key. Any relationship attribute is also copied there.
  5. Many to many relationship (M:N). Make a new table. Its columns are the primary keys of both sides, plus any relationship attributes. The primary key is the pair of foreign keys.
  6. One to one relationship (1:1). Put a foreign key on one side, preferably on the side with total participation. This avoids many empty values. The other choice is to merge the two tables into one.

Let us apply the rules to an example. The entities are Employee (emp_id, name) and Department (dept_id, dept_name). Each employee works in one department, so it is a 1:N relationship from Department to Employee. Each employee has many phone numbers, so phone is multivalued.

Rule 1 gives the tables Employee and Department. Rule 4 copies dept_id into Employee as a foreign key. Rule 2 makes a table Phone with columns emp_id and phone.

Now look at an M:N example. A student enrols in courses, and each enrolment has a grade. The relationship Enrols becomes a table with columns student_id, course_id and grade. Its primary key is (student_id, course_id). Each student-course pair appears once.

TrapDo not copy a foreign key into one side of an M:N relationship. One student has many courses, so the student's table cannot hold a single course id. The M:N relationship always needs its own table.

GATE loves thisCount tables quickly with this rule: strong entities plus weak entities plus M:N relationships plus multivalued attributes. The 1:N and 1:1 relationships add no table when the foreign key approach is used.

How many tables does a single 1:N relationship between two strong entities add to the schema?

None extra. The two entity tables stay, and a foreign key is added to the many side.

What is the primary key of the Enrols table?

The pair (student_id, course_id), because each student takes each course at most once in this model.

Solved GATE-style problems

These problems are original, written in the GATE style. They are not real past questions. For each one, write down the entities, relationships and attributes before you answer.

Classify an attribute

For the entity Customer, which kind of attribute is "number of orders placed so far", if it is calculated by counting rows in an Order table? Choose one: simple, composite, derived or multivalued.

How to think about it

  1. What is asked. The kind of attribute.
  2. Which idea applies. A derived attribute is calculated from other data.
  3. Work it out. The count comes from rows of the Order table, so it is calculated. It is derived. It is not split into parts, and it holds a single value.
  4. Check. Ask whether the value could be recalculated from other data. It can, so it is derived.

Answer: derived.

Primary key of a weak entity

A Room entity is weak, owned by a Building entity with key building_id. Room is identified by room_number, which is unique only within a building. What is the primary key of the Room table?

How to think about it

  1. What is asked. The primary key columns.
  2. Which idea applies. A weak entity's key is the owner's key plus its partial key.
  3. Work it out. The partial key is room_number. The owner key is building_id. So the key is (building_id, room_number).
  4. Check. Room 101 in building B1 and room 101 in building B2 are different rows, and the pair is unique.

Answer: (building_id, room_number).

Select all true statements about an ER diagram

An ER diagram has the entities Student and Course, and a relationship Enrols between them with cardinality many to many. Select all that apply.

  • (A) The Enrols relationship must become its own table.
  • (B) The Student table must hold a foreign key to Course.
  • (C) The primary key of the Enrols table is the pair of foreign keys.
  • (D) A student can take many courses, and a course can have many students.

How to think about it

  1. What is asked. Which statements are true.
  2. Which idea applies. The conversion rule for M:N relationships.
  3. Work it out. (A) True, M:N needs its own table. (B) False, one student has many courses, so one foreign key cannot hold them. (C) True, the primary key is both foreign keys. (D) True, that is the meaning of many to many.
  4. Check. The reasoning follows the rule directly. No code is needed.

Answer: (A), (C) and (D).

Counting tables in a schema

An ER diagram has 4 strong entities, 1 weak entity, 2 many to many relationships, 3 one to many relationships, and 1 multivalued attribute. Convert it using the rules on this page. How many tables does the schema have? This is a NAT question.

How to think about it

  1. What is asked. The total number of tables.
  2. Which idea applies. Strong entities, weak entities, M:N relationships and multivalued attributes each give one table. One to many relationships give none.
  3. Work it out. 4 strong plus 1 weak plus 2 M:N plus 1 multivalued gives 8. The 3 one to many relationships add no tables.
  4. Check. Run the code below, which adds the counts.
strong = 4
weak = 1
mn = 2
multivalued = 1
print(strong + weak + mn + multivalued)
8

Answer: 8.

Foreign key placement

Each Book is written by exactly one Author, and an Author may have written many books. Which table gets the foreign key, and what is the foreign key column? Give the table name and column name.

How to think about it

  1. What is asked. The table and the column of the foreign key.
  2. Which idea applies. For 1:N, the foreign key goes to the many side.
  3. Work it out. The Author is the one side, and Book is the many side. So Book gets a foreign key that holds the author's key.
  4. Check. One author can appear in many book rows, and each book row holds one author id, so the design fits.

Answer: the Book table, with an author_id foreign key that refers to the primary key of Author.

Key of a derived table

Entities Doctor (doc_id, name) and Patient (pat_id, name) are strong. The relationship Treats is many to many, with an attribute visit_date. A doctor and a patient meet at most once on any given date, but the same pair may meet on different dates. How many columns does the table made from Treats have? Give the column count as a NAT answer.

How to think about it

  1. What is asked. The number of columns of the Treats table, and the reason its key has the form it has.
  2. Which idea applies. The M:N rule: a new table with both keys plus relationship attributes.
  3. Work it out. The columns are doc_id, pat_id and visit_date, so there are 3 columns. The pair (doc_id, pat_id) cannot be the key, because the same pair meets on several dates. Adding visit_date makes each row unique, since a pair meets at most once per date. So the primary key is (doc_id, pat_id, visit_date).
  4. Check. Run the code below to count the columns.
columns = ["doc_id", "pat_id", "visit_date"]
print(len(columns))
3

Answer: 3 columns, with primary key (doc_id, pat_id, visit_date).

Select all true statements about cardinality and participation

Select all that apply to an ER relationship between Employee and Department, where each employee works in exactly one department.

  • (A) The Employee side of the relationship has (min, max) equal to (1, 1).
  • (B) The relationship is one to many from Department to Employee.
  • (C) Converting this relationship alone adds a new table.
  • (D) If a department may have no employees, the Department side is partial.

How to think about it

  1. What is asked. Which statements are true.
  2. Which idea applies. The (min, max) notation, the 1:N type, and the 1:N conversion rule.
  3. Work it out. (A) True. Each employee has exactly one department, so the pair is (1, 1). (B) True, one department has many employees. (C) False, a 1:N relationship adds a foreign key, not a table. (D) True, a department with no employees is partial participation.
  4. Check. The reasoning follows directly from the rules above. No code is needed.

Answer: (A), (B) and (D).

Exam-level practice

Exam-level 1: Cardinality mapping (NAT, 2 marks)

An ER diagram has entities A (with 2 attributes) and B (with 3 attributes), and a many-to-many relationship R with 1 attribute. Keys are single attributes. How many tables are needed in the minimal relational mapping, and how many columns does the table for R have?

How to think about it

  1. What is asked. Table count and the R table's width.
  2. Which idea applies. A many-to-many relationship needs its own table holding both keys and its own attributes.
  3. Work it out. Tables: A, B and R, so 3. R columns: key of A, key of B, and its attribute = 3.
  4. Check. A one-to-many relationship would instead fold into the many side, needing only 2 tables.

Answer: 3 tables, and R has 3 columns.

Exam-level 2: Weak entities (MSQ, 2 marks)

Which are TRUE? (A) A weak entity has total participation in its identifying relationship. (B) Its primary key includes the owner's key. (C) A weak entity can exist without its owner. (D) It has a partial key (discriminator).

How to think about it

  1. What is asked. Properties of weak entity sets.
  2. Which idea applies. A weak entity is identified only through its owner.
  3. Work it out. (A) True. (B) True. (C) False. (D) True.
  4. Check. Example: a dependent of an employee, keyed by (employee id, dependent name).

Answer: (A), (B) and (D).

Exam-level 3: Minimum tables (NAT, 2 marks)

Entities E1, E2, E3 each have a simple key. E1-E2 is one-to-one with total participation on both sides, E2-E3 is one-to-many (E2 one side), and E1-E3 is many-to-many. What is the minimum number of tables?

How to think about it

  1. What is asked. The fewest relations after mapping.
  2. Which idea applies. A one-to-one with total participation on both sides can merge into one table. A one-to-many folds into the many side. A many-to-many needs its own table.
  3. Work it out. Merge E1 and E2 into one table. E3 is a table with a foreign key for E2. The many-to-many needs a third table. Total 3.
  4. Check. Each relationship is stored without nulls in this design.

Answer: 3.

Summary

Entity
A thing we store data about, such as a student.
Entity set
All the entities of one kind.
Attribute
A fact stored about each entity.
Simple attribute
An attribute that cannot be split.
Composite attribute
An attribute made of parts, which become columns.
Derived attribute
An attribute calculated from other data, usually not stored.
Multivalued attribute
An attribute with several values, which needs its own table.
Key
An attribute set that identifies each entity uniquely.
Primary key
The chosen key of a table.
Weak entity
An entity identified only with its owner's key.
Partial key
The part of a weak entity's key that separates it within one owner.
Relationship
An association between entities.
Cardinality
One to one, one to many, or many to many.
Total participation
Every entity must take part in the relationship.
Partial participation
An entity may or may not take part.
Foreign key
A column whose values must match a primary key elsewhere.

Remember these

  • Strong entities become tables, with composite attributes split into columns.
  • Multivalued attributes and many to many relationships each need their own table.
  • One to many relationships place a foreign key on the many side.
  • A weak entity's key is the owner's key plus its partial key.
  • Derived attributes are usually not stored.
  • Read cardinality and participation from the words in the question.
