How Git stores your work

Git is a version control system. It records snapshots of a project over time so you can compare, undo and combine changes. Most people learn Git as a list of commands, but interviewers want the model underneath, because the model explains every command's behaviour.

Four kinds of object

Git's storage is a key-value database. Each value is an object, and each key is the object's hash, a fingerprint of its contents. There are four object types:

  • Blob. The contents of one file. A blob stores the bytes only, not the file name.
  • Tree. A directory. It lists names with a file mode and the hash of a blob (for a file) or another tree (for a subdirectory).
  • Commit. A snapshot plus history. It points to one tree (the full project at that moment), to its parent commit or commits, and holds the author, committer and message.
  • Tag. A named, optionally signed pointer to a commit, used for releases such as v1.2.0.

Because a hash depends only on content, identical content is stored once. If you change one file, Git creates a new blob for it, a new tree for each directory on the path to it, and a new commit. Everything else is reused. That is why branching in Git is cheap: a branch is just a pointer.

How a blob hash is computed

Git computes the SHA-1 hash of a header followed by the content. The header is the word blob, a space, the byte length, and a zero byte. The program below repeats that calculation with hashlib and matches the value that git hash-object prints.

import hashlib

def git_blob_hash(content: bytes) -> str:
    header = b"blob " + str(len(content)).encode() + b"\0"
    return hashlib.sha1(header + content).hexdigest()

print(git_blob_hash(b"hello\n"))
print(git_blob_hash(b"hello\n") == git_blob_hash(b"hello\n"))
print(git_blob_hash(b"hello"))

The first hash is the one echo hello | git hash-object --stdin prints, because echo adds a newline. Removing the newline changes the content, so the hash changes completely. This is why Git can detect corruption: any change to stored bytes changes the key.

Refs: names that point to commits

A ref is a human-readable name that points to a commit. A branch is a ref under refs/heads/ that moves forward when you commit. A tag is a ref that stays put. A remote-tracking branch such as origin/main records where a remote's branch was the last time you fetched. HEAD is special: it normally points to the current branch, so committing moves the branch that HEAD names. If HEAD points straight at a commit, you are in a detached HEAD state, and new commits can be lost unless you give them a branch name.

Key ideaA commit is a snapshot, not a diff. Git stores whole trees and reuses unchanged blobs, and it computes the differences on demand.

What are the four Git object types, and what does each store?

A blob stores the contents of one file, with no name. A tree stores a directory: names, modes and the hashes of blobs or subtrees. A commit stores a pointer to a root tree, its parent commits, the author and committer, and the message. A tag stores a named pointer to another object, usually a commit, for releases.

Reset versus revert

Reset moves a branch pointer. Its three common modes differ in how far they go. --soft moves the branch and leaves the staging area and working files alone. --mixed (the default) also resets the staging area. --hard also overwrites the working files, so uncommitted changes are lost. Reset is for undoing commits that have not been shared.

Revert does not touch history. It creates a new commit whose change is the inverse of an earlier commit. Revert is for undoing commits that others may already have. Because it adds a commit, nobody's copy of the history breaks.

echo "bug" >> greeting.txt
git commit -q -am "Add bug"
git revert --no-edit HEAD
git log --format=%s
Revert "Add bug"
Add bug
Extend greeting
Add greeting

The revert commit is a new commit that undoes "Add bug". The earlier commit is still in the log, so the history shows what happened and when it was undone. Reset, by contrast, would have removed "Add bug" from the log entirely.

Interviewers ask"When do you use reset and when revert?" Reset when the commits are local and unshared. Revert when the commits are already on a shared branch, because revert never rewrites history that others may have.

Merge versus rebase

Both methods bring work from one branch into another, but they record the result differently. A merge joins two histories with a new commit that has two parents. The branch shape is kept, and nothing is rewritten. A rebase takes the commits of your branch, sets them aside, moves the branch to the tip of the target, and replays each commit on top. The replayed commits get new hashes, because their parent changed. The result is a straight line of history.

The commands below create a feature branch and a main branch that have each changed the same file in different places. The graph view shows the two lines of work.

git switch -c feature
echo "feature line" >> app.txt
git commit -q -am "Feature change"
git switch -q main
echo "main line" >> app.txt
git commit -q -am "Main change"
git log --graph --format=%s --all

| * Main change
|/
* Base

Now merge main into feature. Both branches appended a line at the same place, so Git cannot decide which text to keep. It stops and asks you to decide.

The first three lines are Git's report. The block after cat is the conflicted file. Git wraps each conflict in markers: the text between the top marker and the ======= line is from your current branch (HEAD), and the text between that line and the bottom marker is from the branch being merged. Finally, git merge --abort returns the branch to its state before the merge.

If you had used git rebase main instead, Git would have replayed "Feature change" on top of "Main change". It would hit the same conflict, and after you resolved it and ran git rebase --continue, the branch would show a straight line: Base, Main change, Feature change, with a new hash for the feature commit.

TrapRebasing a branch that other people have pulled. The rebased commits get new hashes, so their copies and yours disagree. Rebase private branches freely, and merge or revert once a branch is shared.

Resolving conflicts

A conflict means Git needs a human decision. Open each file, edit it into the final text you want, and delete all the marker lines. Then stage the file with git add. If you were merging, run git commit to finish. If you were rebasing, run git rebase --continue and repeat for each commit that conflicts. Use git status to see which files are still unmerged (they show as UU in short status). Tools such as VS Code and git mergetool make the editing easier, but the steps are the same.

Interactive rebase: rewriting your own commits

Interactive rebase lets you edit a range of your own commits before sharing them. It opens a todo list in your editor, and you change the command word at the start of each line.

pick 3a1f2c9 Add login form
squash 8b0e4d1 Fix typo in login form
reword 5c7d9a2 Add tests
drop 0e2f6b8 Debug print
fixup 9d1c3e7 Tidy tests

The command words mean: pick keeps a commit as it is, reword keeps it but changes the message, edit stops so you can amend it, squash merges it into the previous commit and keeps both messages, fixup merges it and discards its message, and drop removes it. Start one with git rebase -i HEAD~5 to edit the last five commits. The hashes above are placeholders. Your editor shows real ones.

Key ideaInteractive rebase is a way to rewrite a private history into a clean story before others see it. It is the same replay mechanism as ordinary rebase, with the todo list letting you choose what to replay.

What is the difference between merge and rebase in the history they produce?

A merge keeps both histories and adds a merge commit with two parents, so the branch structure is visible. A rebase replays your commits on top of the target, so the history is linear, but the replayed commits get new hashes. Merge never rewrites commits, while rebase rewrites the commits it replays.

Recovery with reflog and finding bugs with bisect

Git rarely loses work, but it is easy to lose track of it. Two tools cover the common disasters: the reflog, which remembers where HEAD and branches have been, and bisect, which finds the commit that introduced a bug.

The reflog

The reflog is a local journal of every change to HEAD and to branch tips: commits, resets, checkouts, merges and rebases. Entries are kept for a long time by default (about 90 days for reachable commits), so nearly every commit you have made recently can be recovered. Each entry is named HEAD@{n}, where 0 is the most recent. The commands below show the journal for the demo repository from earlier in this unit.

git reflog --format="%gd %gs"
HEAD@{0} revert: Revert "Add bug"
HEAD@{1} commit: Add bug
HEAD@{2} commit: Extend greeting
HEAD@{3} commit (initial): Add greeting

Suppose you ran git reset --hard HEAD~1 by mistake and the "Add bug" commit disappeared from the branch. The commit still exists, and the reflog points to it. Recovering it is one command: git reset --hard HEAD@{1} (or create a branch at that entry with git branch recovered HEAD@{1}, which is safer when you are not sure).

TrapAssuming the reflog is shared. It lives only in your local clone. A fresh clone has no reflog for the old work, and a commit that nothing points to is eventually deleted by garbage collection.

Bisect: binary search through history

Bisect finds the first bad commit with a binary search. You name one commit known to be good and one known to be bad. Git checks out the commit in the middle, you test it, and you mark it good or bad. Each answer halves the remaining range, so a history of 1,000 commits needs about 10 tests. That is the same idea as binary search on a sorted array, applied to history.

git bisect start
git bisect bad                 # the current commit shows the bug
git bisect good v1.0           # this older tag did not have it
git bisect run pytest          # let the test command decide each step
git bisect reset               # return to the branch you started on

With git bisect run, Git runs the command at each step. Exit code 0 means good, and a code from 1 to 127 (except 125, which means skip) means bad. This is why a test script works so well: pytest exits 0 when everything passes. The command lines above have no printed output because the result depends on your own project. Note that git bisect assumes the bug stayed in place once it appeared. A bug that comes and goes can mislead it.

How do you recover a commit after a hard reset removed it?

Use git reflog to find the commit's entry, for example HEAD@{1}, then move the branch back to it with git reset --hard HEAD@{1} or create a new branch at that entry. The commit was not deleted; it only stopped being reachable from the branch, and the reflog still records it.

Branching strategies, pull requests and code review

Git tells you how to store and combine work. A branching strategy tells a team how to organise that work so many people can ship safely. Three strategies come up in interviews.

Git Flow, GitHub Flow and trunk-based development

  • Git Flow uses two long-lived branches: main holds released code, and develop collects finished features. Work happens on short-lived feature/* branches, releases are cut on release/* branches, and urgent fixes start from main on hotfix/* branches. It suits software with scheduled, versioned releases, such as installable products. Its cost is complexity and long-lived branches that drift apart.
  • GitHub Flow has one long-lived branch, main, which is always deployable. Every change starts on a short-lived branch, goes through a pull request and review, and is merged to main. Main is deployed often. It suits web services with continuous delivery.
  • Trunk-based development has everyone integrate into one trunk at least daily, using very short-lived branches or direct commits. Unfinished features are hidden behind feature flags, which are switches in code or config that turn behaviour on or off without a new deploy. It suits teams that want the smallest possible gap between code and integration, and it relies on strong automated tests.

Pull requests

A pull request (PR) is a request to merge one branch into another, shown with its diff, discussion, and the results of automated checks. On GitHub, a PR is where review happens. A good PR is small (one idea, usually a few hundred changed lines or fewer), has a title that says what changes, and has a description that explains why. Repositories often protect main so that changes need an approving review and passing checks before the merge button works.

Code review

The purpose of review is to catch defects, spread knowledge, and keep the codebase consistent. Good review etiquette follows a few habits:

  • Review the code, not the person. Say "this function could return early" rather than "you wrote this badly".
  • Say what kind of comment it is. Mark style preferences as optional, and mark real bugs as blocking.
  • Ask questions when unsure. "Why do we need this retry?" is often more useful than a guess.
  • Authors should explain the change in the description, and respond to every comment, either with a change or a reason.

Interviewers ask"Walk me through how you would ship a change under GitHub Flow." Answer: branch from main, commit in small steps, open a PR with a clear description, let CI run the tests, get a review, merge, and let the pipeline deploy main.

Automating checks with GitHub Actions

GitHub Actions runs automated workflows on GitHub's servers. A workflow is a YAML file in .github/workflows/. It names the events that start it (for example a push or a pull request), one or more jobs, and the steps inside each job. Each job runs on a fresh virtual machine called a runner. A step either runs a shell command with run, or uses a reusable action with uses. If any step fails, the job fails, and the pull request check turns red.

name: tests

on:
  push:
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4          # download the repository
      - uses: actions/setup-python@v5      # install Python
        with:
          python-version: "3.12"
      - run: pip install pytest
      - run: pytest -q                     # a failing test makes this step fail

Read the workflow top to bottom. on says when it runs, jobs.test is the one job, and the steps run in order on the same runner. The checkout step is needed because the runner starts empty. The final step runs pytest, which exits with a non-zero code if any test fails.

A test file for that workflow is ordinary Python. pytest finds files named test_*.py and runs every function whose name starts with test_. A failing assert counts as a failure.

# test_text_utils.py
def slugify(text):
    return "-".join(text.lower().split())

def test_slugify_lowercases_and_joins_words():
    assert slugify("Hello World") == "hello-world"

def test_slugify_collapses_extra_spaces():
    assert slugify("  Git   and  GitHub ") == "git-and-github"

Run locally with pytest -q, and the same command runs in the workflow. The pytest summary includes timing, so this page does not show its output. The key habit is to run the same command locally and in CI, so a green local run means something.

TrapPutting secrets such as API keys directly in the YAML file. Store them in the repository's secrets settings and reference them as ${{ secrets.NAME }}.

How software gets built: SDLC, Agile and Scrum

The software development life cycle (SDLC) is the set of stages a piece of software goes through: requirements (what is needed), design (how it will be structured), implementation (writing the code), testing (checking it), deployment (releasing it) and maintenance (fixing and changing it afterwards). Every process model is a different way of arranging these stages over time.

Waterfall and Agile

Waterfall finishes each stage before starting the next. It is easy to plan and document, but it discovers mistakes late, when they are expensive to fix. Iterative and incremental models build the product in cycles, each one adding working functionality. Agile is a family of iterative methods based on the 2001 Agile Manifesto. Its four value statements prefer individuals and interactions over processes and tools, working software over comprehensive documentation, customer collaboration over contract negotiation, and responding to change over following a fixed plan. The items on the right still matter; the manifesto says the left items are valued more.

Scrum in one page

Scrum is the most common Agile framework. It defines three roles, five events and three artifacts.

  • Roles. The Product Owner orders the work and decides what is valuable. The Scrum Master coaches the team and removes obstacles, and is not a project manager. The Developers build the increment.
  • Events. The Sprint is a fixed time-box, usually one to four weeks, in which a usable increment is produced. Inside it: Sprint Planning chooses the work, the Daily Scrum is a short daily sync (about 15 minutes), the Sprint Review shows the increment to stakeholders, and the Sprint Retrospective asks how the team will work better next time.
  • Artifacts. The Product Backlog is the ordered list of everything that might be done. The Sprint Backlog is the chosen items plus a plan for them. The Increment is the sum of completed work that meets the team's Definition of Done.

Scrum's core rule is that scope is flexible within a Sprint, and time is fixed. If a Sprint looks at risk, the team negotiates the scope, not the date. Kanban is a related method that uses a board with work-in-progress limits instead of Sprints.

Key ideaAgile is a set of values, and Scrum is one framework that puts them into practice with fixed roles, events and artifacts. Interviewers often test whether you know the difference.

What is the difference between Waterfall and Agile?

Waterfall completes each SDLC stage before starting the next, so requirements are fixed early and changes are costly. Agile works in short cycles that each produce working software, collects feedback after every cycle, and accepts changing requirements. Agile trades up-front certainty for earlier feedback.

Interview questions

Answer each question in your own words first. Then open the model answer and compare.

What is a Git blob, and why does Git use hashes for its keys?

A blob is the content of one file, stored with no name. Git uses a hash of the content (with a header) as the key. Equal content gets the same key and is stored once, and any change to the bytes changes the key, which makes corruption easy to detect.

What does HEAD point to, and what is a detached HEAD?

HEAD normally points to the current branch, which in turn points to a commit, so committing moves the branch forward. A detached HEAD means HEAD points straight at a commit. New commits there are not on any branch, so create a branch before you switch away or they can be hard to find.

When would you use git revert instead of git reset?

Use revert on commits that are already shared, because it adds a new commit that undoes the change and never rewrites history. Use reset for unshared local commits, where moving the branch pointer is safe and keeps the history tidy.

Explain merge versus rebase to a teammate.

A merge combines two histories with a merge commit that has two parents, and keeps the branch structure. A rebase replays your commits onto a new base, giving a straight line of history with new hashes for the replayed commits. Rebase private work; merge or revert shared work.

How would you recover a commit that you lost after a bad reset?

Run git reflog, find the entry for the commit (for example HEAD@{1}), and reset or branch to that entry. The reflog records recent positions of HEAD and branches locally, so the commit is still recoverable until garbage collection removes it.

How does git bisect find a bug, and how many steps does it need?

You give a known bad commit and a known good commit, and bisect checks out the middle one. You or a script test it and mark it good or bad, which halves the range each time. For 1,000 commits it needs about 10 tests, since 2 to the power 10 is 1,024.

Compare Git Flow, GitHub Flow and trunk-based development.

Git Flow uses long-lived main and develop branches with feature, release and hotfix branches, and suits scheduled releases. GitHub Flow uses one main branch, short-lived feature branches and pull requests, and deploys from main often. Trunk-based development has everyone integrate into one trunk at least daily and hides unfinished work behind feature flags.

What makes a good pull request?

It is small, focused on one idea, has a clear title and a description that explains why, includes tests, and passes CI. Reviewers can then understand it in one sitting, which makes reviews faster and bugs easier to spot.

What does a GitHub Actions workflow contain?

A YAML file in .github/workflows that defines triggers (on), one or more jobs with a runner (runs-on), and ordered steps. Each step runs a command with run or uses an action with uses. If a step fails, the job fails and the pull request check turns red.

What is the difference between Scrum roles and Agile values?

Agile values, from the 2001 manifesto, are principles about how to work: collaboration, working software and responding to change. Scrum is a framework that applies those values with three roles (Product Owner, Scrum Master, Developers), five events and three artifacts. Agile is the philosophy, and Scrum is one concrete way to practise it.

What does the Definition of Done do in Scrum?

It is the team's shared checklist for when a piece of work counts as finished, such as tested, reviewed, documented and deployable. It makes the Increment's quality visible and prevents unfinished work from being counted as done.

DSA: Dynamic programming, one dimension

Dynamic programming (DP) solves a problem by breaking it into smaller subproblems, solving each one once, and reusing the answers. It applies when a problem has overlapping subproblems (the same smaller question appears again and again) and optimal substructure (the best answer is built from the best answers to smaller parts). One-dimensional DP keeps one value per position, such as "ways to reach step i" or "best total up to house i".

The five-step recipe

  1. State. Decide what dp[i] means in words, for example "the number of ways to climb i steps".
  2. Base cases. Fill in the smallest values you know directly.
  3. Recurrence. Write dp[i] in terms of earlier entries.
  4. Order. Compute entries so that each one's dependencies are already known (usually left to right).
  5. Answer. Read the result from the place the problem asks about, and check whether you need the whole table or only the last few entries.

Why memoisation matters

The plain recursive Fibonacci function recomputes the same values many times. Memoisation stores each answer the first time it is computed. Bottom-up tabulation fills an array in order instead. Both give the same answers and both turn an exponential search into linear work. The demo below counts the calls to make the difference concrete.

from functools import lru_cache

calls = 0

def fib_naive(n):
    global calls
    calls += 1
    if n < 2:
        return n
    return fib_naive(n - 1) + fib_naive(n - 2)

print(fib_naive(20), calls)

calls = 0

@lru_cache(maxsize=None)          # remember each answer the first time it is computed
def fib_memo(n):
    global calls
    calls += 1
    if n < 2:
        return n
    return fib_memo(n - 1) + fib_memo(n - 2)

print(fib_memo(20), calls)
6765 21891
6765 21

Both versions return 6765, but the naive one makes 21,891 calls and the memoised one makes 21. The gap grows exponentially with n. The @lru_cache decorator from the standard library is a quick way to memoise a pure function.

TrapUsing global counters in production code. The demo uses them only to count calls. Real DP code keeps its state local and passes it explicitly.

Climbing Stairs (LeetCode 70)

You climb a staircase of n steps, one or two steps at a time. Count the distinct ways to reach the top. Example: n = 3 gives 3, because the ways are 1+1+1, 1+2 and 2+1.

How to think about it

  1. Understand. The last move is either a 1-step or a 2-step, so the question is about endings. Order matters: 1+2 and 2+1 count separately.
  2. Brute force. Recurse: ways(n) = ways(n-1) + ways(n-2). That is the Fibonacci recursion, which is exponential.
  3. Find the waste. ways(5) needs ways(4) and ways(3), and ways(4) also needs ways(3). The same values are recomputed.
  4. Optimise. Define dp[i] as the number of ways to reach step i. Base cases: dp[1] = 1, dp[2] = 2. Recurrence: dp[i] = dp[i-1] + dp[i-2]. Only the last two values are needed, so keep two variables instead of an array.
  5. Dry run. Start with prev = 1 (ways to reach 1) and curr = 2 (ways to reach 2). For step 3: new = 1 + 2 = 3. For step 4: new = 2 + 3 = 5. For step 5: new = 3 + 5 = 8. Answer 8.

Code

def climb_stairs(n):
    if n <= 2:
        return n                  # 1 step: one way. 2 steps: 1+1 or 2.
    prev, curr = 1, 2             # ways to reach steps 1 and 2
    for _ in range(3, n + 1):
        prev, curr = curr, prev + curr   # ways(i) = ways(i-1) + ways(i-2)
    return curr

print(climb_stairs(2))
print(climb_stairs(3))
print(climb_stairs(5))
print(climb_stairs(10))

3
8
89

House Robber (LeetCode 198)

Houses stand in a row, each holding some money. You may rob any set of houses, but you cannot rob two adjacent houses (the alarm would sound). Return the largest total you can steal. Example: [2, 7, 9, 3, 1] gives 12, by robbing houses 2, 9 and 1.

How to think about it

  1. Understand. The only constraint is "no two adjacent". An empty row gives 0.
  2. Brute force. Try all subsets with no two neighbours and take the best. There are exponentially many, though fewer than all subsets.
  3. Find the waste. At house i you face a choice: skip it (and keep the best up to i-1), or rob it (add its money to the best up to i-2). Both sub-answers are reused across choices.
  4. Optimise. Let best(i) be the most you can get from houses 0 to i. Then best(i) = max(best(i-1), best(i-2) + nums[i]). Keep only the last two values.
  5. Dry run. On [2, 7, 9, 3, 1]: after 2, best is 2. After 7, best is max(2, 7) = 7. After 9, best is max(7, 2 + 9) = 11. After 3, best is max(11, 7 + 3) = 11. After 1, best is max(11, 11 + 1) = 12.

Code

def rob(nums):
    prev, curr = 0, 0            # best up to two houses back, and best up to the last house
    for x in nums:
        prev, curr = curr, max(curr, prev + x)   # skip x, or rob x and skip the last house
    return curr

print(rob([1, 2, 3, 1]))
print(rob([2, 7, 9, 3, 1]))
print(rob([2, 1, 1, 2]))
print(rob([]))

Pattern to rememberFor "maximum with no two chosen neighbours", the recurrence is max(skip, take plus the value two back).

Coin Change (LeetCode 322)

You have coins of several denominations, with unlimited copies of each. Return the fewest coins that add up to the amount, or -1 if it is impossible. Example: coins [1, 2, 5] and amount 11 give 3 (5 + 5 + 1).

How to think about it

  1. Understand. Unlimited coins means the order of coins does not matter, but the number used does.
  2. Brute force. For the amount, try each coin first and recurse on the rest. The tree of choices is huge.
  3. Find the waste. The fewest coins for amount 7 is the same question no matter how we arrived at 7, so each amount needs solving once.
  4. Optimise. dp[a] is the fewest coins for amount a. dp[0] = 0. For each a, dp[a] = min over coins c with c at most a of dp[a - c] + 1. Use infinity to mark amounts that cannot be made.
  5. Dry run. Coins [2], amount 3. dp[0] = 0, dp[1] is infinity (no way), dp[2] = dp[0] + 1 = 1, dp[3] would need dp[1], which is infinity. Answer -1.

Code

def coin_change(coins, amount):
    INF = float("inf")
    dp = [0] + [INF] * amount        # dp[a]: fewest coins for amount a
    for value in range(1, amount + 1):
        for coin in coins:
            if coin <= value and dp[value - coin] + 1 < dp[value]:
                dp[value] = dp[value - coin] + 1
    return dp[amount] if dp[amount] != INF else -1

print(coin_change([1, 2, 5], 11))
print(coin_change([2], 3))
print(coin_change([1], 0))
print(coin_change([3, 7], 10))

-1
0

Time O(amount × number of coins) · Space O(amount)

TrapUsing a greedy choice for coin change. Greedy fails for coins 1, 3 and 4 with amount 6 (it gives 3 coins, but 3 + 3 uses 2). The DP table is what makes the answer always correct.

Pattern to rememberFor "fewest items to reach a total" with unlimited reuse, the recurrence is min over items of dp[total - item] + 1.

Longest Valid Parentheses (LeetCode 32)

Given a string made only of ( and ), return the length of the longest substring that is a valid, balanced sequence. Example: "()(()" gives 2, because the longest balanced piece is "()". Example: ")()())" gives 4, from "()()".

How to think about it

  1. Understand. A valid substring has equal opening and closing brackets, and no prefix has more closing brackets than opening ones. The substring must be contiguous.
  2. Brute force. Check every substring with a balance counter that goes up on ( and down on ). A substring is valid if the balance never goes negative and ends at zero. That is O(n cubed) in total, which is too slow for long strings.
  3. Find the waste. Many substrings share the same ending. If we know the longest valid substring ending at each index, we can build the next one from it.
  4. Optimise. Let dp[i] be the length of the longest valid substring that ends at index i. Only a closing bracket can end a valid substring, so dp[i] matters only when s[i] is ). Two cases: if s[i-1] is (, the pair forms directly, so dp[i] = dp[i-2] + 2 (with dp[i-2] treated as 0 when i is small). If s[i-1] is ), look at the opening bracket that would match s[i], at index i - dp[i-1] - 1. If it is (, dp[i] = dp[i-1] + 2 plus whatever valid block sits just before that opening bracket.
  5. Dry run. On "(()())": index 1 is (, skip. Index 2 is ) after (, so dp[2] = 2. Index 3 is (, skip. Index 4 is ) after (, so dp[4] = dp[2] + 2 = 4. Index 5 is ) after ); its match is at index 5 - 4 - 1 = 0, which is (, so dp[5] = dp[4] + 2 = 6. The answer is 6.

Code

def longest_valid_brute(s):
    """Check every substring of even length with a balance counter. O(n cubed)."""
    best = 0
    n = len(s)
    for i in range(n):
        for j in range(i + 2, n + 1, 2):
            balance = 0
            ok = True
            for ch in s[i:j]:
                balance += 1 if ch == "(" else -1
                if balance < 0:          # a closing bracket with nothing to close
                    ok = False
                    break
            if ok and balance == 0:
                best = max(best, j - i)
    return best

def longest_valid(s):
    """dp[i] is the length of the longest valid substring ending at index i."""
    dp = [0] * len(s)
    best = 0
    for i in range(1, len(s)):
        if s[i] == ")":
            if s[i - 1] == "(":                          # the pair "()" closes right here
                dp[i] = (dp[i - 2] if i >= 2 else 0) + 2
            elif i - dp[i - 1] - 1 >= 0 and s[i - dp[i - 1] - 1] == "(":
                start = i - dp[i - 1] - 1                # the opening bracket that matches s[i]
                dp[i] = dp[i - 1] + 2 + (dp[start - 1] if start >= 1 else 0)
            best = max(best, dp[i])
    return best

for text in ["(()", ")()())", "", "()(()", "((()))()())(", "()()"]:
    print(repr(text), longest_valid_brute(text), longest_valid(text))

Pattern to rememberFor substrings that end at each position, store the best answer ending there and build from the one before, using the matching bracket to jump back.
