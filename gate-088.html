Integrity constraints

Integrity constraints are the rules a database must never break, such as a student must have a name and every enrolment must point to a real student. This topic covers domain, key, entity and referential integrity, the NOT NULL, UNIQUE and CHECK constraints, and what cascading actions do when a row is deleted, which GATE asks about in scenario questions.

The idea in plain words

Think of a library. The librarian follows rules. A book cannot be lent to a member who does not exist. Every book must have a title. Each book has a unique barcode. If a member is removed from the system, their loans must be handled too. These rules keep the records correct, even when many people are working at once.

A database works the same way. An integrity constraint is a rule that every state of the database must satisfy. The database system checks the rule when you insert, update or delete data, and it refuses any change that would break a rule.

Why this matters: without integrity constraints, a database could store a student enrolled in a course that does not exist, or two students with the same roll number. Errors like these spread silently into reports and decisions. The constraints stop them at the door.

Why this matters for GATE: many GATE questions describe a small database and a change to it, then ask whether the change is allowed, or what happens to the other rows. The answer depends on knowing exactly which rule is broken and what action the database takes.

Key terms

Integrity constraint
A rule that the stored data must always satisfy. Plain meaning: a rule the database will not let you break.
Domain
The set of allowed values for an attribute, such as whole numbers from 0 to 120 for age.
Domain constraint
A rule that each value of an attribute belongs to its domain.
NULL
A marker meaning "no value is known or applicable". It is not zero and not an empty string.
NOT NULL
A constraint that forbids NULL in a column.
UNIQUE
A constraint that no two rows have the same value in the column or set of columns.
CHECK
A constraint that a condition must hold for every row, such as age greater than or equal to 0.
Key constraint
The rule that the primary key of a relation is unique for every row.
Entity integrity
The rule that no primary key attribute may be NULL.
Referential integrity
The rule that every non-NULL foreign key value must match a primary key value in the referenced table.
Referencing (child) table
The table that holds the foreign key.
Referenced (parent) table
The table whose primary key is pointed to.
Violation
A change or state that breaks a constraint.
Cascading action
An automatic change to child rows when a parent row is deleted or changed.

Domain constraints and CHECK

Every attribute has a domain, which is the set of values it may hold. An age column is a set of whole numbers. A grade column may hold only the letters A to F. A name column holds text. The domain constraint says that each stored value must come from the domain.

Most systems express domains as data types, such as INT or VARCHAR. A type does not capture every rule, though. An age must not be negative, even though an INT can be negative. For such rules we use a CHECK constraint. It attaches a condition to the table, and every row must satisfy it.

CREATE TABLE Person (
  pid INT PRIMARY KEY,
  name VARCHAR(30),
  age INT CHECK (age >= 0 AND age <= 120),
  grade CHAR(1) CHECK (grade IN ('A', 'B', 'C', 'D', 'E', 'F'))
);

Read the CHECK lines. The age must be from 0 to 120. The grade must be one of six letters. An insert with age -5 is rejected, because the condition is False. An insert with grade Z is rejected too.

TrapA CHECK constraint is satisfied when its condition is True or UNKNOWN. If the age is NULL, the condition age >= 0 is UNKNOWN, so a plain CHECK accepts the row. To forbid NULL, add NOT NULL as well.

Would an insert with age NULL pass the CHECK on age above?

Yes, the CHECK passes because the condition is UNKNOWN. Only NOT NULL would stop it.

Is a domain constraint always enforced by the data type alone?

No. A type such as INT allows negative numbers, so a CHECK is needed for a rule such as "age is not negative".

NOT NULL, UNIQUE and key constraints

Some values must always be present. A student's name is an example. The NOT NULL constraint forbids NULL in such a column. An insert without a name is rejected.

A UNIQUE constraint says that no two rows may have the same value in that column, or in that group of columns. It is used for things like email addresses, where each address should belong to one person.

The primary key is a special case. It is UNIQUE and NOT NULL, both at once. Its job is to identify each row. This combination is the key constraint.

ConstraintForbidsTypical use
NOT NULLA missing valueName, date of birth
UNIQUETwo rows with the same valueEmail address
PRIMARY KEYBoth a missing value and a duplicateStudent id
CHECKA value that makes the condition FalseAge not negative, grade in a list

TrapIn standard SQL, several rows may have NULL in a UNIQUE column, because two NULLs are not treated as equal. A PRIMARY KEY never allows NULL. Check the rule for the database being discussed if the question names one.

Can a table have two rows with NULL email if email is UNIQUE but not NOT NULL?

Yes, in standard SQL. Two NULLs are not treated as equal, so the UNIQUE rule is not broken.

Which two constraints does a primary key satisfy at once?

UNIQUE and NOT NULL.

Entity integrity

Entity integrity says that no primary key attribute may be NULL. The reason is simple. A row must be identifiable. If its key were NULL, we could not refer to it, and we could not tell it apart from another row with a NULL key.

Example. The Student table below has a row with a NULL sid. This violates entity integrity, even if the other values in the row are correct.

sid (primary key)namedept_id
S1Asha10
NULLEve10

The second row must be rejected. Compare this with a NULL in dept_id, which is a different matter, as the next sections explain.

Key ideaEntity integrity applies only to the primary key. Other attributes may be NULL unless a NOT NULL constraint says otherwise.

Is a NULL in the dept_id column of Student a violation of entity integrity?

No. dept_id is not the primary key of Student. It may be NULL, unless the design forbids it with NOT NULL.

Why must a primary key never be NULL?

Because each row must be identifiable, and a NULL key cannot identify a row. Other tables that refer to the row would also have no value to point to.

Referential integrity and violations

Referential integrity links two tables. A foreign key in the child table must either be NULL, or match a primary key value that exists in the parent table. This keeps references honest. A student cannot belong to a department that does not exist.

Kiran's dept_id is NULL, which is allowed, because Kiran has no department yet. Asha, Ravi and Meera all point to departments that exist, so they are fine.

Now consider three changes, one at a time.

  1. Insert S5, Dev, dept_id 40. Department 40 does not exist. This violates referential integrity, and the insert is rejected.
  2. Insert S6, Tara, dept_id NULL. The foreign key is NULL, which is allowed. The insert is accepted.
  3. Delete department 10 while Asha and Meera still point to it. This would leave two rows pointing to a missing parent. The database must do something, and the next section explains the options.

TrapA NULL foreign key does not violate referential integrity. The rule applies only to non-NULL values. A foreign key with a value that matches no parent row is a violation.

The code below counts the violations in a small list of students. A violation is a non-NULL department that is not in the set of department ids.

dept_ids = {10, 20, 30}
students = [("S1", 10), ("S2", 20), ("S3", 10), ("S4", None), ("S5", 40)]
violations = [s for s, d in students if d is not None and d not in dept_ids]
print(violations)
print(len(violations))

Only S5 breaks the rule. S4 has NULL, so it is allowed.

Which kind of change can break referential integrity in the child table?

Inserting a child row, or updating its foreign key, to a value that does not exist in the parent table.

Is inserting a student with dept_id NULL allowed when dept_id is a foreign key?

Yes, unless the column is declared NOT NULL. The NULL value does not point to any row, so no rule is broken.

Cascading actions: CASCADE, SET NULL and RESTRICT

What should happen when a parent row is deleted and child rows still point to it? The database offers a choice, which the designer declares with the foreign key. These choices are the referential actions.

  • ON DELETE CASCADE. The child rows are deleted too. The change flows down the chain, which is why it is called cascading.
  • ON DELETE SET NULL. The child rows stay, but their foreign key is set to NULL. This is allowed only if the column is not declared NOT NULL.
  • ON DELETE RESTRICT or NO ACTION. The delete of the parent is rejected while any child refers to it.
  • ON DELETE SET DEFAULT. The foreign key is set to a default value, which must exist in the parent table.

Start from the Student table above and delete department 10 under each choice.

ChoiceResult of deleting department 10Rows left in Student
CASCADEAsha and Meera are deleted. Ravi and Kiran remain.2
SET NULLAsha and Meera stay, with dept_id NULL. Kiran was already NULL.4
RESTRICTThe delete of department 10 is rejected, and nothing changes.4

The SQL below shows how a designer declares the cascade. It is written as text for reading and is not run.

CREATE TABLE Student (
  sid CHAR(4) PRIMARY KEY,
  name VARCHAR(30) NOT NULL,
  dept_id INT REFERENCES Department(dept_id) ON DELETE CASCADE
);

The code below simulates the three choices on a small dictionary of students. The key is the sid and the value is the dept_id.

students = {"S1": 10, "S2": 20, "S3": 10, "S4": None}

def delete_dept(students, dept, action):
    if action == "cascade":
        return {s: d for s, d in students.items() if d != dept}
    if action == "set null":
        return {s: (None if d == dept else d) for s, d in students.items()}
    if any(d == dept for d in students.values()):
        raise ValueError("restricted")
    return students

after_cascade = delete_dept(students, 10, "cascade")
print(after_cascade)
after_null = delete_dept(students, 10, "set null")
print(after_null)
print(len(after_cascade))
print(sum(1 for d in after_null.values() if d is None))
try:
    delete_dept(students, 10, "restrict")
    print("deleted")
except ValueError:
    print("rejected")

Key ideaCascades can reach further than one table. If Enrol refers to Student with CASCADE, deleting a department can remove the students and then their enrolments too.

Under SET NULL, why does Kiran's row not change?

Kiran's dept_id is already NULL, and SET NULL only changes rows whose foreign key points to the deleted department.

Which choice would you pick if you want no student to be silently removed?

RESTRICT or NO ACTION, or SET NULL when the column allows NULL. CASCADE removes the child rows.

Chains of cascades and combined rules

Constraints often form a chain. Department is the parent of Student, and Student is the parent of Enrol, which lists the courses each student takes. If Student-to-Enrol uses CASCADE, then deleting a student also deletes that student's enrolments.

sidcid
S1C1
S1C2
S2C1
S3C2
S3C3

Suppose department 10 is deleted with CASCADE all the way down. Asha (S1) and Meera (S3) are deleted. Their enrolments are deleted too. Asha had 2 enrolments and Meera had 2, so 4 enrolment rows go. The total number of deleted rows is 2 students plus 4 enrolments, which is 6.

Count carefully. The cascade counts each deleted row once, whether it was a student or an enrolment. A common mistake is to count only the students and forget the enrolments.

GATE loves thisTo count rows deleted by a chain of cascades, first list the rows of the parent being deleted, then the child rows that point to them, then the grandchild rows that point to those children. Add all the lists.

If department 20 is deleted with CASCADE, which enrolment rows are removed?

The rows of S2, because Ravi is the only student of department 20. That is one row, (S2, C1).

Does RESTRICT on the Student to Enrol link stop the cascade from department to student?

No. The two links are separate. A RESTRICT on the Enrol link would only block deleting a student who still has enrolments.

Solved GATE-style problems

These problems are original, written in the GATE style. They are not real past questions. Use the tables on this page, and write down each change before deciding.

Which rule is broken?

A new row is inserted into Student with sid NULL and all other values correct. Which constraint is violated?

How to think about it

  1. What is asked. The name of the constraint that the insert breaks.
  2. Which idea applies. The primary key cannot be NULL.
  3. Work it out. sid is the primary key of Student. A NULL primary key breaks entity integrity. The other values do not matter.
  4. Check. Compare with a NULL dept_id, which is allowed, because dept_id is not the primary key.

Answer: entity integrity.

Count the referential violations

Department ids are 10, 20 and 30. The students are S1 with 10, S2 with 20, S3 with 10, S4 with NULL, and S5 with 40. How many students break referential integrity? This is a NAT question.

How to think about it

  1. What is asked. The count of students whose non-NULL department does not exist.
  2. Which idea applies. A NULL foreign key is allowed. A non-NULL one must match a parent.
  3. Work it out. S1, S2 and S3 match. S4 is NULL, which is allowed. S5 has 40, which is not a department. So 1 student breaks the rule.
  4. Check. Run the code below.
dept_ids = {10, 20, 30}
students = [("S1", 10), ("S2", 20), ("S3", 10), ("S4", None), ("S5", 40)]
bad = [s for s, d in students if d is not None and d not in dept_ids]
print(len(bad))
1

Answer: 1.

Select all true statements about constraints

Select all that apply.

  • (A) A primary key must be UNIQUE and NOT NULL.
  • (B) A foreign key may be NULL, unless the column is declared NOT NULL.
  • (C) ON DELETE CASCADE deletes the child rows when the parent row is deleted.
  • (D) A CHECK constraint is tested only when the table is first created.

How to think about it

  1. What is asked. Which statements are true.
  2. Which idea applies. The definitions of key, foreign key, cascade and CHECK.
  3. Work it out. (A) True, that is the key constraint. (B) True, a NULL foreign key points to nothing and breaks no rule. (C) True, that is the meaning of CASCADE. (D) False. A CHECK is tested on every insert and update.
  4. Check. The definitions settle each statement. No code is needed.

Answer: (A), (B) and (C).

Students left after a cascade

The students are S1 with department 10, S2 with 20, S3 with 10, and S4 with NULL. Department 10 is deleted with ON DELETE CASCADE. How many student rows remain? This is a NAT question.

How to think about it

  1. What is asked. The number of rows left in Student.
  2. Which idea applies. CASCADE removes every child row that points to the deleted parent.
  3. Work it out. S1 and S3 point to department 10, so both are removed. S2 and S4 remain, which is 2 rows.
  4. Check. Run the code below.
students = {"S1": 10, "S2": 20, "S3": 10, "S4": None}
remaining = {s: d for s, d in students.items() if d != 10}
print(len(remaining))
2

Answer: 2.

NULL count after SET NULL

The same students as in the previous problem are used, but department 10 is deleted with ON DELETE SET NULL. How many student rows have NULL in dept_id afterwards? This is a NAT question.

How to think about it

  1. What is asked. The count of NULL values in dept_id.
  2. Which idea applies. SET NULL keeps the rows and sets the foreign key to NULL.
  3. Work it out. S1 and S3 become NULL. S4 was already NULL. S2 still has 20. So 3 rows have NULL.
  4. Check. Run the code below.
students = {"S1": 10, "S2": 20, "S3": 10, "S4": None}
after = {s: (None if d == 10 else d) for s, d in students.items()}
print(sum(1 for d in after.values() if d is None))
3

Answer: 3.

Rows deleted by a chain of cascades

Department 10 is deleted with CASCADE on both links: Department to Student, and Student to Enrol. Students S1 and S3 belong to department 10. The Enrol rows are (S1, C1), (S1, C2), (S2, C1), (S3, C2) and (S3, C3). How many rows are deleted in total, counting students and enrolments together? This is a NAT question.

How to think about it

  1. What is asked. The total number of deleted rows in both tables.
  2. Which idea applies. Each cascade level adds the rows it removes.
  3. Work it out. Two students are removed. Their enrolments are (S1, C1), (S1, C2), (S3, C2) and (S3, C3), which is 4 rows. The enrolment of S2 is kept. The total is 2 + 4 = 6.
  4. Check. Run the code below.
students_in_dept = ["S1", "S3"]
enrol = [("S1", "C1"), ("S1", "C2"), ("S2", "C1"), ("S3", "C2"), ("S3", "C3")]
deleted_enrol = [e for e in enrol if e[0] in students_in_dept]
print(len(students_in_dept) + len(deleted_enrol))
6

Answer: 6.

Exam-level practice

Exam-level 1: Referential actions (MCQ, 2 marks)

Emp(eid, dept) references Dept(did) with ON DELETE CASCADE. Dept has 3 rows and Emp has 10 rows, 4 of them in department d2. After deleting d2 from Dept, how many Emp rows remain? (A) 10 (B) 6 (C) 4 (D) the delete is rejected

How to think about it

  1. What is asked. The effect of cascading delete.
  2. Which idea applies. CASCADE removes referencing rows along with the referenced row.
  3. Work it out. 10 − 4 = 6.
  4. Check. With ON DELETE RESTRICT, the delete would be rejected instead.

Answer: (B).

Exam-level 2: Keys and nulls (MSQ, 2 marks)

Which are TRUE in SQL? (A) A primary key column cannot be NULL. (B) A UNIQUE column may hold NULLs. (C) A foreign key value may be NULL. (D) A table may have several primary keys.

How to think about it

  1. What is asked. Rules for key constraints.
  2. Which idea applies. Entity integrity applies to primary keys only.
  3. Work it out. (A) True. (B) True in standard SQL. (C) True, meaning no reference. (D) One primary key, though it can span columns. False.
  4. Check. Candidate keys beyond the primary are declared UNIQUE.

Answer: (A), (B) and (C).

Exam-level 3: Superkey count (NAT, 2 marks)

Relation R(A, B, C, D) has candidate keys {A} and {B, C}. How many superkeys does R have?

How to think about it

  1. What is asked. The number of attribute sets containing a candidate key.
  2. Which idea applies. Count sets with A, plus sets with B and C, minus sets with both.
  3. Work it out. With A: 23 = 8. With B, C: 22 = 4. With A, B, C: 2. Total 8 + 4 − 2 = 10.
  4. Check. The code counts subsets.
from itertools import combinations
S = "ABCD"
sk = [c for r in range(1, 5) for c in combinations(S, r) if "A" in c or ("B" in c and "C" in c)]
print(len(sk))

10

Answer: 10.

Summary

Integrity constraint
A rule that stored data must always satisfy.
Domain
The allowed values for an attribute.
NULL
A marker for a missing or unknown value.
NOT NULL
Forbids NULL in a column.
UNIQUE
Forbids two rows with the same non-NULL value.
CHECK
A condition that each row must satisfy, accepted when True or UNKNOWN.
Key constraint
The primary key is unique and not NULL.
Entity integrity
No primary key value may be NULL.
Referential integrity
A non-NULL foreign key must match an existing parent key.
ON DELETE CASCADE
Deleting the parent deletes the child rows.
ON DELETE SET NULL
Deleting the parent sets the child foreign keys to NULL.
ON DELETE RESTRICT
Deleting the parent is rejected while children refer to it.
Violation
A change or state that breaks a constraint.
Cascade chain
Cascades that pass through several tables, one level at a time.

Remember these

  • A primary key is never NULL, and it is always unique.
  • A NULL foreign key breaks no rule. A non-NULL one must match a parent.
  • A CHECK condition that evaluates to UNKNOWN is accepted.
  • CASCADE removes children, SET NULL keeps them with NULL keys, and RESTRICT blocks the delete.
  • Count every row removed by a cascade chain, at every level.
  • For each scenario, name the broken rule first, then choose the action.
