Linear Search & Binary Search

Searching means finding where a value sits in a collection, or learning that it is not there. Linear search checks items one by one, and binary search halves a sorted list at each step. GATE often asks you to count comparisons and to compare the two methods.

The idea in plain words

Suppose a friend asks you to find the name "Meena" in a phone book. You could start on page 1 and read every name until you reach "Meena". That works, but it is slow. Or you could open the book near the middle, see whether "Meena" comes before or after that page, and throw away the half that cannot contain the name. Then repeat on the half that remains. The first method is linear search. The second is binary search.

The two methods have very different costs. If the book has a million names, linear search may read a million names in the worst case. Binary search needs only about 20 steps, because each step halves the work. This difference is the reason binary search is taught so early in algorithm courses.

The catch is that binary search only works when the names are sorted. A phone book is sorted by name. A pile of random receipts is not. If the data is unsorted, the halving trick throws away the wrong half, and the answer is wrong.

Why this matters for GATE. Questions ask you to find the number of comparisons for a given search, the best and worst cases, and the time complexity written in Big-O form. You must also know when each method is allowed. Read the question, look for the word "sorted", and count carefully.

Key terms

Search
Finding the position of a target value in a collection, or deciding that it is absent.
Target
The value you are looking for.
Linear search
Checking the items one after another from the start until the target is found or the list ends.
Binary search
Repeatedly comparing the target with the middle item of a sorted range, and keeping only the half that could contain the target.
Sorted
Arranged in non-decreasing order, so each item is at most the item after it.
Comparison
One test of the form "is this item equal to the target?" or "is this item less than the target?". Counting comparisons is the usual way to measure the cost of a search.
low, high
Two index variables that mark the part of the array still being searched. Index low is the first position still in play, and high is the last.
mid
The middle index of the current range, usually (low + high) // 2.
Iterative
Written with a loop.
Recursive
Written so the function calls itself on a smaller range.
Best case
The input for which the algorithm does the least work.
Worst case
The input for which the algorithm does the most work.
Average case
The expected work when every possible input is equally likely.
Big-O notation
A way to describe how the work grows with the size n. O(n) means the work grows in proportion to n. O(log n) means it grows with the number of times you can halve n.
Logarithm (base 2)
log2(n) is the power you need to raise 2 to, to get n. For example, log2(8) is 3, because 2 * 2 * 2 is 8.
Index
The position of an item in an array. The first position is 0.

Linear search and its cost

The method

Linear search starts at index 0. It compares the target with each item in turn. If it finds an equal item, it returns that index. If it reaches the end without a match, it returns -1, a common way to say "not found". It works on any list, sorted or not, because it never assumes an order.

def linear_search(arr, target):
    comparisons = 0
    for i in range(len(arr)):
        comparisons = comparisons + 1
        if arr[i] == target:
            return i, comparisons
    return -1, comparisons

data = [7, 3, 9, 4, 1]
print(linear_search(data, 9))
print(linear_search(data, 8))
(2, 3)
(-1, 5)

The first call looks for 9. The comparisons are with 7, 3 and 9, so three comparisons are made. The second call looks for 8, which is absent. All five items are compared, and the answer is -1. The variable comparisons counts each test, so you can see the cost directly.

How the cost grows

If the list has n items:

  • Best case: the target is the first item. One comparison. The cost is O(1).
  • Worst case: the target is last, or absent. n comparisons. The cost is O(n).
  • Average case: if the target is equally likely to be at any position, the average number of comparisons for a successful search is (n + 1) / 2. This is still O(n).

Check the average with the list above. Positions 1 to 5 need 1, 2, 3, 4 and 5 comparisons. The average is (1 + 2 + 3 + 4 + 5) / 5 = 3, which equals (5 + 1) / 2 = 3. It matches.

TrapThe average formula (n + 1) / 2 is for a successful search, where the target is in the list and each position is equally likely. It is not the same as the average over all searches, which also includes absent targets.

How many comparisons does linear search make for the first item of a list of 100 items?

One comparison. The target matches at index 0, so the loop returns straight away.

Does linear search need the list to be sorted?

No. It checks each item and never uses the order of the items, so it works for any list.

Binary search: the halving idea

Why halving works

Take a sorted list and look at the middle item. Two things can happen:

  • If the middle item equals the target, you are done.
  • If the middle item is less than the target, the target must be to the right of the middle, because everything to the left is even smaller. So you throw away the left half and the middle.
  • If the middle item is greater than the target, the target must be to the left. You throw away the right half and the middle.

Each comparison removes about half the remaining items. That is the whole idea. The argument is short: if the list has n items, after one comparison about n/2 remain, after two about n/4, and so on. The search ends when no items remain.

The three index variables

The algorithm keeps low and high, the first and last positions still in play. At each step:

  1. Set mid = (low + high) // 2. The double slash rounds down, so for low = 0 and high = 6, mid is 3.
  2. Compare arr[mid] with the target.
  3. If the item is less than the target, set low = mid + 1, because mid is now ruled out.
  4. If the item is greater than the target, set high = mid - 1.
  5. Stop when the target is found, or when low becomes greater than high. That means the range is empty.

Key ideaAdding 1 to low and subtracting 1 from high is what makes the range shrink. If you forget the +1 or the -1, the same middle item can be chosen again, and the loop can run forever.

A runnable example with a count

def binary_search(arr, target):
    low = 0
    high = len(arr) - 1
    comparisons = 0
    while low <= high:
        mid = (low + high) // 2
        comparisons = comparisons + 1
        if arr[mid] == target:
            return mid, comparisons
        elif arr[mid] < target:
            low = mid + 1
        else:
            high = mid - 1
    return -1, comparisons

sorted_data = [1, 3, 4, 7, 9, 12, 15]
print(binary_search(sorted_data, 9))
print(binary_search(sorted_data, 2))
print(binary_search(sorted_data, 1))
(4, 3)
(-1, 3)
(0, 3)

Let us trace the first call by hand, because this is the skill GATE tests. The list has indexes 0 to 6. The target is 9.

TrapWhen the range has an even number of items, the middle is the lower of the two middle positions, because // rounds down. For low = 4 and high = 5, mid is 4, not 5. Forgetting this rounding is a frequent error in hand traces.

For a list of 8 sorted items, with low = 0 and high = 7, what is mid?

mid is (0 + 7) // 2, which is 3 with rounding down. Index 3 is the fourth item.

Why does the algorithm set high = mid - 1 and not high = mid when the middle item is too large?

Because the middle item has already been compared and is known not to be the target. Keeping it in the range would waste a comparison, and the range might never shrink.

Iterative and recursive binary search

Two ways to write the same method

The version above uses a loop, so it is iterative. The same halving idea can also be written as a function that calls itself on the half that remains. This is recursive binary search. It has a base case, which is an empty range, and a recursive case, which is a call on the smaller range.

def bsearch(arr, target, low, high):
    if low > high:
        return -1
    mid = (low + high) // 2
    if arr[mid] == target:
        return mid
    if arr[mid] < target:
        return bsearch(arr, target, mid + 1, high)
    return bsearch(arr, target, low, mid - 1)

sorted_data = [1, 3, 4, 7, 9, 12, 15]
print(bsearch(sorted_data, 12, 0, len(sorted_data) - 1))
print(bsearch(sorted_data, 5, 0, len(sorted_data) - 1))
5
-1

The first call finds 12 at index 5. The second call looks for 5, which is absent. Trace it by hand. The first call has range 0 to 6, mid 3, and arr[3] is 7. Since 7 is greater than 5, the next call uses range 0 to 2. Its mid is 1, and arr[1] is 3, which is less than 5, so the next call uses range 2 to 2. Its mid is 2, and arr[2] is 4, still less than 5. The next call uses range 3 to 2, where low is greater than high, so it returns -1. That is four calls in total.

Which one should you use?

  • The iterative version uses a fixed amount of memory. It is usually the better choice in real code.
  • The recursive version uses one stack frame for each call. For binary search there are only about log n frames, so it is safe, but the call stack still grows.
  • In an exam, trace exactly the version the question describes. Both give the same answer, but the count of calls and the count of loop passes can be asked separately.

GATE loves thisQuestions often ask for the number of recursive calls or the number of loop iterations. Here each call or loop pass makes one comparison, so the numbers match. Read the wording carefully, because a question about calls may count the base call too.

In the recursive version, what does the base case low > high represent?

An empty range. The target is not in the array, so the function returns -1 without comparing anything.

Does the recursive version make one comparison per call?

Almost. Each call that reaches mid compares arr[mid] with the target once. The base case returns before reaching mid, so it makes no comparison.

Best, worst and average case

The best case

For binary search, the best case is when the middle item is the target at the very first step. One comparison, so the cost is O(1). For linear search the best case is the same: the target is first in the list.

The worst case

For binary search, the worst case is when the target is absent, or is found only after the range has shrunk to one item. Each step removes about half of the range, so the number of comparisons is at most floor(log2 n) + 1. Here floor means round down. The cost is O(log n).

import math
print(math.floor(math.log2(1000)) + 1)
print(math.ceil(math.log2(1001)))
10
10

For n = 1000, the bound is 10 comparisons. Linear search needs up to 1000. The two formulas floor(log2 n) + 1 and ceiling(log2(n + 1)) agree for every n, so either can be used.

The average case

The average depends on where the target sits. For a successful search where each item is equally likely, the average is a little below the worst case, and it still grows like log n. For example, the next code finds every item of a sorted list and counts the comparisons.

def binary_search(arr, target):
    low = 0
    high = len(arr) - 1
    comparisons = 0
    while low <= high:
        mid = (low + high) // 2
        comparisons = comparisons + 1
        if arr[mid] == target:
            return mid, comparisons
        elif arr[mid] < target:
            low = mid + 1
        else:
            high = mid - 1
    return -1, comparisons

sorted_data = [1, 3, 4, 7, 9, 12, 15]
for x in sorted_data:
    print(x, binary_search(sorted_data, x)[1])
1 3
3 2
4 3
7 1
9 3
12 2
15 3

Read the second column. The middle item 7 needs one comparison. Items 3 and 12 need two. Items 1, 4, 9 and 15 need three. Each value is the number of comparisons for one successful search.

from fractions import Fraction
counts = [3, 2, 3, 1, 3, 2, 3]
print(sum(counts), Fraction(sum(counts), len(counts)))
17 17/7

The total is 17 comparisons over 7 searches, so the average is 17/7, about 2.43 comparisons per successful search. Linear search would average (7 + 1) / 2 = 4 comparisons on this list, so binary search is clearly cheaper here.

Traps: sorted data, mid-point, stopping rule

Most lost marks in this topic come from three traps. The sections below show each one.

Trap 1: unsorted data

The code below runs both searches on the same unsorted list. The output shows what goes wrong.

def linear_search(arr, target):
    for i in range(len(arr)):
        if arr[i] == target:
            return i
    return -1

def binary_search(arr, target):
    low = 0
    high = len(arr) - 1
    comparisons = 0
    while low <= high:
        mid = (low + high) // 2
        comparisons = comparisons + 1
        if arr[mid] == target:
            return mid, comparisons
        elif arr[mid] < target:
            low = mid + 1
        else:
            high = mid - 1
    return -1, comparisons

data = [9, 2, 7, 1]
print(binary_search(data, 9))
print(linear_search(data, 9))
(-1, 3)
0

The value 9 is at index 0, so linear search is right. Binary search says "not found". It compared 9 with the middle items 2 and 7, decided 9 must be to the right, and looked in the wrong half. The halving rule depends completely on the order. Always check the question for the word "sorted" before you use binary search.

Trap 2: the mid-point formula

The formula (low + high) // 2 is correct for Python, because Python integers never overflow. In languages with fixed-size integers, such as C or Java, the sum low + high can overflow when both are large. The safe form is low + (high - low) // 2, which gives the same answer and never overflows. Exam questions sometimes use the safe form, so recognise it.

Trap 3: the stopping rule and empty arrays

The loop must continue while low <= high. With low < high the single remaining item would never be checked. An empty array is handled by the same rule: its high is -1, so low <= high is False from the start, and the function returns -1 with zero comparisons.

TrapStudents often say binary search "takes log n steps" and stop there. The exact count matters in exams. Work out the number of comparisons for the given array and target, or use floor(log2 n) + 1 for the worst case.

What does binary search return for an empty list, with the code in this topic?

It returns -1 and 0 comparisons, because high starts at -1 and the loop condition fails at once.

Which is faster on a list of 1000 sorted items for an absent target: linear or binary search?

Binary search. Linear search makes 1000 comparisons, and binary search makes at most 10.

Solved GATE-style problems

These problems are original, written in the GATE style, and are not taken from any past paper. Trace each one on paper before you read the steps.

Counting a linear search

Linear search starts at index 0 and compares the target with each item in turn. It stops as soon as it finds the target. It is run on the unsorted list 5, 8, 2, 6 to find the value 2. How many comparisons are made, counting the one that finds 2?

How to think about it

  1. What is asked. The number of comparisons up to and including the successful one.
  2. Which idea applies. Linear search compares items in order from the first, and it does not need sorted data.
  3. Work it out. Compare 2 with 5: not equal. Compare with 8: not equal. Compare with 2 (index 2): equal, so stop. That is 3 comparisons.
  4. Check. The position of 2 is index 2, which is the third item, so 3 comparisons is the right count.

Answer: 3

True statements about searching

Select all the true statements. (A) Linear search needs the list to be sorted. (B) Binary search on n sorted items makes at most floor(log2 n) + 1 comparisons. (C) Binary search needs direct access to the middle item, which an array provides. (D) The best case of linear search takes one comparison.

How to think about it

  1. What is asked. Every statement that is true, and only those.
  2. Which idea applies. Linear search works on any order. Binary search halves a sorted range and needs fast access to arr[mid].
  3. Work it out. (A) is false, because linear search does not need order. (B) is true, as this topic showed. (C) is true, since an array gives instant access by index. (D) is true, because the target can be the first item.
  4. Check. Statement A is the usual trap, because it describes binary search and not linear search.

Answer: (B), (C) and (D)

Binary search on ten values

The array is 2, 5, 8, 12, 16, 23, 38, 56, 72, 91 (indexes 0 to 9, sorted). Binary search with the rule mid = (low + high) // 2 looks for 23. How many comparisons are made, counting the one that finds 23?

How to think about it

  1. What is asked. The count of comparisons until 23 is found.
  2. Which idea applies. Keep the range from low to high, and look at the middle each time.
  3. Work it out. Start: low 0, high 9, mid 4, arr[4] is 16. 16 is less than 23, so low = 5. Next: low 5, high 9, mid 7, arr[7] is 56. 56 is greater than 23, so high = 6. Next: low 5, high 6, mid 5, arr[5] is 23. Found, after 3 comparisons.
  4. Check. The range sizes went 10, then 5, then 2, and the target was found at the third look. That matches the halving pattern.

Answer: 3

Binary search for an absent value

Use the same array as the previous problem, which is 2, 5, 8, 12, 16, 23, 38, 56, 72, 91. Binary search with mid = (low + high) // 2 looks for 40. How many comparisons are made before the search stops?

How to think about it

  1. What is asked. The number of comparisons, for a target that is not present.
  2. Which idea applies. The search stops when low is greater than high.
  3. Work it out. Start: low 0, high 9, mid 4 (16), less than 40, so low = 5. Next: low 5, high 9, mid 7 (56), greater than 40, so high = 6. Next: low 5, high 6, mid 5 (23), less than 40, so low = 6. Next: low 6, high 6, mid 6 (38), less than 40, so low = 7. Now low 7 is greater than high 6, so the search stops. That is 4 comparisons.
  4. Check. The answer 4 is within the bound floor(log2 10) + 1 = 4 for this array size, so it is a possible worst case.

Answer: 4

Worst case on 1000 items

A sorted array holds 1000 items. Using the worst-case bound for binary search from this topic, what is the maximum number of comparisons?

How to think about it

  1. What is asked. The bound floor(log2 n) + 1 for n = 1000.
  2. Which idea applies. The number of times 1000 can be halved before only one item is left.
  3. Work it out. 2 to the power 9 is 512, and 2 to the power 10 is 1024. Since 512 is at most 1000 and 1024 is more than 1000, floor(log2 1000) is 9. Then 9 + 1 = 10.
  4. Check. The earlier code printed 10 for this bound, and linear search would need up to 1000.

Answer: 10

Recursive search that fails

The recursive function below is called on the sorted array 1, 3, 4, 7, 9, 12, 15 with the target 5. Indexes run from 0 to 6, and the call is bsearch(arr, 5, 0, 6). How many calls are made in total, including the first call and the base-case call? What value is returned?

def bsearch(arr, target, low, high):
    if low > high:
        return -1
    mid = (low + high) // 2
    if arr[mid] == target:
        return mid
    if arr[mid] < target:
        return bsearch(arr, target, mid + 1, high)
    return bsearch(arr, target, low, mid - 1)

How to think about it

  1. What is asked. The number of calls, and the final return value.
  2. Which idea applies. Each call either returns, or makes one call on a smaller range.
  3. Work it out. Call 1: range 0 to 6, mid 3, arr[3] is 7, which is greater than 5, so call with range 0 to 2. Call 2: mid 1, arr[1] is 3, which is less than 5, so call with range 2 to 2. Call 3: mid 2, arr[2] is 4, which is less than 5, so call with range 3 to 2. Call 4: low 3 is greater than high 2, so it returns -1. The return value passes back up unchanged.
  4. Check. Four calls, each halving the range, and the final value is -1 because 5 is absent.

Answer: 4 calls, and the returned value is -1

Total comparisons over all items

The sorted array is 2, 4, 6, 8, 10, 12, 14, 16. Binary search with the loop version from this topic is run once for each item, searching for that item. What is the total number of comparisons over all 8 searches?

How to think about it

  1. What is asked. A single total, the sum of the 8 separate search costs.
  2. Which idea applies. Trace each successful search, counting the middle checks until the item is found.
  3. Work it out. Searching 2 takes 3 checks (mid 8, then 4, then 2). Searching 4 takes 2 (mid 8, then 4). Searching 6 takes 3 (mid 8, then 4, then 6). Searching 8 takes 1. Searching 10 takes 3 (mid 8, then 12, then 10). Searching 12 takes 2 (mid 8, then 12). Searching 14 takes 3 (mid 8, then 12, then 14). Searching 16 takes 4 (mid 8, then 12, then 14, then 16). Adding 3 + 2 + 3 + 1 + 3 + 2 + 3 + 4 gives 21.
  4. Check. The average is 21/8, which is a little under 3. That fits the sizes of the search paths, which are 1 to 4 checks.

Answer: 21

Two costs for an absent value

A sorted array has 100 items, and the target is not in the array. Give two numbers, separated by one space: the number of comparisons linear search makes, and the largest number binary search can make using the bound from this topic.

How to think about it

  1. What is asked. Two numbers, one for each method.
  2. Which idea applies. Linear search checks every item when the target is absent. Binary search is bounded by floor(log2 n) + 1.
  3. Work it out. Linear search compares with all 100 items, so it makes 100 comparisons. For binary search, 2 to the power 6 is 64 and 2 to the power 7 is 128. So floor(log2 100) is 6, and the bound is 6 + 1 = 7.
  4. Check. 100 is much larger than 7, which shows why binary search is preferred on sorted data.

Answer: 100 7

Exam-level practice

Exam-level 1: Binary search comparisons (NAT, 2 marks)

Binary search on a sorted array of 1000 elements. What is the maximum number of comparisons (of the key with an element) needed in the worst case?

How to think about it

  1. What is asked. The worst-case probe count.
  2. Which idea applies. Each probe halves the remaining range, so the worst case is ⌊log2 n⌋ + 1.
  3. Work it out. log2 1000 ≈ 9.97, so 9 + 1 = 10.
  4. Check. The code tries every key and missing key.
def probes(a, key):
    lo, hi, c = 0, len(a) - 1, 0
    while lo <= hi:
        mid = (lo + hi) // 2; c += 1
        if a[mid] == key: return c
        if a[mid] < key: lo = mid + 1
        else: hi = mid - 1
    return c
a = list(range(0, 2000, 2))
print(max(probes(a, k) for k in range(-1, 2001)))

10

Answer: 10.

Exam-level 2: First occurrence (NAT, 2 marks)

In a = [1, 2, 2, 2, 3, 5, 5, 8], a lower bound binary search returns the first index i with a[i] ≥ key. What does it return for key = 5, and for key = 4?

How to think about it

  1. What is asked. Two lower bound indices.
  2. Which idea applies. Lower bound narrows to the first position where the key could be inserted.
  3. Work it out. For 5, the first 5 is at index 5. For 4, the insertion point is also index 5.
  4. Check. Python's bisect_left gives the same.
import bisect
a = [1, 2, 2, 2, 3, 5, 5, 8]
print(bisect.bisect_left(a, 5), bisect.bisect_left(a, 4))

5 5

Answer: 5 and 5.

Exam-level 3: Search facts (MSQ, 2 marks)

Which are TRUE? (A) Binary search needs random access to be O(log n). (B) Linear search on an unsorted array has average cost about n/2 for a present key. (C) Binary search works on any array. (D) On a sorted linked list, binary search is O(log n).

How to think about it

  1. What is asked. Conditions for each search to be efficient.
  2. Which idea applies. Binary search depends on sorted order and O(1) access to the middle.
  3. Work it out. (A) True. (B) True. (C) The array must be sorted. False. (D) Finding the middle of a linked list costs O(n). False.
  4. Check. Skip lists exist precisely to give linked lists fast search.

Answer: (A) and (B).

Remember these

  1. Linear search works on any list. Binary search needs a sorted list.
  2. Binary search keeps low and high, and sets low = mid + 1 or high = mid - 1.
  3. The loop continues while low is less than or equal to high.
