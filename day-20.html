SQL versus NoSQL, and the BASE model

A relational database stores data in tables with fixed columns, connects tables with keys, and answers questions with SQL. Its main promise is ACID: transactions are atomic, consistent, isolated and durable, so an application can reason about data as if one thing happens at a time. You met this promise in the DBMS days.

NoSQL is a loose name for databases that do not use the relational model as their core. The name is usually read as "not only SQL", because many of these systems offer their own query languages. What they have in common is a set of design choices made for different goals:

  • Horizontal scale. Data is split across many machines, so capacity grows by adding servers rather than buying one bigger server. Joins across machines are slow, so NoSQL designs avoid them.
  • Flexible schema. Each record can have its own shape. Adding a field to some records does not require a migration of the whole table.
  • Access patterns first. You design the data around the questions the application asks. In SQL you normalise first and write queries later. In NoSQL you often store the data in the shape it will be read.
  • Relaxed guarantees. Many NoSQL systems give up some consistency or transactions in exchange for availability and speed. The next sections explain that trade-off.

BASE: the relaxed counterpart of ACID

BASE is the name given to the philosophy behind many distributed NoSQL systems. It stands for three ideas:

  • Basically Available. The system keeps responding, even when some nodes are down. The response might be older data or a partial result.
  • Soft state. The state of the system can change over time, even without new input, because replicas are still catching up with each other.
  • Eventually consistent. If no new writes arrive, all replicas eventually hold the same value. "Eventually" can mean milliseconds or seconds, and during that window readers may see different values.

Take a counter of likes on a post. If one replica records a like and another has not received it yet, a reader who asks the second replica sees one fewer like for a short time. Nobody is harmed, and a few seconds later the numbers agree. A bank balance does not tolerate that kind of delay, which is why banks use ACID systems.

Key ideaACID trades availability for correctness; BASE trades immediate correctness for availability and scale. Neither is better in general. The question is what your data can tolerate.

Interviewers askIs NoSQL faster than SQL? Not in general. A single-machine SQL database with the right indexes is often faster than a poorly used NoSQL cluster. NoSQL wins when the data must be spread across many machines and the access pattern is known in advance.

CAP and PACELC: the trade-offs every interviewer asks about

The CAP theorem, proposed by Eric Brewer and later proved by Gilbert and Lynch, says that a distributed data store cannot guarantee all three of these properties at the same time:

  • Consistency (C). Every read returns the most recent write, or an error. Here C means one single up-to-date view of the data, a property usually called linearizability. It is a different idea from the C in ACID.
  • Availability (A). Every request received by a working node gets a non-error response, although the data may be stale.
  • Partition tolerance (P). The system keeps working when the network drops or delays messages between nodes.

Network partitions happen in real data centres, so P is not optional for a distributed system. That leaves a choice when a partition occurs: keep answering and risk stale data (AP), or refuse some requests to keep data consistent (CP). "CA" is only possible on a single machine, where there is no partition to tolerate.

Here is a small simulation of the choice. Two replicas, A and B, hold a value. The network between them is broken, so a write to A cannot reach B. In AP mode the write is accepted and B serves an old value. In CP mode the write is refused. 

class Replica:
    def __init__(self, name):
        self.name = name
        self.value = "v0"
        self.other = None


class Cluster:
    def __init__(self, mode):
        self.mode = mode              # "CP" or "AP"
        self.partitioned = False
        self.a = Replica("A")
        self.b = Replica("B")
        self.a.other = self.b
        self.b.other = self.a

    def write(self, replica, value):
        if self.partitioned and self.mode == "CP":
            raise RuntimeError("write refused: cannot reach the other replica")
        replica.value = value
        if not self.partitioned:
            replica.other.value = value    # copy to the other replica
        return "ok"

    def read(self, replica):
        return replica.value


ap = Cluster("AP")
ap.partitioned = True
print(ap.write(ap.a, "v1"))
print("read from A:", ap.read(ap.a))
print("read from B:", ap.read(ap.b))

cp = Cluster("CP")
cp.partitioned = True
try:
    cp.write(cp.a, "v1")
except RuntimeError as e:
    print("error:", e)
print("read from B after refusal:", cp.read(cp.b))
ok
read from A: v1
read from B: v0
error: write refused: cannot reach the other replica
read from B after refusal: v0

Read the output carefully. In AP mode the write succeeded on A, and B still says v0. That is the stale read that AP accepts. In CP mode the write was refused, so no replica changed and the system never showed two different values. The price is that the user gets an error. Real systems are more subtle than this two-replica model, but the decision is the same.

TrapCAP says nothing about behaviour when the network is healthy. Many candidates say "NoSQL is AP, SQL is CP", which is too simple. Most systems are configurable, and the same database can behave differently per request.

PACELC: the part CAP leaves out

CAP only describes what happens during a partition, and partitions are rare. Daniel Abadi proposed PACELC to cover the normal case as well. It reads: if there is a Partition, choose Availability or Consistency; Else, when the system is running normally, choose Latency or Consistency.

The "else" part captures a real trade-off. To keep copies consistent, a write must wait for other replicas to confirm it, which adds latency. A system that replies as soon as one copy has the write is faster but may serve stale reads from another copy. So a system is described by two pairs, such as PA/EL (available during partitions, low latency normally) or PC/EC (consistent always, slower normally).

Bank transfer between two accountsPC/ECA stale balance can allow overdrafts or double spending, so refusing requests is better than being wrong.
Shopping cartPA/ELLosing a cart item is annoying but tolerable. Staying up and fast matters more.

Interviewers askExplain CAP in one sentence with an example. During a network partition, a system must either refuse some requests to keep all replicas consistent, or answer from possibly stale replicas. A bank refuses; a shopping cart answers.

The five families of NoSQL, including vector databases

"NoSQL" covers several different data models. Each family is built for a shape of data and a set of queries. Choosing well starts with knowing what each family is good at, and what it does badly.

Start with one question: "How do I usually find the data?" If the answer is always "by a single key", a key-value store is the simplest fit. If the answer is "by fields inside an object", a document store fits. If you walk relationships, use a graph. Wide-column stores fit very large write-heavy workloads where you know the partition key in advance. Vector stores fit similarity search.

Vector databases and similarity search

An embedding is a list of numbers that represents the meaning of an item. A language model turns a sentence into a vector with, for example, 768 or 1536 numbers. Items with similar meanings get vectors that point in similar directions. A vector database stores these vectors and answers "which stored vectors are closest to this query vector?" That is the core of semantic search and of retrieval for chatbots (RAG).

The usual similarity measure is cosine similarity. It is the cosine of the angle between two vectors: 1 means the same direction, 0 means unrelated, and -1 means opposite. It ignores the length of a vector, so a long document and a short one about the same topic still match. The next program ranks four toy three-number vectors against a query, using only the standard library. 

import math

docs = {
    "cats are small pets": [0.9, 0.1, 0.0],
    "kittens purr a lot": [0.7, 0.3, 0.1],
    "stock prices fell today": [0.0, 0.2, 0.9],
    "the market closed higher": [0.1, 0.1, 0.8],
}


def cosine(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    norm_a = math.sqrt(sum(x * x for x in a))
    norm_b = math.sqrt(sum(y * y for y in b))
    return dot / (norm_a * norm_b)


query = [0.85, 0.15, 0.05]   # the embedding of "pet kittens"

ranked = sorted(docs.items(), key=lambda kv: cosine(query, kv[1]), reverse=True)
for text, vec in ranked:
    print(f"{cosine(query, vec):.3f}  {text}")
0.996  cats are small pets
0.971  kittens purr a lot
0.199  the market closed higher
0.094  stock prices fell today

The two pet sentences score about 0.97 and 0.99, and the two finance sentences score under 0.2. The ranking is the search result. This program compares the query with every stored vector, which is fine for thousands of items. For millions of items, vector databases use approximate nearest neighbour indexes such as HNSW (a layered graph of links between vectors) or IVF (clusters of vectors). They accept a small chance of missing the true nearest neighbour in exchange for much faster search.

TrapEvery vector in one index must come from the same embedding model and have the same dimension. Mixing models gives scores that look numeric but mean nothing.

Interviewers askWhy not just use a vector database for everything? Vector stores are weak at exact matching, filtering by many fields, and transactions. Most applications keep their normal data in a relational or document database and add vector search next to it, or use pgvector to keep both in PostgreSQL.

MongoDB: document design and the aggregation pipeline

MongoDB is a document database. It stores documents, which are JSON-like objects written in a binary form called BSON, inside collections. A collection is roughly the equivalent of a table, but its documents do not need identical fields. Every document has an _id field that acts as its primary key; if you do not provide one, MongoDB generates a unique value. A single document can be at most 16 MB.

Design: embed or reference

The central modelling decision is whether related data lives inside one document (embedding) or in separate documents linked by an id (referencing). Here is the same order in both styles. 

// Embedded: one read returns the order and its items
{
  "_id": 101,
  "customer": "Ana",
  "status": "paid",
  "items": [
    { "sku": "pen", "qty": 2, "price": 3 },
    { "sku": "pad", "qty": 1, "price": 5 }
  ]
}

// Referenced: the order points at a customer document in another collection
{ "_id": 101, "customer_id": 7, "status": "paid" }

Embed when the child data is read together with the parent, belongs to one parent only, and has a bounded size. Reference when the same data is shared by many parents, changes often on its own, or can grow without limit. An order's line items are a classic embedding case. A product's list of every review ever written is a referencing case, because it grows without limit and would push the document toward the 16 MB limit.

TrapAn array that grows forever, such as all the comments on a popular post stored in the post document, slowly makes every read and write of that document more expensive. Keep arrays bounded, or move the unbounded part into its own collection.

Queries and indexes

The MongoDB shell, mongosh, uses JavaScript syntax. A filter is a JSON object, and operators start with $. Note that the examples in this unit are not run here, because they need a MongoDB server. The aggregation example later has its output shown as a JSON result instead. 

db.orders.insertMany([
  { customer: "Ana", items: [{ sku: "pen", qty: 2, price: 3 }, { sku: "pad", qty: 1, price: 5 }], status: "paid" },
  { customer: "Ben", items: [{ sku: "pen", qty: 1, price: 3 }], status: "paid" },
  { customer: "Ana", items: [{ sku: "ink", qty: 1, price: 7 }], status: "refunded" }
])

// find: a filter object, then a projection (1 keeps a field, 0 removes it)
db.orders.find({ "items.sku": "pen" }, { customer: 1, status: 1, _id: 0 })

// an index on the fields used together in filters
db.orders.createIndex({ customer: 1, status: 1 })

The find filter "items.sku": "pen" uses dot notation to reach inside the embedded array. MongoDB matches a document if any element of the array matches. Without an index, that filter scans every order.

The aggregation pipeline

An aggregation pipeline is a list of stages. Each stage receives the documents produced by the previous stage, transforms them, and passes the result on. It plays the role of SQL's WHERE, GROUP BY, ORDER BY and joins, combined into one ordered list. The most-used stages are:

  • $match filters documents, like WHERE. Put it first so later stages handle less data.
  • $unwind turns an array into one document per element, so each item can be grouped.
  • $group groups documents by a key and computes totals such as $sum, $avg or $count, like GROUP BY.
  • $sort, $project and $limit order, reshape and cap the output.
  • $lookup joins another collection, which is the closest equivalent of a SQL JOIN. Use it sparingly.

The pipeline below computes revenue and units per customer for paid orders only. It runs against the three orders inserted above. 

db.orders.aggregate([
  { $match: { status: "paid" } },
  { $unwind: "$items" },
  { $group: {
      _id: "$customer",
      revenue: { $sum: { $multiply: ["$items.qty", "$items.price"] } },
      units: { $sum: "$items.qty" }
  } },
  { $sort: { revenue: -1 } }
])

Result

[
  { "_id": "Ana", "revenue": 11, "units": 3 },
  { "_id": "Ben", "revenue": 3, "units": 1 }
]

Walk through the numbers. The refunded order is removed by $match. Ana's first order has two pens at 3 (6) and one pad at 5 (5), so her revenue is 11 and she bought 3 units. Ben has one pen at 3, so his revenue is 3 and his units are 1. $sort puts the larger revenue first.

Key ideaPut $match first. Filtering early lets MongoDB use an index and reduces the work for every later stage.

Interviewers askWhat is the difference between MongoDB and PostgreSQL with JSONB? Both store documents. MongoDB is built around documents, sharding and a flexible pipeline. PostgreSQL gives you ACID transactions across many tables, joins and mature SQL tooling, plus JSONB when some fields are flexible.

Redis: data types, commands and caching patterns

Redis is an in-memory key-value store that also offers rich data types. Keeping data in RAM makes reads and writes very fast, typically well under a millisecond on one server. Redis executes each command atomically on one main thread, so two clients never see a half-finished command. Redis can write snapshots to disk (RDB) and log every write (AOF) so that data survives a restart, but its main role is speed.

The data types

The value stored under a key can be one of several structures, and each has its own commands:

  • Strings hold text, numbers or binary data. Use them for counters (INCR), cached pages and tokens.
  • Hashes are field-value maps inside one key, like a small object. Use them for a user profile.
  • Lists are ordered sequences that push and pop at either end. Use them for simple queues.
  • Sets are unordered collections of unique members. Use them for tags or "has this user already done X?" checks.
  • Sorted sets keep members ordered by a numeric score. Use them for leaderboards and time-ordered indexes.

Redis also has bitmaps, HyperLogLog (approximate unique counts) and streams (append-only logs), which are beyond this day.

Expiry and eviction

A key with a TTL is deleted automatically after the time runs out. Memory is limited, so Redis also has an eviction policy that decides what to remove when it is full. Common policies include allkeys-lru (remove the least recently used key), allkeys-lfu (remove the least frequently used key), and noeviction (refuse new writes instead). For a cache, an LRU-style policy is the usual choice.

Caching patterns

A cache keeps a copy of data that is expensive to fetch, so most requests skip the slow database. The main patterns differ in who loads the cache and when writes reach the database:

  • Cache-aside (lazy loading). The application checks the cache first. On a miss it reads the database and stores the result. This is the most common pattern.
  • Write-through. Every write goes to the cache and the database together, so the cache is never stale, at the cost of slower writes.
  • Write-behind. Writes go to the cache and are saved to the database later in batches. Fast, but data can be lost if the cache fails before the batch is saved.

The next program simulates cache-aside with a fake database and a fake clock, so the output is fixed. It counts how many times the database is read. 

class FakeDB:
    def __init__(self):
        self.rows = {"user:1": "Ana", "user:2": "Ben"}
        self.reads = 0

    def get(self, key):
        self.reads += 1
        return self.rows.get(key)


class Cache:
    def __init__(self):
        self.store = {}        # key -> (value, expires_at)
        self.now = 0           # a fake clock, in seconds

    def get(self, key):
        item = self.store.get(key)
        if item is None:
            return None
        value, expires_at = item
        if self.now >= expires_at:
            del self.store[key]
            return None
        return value

    def set(self, key, value, ttl):
        self.store[key] = (value, self.now + ttl)


def get_user(key, cache, db):
    value = cache.get(key)
    if value is not None:
        return value, "hit"
    value = db.get(key)
    if value is not None:
        cache.set(key, value, ttl=10)
    return value, "miss"


db = FakeDB()
cache = Cache()
print(get_user("user:1", cache, db))
print(get_user("user:1", cache, db))
cache.now = 11                 # more than the 10 second TTL has passed
print(get_user("user:1", cache, db))
print("database reads:", db.reads)
('Ana', 'miss')
('Ana', 'hit')
('Ana', 'miss')
database reads: 2

The first call misses and loads from the database. The second call hits the cache, so the database is not touched. After the TTL expires, the third call misses again. Two database reads served three requests.

TrapCache-aside can serve stale data after a write unless you delete or update the cached key when the database changes. A common fix is to delete the key after each write and let the next read reload it.

TrapA popular key that expires can cause a cache stampede: many requests miss at the same moment and all hit the database. Mitigations are a lock so only one request reloads the key, random jitter added to TTLs so keys do not expire together, or refreshing the value before it expires.

Interviewers askWhy is Redis not a replacement for your primary database? It keeps data in memory, so the dataset must fit in RAM, and its durability settings trade speed for safety. It is excellent as a cache, a session store and a set of counters next to a durable database.

Consistent hashing: spreading keys across servers

A cache or a sharded database has many servers, and every key must be assigned to one of them. The simplest rule is server = hash(key) % N, where N is the number of servers. It works until N changes. If you add a fourth server, the modulus changes from 3 to 4, and almost every key maps to a different server. A cache that loses almost all its keys at once sends a flood of requests to the database.

Consistent hashing fixes this. Imagine a ring of positions from 0 up to a very large number. Hash each server's name to a point on the ring. Hash each key to a point too. A key belongs to the first server found going clockwise from its point. When a server is added, it takes over only the keys between it and the server before it on the ring. Roughly 1 out of N keys moves, instead of nearly all of them.

One server per ring point gives an uneven spread, because random points can cluster. The standard fix is virtual nodes: each real server is hashed to many points, often 100 or more, so its share averages out. The program below builds a ring of 3 servers with 100 virtual nodes each, places 1000 keys, then adds a fourth server and counts the keys that moved. For comparison it does the same count with plain modulo. 

import bisect
import hashlib


def h(text):
    return int(hashlib.md5(text.encode()).hexdigest(), 16)


class Ring:
    def __init__(self, nodes, virtual=100):
        self.points = []
        for node in nodes:
            for i in range(virtual):
                self.points.append((h(f"{node}#{i}"), node))
        self.points.sort()
        self.keys = [p for p, _ in self.points]

    def node_for(self, key):
        i = bisect.bisect(self.keys, h(key)) % len(self.keys)
        return self.points[i][1]


keys = [f"key{i}" for i in range(1000)]

ring3 = Ring(["A", "B", "C"])
counts = {}
for k in keys:
    n = ring3.node_for(k)
    counts[n] = counts.get(n, 0) + 1
print("ring of 3:", dict(sorted(counts.items())))

ring4 = Ring(["A", "B", "C", "D"])
moved = sum(1 for k in keys if ring3.node_for(k) != ring4.node_for(k))
print("keys moved by consistent hashing:", moved)

modulo_moved = sum(1 for k in keys if h(k) % 3 != h(k) % 4)
print("keys moved by hash modulo N:", modulo_moved)
ring of 3: {'A': 303, 'B': 361, 'C': 336}
keys moved by consistent hashing: 269
keys moved by hash modulo N: 748

Read the three numbers. Consistent hashing spreads the keys fairly evenly, with counts between 303 and 361 for 1000 keys. When the fourth server arrives, 269 keys move. Those are the keys the new server takes over, which is about one quarter of the total, the fair share for a server joining a ring of four. Plain modulo moves 748 keys, about three quarters, because nearly every key's remainder changes.

TrapNever use Python's built-in hash() to place keys on servers. For strings it is randomised for every new Python process, so two servers would disagree about where a key lives. Use a stable hash such as MD5, SHA-1, MurmurHash or xxHash, as the program does.

Interviewers askWhere is consistent hashing used? Caches such as memcached clients, sharded databases such as Cassandra and DynamoDB (through its partitioning scheme), and load balancers that need sticky routing. The idea is the same in each: adding or removing a node should move only a fair share of the keys.

Choosing a database: a practical method

Interviewers often ask "which database would you use here?" A strong answer is a method, not a brand name. Ask these questions in order:

  1. What questions will the data answer? Lookups by key, filters on many fields, relationship traversals, or similarity search each point to a different family.
  2. Do writes need transactions across several records? If yes, a relational database or a transactional store is the safe default.
  3. How much consistency is needed during failures? Use the CAP and PACELC reasoning from earlier to decide between refusing requests and serving stale ones.
  4. How big is the data, and how fast does it grow? Millions of rows on one machine rarely need a distributed database. Billions of writes per day usually do.
  5. What latency does the user need? Sub-millisecond reads often mean an in-memory store in front of the main database.
  6. What does the team already run and operate? A well-known database run well beats an exotic one run badly.

Orders, payments, accountsRelational (PostgreSQL)ACID transactions across tables, joins, constraints

Most real systems use more than one of these at once. This is sometimes called polyglot persistence: PostgreSQL holds orders, Redis caches hot data, and a vector index serves search. Each store does the job it is best at.

TrapChoosing a NoSQL database for scale you do not yet have is a common mistake. Start with PostgreSQL, which handles JSON, full-text search and vectors. Move a workload to a specialised store when measurements show a real need, not when a blog post sounds exciting.

Key ideaPick the database from the queries, the consistency needs and the scale, then state the trade-off out loud. Interviewers grade the reasoning, not the brand.

Interview questions

Answer each one aloud before opening it. The model answers are written the way you would say them in an interview.

Give one reason to choose NoSQL and one reason to stay with SQL.

NoSQL suits data that must spread across many machines with a flexible shape and a known access pattern, such as session data at large scale. SQL is the better choice when data has many relationships and needs multi-record ACID transactions, such as orders and payments.

What does BASE stand for, and how does it differ from ACID?

BASE stands for Basically Available, Soft state and Eventually consistent. ACID promises that each transaction is correct before anyone else sees it. BASE accepts that replicas may disagree for a while, so the system keeps responding during failures and converges later.

Explain CAP in one sentence, with an example of each choice.

When a network partition splits the nodes, a distributed system must either refuse some requests to keep data consistent (CP), as a bank transfer should, or keep answering with possibly stale data (AP), as a shopping cart can.

What does PACELC add to CAP?

PACELC covers the normal case, when there is no partition. Else, the system chooses between latency and consistency, because waiting for replicas to confirm writes costs time. It describes a system with two pairs, such as PA/EL or PC/EC.

Name the five families of NoSQL databases, with one example each.

Key-value (Redis), document (MongoDB), wide-column (Cassandra), graph (Neo4j), and vector (Pinecone, Milvus, or pgvector for similarity search on embeddings).

What is cosine similarity, and why do vector databases use approximate indexes?

Cosine similarity is the cosine of the angle between two vectors, so 1 means the same direction and it ignores vector length. Exact search compares the query with every vector, which is slow for millions of items. Approximate indexes such as HNSW or IVF find near neighbours much faster, accepting a small chance of missing the true nearest one.

When do you embed related data in MongoDB, and when do you reference it?

Embed when the child data is read with its parent, belongs to one parent, and has a bounded size, such as order line items. Reference when data is shared by many parents, changes independently, or grows without limit, because embedded arrays that grow forever make documents slow and can hit the 16 MB limit.

What is cache-aside, and how do you stop the cache from serving stale data?

In cache-aside the application checks the cache first, and on a miss it reads the database and stores the result with a TTL. To avoid stale data, delete or update the cached key whenever the database row changes, and keep TTLs short for data that changes often.

Why does consistent hashing move fewer keys than hash modulo N when a server is added?

With modulo, the divisor changes, so nearly every key's server changes. With consistent hashing, keys sit on a ring and a key belongs to the next server clockwise, so a new server takes over only the keys in its arc, about 1 out of N. Virtual nodes give each server many ring positions so the arcs, and therefore the load, are spread evenly.

What is union-find, and what two problems does it solve most often?

Union-find keeps disjoint sets and supports find (which set does this element belong to?) and union (merge two sets). With path compression and union by rank, each operation is effectively constant time. It is used to detect cycles in an undirected graph and inside Kruskal's algorithm for minimum spanning trees.

DSA: union-find and minimum spanning trees

Union-find, also called disjoint set union, tracks which items belong to the same group. Its two operations are find(x), which returns a representative of the group containing x, and union(a, b), which merges the groups of a and b. Two optimisations make it almost constant time: path compression, which points every node visited during find straight at the root, and union by rank, which attaches the shorter tree under the taller one. The combined cost is effectively constant per operation.

A spanning tree of a connected graph touches every node using exactly n minus 1 edges, with no cycle. A minimum spanning tree (MST) is one whose total edge weight is as small as possible. Kruskal's algorithm builds one by sorting all edges by weight and adding each edge that joins two different groups, skipping any edge that would close a cycle. Union-find is the tool that answers "are these two nodes already connected?" quickly. Prim's algorithm is the other standard method. It grows one tree from a start node and always adds the cheapest edge that leaves the tree, using a heap.

Redundant Connection (LeetCode 684)

A graph started as a tree on nodes 1 to n, and then one extra edge was added. The extra edge makes exactly one cycle. Each edge [a, b] connects two nodes in both directions. Return an edge that can be removed to leave a tree. If several edges could be removed, return the one that appears last in the input. Example: [[1,2],[1,3],[2,3]] gives [2,3], because the cycle 1, 2, 3 contains the edges [1,2], [1,3] and [2,3], and [2,3] is the last one in the input.

How to think about it

  1. Understand. The graph is undirected and has exactly one cycle. Any edge on that cycle can be removed. The tie-break is the last in the input order.
  2. Brute force. Try removing each edge, starting from the last, and check whether the remaining graph is connected and has no cycle. Each check is a graph traversal, so the total work is O(n squared) in the worst case.
  3. Find the waste. Each check starts from scratch, and most of the work repeats the same connectivity questions.
  4. Optimise. Process the edges in input order and merge their endpoints in union-find. The first edge whose endpoints are already in the same group closes the cycle. That edge is the answer. All other edges of the cycle appeared earlier, so this edge is the last one on the cycle, which is exactly the tie-break the problem asks for. Time is O(n) with near-constant union-find operations.
  5. Dry run. On [[1,2],[1,3],[2,3]]: union(1,2) joins two groups. union(1,3) joins a third node. union(2,3) finds that 2 and 3 are already in one group, so [2,3] is returned.

class DSU:
    def __init__(self, n):
        self.parent = list(range(n))
        self.rank = [0] * n

    def find(self, x):
        while self.parent[x] != x:
            self.parent[x] = self.parent[self.parent[x]]   # path halving
            x = self.parent[x]
        return x

    def union(self, a, b):
        ra, rb = self.find(a), self.find(b)
        if ra == rb:
            return False                                    # already connected: a cycle
        if self.rank[ra] < self.rank[rb]:
            ra, rb = rb, ra
        self.parent[rb] = ra
        if self.rank[ra] == self.rank[rb]:
            self.rank[ra] += 1
        return True


def find_redundant_connection(edges):
    dsu = DSU(len(edges) + 1)              # nodes are 1-based, so index 0 is unused
    for u, v in edges:
        if not dsu.union(u, v):
            return [u, v]


print(find_redundant_connection([[1, 2], [1, 3], [2, 3]]))
print(find_redundant_connection([[1, 2], [2, 3], [3, 4], [1, 4], [1, 5]]))
[2, 3]
[1, 4]

Min Cost to Connect All Points (LeetCode 1584)

You are given n points [x, y] on a plane. The cost of connecting two points is their Manhattan distance, |xi - xj| + |yi - yj|. Return the minimum total cost to connect all points, so that any point can reach any other through connections. Example: [[0,0],[2,2],[3,10],[5,2],[7,0]] gives 20. Example: [[3,12],[-2,5],[-4,1]] gives 18.

How to think about it

  1. Understand. Every pair of points can be connected, so the graph is complete. Connecting all points at the lowest cost means choosing a set of n minus 1 edges that forms a tree with the smallest total weight. That is a minimum spanning tree.
  2. Brute force. Try every set of n minus 1 edges, check that it connects all points without a cycle, and keep the cheapest. With n up to 1000 there are far too many sets to try.
  3. Find the waste. Most sets are obviously bad, because they use an expensive edge when a cheap one would connect the same points.
  4. Optimise. Kruskal's algorithm. Build all pairwise edges with their Manhattan costs, sort them by cost, and walk through them. Add an edge when its two points are in different union-find groups, and stop after n minus 1 edges. Sorting dominates, so the time is O(n squared log n) for the roughly n squared over 2 edges.
  5. Dry run. On [[3,12],[-2,5],[-4,1]], the costs are: points 1 and 2 cost |-2+4| + |5-1| = 6; points 0 and 1 cost |3+2| + |12-5| = 12; points 0 and 2 cost |3+4| + |12-1| = 18. Sorted: 6, 12, 18. Take 6 (joins 1 and 2), take 12 (joins 0 to them, now all connected), stop. Total 18.

def min_cost_connect_points(points):
    n = len(points)
    edges = []
    for i in range(n):
        xi, yi = points[i]
        for j in range(i + 1, n):
            xj, yj = points[j]
            edges.append((abs(xi - xj) + abs(yi - yj), i, j))
    edges.sort()                           # cheapest edges first

    dsu = DSU(n)
    total = 0
    joined = 0
    for cost, i, j in edges:
        if dsu.union(i, j):                # different groups: safe to add
            total += cost
            joined += 1
            if joined == n - 1:
                break
    return total


print(min_cost_connect_points([[0, 0], [2, 2], [3, 10], [5, 2], [7, 0]]))
print(min_cost_connect_points([[3, 12], [-2, 5], [-4, 1]]))
20
18

Time O(n² log n) · Space O(n²) for the edge list

TrapKruskal needs the edges sorted by cost, not by position. Sorting the tuples (cost, i, j) does that, because Python compares tuples element by element.

Pattern to rememberWhen you must connect everything at minimum total cost, think minimum spanning tree: sort the edges, use union-find to skip cycles, and stop at n minus 1 edges.

Redundant Connection II (LeetCode 685)

A rooted tree on nodes 1 to n was built, where each directed edge [u, v] goes from parent u to child v, and then one extra directed edge was added. The result is no longer a rooted tree. Remove one edge so that it becomes a rooted tree again: one root, and every other node has exactly one parent. If several answers exist, return the one that appears last in the input. Example: [[1,2],[1,3],[2,3]] gives [2,3], because node 3 has two parents, 1 and 2. Example: [[1,2],[2,3],[3,4],[4,1],[1,5]] gives [4,1], because the edges form a cycle 1 to 2 to 3 to 4 to 1.

How to think about it

  1. Understand. There are two possible faults, and they can occur together. A node can have two parents, or the directed edges can form a cycle. A cycle with no double parent can only be broken by removing an edge on the cycle. A double parent can only be fixed by removing one of its two incoming edges.
  2. Brute force. Try removing each edge from last to first, and check whether the rest is a rooted tree. A check is valid when no node has two parents and the undirected graph has no cycle. The first edge that passes is the answer. This costs O(n squared) with union-find checks.
  3. Find the waste. Only the edges touching the faults can be the answer. Checking every edge repeats the same cycle work.
  4. Optimise. First scan for a node with two parents. If one exists, call the earlier incoming edge cand1 and the later one cand2. Then run union-find over all edges except cand2. If that produces no cycle, removing cand2 is valid, so return it. If it does produce a cycle, the cycle must include cand1, so remove cand1. If no node has two parents, the only fault is a cycle, and the edge that closes it in union-find is the answer.
  5. Dry run. On [[1,2],[1,3],[2,3]], node 3 has two parents: cand1 is [1,3] and cand2 is [2,3]. Skip [2,3] and union [1,2] and [1,3]. No cycle appears, so return cand2, [2,3].

            x = self.parent[x]
        return x

        if ra == rb:
            return False
        if self.rank[ra] < self.rank[rb]:

def find_redundant_directed(edges):
    n = len(edges)
    parent = [0] * (n + 1)
    cand1 = cand2 = None
    for u, v in edges:
        if parent[v] == 0:
            parent[v] = u                  # first parent of v
        else:
            cand1 = [parent[v], v]         # the earlier edge into v
            cand2 = [u, v]                 # the later edge into v

    dsu = DSU(n + 1)
    for u, v in edges:
        if cand2 is not None and [u, v] == cand2:
            continue                       # pretend cand2 was never added
        if not dsu.union(u, v):            # a cycle appeared
            return cand1 if cand1 is not None else [u, v]
    return cand2


def redundant_brute(edges):
    n = len(edges)
    for skip in range(n - 1, -1, -1):      # last edge first
        indeg = [0] * (n + 1)
        dsu = DSU(n + 1)
        ok = True
        for i, (u, v) in enumerate(edges):
            if i == skip:
                continue
            indeg[v] += 1
            if indeg[v] > 1 or not dsu.union(u, v):
                ok = False
                break
        if ok:
            return list(edges[skip])
    return None

NoSQL
A family of databases built for horizontal scale, flexible schemas and known access patterns, often with relaxed guarantees.

Atomicity, consistency, isolation and durability: the transaction guarantees of relational systems.

Basically available, soft state, eventually consistent: the relaxed model behind many distributed NoSQL systems.

Replicas converge to the same value if no new writes arrive; readers may see old values meanwhile.
CAP theorem
During a network partition, a distributed system must give up either consistency or availability.
PACELC
Extends CAP: during a partition choose availability or consistency; otherwise choose latency or consistency.

The strongest single-object consistency: every read sees the most recent completed write.

Search that returns close matches quickly, accepting a small chance of missing the exact nearest item.

Strings, hashes, lists, sets and sorted sets, each with its own commands.

Using several database types in one system, each for the job it does best.
