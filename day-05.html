The four pillars of object-oriented programming

Object-oriented programming (OOP) organizes a program around objects, which bundle data (their state) with the functions that act on that data (their behaviour). A class is the blueprint for objects, and an object is one instance of a class. Four ideas are called the pillars of OOP. Interviewers expect you to name them, define each one in a sentence, and give an example.

Encapsulation

Encapsulation means hiding a class's data behind its functions. Outside code changes the state only through methods the class chooses to expose, so the class can check its own rules. A bank account that stores its balance in a private field can refuse a withdrawal larger than the balance. If the balance were public, any code could set it to any value.

Abstraction

Abstraction means exposing what an object does and hiding how it does it. A caller that asks a Notifier to send a message does not need to know whether the message goes by email or by SMS. Abstraction is about the interface a caller sees. Encapsulation is about protecting the data behind that interface. The two work together, but they are not the same idea.

Inheritance

Inheritance lets a new class (the derived or child class) reuse and extend an existing class (the base or parent class). The child gets the base's members and can add its own. The phrase to remember is "is-a": a dog is an animal, so Dog can inherit from Animal.

Polymorphism

Polymorphism means one name or call that behaves differently depending on the object. The word comes from Greek for "many forms". Polymorphism is what lets a loop call sound() on a list of mixed animals and get "Woof" from a dog and "Meow" from a cat, without an if for each type. There are two kinds, compile-time (overloading) and run-time (overriding through virtual functions), and the next section compares them.

The example below uses all four pillars in one small C++ program. The base class Animal keeps its name private (encapsulation), declares a pure virtual sound function that describes what an animal does without saying how (abstraction), is inherited by Dog and Cat (inheritance), and is called through a pointer to the base (polymorphism).

#include <iostream>
#include <memory>
#include <string>
#include <utility>
#include <vector>

// Abstraction: callers only see this interface.
class Animal {
public:
    explicit Animal(std::string name) : name_(std::move(name)) {}  // encapsulation: name_ is private
    virtual ~Animal() = default;                                  // needed so deleting through a base pointer is safe
    const std::string& name() const { return name_; }
    virtual std::string sound() const = 0;                        // pure virtual: each animal decides
private:
    std::string name_;
};

// Inheritance: Dog reuses name() and provides its own sound().
class Dog : public Animal {
public:
    using Animal::Animal;                                         // inherit the constructor
    std::string sound() const override { return "Woof"; }
};

class Cat : public Animal {
public:
    using Animal::Animal;
    std::string sound() const override { return "Meow"; }
};

int main() {
    // Polymorphism: one loop, different behaviour per object.
    std::vector<std::unique_ptr<Animal>> zoo;
    zoo.push_back(std::make_unique<Dog>("Rex"));
    zoo.push_back(std::make_unique<Cat>("Tom"));
    for (const auto& a : zoo) {
        std::cout << a->name() << " says " << a->sound() << "\n";
    }
    return 0;
}
Rex says Woof
Tom says Meow

The vector stores std::unique_ptr values, which own the animals and delete them automatically. The loop asks each animal for its sound through a pointer to Animal. The compiler picks Dog::sound or Cat::sound at run time, which is the behaviour that makes the program polymorphic.

Key ideaEncapsulation protects data, abstraction hides details behind an interface, inheritance reuses a base class, and polymorphism lets one call dispatch to different code. Name them in that order and give one example each.

What is the difference between encapsulation and abstraction?

Encapsulation hides the data of an object and protects it with methods that check its rules. Abstraction hides the details of how an operation is done and shows only what it does. A class can have one without the other, but good designs usually use both.

Overloading versus overriding

Both words describe having several functions with related behaviour, and they are the most confused pair of terms in OOP interviews. The difference is simple to state. Overloading means two or more functions in the same scope share a name but have different parameter lists. The compiler chooses between them when it compiles the call. This is compile-time polymorphism. Overriding means a derived class provides a new version of a function that the base class declared, with the same signature. The choice happens at run time when the function is virtual. This is run-time polymorphism.

Overloading: same name, different parameters

The compiler matches a call to the best overload by looking at the number and types of the arguments. An exact match is preferred to a conversion. The program below shows how the choice follows the argument type.

#include <iostream>

struct Printer {
    void show(int x)    { std::cout << "show(int) " << x << "\n"; }
    void show(double x) { std::cout << "show(double) " << x << "\n"; }
};

int main() {
    Printer p;
    p.show(3);      // exact match for int
    p.show(2.5);    // exact match for double
    return 0;
}
show(int) 3
show(double) 2.5

Nothing about these calls depends on run-time objects. The compiler writes a direct call to the right function, so there is no runtime cost. Overloading is useful for constructors, arithmetic helpers and functions that do the same job on different types.

Overriding: same signature, new behaviour

Overriding requires three things: a base-class function declared virtual, a derived-class function with the same name, parameters and const qualifier, and, as good practice, the keyword override. The override keyword asks the compiler to check that a base function exists with that exact signature. A typo in the name then becomes a compile error instead of a silently new function.

#include <iostream>

struct Base {
    virtual void hello() const { std::cout << "Base hello\n"; }
};

struct Derived : Base {
    void hello() const override { std::cout << "Derived hello\n"; }
};

int main() {
    Derived d;
    Base &r = d;       // a reference to the base part of d
    r.hello();        // the object decides, not the reference type
    d.hello();
    return 0;
}
Derived hello
Derived hello

Both calls print "Derived hello", even though r has type Base &. Because hello is virtual, the call goes through a hidden pointer stored in the object, which names the derived version. That is the essence of overriding: the reference type chooses the name, and the actual object chooses the code.

TrapIf you forget virtual in the base class, the call through a base reference runs the base version and prints "Base hello". Adding override in the derived class makes the compiler catch the mistake.

A derived class declares void show(std::string) and the base has show(int). Is this overloading or overriding, and what changes for callers?

It is overloading, because the parameter lists differ and both functions are visible through the same class name in one scope. It is not overriding, because the signatures differ. A subtle point: if the derived class declares any show, the base show overloads are hidden inside the derived class unless you add using Base::show;.

Abstract classes versus interfaces

An abstract class is a class that cannot be instantiated because it has at least one pure virtual function. A pure virtual function is declared with = 0 and has no required implementation in the base class. An interface is a contract: a class that only declares functions and holds no data. In C++ there is no separate keyword for an interface. It is a convention, an abstract class with only pure virtual functions and a virtual destructor. Java and C# have a dedicated interface keyword, which you will meet on day 6.

The choice is about what you want to share. An abstract class can hold data and provide default code that derived classes inherit, so it fits closely related classes that share state. An interface holds no state, so it fits unrelated classes that need to offer the same ability, such as "can be saved" or "can be sent". A class in C++ can inherit from several interfaces but usually from only one class with data, which keeps the design simple.

#include <iostream>
#include <string>
#include <utility>

// Interface style: only pure virtual functions and a virtual destructor, no data.
class Notifier {
public:
    virtual ~Notifier() = default;
    virtual void send(const std::string &msg) = 0;
};

// Abstract class with shared state and a default implementation.
class Service {
public:
    explicit Service(std::string name) : name_(std::move(name)) {}
    virtual ~Service() = default;
    void start() { std::cout << name_ << " started\n"; }   // shared code, inherited as is
    virtual void run() = 0;                                 // each service must provide this
protected:
    std::string name_;
};

class EmailNotifier : public Notifier {
public:
    void send(const std::string &msg) override { std::cout << "email: " << msg << "\n"; }
};

class Mailer : public Service {
public:
    Mailer() : Service("mailer") {}
    void run() override { std::cout << "mailer running\n"; }
};

int main() {
    EmailNotifier n;
    n.send("hello");
    Mailer m;
    m.start();
    m.run();
    // Notifier nope;   // compile error: Notifier has pure virtual functions only
    return 0;
}
email: hello
mailer started
mailer running

Read the code for the roles. Notifier promises a capability and nothing else, so EmailNotifier and any future SmsNotifier can implement it independently. Service has real data (name_) and real code (start), so every service shares the same startup behaviour. The commented line would not compile, because an abstract class cannot be created as an object.

Interviewers askWhat is the difference between an abstract class and an interface? Answer: an abstract class can hold state and default behaviour, and a class inherits it once. An interface holds only the contract, and a class can implement many of them.

Composition versus inheritance

Inheritance models "is-a". A Square is a shape, so it can inherit from Shape. Composition models "has-a". A car has an engine, so the car holds an engine object as a member. The usual advice, sometimes called "favour composition over inheritance", comes from the problems deep hierarchies cause. A derived class is tied to every decision of its base. When the base changes, the derived classes can break, and the child inherits behaviour it does not want.

Composition avoids that coupling. The outer object delegates work to its parts, and you can swap a part without touching the outer class. The example shows a car that uses an engine it owns.

#include <iostream>

class Engine {
public:
    void start() const { std::cout << "engine started\n"; }
};

class Car {                     // composition: a Car HAS an Engine
public:
    void drive() const {
        engine_.start();        // delegate the work to the part
        std::cout << "car driving\n";
    }
private:
    Engine engine_;             // the engine is a member, owned by the car
};

int main() {
    Car c;
    c.drive();
    return 0;
}
engine started
car driving

If the car inherited from Engine instead, a car would be an engine, which is wrong, and it would expose every public method of Engine to callers of Car. With composition, Car decides what to expose. If a future car uses an electric motor, you change one member, not the whole class tree.

TipAsk whether you can say "is a" in a full sentence without it sounding odd. If not, use composition. Inheritance should be used for a true specialization, such as a Dog that behaves like any Animal everywhere.

Why does composition usually lead to fewer breaking changes than inheritance?

A derived class inherits the base's behaviour and must keep working whenever the base changes. A class that uses another object through composition depends only on the public interface of that object, and it can keep the same interface while the internals change. Composition also makes it easy to swap parts at run time.

OOP in C++: constructors, virtual functions, vtable and RAII

C++ adds classes to C, and the details of object creation and destruction are a favourite interview topic. This unit covers four ideas in order: the order in which constructors and destructors run, how a virtual call finds the right function, what a vtable is, and the RAII pattern that makes resource handling safe.

Construction and destruction order

When you create a derived object, the base part is constructed first, then the derived part. When the object is destroyed, the order is reversed: the derived part is destroyed first, then the base. This rule guarantees that a derived class can rely on its base being fully set up and that the base is still alive while the derived part cleans up. A destructor should be virtual in any class meant to be used as a base, so that deleting an object through a base pointer runs the derived destructor too.

#include <iostream>

struct Base {
    Base()          { std::cout << "Base ctor\n"; }
    virtual ~Base() { std::cout << "Base dtor\n"; }
    virtual void who() const { std::cout << "Base\n"; }
    void call() const { who(); }    // calls through the virtual function
};

struct Derived : Base {
    Derived()          { std::cout << "Derived ctor\n"; }
    ~Derived() override { std::cout << "Derived dtor\n"; }
    void who() const override { std::cout << "Derived\n"; }
};

int main() {
    {
        Derived d;                 // constructed on the stack, destroyed at the closing brace
        d.call();
        Base &b = d;
        b.who();
    }
    std::cout << "--\n";
    Base *p = new Derived();       // heap object, destroyed with delete
    delete p;                      // virtual destructor: the Derived destructor runs first
    return 0;
}

Derived ctor

Derived dtor
Base dtor

Base ctor

Derived dtor
Base dtor

Trace the first block. Creating d runs Base ctor and then Derived ctor. Both d.call() and b.who() print "Derived", because the virtual call finds Derived::who. Leaving the block destroys d, which runs Derived dtor and then Base dtor. The second block repeats the sequence on the heap. Without a virtual destructor, delete p would destroy only the Base part, which is undefined behaviour for a derived object.

TrapVirtual functions do not reach into a base constructor or destructor. While the base constructor runs, the object is still a base object, so a virtual call there calls the base version. The same holds during destruction after the derived part is gone.

Virtual functions and the vtable

A vtable (virtual table) is a table of function addresses that the compiler creates for each class with virtual functions. Each object of such a class carries a hidden pointer, usually called the vptr, that points to its class's vtable. A virtual call such as b.who() works in three steps: read the vptr from the object, read the entry for who from the table, and call the address found there. The entry for Derived points to Derived::who, which is why the program prints "Derived".

The cost is one extra pointer per object and one extra indirect call per virtual call. A non-virtual call is resolved at compile time and has no such cost. The standard does not require a vtable, but nearly every mainstream compiler uses this design, and interviewers expect you to explain it.

Interviewers askHow does a virtual function call work? Answer: each polymorphic object holds a pointer to its class's vtable, and the call reads the function address for that slot from the table, then calls it.

RAII: tie a resource to an object's lifetime

RAII stands for "Resource Acquisition Is Initialization". The idea is that a resource such as a file, a lock, a socket or heap memory is acquired in a constructor and released in the destructor. Because C++ destroys local objects when a scope ends, even when an exception leaves the scope, the resource is always released. This removes the need for manual cleanup code on every exit path.

#include <iostream>
#include <stdexcept>

class FileGuard {                      // RAII: acquire in the constructor, release in the destructor
public:
    explicit FileGuard(const char *name) : name_(name) {
        std::cout << "open " << name_ << "\n";
    }
    ~FileGuard() {
        std::cout << "close " << name_ << "\n";
    }
    FileGuard(const FileGuard &) = delete;             // copying would close the file twice
    FileGuard &operator=(const FileGuard &) = delete;
private:
    const char *name_;
};

void work(bool fail) {
    FileGuard guard("data.txt");
    if (fail) {
        throw std::runtime_error("boom");   // the guard is still destroyed on the way out
    }
    std::cout << "working\n";
}

int main() {
    work(false);
    try {
        work(true);
    } catch (const std::exception &e) {
        std::cout << "caught " << e.what() << "\n";
    }
    return 0;
}
open data.txt
working
close data.txt
open data.txt
close data.txt
caught boom

In the failing call, the exception unwinds work. The local guard is destroyed during unwinding, so "close data.txt" prints before the catch handler runs. The deleted copy operations express a rule: a resource owner must not be copied, because two owners would release the same resource twice. The standard library follows the same idea with std::unique_ptr, which owns heap memory and frees it automatically, and std::lock_guard, which holds a lock.

Key ideaRAII turns cleanup into destruction. If you find yourself writing a matching release call for every acquire, wrap the resource in a class instead.

Why must the destructor of a base class be virtual when you delete through a base pointer?

Without a virtual destructor, delete on a base pointer calls only the base destructor, so the derived part is never cleaned up. Declaring the base destructor virtual makes the call go through the vtable to the derived destructor first, and then the base destructor runs.

Python, C++ and C side by side

Comparing the same small task in three languages shows what each one adds. The task is to store a rectangle and compute its area. The three programs below print the same line, so the differences are in how each language expresses the idea.

#include <stdio.h>

typedef struct { int w; int h; } Rect;

int area(const Rect *r) {
    return r->w * r->h;
}

int main(void) {
    Rect r = {3, 4};
    printf("area = %d\n", area(&r));
    return 0;
}
area = 12
#include <iostream>

class Rect {
public:
    Rect(int w, int h) : w_(w), h_(h) {}
    int area() const { return w_ * h_; }
private:
    int w_, h_;
};

int main() {
    Rect r(3, 4);
    std::cout << "area = " << r.area() << "\n";
    return 0;
}

class Rect:

        self.w = w
        self.h = h

    def area(self):
        return self.w * self.h

The C version keeps data and functions apart. The struct holds the numbers, and area is a free function that receives a pointer. Nothing ties the function to the struct except the programmer's habit. The C++ version puts the function inside the class, and the fields are private, so the compiler enforces encapsulation. The Python version has the same shape as C++, but the fields are attributes that anyone can read and change, and types are checked only when the code runs.

SOLID principles

SOLID is an acronym for five design principles, collected by Robert C. Martin. They describe how to split responsibilities so that code stays easy to change. The principles are guidelines, not laws, and applying them mechanically can add needless classes. Know what each one protects against, and be ready to say when you would break one on purpose.

  • S, Single Responsibility. A class should have one reason to change. An invoice class that both calculates totals and sends emails has two reasons to change.
  • O, Open/Closed. Code should be open for extension and closed for modification. You add a new behaviour by writing new code, not by editing tested code.
  • L, Liskov Substitution. A subtype must be usable wherever its base type is expected, without surprising the caller.
  • I, Interface Segregation. Clients should not be forced to depend on methods they do not use. Several small interfaces beat one large one.
  • D, Dependency Inversion. High-level code should depend on abstractions, and low-level details should depend on those abstractions too.

Open/Closed and Dependency Inversion in one example

The example below computes the total area of a list of shapes. Adding a triangle must not require changing total_area, which is the open/closed idea. The report class depends on an abstract storage object rather than a specific file format, which is dependency inversion.

from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self):
        """Return the area as a number."""

class Square(Shape):
    def __init__(self, side):
        self.side = side

    def area(self):
        return self.side * self.side

class Circle(Shape):
    def __init__(self, r):
        self.r = r

    def area(self):
        return 3 * self.r * self.r      # 3 as a simple approximation of pi, for this demo

def total_area(shapes):                 # never changes when a new shape is added
    return sum(s.area() for s in shapes)

class MemoryStore:
    def __init__(self):
        self.items = []

    def save(self, text):
        self.items.append(text)

class Report:                           # depends on any object with a save method
    def __init__(self, store):
        self.store = store

    def publish(self, shapes):
        self.store.save("total=" + str(total_area(shapes)))

print(total_area([Square(2), Circle(1)]))
store = MemoryStore()
Report(store).publish([Square(3)])
print(store.items)
7
['total=9']

Look at the first print. Square(2) has area 4 and Circle(1) has area 3 in this demo, so the total is 7. The loop in total_area never mentions a concrete class. Add a Triangle that subclasses Shape, and the function works unchanged. That is open/closed in practice.

The second part shows dependency inversion. Report needs only something that has a save method. In a real program the store could write to a database, and the report code would not change. Tests can pass a MemoryStore instead. The dependency points at the abstraction (the method name and its meaning), not at the detail (the database).

The other three principles

Single responsibility is easiest to see as a warning sign. If a class's methods fall into two groups that never call each other, such as "calculate tax" and "format a PDF", split the class. Each part can then change for its own reason without disturbing the other.

Liskov substitution is the classic trap question. A Square that inherits from Rectangle and forces width and height to match breaks code that sets the width and expects the height to stay the same. The subtype changed an expectation the base promised. Ask whether a caller could tell the difference, and if so, the inheritance is wrong.

Interface segregation means a Printer interface with print, scan and fax forces a simple printer to implement scanning it cannot do. Split the interface into Printable and Scannable, and each device implements only what it supports.

Interviewers askName the SOLID principle that a class with two unrelated reasons to change breaks. Answer: Single Responsibility. Then say how you would split the class.

Design patterns

A design pattern is a named, reusable solution to a common design problem. Patterns come from the "Gang of Four" book and are grouped into creational (how objects are made), structural (how they are combined) and behavioural (how they interact). Interviewers rarely want a pattern recited. They want to hear the problem it solves and see a short example. Four patterns cover most questions: Strategy, Observer, Factory and Singleton.

Strategy: swap an algorithm at run time

Strategy puts each algorithm behind a common interface, and the context object uses whichever strategy it was given. The context never changes when you add a new algorithm.

from abc import ABC, abstractmethod

class DiscountStrategy(ABC):
    @abstractmethod
    def apply(self, price):
        ...

class NoDiscount(DiscountStrategy):
    def apply(self, price):
        return price

class PercentOff(DiscountStrategy):
    def __init__(self, percent):
        self.percent = percent

    def apply(self, price):
        return price * (100 - self.percent) // 100

class Checkout:
    def __init__(self, strategy):
        self.strategy = strategy

    def total(self, price):
        return self.strategy.apply(price)

print(Checkout(NoDiscount()).total(200))
print(Checkout(PercentOff(15)).total(200))
200
170

The checkout class holds a reference to a strategy and calls apply on it. Changing the discount means passing a different object. The arithmetic price * (100 - self.percent) // 100 uses integers, so 200 with 15 percent off becomes 170 exactly. Without the integer division, Python would print a float such as 170.0.

Observer: notify many listeners about one event

Observer lets one object announce changes to any number of subscribers, without knowing who they are. A button fires "clicked", and a logger and a user interface both react. Subscribers can be added or removed at run time.

class Button:
    def __init__(self):
        self._listeners = []

    def subscribe(self, callback):
        self._listeners.append(callback)

    def click(self):
        for callback in self._listeners:
            callback("clicked")

button = Button()
button.subscribe(lambda event: print("logger got", event))
button.subscribe(lambda event: print("ui got", event))
button.click()
logger got clicked
ui got clicked

The listeners run in the order they subscribed. The button never imports the logger or the user interface, which keeps the two sides independent. This pattern underlies event handling in GUI toolkits and many message systems.

Factory: create objects without naming their classes

A factory is a function or method that returns an object, choosing the class from an input. Callers ask for "square" and get a square, without writing the class name in every place they create one. If a new shape is added, only the factory changes.

class Square:
    def __init__(self, side):
        self.side = side

    def area(self):
        return self.side * self.side

class Rectangle:
    def __init__(self, w, h):
        self.w = w
        self.h = h

    def area(self):
        return self.w * self.h

def create_shape(kind, *args):
    shapes = {"square": Square, "rectangle": Rectangle}
    if kind not in shapes:
        raise ValueError("unknown shape: " + kind)
    return shapes[kind](*args)

print(create_shape("square", 4).area())
print(create_shape("rectangle", 2, 5).area())
16
10

TrapA factory that uses a long if-else chain grows every time a class is added. A dictionary from names to classes, as above, keeps the lookup in one place and makes adding a shape a single line.

Singleton: only one instance

A singleton guarantees that a class has exactly one object, and gives every caller access to it. It is used for shared configuration or a connection pool. The pattern is often overused, because a single global object makes testing harder. In an interview, mention that risk along with the pattern.

class Config:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

first = Config()
second = Config()
print(first is second)
first.debug = True
print(second.debug)
True
True

__new__ runs before __init__ and creates the object. The first call stores the new object in a class attribute, and later calls return that same object. The two names first and second refer to one object, so the attribute set through one name is visible through the other.

Interviewers askWhat problem does Strategy solve? Answer: it removes a long if-else over algorithm types. Each algorithm lives in its own class behind one interface, and the context chooses one at run time.

What is the difference between the Strategy and Factory patterns?

Strategy chooses behaviour for an object that already exists, by giving it a different algorithm object. Factory chooses which class to create. A factory produces the object; a strategy is the part an object uses to do its work.

Interview questions

Answer each question aloud in two or three sentences, then open the answer to compare. The model answers use the same vocabulary you will hear in interviews.

Name the four pillars of OOP and give one example of each.

Encapsulation: a bank account keeps its balance private and changes it through deposit and withdraw. Abstraction: a caller asks a notifier to send a message and does not care about the transport. Inheritance: Dog extends Animal and reuses its name. Polymorphism: a loop calls sound on a mixed list and each object answers in its own way.

What is the difference between overloading and overriding?

Overloading gives several functions in one scope the same name with different parameter lists, and the compiler chooses at compile time. Overriding gives a derived class its own version of a virtual base function with the same signature, and the object's actual type chooses at run time.

What is an abstract class, and how does it differ from an interface in C++?

An abstract class has at least one pure virtual function, so it cannot be instantiated. It can hold data and shared code. An interface in C++ is a convention: an abstract class with only pure virtual functions and no data. A class can implement several interfaces, but usually inherits from one class with data.

Why do we say favour composition over inheritance?

Inheritance couples a derived class to every behaviour of its base, so base changes can break children. Composition lets a class use parts through their public interfaces, and parts can be replaced without changing the outer class. Use inheritance only for a true is-a relationship.

What is a vtable, and what does a virtual call do?

A vtable is a table of function addresses created for a class with virtual functions. Each object holds a pointer, the vptr, to its class's table. A virtual call reads the vptr, looks up the function's slot, and calls the address found there, so the derived version runs.

Why should a base class destructor be virtual?

So that deleting a derived object through a base pointer runs the derived destructor. Without it, only the base part is cleaned up, which is undefined behaviour.

What is RAII, and why does it matter for exceptions?

RAII ties a resource to an object: acquired in the constructor, released in the destructor. When an exception leaves a scope, C++ destroys the local objects, so the release still happens without extra cleanup code.

State the Single Responsibility principle and show how a violation looks.

A class should have one reason to change. A violation is a class that computes an invoice total and also sends email, because a change to the email format and a change to the tax rule would both touch it. Split it into an invoice class and a mailer.

Why is a Square that inherits from Rectangle a Liskov violation?

Code written for Rectangle assumes that setting the width leaves the height alone. A Square that forces width and height to match breaks that promise, so a caller that works with any Rectangle gets wrong results from a Square.

When would you use the Strategy pattern?

When one object needs to perform an operation in several ways that can be chosen at run time, such as different discount rules or sort orders. Each way is a class behind a common interface, and the context calls it without knowing which one it has.

DSA: sliding window

A sliding window is a contiguous range of an array or string, described by a left index and a right index. The right index moves forward to take in one element at a time. The left index moves forward only when the window breaks a rule, to remove elements until the rule holds again. Because each index moves forward and never back, the whole scan costs O(n), where a brute force search over all subarrays costs O(n^2) or more.

Sliding windows fit two kinds of question. A fixed-size window keeps the same length, and you slide it one step at a time. A variable-size window grows and shrinks, and you look for the longest or shortest window that satisfies a condition. The four problems today use both kinds, and the Hard problem uses the variable kind with a count of required characters.

Pattern to rememberWhen a problem asks for the longest, shortest, or best contiguous subarray or substring with a property, keep a window, grow the right end on every step, and shrink the left end only as needed to keep the window valid.

Best Time to Buy and Sell Stock (LeetCode 121)

You are given a list of prices, where prices[i] is the price of a stock on day i. Choose one day to buy and a later day to sell, and return the largest profit. If no profit is possible, return 0. For [7, 1, 5, 3, 6, 4], buy on day 1 at price 1 and sell on day 4 at price 6, for a profit of 5.

How to think about it

  1. Understand. The sell day must come after the buy day. Profit is the sell price minus the buy price, and the answer is never negative because doing nothing gives 0.
  2. Brute force. Try every pair of days where the sell day is after the buy day. That is O(n^2).
  3. Find the waste. For each sell day, the best buy day is the cheapest day seen before it. You do not need to compare with every earlier day, only with the cheapest one.
  4. Optimise. Keep a window with a left index for the buy day. Move right through the prices. If the price at right is lower than the price at left, the window restarts at right, because a cheaper buy day is always better. Otherwise, record the profit of selling at right. This is one pass with O(1) extra space.
  5. Dry run. Prices [7, 1, 5, 3, 6, 4], left = 0 (price 7). right = 1 (price 1) is lower, so left moves to 1. right = 2 (price 5): profit 4, best = 4. right = 3 (price 3): profit 2, best stays 4. right = 4 (price 6): profit 5, best = 5. right = 5 (price 4): profit 3, best stays 5. The answer is 5.

Code

def max_profit(prices):
    left = 0                                  # index of the buy day
    best = 0
    for right in range(1, len(prices)):       # right is the candidate sell day
        if prices[right] < prices[left]:
            left = right                      # a cheaper buy day starts a new window
        else:
            best = max(best, prices[right] - prices[left])
    return best

print(max_profit([7, 1, 5, 3, 6, 4]))
print(max_profit([7, 6, 4, 3, 1]))
5
0

Time O(n) · Space O(1)

TrapSelling and buying on the same day is not allowed, so the loop starts at day 1. A common bug is to compute profit before comparing with the cheapest buy day, which can give a negative value that is wrongly kept as the best.

Longest Repeating Character Replacement (LeetCode 424)

You are given a string s and an integer k. In one operation you may replace any character with another uppercase letter, and you may do this up to k times. Return the length of the longest substring that can be made to contain one repeated letter. For "ABAB" with k = 2, replace the two B's to get "AAAA", so the answer is 4.

How to think about it

  1. Understand. A substring can be fixed with k replacements when its length minus the count of its most frequent letter is at most k. Those other letters are the ones replaced.
  2. Brute force. Try every substring, count its letters and check the condition. That is O(n^3) with a naive count, or O(n^2 * 26) with incremental counts.
  3. Find the waste. Scanning all substrings repeats work. A window that moves right and shrinks from the left needs one count update per step.
  4. Optimise. Keep counts of letters inside the window and track the count of the most frequent letter, called most. Add the new right character. While the window length minus most is greater than k, remove the left character and move left. The answer is the largest window length seen. The trick that makes this O(n): most never has to decrease. A larger answer can only come from a larger most, so a stale value does not produce a wrong longer answer.
  5. Dry run. s = "AABABBA", k = 1. The window grows to "AABA" (length 4, most A = 3, 4 - 3 = 1 is at most 1), so the answer is at least 4. Adding "B" gives length 5 with most = 3, and 5 - 3 = 2 is more than 1, so left moves until the window is valid again. The best window length is 4.
def character_replacement(s, k):
    counts = {}
    left = 0
    most = 0                                  # count of the most frequent letter seen in any window
    best = 0
    for right, ch in enumerate(s):
        counts[ch] = counts.get(ch, 0) + 1
        most = max(most, counts[ch])
        while (right - left + 1) - most > k:    # too many letters would need replacing
            counts[s[left]] -= 1
            left += 1
        best = max(best, right - left + 1)
    return best

print(character_replacement("ABAB", 2))
print(character_replacement("AABABBA", 1))
print(character_replacement("AAAA", 0))
4
4
4

Time O(n) · Space O(1), since the dictionary holds at most 26 letters

Pattern to rememberWhen a window has a rule about its most common element, track that element as the window moves. Shrinking only removes one character at a time, so one pass is enough.

Permutation in String (LeetCode 567)

Given two strings s1 and s2, return True if s2 contains a permutation of s1, which means some substring of s2 has exactly the same letters with the same counts as s1, in any order. For s1 = "ab" and s2 = "eidbaooo", the answer is True, because "ba" is a permutation of "ab".

How to think about it

  1. Understand. A permutation has the same length and the same letter counts. So the target is a window of exactly len(s1) characters with matching counts.
  2. Brute force. For each start index in s2, take a substring of length len(s1), sort it, and compare with sorted s1. That is O(n * m log m).
  3. Find the waste. Sorting every window repeats work. Counts can be compared in constant time for lowercase letters, and neighbouring windows differ by one character on each side.
  4. Optimise. Keep a fixed-size window of len(s1) characters in s2 and a count array for it. Add the new character on the right and remove the character that leaves on the left. When the window counts equal the counts of s1, return True. Each step is O(26), so the total is O(26 * n).
  5. Dry run. s1 = "ab", counts a=1, b=1. s2 = "eidbaooo", window size 2. The windows are "ei", "id", "db", "ba". At "ba" the counts are a=1 and b=1, which match, so the answer is True.
def check_inclusion(s1, s2):
    if len(s1) > len(s2):
        return False
    need = [0] * 26
    window = [0] * 26
    for ch in s1:
        need[ord(ch) - ord('a')] += 1
    k = len(s1)
    for i, ch in enumerate(s2):
        window[ord(ch) - ord('a')] += 1          # the character entering on the right
        if i >= k:
            window[ord(s2[i - k]) - ord('a')] -= 1   # the character leaving on the left
        if i >= k - 1 and window == need:
            return True
    return False

print(check_inclusion("ab", "eidbaooo"))
print(check_inclusion("ab", "eidboaoo"))
print(check_inclusion("adc", "dcda"))
True
False
True

Time O(26 · n) which is O(n) · Space O(1)

TipFixed-size windows are easy to get wrong at the boundary. The window is complete only when the index reaches k - 1, so the comparison must wait until then.

Minimum Window Substring (LeetCode 76)

Given strings s and t, return the shortest substring of s that contains every character of t, including repeats. If no such substring exists, return the empty string. For s = "ADOBECODEBANC" and t = "ABC", the answer is "BANC", because it is the shortest window holding one A, one B and one C.

How to think about it

  1. Understand. Repeats matter: t = "AA" needs two A's in the window. The answer is the shortest valid window, and ties can be broken by the first one found. An empty answer is possible when s is too short or lacks a letter.
  2. Brute force. Try every start index and every end index, and check whether the substring contains t by counting letters. That is O(n^2) substrings, each checked in O(n) or more, so O(n^3) overall in the simple form.
  3. Find the waste. Re-counting letters for each substring repeats the same work. A window can carry a single number, called missing, for how many required letters it still lacks. That number changes by at most one per step.
  4. Optimise. Build need, the counts required by t. Move right and add each character to the window. A character that is still needed lowers missing by one. Once missing is 0, the window is valid: record it if it is the shortest so far, then move left to try a smaller one. Removing a needed character raises missing again. Each index enters and leaves the window once, so the time is O(len(s) + len(t)).
  5. Dry run. s = "ADOBECODEBANC", t = "ABC". need starts as A=1, B=1, C=1, and missing = 3. Moving right, the first valid window is "ADOBEC" (indexes 0 to 5), length 6. Shrinking from the left removes the A, which makes the window invalid again. Moving right, the window becomes valid once more at index 10 (the A), and shrinking from the left finds the window from index 9 to 12, which is "BANC", the shortest valid window with length 4. The answer is "BANC".
def min_window(s, t):
    if not t or len(t) > len(s):
        return ""
    need = {}
    for ch in t:
        need[ch] = need.get(ch, 0) + 1
    missing = len(t)                          # how many required letters the window still lacks
    best_start, best_len = 0, float("inf")
    left = 0
    for right, ch in enumerate(s):
        if need.get(ch, 0) > 0:
            missing -= 1
        need[ch] = need.get(ch, 0) - 1
        while missing == 0:                   # the window is valid, try to shrink it
            if right - left + 1 < best_len:
                best_start, best_len = left, right - left + 1
            out = s[left]
            need[out] += 1
            if need[out] > 0:                  # we removed a letter the window needs
                missing += 1
            left += 1
    return "" if best_len == float("inf") else s[best_start:best_start + best_len]

print(min_window("ADOBECODEBANC", "ABC"))
print(min_window("a", "a"))
print(min_window("a", "aa"))
BANC
a

Time O(len(s) + len(t)) · Space O(len(t)) for the counts

TrapThe window must shrink only while it is valid. Shrinking an invalid window misses answers, and forgetting to update missing when you remove a character leaves the loop stuck in a wrong state.

Pattern to rememberFor "shortest window that covers a requirement", keep a count of what is still missing. Expand right until the window is valid, then shrink left as far as possible while it stays valid.
