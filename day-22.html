How a request travels through a backend

A backend is the part of an application that runs on a server, away from the user's browser or phone. It receives requests, decides what to do, reads or writes data, and sends back a response. Almost every backend interview starts from the same picture, so learn it first.

The request lifecycle, step by step

A request is a message from a client (a browser, a mobile app, another service) asking for something, for example GET /api/users/42. A response is the message that comes back, usually with a status code such as 200 OK or 404 Not Found. Between the two, a typical request passes through these stages:

  1. Network and proxy. The request reaches a reverse proxy or load balancer (for example nginx or a cloud load balancer). It may terminate TLS (the HTTPS encryption), enforce limits, and pick one of several identical app servers.
  2. Application server. A process such as gunicorn (Python) or Node.js parses the raw bytes into a request object and hands it to your framework.
  3. Middleware. Small functions that run before the handler, one after another. Typical jobs: parse JSON, check the session cookie, log the request, add CORS headers. Middleware can stop a request early, for example returning 401 Unauthorized when there is no valid login.
  4. Routing. The framework matches the method and path (GET and /api/users/42) to one handler function, and extracts path variables such as 42.
  5. Handler (controller). The function validates the input, calls the business logic, and builds the result.
  6. Data access. The handler asks the database or a cache for data. This is often the slowest step, so most performance work happens here.
  7. Serialisation and response. The result (a Python dict, a Java object) is turned into text, usually JSON, and given headers such as Content-Type: application/json.
  8. Logging and clean-up. The request is logged with its status and duration, and per-request resources such as database connections are released.

If you can narrate these eight steps for any framework, you can answer most "what happens when a request arrives" questions.

Key ideaThe handler should be the thin middle of the request. Parsing, auth and logging happen around it, and storage happens below it.

Layered architecture and MVC

MVC stands for Model, View, Controller. The model holds data and the rules about it, the view renders output (an HTML page or a JSON document), and the controller receives the request, asks the model for data, and picks the view. MVC is mostly about separating presentation from data. Web frameworks such as Django, Rails and Spring MVC all use some version of it.

Layered architecture goes one step further and splits the backend into horizontal layers, each one talking only to the layer directly below it:

  • Presentation (routes and controllers). Parses HTTP input, checks the shape of the data, returns HTTP output.
  • Service (business logic). Rules such as "a user cannot place an order above their credit limit". It knows nothing about HTTP, so the same rule can be called from a web route, a background job or a test.
  • Repository or data access. The only code that writes SQL or calls the ORM. If the team later changes databases, only this layer changes.

A common mistake is a route that contains SQL, pricing rules and email sending all at once. It works on day one and becomes hard to test by month three.

TrapPutting business rules inside route handlers. Move the rule into a service function that takes plain arguments and returns plain values, then call that function from the route.

Express and Spring Boot in one minute each

Express is a minimal web framework for Node.js (JavaScript on the server). Its central idea is middleware: app.use adds a step that runs for every request, and app.get adds a route. Each handler receives a request object and a response object and must send exactly one response.

const express = require("express");

const app = express();
app.use(express.json());                 // middleware: parse JSON request bodies

app.get("/health", (req, res) => {       // route: GET /health
  res.json({ status: "ok" });            // send a JSON response with status 200
});

app.listen(3000, () => console.log("listening on 3000"));

Spring Boot is a Java framework. It uses dependency injection, which means a class declares what it needs (for example a repository) and the framework creates and passes those objects in, instead of the class building them itself. Annotations describe roles: @RestController marks a class that handles web requests, @GetMapping maps a method to a path, and @Service and @Repository mark the business and data layers.

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class HealthController {

    @GetMapping("/health")
    public String health() {
        return "ok";
    }
}

Both examples are shown without printed output because they need a running server to produce any. In an interview you do not need to memorise their syntax. You need to say that both use middleware or annotations to plug code into the request lifecycle, and that both support the layered style above.

What are the main stages of a request in a typical backend?

The request reaches a reverse proxy or load balancer, then an application server, then middleware (parsing, auth, logging), then routing to a handler. The handler calls the service layer and the data layer, the result is serialised into a response, and the request is logged before the response is sent.

Data access: ORMs, migrations and caching

Most backend bugs and slow endpoints come from data access. This unit covers three ideas that interviewers ask about constantly: the ORM and the N+1 problem, migrations that change a live schema safely, and caching with Redis.

ORMs and the N+1 problem

An ORM (object-relational mapper) lets you work with database rows as objects. SQLAlchemy (Python), Django ORM (Python), Hibernate or JPA (Java) and Prisma or Sequelize (JavaScript) are common examples. The ORM writes the SQL for you, which saves time but hides the number of queries it runs.

The N+1 problem is the most common ORM performance bug. Suppose you want every author and their books. The naive code does this:

  1. Run one query to get the N authors.
  2. For each author, run one more query to get that author's books.

That is 1 + N queries, which is why it is called N+1. With 1,000 authors you send 1,001 round trips to the database, and each round trip costs network time. The fix is to fetch everything in one query (a JOIN) or in two queries (one for authors, one for all their books using IN). ORMs provide this as eager loading. SQLAlchemy has joinedload and selectinload. Django has select_related (for single-valued relations, using a JOIN) and prefetch_related (for many-valued relations, using a second query).

The program below uses Python's built-in sqlite3 module so you can count the queries directly. It builds a small database in memory, runs the N+1 pattern, then runs one JOIN. A LEFT JOIN keeps authors who have no books; an ordinary JOIN would drop them.

import sqlite3

db = sqlite3.connect(":memory:")          # a database that lives only in RAM
db.executescript("""
CREATE TABLE author (id INTEGER PRIMARY KEY, name TEXT);
CREATE TABLE book (id INTEGER PRIMARY KEY, author_id INTEGER, title TEXT);
INSERT INTO author VALUES (1, 'Ada'), (2, 'Brian'), (3, 'Chen');
INSERT INTO book VALUES (1, 1, 'Notes'), (2, 2, 'Compilers'), (3, 3, 'Networks'), (4, 1, 'Proofs');
""")

query_count = 0

def run(sql, params=()):
    """Run one SQL statement and count it."""
    global query_count
    query_count += 1
    return db.execute(sql, params).fetchall()

# The N+1 pattern: one query for the authors, then one query per author.
authors = run("SELECT id, name FROM author")
for author_id, name in authors:
    books = run("SELECT title FROM book WHERE author_id = ?", (author_id,))
    print(name, [title for (title,) in books])
print("queries with N+1:", query_count)

# The fix: one JOIN returns every author and book pair in a single query.
query_count = 0
rows = run("""SELECT author.name, book.title
              FROM author LEFT JOIN book ON book.author_id = author.id
              ORDER BY author.id, book.id""")
print("rows from the JOIN:", len(rows))
print("queries with JOIN:", query_count)
Ada ['Notes', 'Proofs']
Brian ['Compilers']
Chen ['Networks']
queries with N+1: 4
rows from the JOIN: 4
queries with JOIN: 1

Read the output carefully. The N+1 version made 4 queries for 3 authors: one for the list and one per author. The JOIN made one query and returned 4 rows, one per author and book pair. Fewer queries is usually the win, and the result holds the same data.

TrapCounting rows as a proxy for queries. A JOIN can return many rows, and that is fine. The problem is the number of round trips, so count statements, not rows.

Migrations: changing the schema safely

A schema is the structure of your database: tables, columns, types and indexes. A migration is a versioned script that changes the schema, such as adding a column. Migrations let every developer and every server move the database through the same sequence of changes. Tools include Alembic (used with SQLAlchemy and Flask-Migrate), Django's built-in migrations, and Flyway or Liquibase for Java.

Each migration has a version number, and the database records which version it has reached. Starting the app runs only the migrations that have not been applied yet. The program below stores the version in SQLite's user_version field, a small integer the database keeps for the application.

  • Never edit a migration that has already run. Add a new one instead. Other machines already applied the old version.
  • Make changes backward compatible. When a column is renamed, add the new column, copy the data, switch the code, then drop the old column in a later release. This lets old and new app versions run during a deploy.
  • Be careful with large tables. Some ALTER TABLE statements lock the table for a long time. Add nullable columns first, then backfill in batches.
import sqlite3

MIGRATIONS = [
    # version 1: the first table
    "CREATE TABLE user (id INTEGER PRIMARY KEY, email TEXT NOT NULL)",
    # version 2: a new column with a default, so existing rows stay valid
    "ALTER TABLE user ADD COLUMN is_active INTEGER NOT NULL DEFAULT 1",
    # version 3: a unique index so two users cannot share an email
    "CREATE UNIQUE INDEX idx_user_email ON user (email)",
]

def migrate(db):
    """Apply every migration newer than the version stored in the database."""
    current = db.execute("PRAGMA user_version").fetchone()[0]
    print("starting at version", current)
    for version in range(current, len(MIGRATIONS)):
        db.execute(MIGRATIONS[version])
        db.execute(f"PRAGMA user_version = {version + 1}")
        print("applied", version + 1)
    db.commit()

db = sqlite3.connect(":memory:")
migrate(db)      # first run: applies versions 1, 2 and 3
migrate(db)      # second run: nothing left to do
print(db.execute("PRAGMA table_info(user)").fetchall())

[(0, 'id', 'INTEGER', 0, None, 1), (1, 'email', 'TEXT', 1, None, 0), (2, 'is_active', 'INTEGER', 1, '1', 0)]

The second call prints "starting at version 3" and then does nothing, which is what makes migrations safe to run on every deploy. Each line of the table information is a tuple: column id, name, type, whether it is NOT NULL, default value, and whether it is part of the primary key.

Caching with Redis

A cache stores the result of expensive work so the next request can skip it. Redis is an in-memory key-value store, often used as a shared cache across many app servers. Its values can carry a TTL (time to live), after which Redis deletes them automatically.

The most common pattern is cache-aside, sometimes called lazy loading. The application owns the logic:

  1. On a read, look in the cache first.
  2. On a hit, return the cached value.
  3. On a miss, read the database, store the result in the cache with a TTL, and return it.
  4. On a write, update the database and then delete (invalidate) the cached key, so the next read loads fresh data.

Deleting on write is usually safer than updating the cache, because two writers racing to update the cache can leave a stale value behind. The sketch below replaces Redis with a dict so it runs with no server. The method names match the idea, not a specific client library.

class FakeCache:
    """Stands in for Redis: a dict of key to value (expiry is not simulated)."""
    def __init__(self):
        self.data = {}

    def get(self, key):
        return self.data.get(key)

    def set(self, key, value, ttl_seconds):
        self.data[key] = value          # real Redis also remembers the TTL

    def delete(self, key):
        self.data.pop(key, None)

DB = {42: {"id": 42, "name": "Grace"}}  # pretend this is the database table
db_reads = 0

def load_user_from_db(user_id):
    global db_reads
    db_reads += 1
    return DB.get(user_id)

cache = FakeCache()

def get_user(user_id):
    key = f"user:{user_id}"
    cached = cache.get(key)
    if cached is not None:              # cache hit
        return cached
    user = load_user_from_db(user_id)   # cache miss
    if user is not None:
        cache.set(key, user, ttl_seconds=300)
    return user

def update_user(user_id, name):
    DB[user_id]["name"] = name
    cache.delete(f"user:{user_id}")     # invalidate, so the next read refills it

print(get_user(42)["name"])
print(get_user(42)["name"])
print("db reads so far:", db_reads)
update_user(42, "Grace Hopper")
print(get_user(42)["name"])
print("db reads so far:", db_reads)
Grace
Grace
db reads so far: 1
Grace Hopper
db reads so far: 2

The first two reads cost one database read in total: the first was a miss and the second was a hit. After the update, the cache entry was deleted, so the next read was a miss and went back to the database. Real systems add more care: a TTL bounds how stale a value can get, and many keys expiring at the same moment can cause a cache stampede, where many requests hit the database together. Adding a little random jitter to each TTL is a common fix.

Interviewers ask"How do you keep a cache consistent with the database?" Answer with cache-aside, invalidate on write rather than update, use a TTL as a safety net, and accept that a short window of staleness is the price of speed.

Why does the N+1 pattern get slower as data grows?

Each extra row in the parent list adds one more query, so the number of round trips grows in step with the data. Each round trip also has latency, so the total time is roughly the number of queries multiplied by the cost of one round trip. A single JOIN or a two-query IN lookup keeps the number of round trips constant as the list grows.

Authentication and authorisation

Authentication answers "who are you?". Authorisation answers "what are you allowed to do?". Mixing them up is a classic interview slip, so keep them apart in your head: a login proves identity, and every later request still needs its own permission check.

Password hashing: never store the password

You must never store a user's password as plain text, and you should not store it with a fast hash such as plain SHA-256 either. A hash is a one-way function: you can compute the hash from the password, but not the password from the hash. A salt is a random value, unique per user, mixed in before hashing. The salt stops two users with the same password from getting the same stored value, and it defeats precomputed lookup tables called rainbow tables.

The second requirement is that hashing should be slow. An attacker who steals the database will try billions of guesses, so each guess should cost real CPU time. The standard choices are:

  • Argon2id (the winner of the 2015 Password Hashing Competition). It is the recommended choice for new systems. It is memory-hard, which makes GPU attacks expensive.
  • bcrypt. Widely deployed, with a tunable cost factor. It silently uses only the first 72 bytes of the password, which is a trap for very long passphrases.
  • PBKDF2 and scrypt. PBKDF2 is the one most often required by compliance rules, and Python ships it in the standard library.

The program below uses PBKDF2 from the standard library so it runs with no installs. In real code the salt must come from secrets.token_bytes(16) or a library. This demo uses a fixed salt only so the output is repeatable. Verification recomputes the hash from the same salt and compares the results with hmac.compare_digest, which takes the same time whether the strings match early or late. A plain == can leak information through timing.

import hashlib
import hmac

ITERATIONS = 100_000

def hash_password(password, salt):
    digest = hashlib.pbkdf2_hmac("sha256", password.encode(), salt, ITERATIONS)
    return salt.hex() + "$" + digest.hex()          # store salt and hash together

def verify_password(password, stored):
    salt_hex, digest_hex = stored.split("$")
    digest = hashlib.pbkdf2_hmac("sha256", password.encode(), bytes.fromhex(salt_hex), ITERATIONS)
    return hmac.compare_digest(digest.hex(), digest_hex)

salt = bytes(range(16))            # fixed only so this demo is repeatable
stored = hash_password("correct horse", salt)
print(len(stored))
print(verify_password("correct horse", stored))
print(verify_password("wrong guess", stored))

True
False

The stored value is 97 characters: 32 hex characters for the 16-byte salt, one separator, and 64 hex characters for the 32-byte SHA-256 output. The number 97 is a useful sanity check when you explain the format.

TrapUsing a general-purpose hash such as MD5 or SHA-256 alone for passwords. They are designed to be fast, which is exactly wrong here. Use Argon2id, bcrypt, scrypt or PBKDF2 through a well-tested library.

Sessions versus JWT

After a successful login, the server must remember that the user is logged in. There are two common designs.

A server-side session stores the user's state on the server, keyed by a random session ID. The browser holds only that ID, usually in a cookie. The cookie should be marked HttpOnly (JavaScript cannot read it), Secure (sent only over HTTPS) and SameSite (limits cross-site sending, which helps against CSRF). Logging out is easy: delete the session on the server. The cost is that every server must reach the same session store, usually Redis or a database.

A JWT (JSON Web Token, pronounced "jot") is a self-contained token. It has three parts separated by dots: a header that names the signing algorithm, a payload of claims such as the user ID and expiry time, and a signature. The server signs the first two parts with a secret key and checks the signature on each request, without a database lookup. That is the big advantage: the token is stateless. The disadvantages are that a JWT cannot be revoked before it expires unless you add a block list, and that its payload is only base64url-encoded, which anyone can decode. Never put secrets in a JWT.

The program below builds a toy HS256 token (HMAC with SHA-256) using only the standard library, so you can see exactly what the three parts are. Production code should use a maintained library such as PyJWT, which also checks expiry and the algorithm.

import base64
import hashlib
import hmac
import json

SECRET = b"demo-secret"

def b64url(data):
    return base64.urlsafe_b64encode(data).rstrip(b"=").decode()

def make_token(claims):
    header = {"alg": "HS256", "typ": "JWT"}
    h = b64url(json.dumps(header, separators=(",", ":"), sort_keys=True).encode())
    p = b64url(json.dumps(claims, separators=(",", ":"), sort_keys=True).encode())
    sig = hmac.new(SECRET, f"{h}.{p}".encode(), hashlib.sha256).digest()
    return f"{h}.{p}.{b64url(sig)}"

def check_token(token):
    h, p, s = token.split(".")
    expected = b64url(hmac.new(SECRET, f"{h}.{p}".encode(), hashlib.sha256).digest())
    if not hmac.compare_digest(s, expected):
        return None                      # signature does not match: reject
    padded = p + "=" * (-len(p) % 4)     # restore the padding base64 needs
    return json.loads(base64.urlsafe_b64decode(padded))

token = make_token({"sub": "user-7", "role": "admin"})
print(token)
print(check_token(token))
tampered = token[:-2] + ("AA" if token[-2:] != "AA" else "BB")
print(check_token(tampered))

The first line is the token. The second line shows the decoded payload, and the tampered copy fails the signature check and returns None. The payload is readable by anyone, so the signature protects integrity (nobody can change it) but not confidentiality (nobody can read it). That is why sensitive data does not belong in a JWT.

Interviewers ask"Session or JWT?" A strong answer: sessions when you need instant revocation and have a shared store; JWTs when you need stateless verification across many services and accept that revocation waits for expiry. Many systems use short-lived JWTs plus a revocable refresh token.

Refresh tokens

Because a JWT cannot be revoked easily, teams keep it short-lived, for example 15 minutes. That creates a usability problem: users would have to log in again every quarter hour. A refresh token solves this. It is a long-lived credential (days or weeks) that the client exchanges for a new access token when the short one expires. Unlike the access token, the refresh token is stored server-side or in a revocable form, so it can be cancelled.

The important defence is rotation with reuse detection. Each time a refresh token is used, the server issues a new refresh token and marks the old one as used. Refresh tokens belong to a family that started at login. If a token that was already used comes back, someone has probably copied it, so the server revokes the whole family and the user must log in again. The program below simulates this with a dict.

import itertools

class AuthStore:
    def __init__(self):
        self.ids = itertools.count(1)       # simple counter for readable IDs
        self.refresh = {}                   # token -> (user, family, used?)
        self.revoked_families = set()

    def login(self, user):
        family = next(self.ids)             # a new family starts at login
        token = f"rt-{next(self.ids)}"
        self.refresh[token] = (user, family, False)
        return token

    def rotate(self, token):
        if token not in self.refresh:
            return None, "unknown token"
        user, family, used = self.refresh[token]
        if family in self.revoked_families:
            return None, "family revoked"
        if used:
            # a token that was already used came back: treat it as stolen
            self.revoked_families.add(family)
            return None, "reuse detected, family revoked"
        self.refresh[token] = (user, family, True)     # mark the old token used
        new_token = f"rt-{next(self.ids)}"
        self.refresh[new_token] = (user, family, False)
        return new_token, "ok"

store = AuthStore()
t1 = store.login("ada")
t2, msg = store.rotate(t1)          # normal refresh: succeeds
print(msg, t2)
_, msg = store.rotate(t1)           # replay the old token: detected
print(msg)
_, msg = store.rotate(t2)           # the newer token is now dead too
print(msg)
ok rt-3
reuse detected, family revoked
family revoked

The first refresh works and returns rt-3. Replaying rt-2 is detected because it was already used, which revokes the whole family, so even the legitimate newest token rt-3 stops working. This trade-off is intentional: when in doubt, the server signs the user out.

TrapStoring refresh tokens in local storage, where any script on the page can read them. Prefer an HttpOnly, Secure cookie that is sent only to the refresh endpoint.

RBAC: role-based access control

RBAC (role-based access control) grants permissions to roles, and gives roles to users. A user who holds the role editor can do everything that role allows. The key design rule is to check a permission in your code, not a role name. Writing if role == "admin" all over the codebase makes every new role a rewrite. Writing if can(user, "article:delete") keeps the rule in one table.

Two principles go with RBAC. Least privilege means each role gets only the permissions it needs. Deny by default means a missing entry means no access. Some systems add ABAC (attribute-based access control), which also looks at things like ownership ("this user may edit only their own posts"). The code below shows the basic RBAC table.

ROLE_PERMISSIONS = {
    "viewer": {"article:read"},
    "editor": {"article:read", "article:write"},
    "admin": {"article:read", "article:write", "article:delete", "user:manage"},
}

def can(user_roles, permission):
    """True if any of the user's roles grants the permission (deny by default)."""
    return any(permission in ROLE_PERMISSIONS.get(role, set()) for role in user_roles)

def delete_article(user_roles, article_id):
    if not can(user_roles, "article:delete"):
        return f"403 Forbidden: article {article_id}"
    return f"200 OK: deleted article {article_id}"

print(can(["viewer"], "article:read"))
print(can(["editor"], "article:delete"))
print(delete_article(["editor"], 9))
print(delete_article(["editor", "admin"], 9))
True
False
403 Forbidden: article 9
200 OK: deleted article 9

Notice the difference between the two status codes. 401 Unauthorized means "I do not know who you are" (missing or invalid login). 403 Forbidden means "I know who you are, and you may not do this." The editor is authenticated but lacks the permission, so the answer is 403.

What is the difference between 401 and 403?

401 Unauthorized means the request has no valid authentication, so the client should log in and try again. 403 Forbidden means the server knows who the caller is, but that caller is not allowed to perform this action. Repeating the same request with the same identity will keep failing with 403.

Background jobs, retries, idempotency and uploads

A web request should finish quickly, usually well under a second. Anything slow or unreliable, such as sending an email, resizing an image, or calling a flaky payment provider, should not hold the user's request open. This unit covers how to move that work out of the request path and how to make it safe to repeat.

Background jobs

A background job is a unit of work that runs outside the request. The web handler does three things: validate the input, save a record of what must happen (a job message), and return a response such as 202 Accepted, which means "received, will process later". A separate worker process takes jobs from a queue and runs them. Common tools are Celery (Python, often with Redis or RabbitMQ as the broker), RQ, Sidekiq (Ruby), and BullMQ (Node.js).

Jobs should be small, carry only IDs rather than large objects, and be safe to run more than once. That last point leads straight to the next section, because most queue systems deliver each job at least once, not exactly once.

TrapPassing a whole database object in the job message. By the time the worker runs, the object may be stale or deleted. Pass the ID and load fresh data inside the job.

Retries and exponential backoff

Networks fail, and so do other services. A retry repeats an operation after a failure. Retry only transient errors (timeouts, HTTP 503, connection resets). Retrying a validation error, or a 400 Bad Request, will fail forever. The usual schedule is exponential backoff: wait a little, then double the wait each time, with a cap so the wait never becomes absurd. Many systems add jitter, a random amount, so thousands of clients do not all retry at the same moment and overload the service again.

The function below computes the delays without any randomness, so you can read them directly.

def backoff_delays(attempts, base=0.5, cap=8.0):
    """Seconds to wait before each retry: base, 2x base, 4x base, ... up to cap."""
    return [min(cap, base * 2 ** n) for n in range(attempts)]

print(backoff_delays(6))
[0.5, 1.0, 2.0, 4.0, 8.0, 8.0]

The delays grow 0.5, 1, 2, 4, then reach the cap of 8 seconds and stay there. Without the cap, the sixth wait would be 16 seconds and the tenth would be over eight minutes, which is rarely what a user wants.

Idempotency: safe to repeat

An operation is idempotent if doing it twice has the same effect as doing it once. Reading data is naturally idempotent. Charging a card is not. Suppose the client sends "charge 25 dollars", the server charges the card, but the response is lost in the network. The client retries, and the customer is charged twice. The standard fix is an idempotency key: the client generates a unique key per logical operation and sends it in a header such as Idempotency-Key. The server stores the result under that key, and any retry with the same key returns the stored result instead of acting again.

class PaymentService:
    def __init__(self):
        self.results = {}       # idempotency key to the response we already sent
        self.charges = 0

    def charge(self, amount_cents, idempotency_key):
        if idempotency_key in self.results:
            return self.results[idempotency_key]     # replay: no second charge
        self.charges += 1
        response = {"status": "charged", "amount": amount_cents, "charge_no": self.charges}
        self.results[idempotency_key] = response
        return response

svc = PaymentService()
print(svc.charge(2500, "key-abc"))
print(svc.charge(2500, "key-abc"))     # the client retried after a timeout
print("total charges:", svc.charges)
{'status': 'charged', 'amount': 2500, 'charge_no': 1}
{'status': 'charged', 'amount': 2500, 'charge_no': 1}
total charges: 1

The second call returns the first response unchanged and the charge counter stays at 1. In production the key store must be durable (a database table with a unique constraint is typical), and the key must be checked and the result saved atomically, or two concurrent requests with the same key can both slip through.

Interviewers ask"How do you make a retried payment safe?" Use an idempotency key stored with the result, return the stored result on replay, retry only transient errors with exponential backoff and jitter, and enforce uniqueness in the database so concurrent duplicates cannot both succeed.

WebSockets for real-time updates

HTTP is request then response: the server cannot speak first. A WebSocket is a long-lived connection, started as an ordinary HTTP request with an Upgrade header, that then stays open so either side can send messages at any time. It suits chat, live dashboards and multiplayer games. The URL scheme is wss:// over TLS, the equivalent of https://.

Simpler options are often enough. Polling asks the server every few seconds. Server-Sent Events (SSE) keep one stream open from server to browser only. Use WebSockets when the client must also send frequent messages. Scaling is the hard part: a message sent to a user connected to server A must reach server B if that user is connected there. Teams solve this with a pub/sub layer such as Redis, so that any server can publish a message and every server holding a relevant connection delivers it.

A typical message is just JSON on the open connection. The shape below is only an example of a message your own protocol might use:

{"type": "chat.message", "room": "general", "text": "Build passed"}

File uploads to S3 with presigned URLs

Amazon S3 is object storage for files. If a user uploads a 200 MB video through your API server, the bytes flow through your server twice (in and out to S3), which ties up memory and bandwidth. A presigned URL avoids that. Your server checks the user is allowed to upload, then asks S3 for a URL that contains a signature and an expiry time. The client uploads straight to S3 with an HTTP PUT to that URL. The URL works only for that object, for that method, until it expires.

import boto3

s3 = boto3.client("s3")
upload_url = s3.generate_presigned_url(
    ClientMethod="put_object",
    Params={"Bucket": "my-uploads", "Key": "avatars/user-7.png", "ContentType": "image/png"},
    ExpiresIn=300,          # the URL stops working after 5 minutes
)
# Return upload_url to the client. The client sends a PUT with the same Content-Type.

This snippet needs the boto3 package and AWS credentials, so it has no printed output here. The design points matter more than the call. Keep expiry short, restrict the key prefix to the user's own folder, and check the file type and size after the upload (for example in an S3 event that triggers a job), because the presigned URL itself does not inspect the file.

TrapTrusting the client's file name or content type. The client chooses both. Generate the object key on the server and verify the real content after upload.

Operating the service: logging, health checks and twelve-factor

A backend that works on your laptop is not yet a backend that works in production. This unit covers the habits that keep a service observable and easy to deploy.

Logging

A log is a record of events written as the program runs. Use the standard logging module rather than print, because logging gives you levels, names and handlers. The levels, from least to most severe, are DEBUG, INFO, WARNING, ERROR and CRITICAL. A logger drops any message below its level, which is why the debug line below does not appear.

In production, prefer structured logs: one JSON object per line, with fields such as request ID, user ID and duration. Log aggregation tools can then filter by field. Always include a request or correlation ID so you can follow one request across services. Never log passwords, tokens, or full card numbers.

import io
import logging

stream = io.StringIO()                     # capture output in memory for the demo
handler = logging.StreamHandler(stream)
handler.setFormatter(logging.Formatter("%(levelname)s %(name)s: %(message)s"))
log = logging.getLogger("orders")
log.setLevel(logging.INFO)                 # DEBUG messages are dropped
log.addHandler(handler)
log.propagate = False                      # do not also send to the root logger

log.debug("cache lookup for order 7")
log.info("order %s created", 7)
log.warning("payment provider slow: %d ms", 2300)
log.error("could not send receipt for order %s", 7)
print(stream.getvalue(), end="")
INFO orders: order 7 created
WARNING orders: payment provider slow: 2300 ms
ERROR orders: could not send receipt for order 7

Notice that the arguments are passed separately ("order %s created", 7) rather than formatted with an f-string. The logger formats the message only if the level is enabled, which saves work on busy paths.

Health checks

A health check is an endpoint that tells an orchestrator or load balancer whether an instance is working. Keep two separate ones:

  • Liveness answers "is the process stuck or crashed?". It should be cheap and should not check external services. If it fails, the orchestrator restarts the instance.
  • Readiness answers "can this instance serve traffic right now?". It may check the database and cache. If it fails, the load balancer stops sending requests to this instance, but it is not restarted.

Kubernetes has both as probes (livenessProbe and readinessProbe). Mixing them up is a real incident pattern: if liveness checks the database, a short database outage causes every instance to restart at once.

def check_database():
    return True                  # pretend a "SELECT 1" succeeded

def liveness():
    return {"status": "alive"}, 200

def readiness(checks):
    results = {name: fn() for name, fn in checks.items()}
    ok = all(results.values())
    return {"status": "ready" if ok else "not ready", "checks": results}, (200 if ok else 503)

print(liveness())
print(readiness({"database": check_database, "cache": lambda: False}))
({'status': 'alive'}, 200)
({'status': 'not ready', 'checks': {'database': True, 'cache': False}}, 503)

The readiness result uses 503 Service Unavailable because one dependency (the cache) failed, so the instance should be taken out of rotation until it recovers.

The twelve-factor app

The twelve-factor app is a set of principles, written by engineers at Heroku, for building cloud-ready services. Interviewers use it as a checklist, so know the list and the reason behind the important ones:

  1. Codebase. One repository per app, many deploys (dev, staging, production).
  2. Dependencies. Declare every dependency explicitly (requirements.txt, package.json, pom.xml) and never rely on system-wide packages.
  3. Config. Store config, including secrets and per-environment URLs, in environment variables, not in code.
  4. Backing services. Treat the database, cache and queue as attached resources identified by a URL in config. Swapping one should need no code change.
  5. Build, release, run. Keep the three stages separate. A release is a build plus config, and it is immutable.
  6. Processes. Run the app as stateless processes. Anything that must persist goes to a backing service, not to local memory or disk.
  7. Port binding. The app exports its own HTTP service on a port, rather than relying on an external server being injected.
  8. Concurrency. Scale out by running more processes of each type (web, worker).
  9. Disposability. Start fast and shut down gracefully, handling the termination signal and finishing in-flight work.
  10. Dev/prod parity. Keep development, staging and production as similar as possible.
  11. Logs. Treat logs as event streams written to stdout, and let the platform route them.
  12. Admin processes. Run one-off tasks such as migrations as separate processes using the same codebase and config.

Factor 3 (config in the environment) explains why the Flask example later reads its database URL from the environment rather than hard-coding it, and why secrets never belong in git.

What is the difference between a liveness and a readiness check?

Liveness asks whether the process is alive and should be restarted if it is stuck. Readiness asks whether the instance can currently serve traffic, which may depend on the database or cache. A failed readiness check removes the instance from the load balancer without restarting it, which is the right response to a temporary dependency outage.

Flask: a small framework that you assemble yourself

Flask is a Python micro-framework. "Micro" does not mean small in capability. It means Flask supplies the routing, request and response handling, and templating, and leaves the database, authentication and forms to extensions you choose. It is built on Werkzeug (a library of WSGI tools for requests, routing and the development server) and Jinja2 (the template engine). The official documentation is at flask.palletsprojects.com.

The request lifecycle inside Flask

The WSGI server calls your Flask app with the raw request. Flask creates a request context that holds the current request, matches the URL to a view function, and runs any before-request hooks and middleware. The view returns a value, which Flask converts into a response: a string becomes an HTML body, a dict becomes JSON, and a tuple such as (body, 201) sets the status. After-request hooks run, then teardown code releases per-request resources such as database sessions.

The application factory

A small app can create app = Flask(__name__) at the top of one file. Real projects use an application factory: a function named create_app that builds and returns a configured app. This lets tests create an app with a test configuration, lets you run several configurations side by side, and avoids circular imports, because extensions are created first and bound to an app later. The layout below uses Flask-SQLAlchemy, which connects the SQLAlchemy ORM to Flask.

# app/extensions.py
from flask_sqlalchemy import SQLAlchemy

db = SQLAlchemy()              # created once, attached to an app later
# app/__init__.py
import os
from flask import Flask
from .extensions import db

def create_app(config_overrides=None):
    app = Flask(__name__)
    app.config.from_mapping(
        # read secrets and URLs from the environment (twelve-factor, factor 3)
        SECRET_KEY=os.environ.get("SECRET_KEY", "dev-only-change-me"),
        SQLALCHEMY_DATABASE_URI=os.environ.get("DATABASE_URL", "sqlite:///app.db"),
    )
    if config_overrides:
        app.config.update(config_overrides)   # tests pass their own values here
    db.init_app(app)                          # bind the extension to this app

    from .users import users_bp               # imported here to avoid circular imports
    app.register_blueprint(users_bp, url_prefix="/api/users")
    return app

Each line matters. from_mapping sets configuration keys. os.environ.get reads an environment variable and falls back to a development default, which is safe only for local runs. db.init_app(app) connects the extension to this specific app object. The import of the blueprint sits inside the function so the models and routes can import db without loading a half-built app.

Routing, requests and responses

A route maps a URL pattern and HTTP method to a view function. Flask uses converters in angle brackets: <int:user_id> matches only digits and passes an integer to your function, and <uuid:id> and <path:file> also exist. The short decorators @bp.get, @bp.post, @bp.put and @bp.delete are shortcuts for route with a fixed method.

The request object gives you query parameters (request.args), form fields (request.form), JSON bodies (request.get_json()) and headers (request.headers). jsonify builds a JSON response, and abort(404) stops the view and returns an error response right away. Here is a blueprint with two routes:

# app/users.py
from flask import Blueprint, abort, jsonify, request
from .extensions import db
from .models import User

users_bp = Blueprint("users", __name__)

@users_bp.get("/<int:user_id>")
def get_user(user_id):
    user = db.session.get(User, user_id)     # look up by primary key
    if user is None:
        abort(404)                           # stop here and return 404 Not Found
    return jsonify(id=user.id, email=user.email)

@users_bp.post("/")
def create_user():
    data = request.get_json()                # parsed JSON body, or None
    user = User(email=data["email"])
    db.session.add(user)
    db.session.commit()
    return jsonify(id=user.id, email=user.email), 201   # 201 Created

The model used above is a small class. Flask-SQLAlchemy maps each class to a table, so User becomes the user table:

# app/models.py
from .extensions import db

class User(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    email = db.Column(db.String(255), unique=True, nullable=False)

A client that calls GET /api/users/1 for an existing user would receive a JSON body like this:

Response

{"id": 1, "email": "ada@example.com"}

A request for a missing ID returns status 404. Real APIs usually add a custom error handler so every error has the same JSON shape.

TrapCalling request.get_json() without checking the content type or the required keys. A missing key raises an error and produces a 500 response. Validate the input and return 400 Bad Request with a clear message instead.

Blueprints and templates

A blueprint is a group of routes, error handlers and static files that can be registered on an app, optionally under a URL prefix. The example above used url_prefix="/api/users", so @users_bp.get("/<int:user_id>") becomes /api/users/<int:user_id>. Blueprints let each feature live in its own module and keep create_app short.

For server-rendered pages, Flask uses Jinja2 templates. render_template loads a file and fills in variables. Jinja escapes output by default in HTML templates, so a value containing a script tag is displayed as text rather than run. That automatic escaping is a key protection against cross-site scripting (XSS).

<!-- templates/users.html -->
<h1>Hello, {{ name }}!</h1>
{% for post in posts %}
  <p>{{ post.title }}</p>
{% endfor %}

The view would call render_template("users.html", name=name, posts=posts). The variables are plain Python values, and the template never runs database queries itself.

Extensions and the usual companions

Flask stays small by delegating. The common companions are Flask-SQLAlchemy (ORM integration), Flask-Migrate (Alembic migrations driven from the command line), Flask-Login (session-based login state), Flask-JWT-Extended (JWT issuing and checking), Flask-WTF (forms with CSRF protection) and Flask-CORS (cross-origin headers). Each one follows the same pattern as db above: create the object, then bind it to an app with an init_app call.

WSGI versus ASGI

WSGI (Web Server Gateway Interface) is the standard contract between a Python web app and a server. The app is a callable that receives the environment and a start-response function, and returns the body. WSGI is synchronous: one request occupies one worker until it finishes. Flask, classic Django and Bottle are WSGI apps, served by gunicorn or uWSGI. A typical production command looks like gunicorn "app:create_app()", which calls the factory and serves the result.

ASGI (Asynchronous Server Gateway Interface) is the successor. It supports async code and long-lived connections such as WebSockets, because the app can await I/O instead of blocking a worker. FastAPI and Starlette are ASGI frameworks, served by uvicorn. Django 3.0 and later can also run as ASGI.

Flask 2.0 and later accept async def view functions, but Flask is still a WSGI app. Async views need the asgiref package and run through a bridge, so you gain little for I/O-heavy work, and the server still handles one request per worker. Say this precisely in an interview: async views in Flask do not make Flask an ASGI framework.

Key ideaWSGI is the synchronous contract between app and server. ASGI is the asynchronous one, and it is what you need for WebSockets and high-concurrency I/O.

Why does Flask use an application factory?

A factory creates a fresh, configured app on each call. Tests can pass a test configuration, several apps can run with different settings, and extensions are created at import time but bound to an app later with init_app. This avoids circular imports and global state that is hard to reset between tests.

Interview questions

Read each question aloud, answer it in your own words, then open the model answer to check. Aim for a clear answer in under a minute.

Walk me through what happens when a client sends GET /api/users/42.

The request reaches a load balancer, which forwards it to an app server such as gunicorn. The framework runs middleware (for example, reading the session or token), matches the path to the user handler, and extracts 42. The handler calls the service layer, which asks the repository for user 42, probably checking a Redis cache first. The result is serialised to JSON with a 200 status, the request is logged, and the response travels back through the load balancer.

What is the N+1 problem and how do you fix it?

N+1 is running one query to load a list and then one extra query per item to load a related object. It makes the number of round trips grow with the data. Fix it with eager loading: a JOIN (SQLAlchemy joinedload, Django select_related) or a second query with IN (selectinload, prefetch_related).

How do you run a schema change on a live database with no downtime?

Use a versioned migration and keep it backward compatible. Add the new nullable column first, deploy code that writes to both old and new, backfill the data in batches, switch reads to the new column, and drop the old column in a later release. Old and new code can run side by side during the deploy.

Why should you hash passwords with Argon2 or bcrypt instead of SHA-256?

SHA-256 is designed to be fast, so an attacker with a stolen database can test billions of guesses per second. Argon2id, bcrypt and PBKDF2 are deliberately slow, have a tunable cost, and include a per-user salt. Argon2id is memory-hard, which also makes GPU attacks expensive.

Compare sessions and JWTs. When would you choose each?

A server-side session keeps state on the server and gives the client an opaque ID in a cookie, so revocation is immediate, but every server needs access to the session store. A JWT is a signed, self-contained token that any service can verify without a lookup, which suits many services, but it cannot be revoked before expiry without extra work. Choose sessions for a single web app that needs instant logout, and JWTs for stateless APIs across services, usually with short expiry and refresh tokens.

What is refresh token rotation and why does it help?

Each refresh issues a new refresh token and invalidates the old one. If an old token is presented again, the server assumes it was stolen and revokes the whole family of tokens, forcing a fresh login. This limits the damage of a leaked refresh token, which is long-lived and therefore dangerous.

What does RBAC mean, and why check permissions rather than role names?

Role-based access control assigns permissions to roles and roles to users. Checking a permission such as article:delete keeps the rule in one table, so adding a role means editing data rather than every route. Combine it with least privilege and deny by default.

How do you make an API endpoint safe to retry?

Make it idempotent. The client sends an idempotency key, the server stores the result under that key in a table with a unique constraint, and a repeat with the same key returns the stored result without acting again. Retries should use exponential backoff with jitter, and only for transient errors.

Why should a web request not send an email directly?

Sending email is slow and can fail, and the user should not wait for it or see an error because of it. The request should save a job record and return 202 Accepted, and a worker sends the email and retries on failure. The job must be idempotent because queues usually deliver at least once.

What is the difference between liveness and readiness?

Liveness tells the orchestrator whether to restart the process. Readiness tells the load balancer whether to send traffic to it. Keep liveness cheap and independent of external services, so a database outage removes instances from rotation rather than restarting them all.

What is WSGI and why does ASGI matter?

WSGI is the synchronous interface between a Python app and its server, so one worker handles one request at a time. ASGI is the asynchronous interface that supports WebSockets and long-lived connections efficiently. Flask is WSGI even though it accepts async views.

What is the difference between eager and lazy loading?

Lazy loading fetches related data only when the code first touches it, which is the cause of N+1 when it happens inside a loop. Eager loading fetches the related data up front in the same query or one extra query. Lazy loading is a sensible default for rarely used relations, and eager loading is the fix when a loop needs them.

DSA: Greedy algorithms

A greedy algorithm builds the answer step by step and, at each step, makes the choice that looks best right now, then never reconsiders it. It is fast because it avoids exploring alternatives. Its risk is that a locally best choice can be globally wrong. Greedy works only when the problem has the greedy-choice property: some optimal solution begins with the greedy choice.

When greedy works, and when it fails

The usual way to justify a greedy idea is an exchange argument. Suppose an optimal solution makes a different choice at some step. Show that you can swap in the greedy choice without making the solution worse. Repeat the swap until the optimal solution matches the greedy one.

Coin change shows the difference clearly. With US coins (1, 5, 10, 25), taking the largest coin first gives the minimum number of coins, so greedy works. With the coins 1, 3 and 4, and an amount of 6, the greedy choice 4 + 1 + 1 uses three coins, but 3 + 3 uses two. Here is a runnable check that shows both results.

def greedy_coins(coins, amount):
    """Take as many of the largest coin as possible, then the next, and so on."""
    count = 0
    for coin in sorted(coins, reverse=True):
        count += amount // coin      # how many of this coin fit
        amount %= coin               # what is left over
    return count if amount == 0 else None

print(greedy_coins([1, 3, 4], 6))          # greedy: 4 + 1 + 1
print(greedy_coins([1, 5, 10, 25], 63))    # greedy is optimal for these coins
3
6

The first answer, 3, is not the minimum for coins 1, 3, 4 (the true minimum is 2). Greedy is only a heuristic there, and dynamic programming (the next day's topic) is the tool that always finds the minimum. For the interview, the rule is: if you can state an exchange argument, greedy is a valid answer; if you cannot, check a counterexample before you commit.

TrapAssuming greedy is correct because the first example worked. Try a small counterexample such as coins 1, 3, 4 and amount 6 before you rely on the idea.

Common greedy shapes

  • Sort, then scan. Sorting creates the order that makes the greedy choice obvious (assign-cookies).
  • Track a reach. Keep the farthest point you can get to so far, and extend it as you scan (jump-game-ii).
  • Record the last occurrence. Decide the end of a segment as soon as you pass the last occurrence of every character in it (partition-labels).
  • Fuel or budget with a heap. When you run short, undo an earlier decision by taking the best option you passed (minimum-number-of-refueling-stops).

Assign Cookies (LeetCode 455)

Each child has a greed factor (the smallest cookie size they will accept), and each cookie has a size. Give each child at most one cookie so that as many children as possible are content. Example: greed factors [1, 2, 3] and cookie sizes [1, 1] give 1, because only the first child can take a size-1 cookie.

How to think about it

  1. Understand. Maximise the number of satisfied children. A cookie can only satisfy a child whose greed factor it meets or beats. Each child and each cookie is used at most once.
  2. Brute force. Try every matching of children to cookies and keep the best. There are too many matchings to list, so this is exponential in the worst case.
  3. Find the waste. The brute force treats every pairing as equally worth exploring. But a small cookie is useless to a greedy child, and a big cookie is wasted on a child who would have accepted a small one.
  4. Optimise. Sort both lists. Serve the least greedy child first, with the smallest cookie that satisfies them. Exchange argument: if a cookie satisfies this child, giving them the smallest such cookie is never worse, because a bigger cookie would only be more useful to a greedier child. Two pointers then do the whole job in one pass.
  5. Dry run. Sorted greed [1, 2, 3], sorted sizes [1, 1]. The child pointer starts at the first child (greed 1). Cookie 1 satisfies greed 1, so the pointer moves to the second child (greed 2). The next cookie, 1, is smaller than 2, so no match. Answer 1.

Code

def find_content_children(greed, sizes):
    greed = sorted(greed)              # least demanding child first
    sizes = sorted(sizes)              # smallest cookie first
    child = 0                          # index of the child we are trying to satisfy
    for size in sizes:
        if child < len(greed) and size >= greed[child]:
            child += 1                 # this cookie satisfies that child, move on
    return child

print(find_content_children([1, 2, 3], [1, 1]))
print(find_content_children([1, 2], [1, 2, 3]))
print(find_content_children([10, 9, 8, 7], [5, 6, 7, 8]))
1
2
2

Time O(n log n) for sorting · Space O(1) extra, apart from the sort

Pattern to rememberWhen matching two lists to maximise pairs, sort both and match the smallest that works.

Jump Game II (LeetCode 45)

You start at index 0 of an array. Each value nums[i] is the maximum jump length from index i. Return the minimum number of jumps needed to reach the last index. You can always reach the end. Example: [2, 3, 1, 1, 4] gives 2 (jump from index 0 to 1, then from 1 to the last index).

How to think about it

  1. Understand. Jumps are at most the stated length, and you want the fewest. The array is guaranteed to be reachable.
  2. Brute force. Recursion: from each index, try every jump length and take the minimum. It revisits the same indices again and again.
  3. Find the waste. Think in levels. After one jump you can reach some range of indices. After two jumps you reach a larger range. The question is how far the next level extends.
  4. Optimise. Track two values while scanning: current_end, the end of the range reachable with the jumps counted so far, and farthest, the farthest index reachable from anything seen so far. When you reach current_end, you must jump once more, and the new range ends at farthest. This is a breadth-first search in disguise, done with two integers.
  5. Dry run. On [2, 3, 0, 1, 4]: at index 0, farthest becomes 2, and the index equals current_end (0), so jumps becomes 1 and current_end becomes 2. At index 1, farthest becomes 4. At index 2, farthest stays 4, and the index equals current_end (2), so jumps becomes 2 and current_end becomes 4. The loop stops before the last index, so the answer is 2.

Code

def jump(nums):
    jumps = 0
    current_end = 0          # last index reachable with the jumps counted so far
    farthest = 0             # farthest index reachable from any index seen so far
    for i in range(len(nums) - 1):      # no need to jump from the last index
        farthest = max(farthest, i + nums[i])
        if i == current_end:            # the current range is used up
            jumps += 1
            current_end = farthest
    return jumps

print(jump([2, 3, 1, 1, 4]))
print(jump([2, 3, 0, 1, 4]))
print(jump([1]))
2
2
0

Time O(n) · Space O(1)

Pattern to rememberWhen you need the fewest steps and each step opens a range, track the end of the current range and the farthest point, and count a step only when you reach the end of the range.

Partition Labels (LeetCode 763)

Split a string into as many parts as possible so that each letter appears in at most one part. Return the length of each part, in order. Example: "ababcbacadefegdehijhklij" gives [9, 7, 8], because the first part "ababcbaca" contains every a, b and c in the string.

How to think about it

  1. Understand. Parts are contiguous, and a letter may not appear in two parts. The parts must cover the whole string in order.
  2. Brute force. Try every way of cutting the string and check each cut for the rule. That is exponential in the length.
  3. Find the waste. The brute force rechecks letters over and over. The only fact a cut needs is whether any letter in the current part appears later on.
  4. Optimise. First record the last index of each letter in one pass. Then scan again, keeping end, the furthest last index of any letter seen in the current part. When the scan index reaches end, no letter in the part appears later, so you can cut there.
  5. Dry run. On "abac": the last indices are a at 2, b at 1, c at 3. At i=0 (a), end becomes 2. At i=1 (b), end stays 2. At i=2 (a), end stays 2 and i equals end, so the part length is 3 and the next part starts at 3. At i=3 (c), end becomes 3 and i equals end, so the part length is 1. Answer [3, 1].

Code

def partition_labels(s):
    last = {ch: i for i, ch in enumerate(s)}   # last index of each letter
    result = []
    start = 0                                  # where the current part begins
    end = 0                                    # furthest last index seen in this part
    for i, ch in enumerate(s):
        end = max(end, last[ch])
        if i == end:                           # no letter here appears later
            result.append(end - start + 1)
            start = i + 1
    return result

print(partition_labels("ababcbacadefegdehijhklij"))
print(partition_labels("eccbbbbdec"))
print(partition_labels("abc"))

[1, 1, 1]

Minimum Number of Refueling Stops (LeetCode 871)

A car must drive target miles east. It starts with startFuel litres of fuel and burns one litre per mile. Gas stations are listed as [position, fuel] pairs, sorted by position. When the car reaches a station it may fill up with all of that station's fuel. Return the minimum number of stops needed to reach the target, or -1 if it cannot. Example: target 100, start fuel 10, stations [[10, 60], [20, 30], [30, 30], [60, 40]] gives 2 (stop at 10, then at 60).

How to think about it

  1. Understand. Fuel is the only resource. You can refuel only at stations, and stopping costs one stop. Stations are sorted, so you always pass them in order. Fuel never goes below zero, so the car must reach each point with fuel to spare.
  2. Brute force. Try every subset of stations as the stops, check whether the car can reach the target, and keep the smallest subset that works. That is 2 to the power n subsets, far too many.
  3. Find the waste. A smarter brute force is dynamic programming. Let dp[t] be the farthest point reachable using exactly t stops. Each station is considered once, and for each one we update every t that can reach it. That costs O(n squared), which is acceptable for a first solution.
  4. Optimise. The greedy insight: drive forward and remember every station you have passed, as a candidate with its fuel amount. Whenever you run out before the next station, you must have stopped at one of the passed stations, so retroactively take the largest candidate. Taking the largest fuel gives the most progress per stop, and a max-heap finds it in O(log n). Adding the target as a final station with 0 fuel makes the last check the same as the others.
  5. Dry run (heap version). Start with 10 litres. Drive to station 10: fuel is 0, and station 10 (60 litres) goes into the heap. Drive to station 20: fuel is -10, so take the best candidate, 60 litres, and count one stop, giving fuel 50. Push station 20 (30 litres). Drive to station 30: fuel is 40, push 30. Drive to 60: fuel is 10, push 40. Drive to the target 100: fuel is -30, so take the best candidate, 40 litres, count a second stop, and fuel is 10, which is enough. Answer 2.

Code

import heapq

def min_refuel_dp(target, start_fuel, stations):
    """O(n squared): dp[t] is the farthest point reachable using exactly t stops."""
    n = len(stations)
    dp = [start_fuel] + [0] * n
    for i, (pos, fuel) in enumerate(stations):
        for t in range(i, -1, -1):         # go backwards so each station is used once
            if dp[t] >= pos:
                dp[t + 1] = max(dp[t + 1], dp[t] + fuel)
    for t in range(n + 1):
        if dp[t] >= target:
            return t
    return -1

def min_refuel_heap(target, start_fuel, stations):
    """O(n log n): drive greedily, and retroactively refuel at the best passed station."""
    stations = stations + [[target, 0]]    # the target acts as a final station
    fuel = start_fuel
    position = 0
    stops = 0
    available = []                         # fuel of passed stations, as a max-heap
    for station_pos, station_fuel in stations:
        fuel -= station_pos - position     # drive to this station
        while fuel < 0 and available:      # we ran out before reaching it
            fuel += -heapq.heappop(available)   # heapq is a min-heap, so store negatives
            stops += 1
        if fuel < 0:
            return -1                      # no passed station can fix the shortage
        heapq.heappush(available, -station_fuel)
        position = station_pos
    return stops

tests = [
    (1, 1, []),
    (100, 1, [[10, 100]]),
    (100, 10, [[10, 60], [20, 30], [30, 30], [60, 40]]),
]
for target, start, stations in tests:
    print(min_refuel_dp(target, start, stations), min_refuel_heap(target, start, stations))

-1 -1
2 2

Brute force DP: Time O(n squared) · Space O(n). Heap version: Time O(n log n) · Space O(n)

Pattern to rememberWhen a greedy choice may need to be undone later, keep the candidates you passed in a heap and pay for the best one only at the moment you run short.

Summary

Revise from these one-line definitions. If any of them feels unfamiliar, scroll back to its unit and reread the example.

Request lifecycle
The path a request takes: proxy, app server, middleware, routing, handler, data access, response, logging.
Middleware
A function that runs before or after the handler for every request, used for parsing, auth and logging.
MVC
Model, View, Controller: separates data, presentation and request handling.
Layered architecture
Routes, then services with business logic, then repositories with data access, each calling only the layer below.
Dependency injection
The framework creates and passes in the objects a class needs, instead of the class building them.
ORM
Object-relational mapper: maps database rows to objects and writes the SQL for you.
N+1 problem
One query for a list plus one query per item, so round trips grow with the data. Fix with a JOIN or eager loading.
Migration
A versioned script that changes the schema, applied once in order and recorded in the database.
Backward-compatible change
A schema change that old and new code can both run against, so deploys do not need downtime.
Cache-aside
Read the cache first, load from the database on a miss, and delete the cached key on write.
TTL
Time to live: how long a cached value may live before it expires.
Salt
A random per-user value mixed into a password hash so identical passwords get different hashes.
Argon2id, bcrypt, PBKDF2
Deliberately slow, salted password hashing functions. Never use a fast hash such as plain SHA-256 for passwords.
Session
Server-side state keyed by a random ID held in a cookie. Easy to revoke, but needs a shared store.
JWT
A signed, self-contained token (header, payload, signature). Verified without a lookup, but hard to revoke early and readable by anyone.
Refresh token rotation
Each refresh issues a new refresh token and retires the old one. Reuse of a retired token revokes the family.
RBAC
Role-based access control: roles carry permissions, users carry roles, and code checks permissions.
401 vs 403
401 means not authenticated; 403 means authenticated but not allowed.
Background job
Work moved off the request path into a queue and run later by a worker.
Exponential backoff
Waiting longer after each failed retry, usually capped and often with random jitter.
Idempotent
Safe to repeat: doing the operation twice has the same effect as doing it once.
Idempotency key
A client-generated key stored with a result, so a retry returns the stored result instead of acting again.
WebSocket
A long-lived two-way connection, started over HTTP with an Upgrade header.
Presigned URL
A time-limited, signed URL that lets a client upload or download an S3 object directly.
Structured logging
Writing each log event as a machine-readable record, usually JSON, with fields such as request ID.
Liveness and readiness
Liveness: restart the process if it is stuck. Readiness: stop sending traffic to it if it cannot serve.
Twelve-factor app
A checklist for cloud services, including config in environment variables and stateless processes.
Blueprint (Flask)
A reusable group of routes that is registered on an app, optionally under a URL prefix.
Application factory
A function that builds and configures a new app each time it is called, which helps tests and avoids circular imports.
WSGI vs ASGI
WSGI is the synchronous Python web interface (Flask). ASGI is the asynchronous one that supports WebSockets (FastAPI).
Greedy algorithm
Makes the locally best choice at each step and never reconsiders it. Correct only when an exchange argument holds.
