How numbers are stored: binary and IEEE 754

A computer stores everything as bits, each 0 or 1. A group of 8 bits is a byte. Integers are stored in binary, and most processors use two's complement for negative integers. In an 8-bit two's complement number, the leftmost bit has the value -128 instead of +128. So 11111111 is -1, and 10000000 is -128. The rule for negating a number is "flip all the bits, then add 1".

Two's complement lets the same adder work for positive and negative numbers, which is why it is used everywhere. The range of an n-bit signed integer runs from -2 to the power (n-1) up to 2 to the power (n-1) minus 1. For a 32-bit int that is -2147483648 to 2147483647.

Why decimal fractions are a problem

Some decimal fractions cannot be written exactly in binary. The fraction 1/3 has the repeating binary expansion 0.010101..., and 0.1 in decimal is the repeating binary 0.0001100110011... Because the number of bits is finite, the stored value is rounded. This is why a program can print 0.30000000000000004 for 0.1 + 0.2.

The standard for storing real numbers is IEEE 754, the floating-point standard. A value is stored in three fields:

  • Sign bit (1 bit): 0 for positive, 1 for negative.
  • Exponent (8 bits in single precision, 11 in double): the power of two, stored with a bias. Single precision uses bias 127, so a stored exponent of 127 means 2 to the power 0.
  • Fraction or mantissa (23 bits in single precision, 52 in double): the digits after the leading 1.

For a normal single-precision number, the value is (-1) to the power sign, times (1 + fraction), times 2 to the power (exponent minus 127). The leading 1 is implicit, so it is not stored. That gives one extra bit of precision for free.

Worked example: 0.5 and -2.0

Take 0.5. It equals 1.0 times 2 to the power -1. The exponent field is -1 + 127 = 126, which is 01111110 in binary. The fraction is all zeros, and the sign is 0. Putting the fields together gives 0 01111110 followed by 23 zeros, which in hexadecimal is 0x3F000000.

Take -2.0. It equals -1.0 times 2 to the power 1. The sign is 1, the exponent field is 1 + 127 = 128 (10000000), and the fraction is zero. The bits are 1 10000000 followed by 23 zeros, which is 0xC0000000.

Key ideaA float is sign, exponent and fraction. The exponent gives the size (the power of two) and the fraction gives the precision (the digits). Most surprising float results come from the fraction being too short to store a decimal exactly.

Special values

  • If the exponent field is all ones and the fraction is zero, the value is infinity (positive or negative), for example from dividing 1.0 by 0.0.
  • If the exponent field is all ones and the fraction is not zero, the value is NaN (not a number), for example the result of 0.0 divided by 0.0. NaN is not equal to anything, not even to itself.
  • If the exponent field is all zeros, the number is subnormal: a very small value with no implicit leading 1. This gives gradual underflow near zero.

Seeing the bits in Python

The struct module from the standard library can pack a Python float into its IEEE 754 single-precision bytes. The code below extracts the three fields for several values. It also prints two's complement patterns, and it shows the 0.1 + 0.2 surprise.

import struct

def float32_bits(x):
    # Pack the float as big-endian IEEE 754 single precision, then read the 32 bits as an integer.
    return struct.unpack('>I', struct.pack('>f', x))[0]

for value in [1.0, -2.0, 0.5, 0.1]:
    b = float32_bits(value)
    sign = b >> 31
    exponent = (b >> 23) & 0xFF
    fraction = b & 0x7FFFFF
    print(f"{value}: sign={sign} exponent={exponent:08b} fraction={fraction:023b} hex={b:08X}")

print(format(-1 & 0xFF, '08b'))
print(format(-128 & 0xFF, '08b'))
print(0.1 + 0.2, 0.1 + 0.2 == 0.3)

TrapNever compare floats with == when you mean "close enough". Compare the difference with a small tolerance, for example abs(a - b) < 1e-9, or use an exact type such as integers in cents for money.

Interviewers ask"Why does 0.1 + 0.2 not equal 0.3?" Answer: 0.1 and 0.2 have no exact binary representation, so each is stored with a small rounding error, and the sum carries the errors into a value slightly above 0.3.

The CPU: instruction cycle, addressing modes and architecture styles

The central processing unit (CPU) runs a program by repeating one small cycle billions of times per second. To understand that cycle, you need the parts it uses. The arithmetic logic unit (ALU) does the arithmetic and logic. The control unit decodes instructions and sends signals to the other parts. The registers are very fast storage inside the CPU, and the main memory holds everything else. The clock sets the rhythm of every step.

Four special registers appear in every textbook description of the cycle:

  • Program counter (PC): the address of the next instruction.
  • Instruction register (IR): the instruction currently being decoded.
  • Memory address register (MAR): the address being read or written.
  • Memory data register (MDR): the data being moved to or from memory.

The fetch-decode-execute cycle

The basic cycle has three steps, often written with extra steps for memory and write-back:

  1. Fetch. Put the PC on the address bus, read the instruction into the IR, and advance the PC so that it points to the next instruction. In register-transfer notation: MAR <- PC; MDR <- Memory[MAR]; IR <- MDR; PC <- PC + 1 (for fixed-length instructions).
  2. Decode. The control unit reads the opcode (the operation part of the instruction) and the operand fields, and works out which hardware units are needed.
  3. Execute. The ALU computes a result, or the CPU reads or writes memory. The result is written to a register or to memory. Then the cycle starts again.

The code below is a toy machine with four registers and four instructions. It shows the three steps in ordinary Python, one instruction at a time, and prints the state after each cycle.

program = [
    ("LOAD", 0, 5),     # R0 = 5
    ("LOAD", 1, 7),     # R1 = 7
    ("ADD", 0, 1),      # R0 = R0 + R1
    ("PRINT", 0),       # output R0
    ("HALT",),
]

regs = [0, 0, 0, 0]
pc = 0
cycle = 0
running = True

while running:
    # FETCH: read the instruction at the program counter, then advance the counter.
    instr = program[pc]
    pc += 1
    # DECODE: the opcode says which operation to perform.
    op = instr[0]
    # EXECUTE: perform the operation.
    cycle += 1
    if op == "LOAD":
        regs[instr[1]] = instr[2]
    elif op == "ADD":
        regs[instr[1]] = regs[instr[1]] + regs[instr[2]]
    elif op == "PRINT":
        print("output:", regs[instr[1]])
    elif op == "HALT":
        running = False
    print(f"cycle {cycle}: {op:<5} pc={pc} regs={regs}")
cycle 1: LOAD  pc=1 regs=[5, 0, 0, 0]
cycle 2: LOAD  pc=2 regs=[5, 7, 0, 0]
cycle 3: ADD   pc=3 regs=[12, 7, 0, 0]
output: 12
cycle 4: PRINT pc=4 regs=[12, 7, 0, 0]
cycle 5: HALT  pc=5 regs=[12, 7, 0, 0]

Notice that the PC moves forward by one before the instruction runs. That is why a jump instruction must overwrite the PC, not add to it: the PC already points past the jump when the jump executes.

Key ideaEvery instruction, from a simple add to a complex string copy, is run by this same loop of fetch, decode and execute. Pipelining (below) overlaps these steps across instructions to finish more work in the same time.

Addressing modes

An addressing mode tells the CPU where to find an operand. The same operation, such as "add", can take its operand from an instruction, a register or a memory location, depending on the mode. Each mode is a way to compute the effective address, which is the final memory location used by the instruction.

  • Immediate. The operand is inside the instruction. Example: ADD R1, #7 adds the constant 7. There is no memory access.
  • Direct (absolute). The instruction holds the memory address. Example: LOAD R1, [100] reads memory cell 100.
  • Indirect. The instruction holds the address of a cell that holds the real address. This takes two memory reads.
  • Register. The operand is in a register. No memory access is needed, so this is the fastest mode.
  • Register indirect. A register holds the address of the operand. Pointers in C work this way.
  • Indexed. The effective address is a base address plus an index register. Array access such as a[i] uses this pattern.
  • Relative (PC-relative). The effective address is the PC plus a signed offset. Branches and jumps use this, so that code can move in memory without changes.

The Python code below computes the effective address and the operand for each mode, using a small pretend memory.

memory = {100: 40, 101: 50, 102: 60, 200: 101}   # address to value
regs = {"R1": 100, "R2": 2}
pc = 50

def immediate(value):
    return value                       # the operand is inside the instruction

def direct(address):
    return memory[address]             # the instruction holds the address

def indirect(address):
    pointer = memory[address]          # the cell holds the real address
    return memory[pointer]             # second memory read

def register(name):
    return regs[name]                  # operand is in a register

def register_indirect(name):
    return memory[regs[name]]          # the register holds the address

def indexed(base, name):
    return memory[base + regs[name]]   # base address plus index register

def relative(offset):
    return memory[pc + offset]         # offset added to the program counter

print("immediate 7:", immediate(7))
print("direct 100:", direct(100))
print("indirect through 200:", indirect(200))
print("register R1:", register("R1"))
print("register indirect R1:", register_indirect("R1"))
print("indexed base 100 plus R2:", indexed(100, "R2"))
print("relative pc 50 offset 52:", relative(52))

Trace the indirect case by hand. The instruction names address 200. Memory cell 200 holds 101, which is a pointer. Cell 101 holds 50, and that is the operand. Two memory reads were needed, which is why indirect addressing is slower than direct.

Trap"Indirect" and "register indirect" are different. In register indirect, the register holds the address and there is one memory read. In indirect, a memory cell holds the address and there are two reads.

RISC versus CISC

Processor designers have two broad styles. CISC (complex instruction set computer) gives you many powerful instructions, some of which read and write memory and perform several steps in one instruction. The x86 family is the best-known CISC design. RISC (reduced instruction set computer) keeps the instruction set small and simple. Most instructions work on registers, and only special load and store instructions touch memory. ARM, RISC-V and MIPS are RISC designs.

FeatureRISCCISC
Instruction setSmall, simple instructionsLarge, feature-rich instructions
Memory accessOnly load and store instructions touch memory (load/store architecture)Many instructions can take memory operands directly
Instruction lengthUsually fixed length, which makes decoding simpleOften variable length
RegistersUsually many general-purpose registersUsually fewer, with more special-purpose uses
PipeliningSimple decoding suits pipelining wellHarder to pipeline, so modern CISC chips decode into simpler internal operations
Compiler effortThe compiler does more work to combine simple stepsComplex instructions can match high-level code more directly

The line between the two is blurred today. Modern x86 processors decode their CISC instructions into simpler internal operations, often called micro-operations, and execute those on a RISC-like core. In an interview, say that the difference is in the instruction set design, and that real chips mix the ideas.

Interviewers ask"Why did RISC designs become popular?" Answer: simple, fixed-length instructions are fast to decode and easy to pipeline, and a small set of load and store instructions keeps the pipeline busy. The compiler takes on the work of combining simple steps.

Pipelining and hazards

Without pipelining, the CPU finishes one instruction completely before it starts the next. A pipeline splits the work into stages and lets several instructions be in progress at once, each in a different stage. The idea is the same as a laundry line: while one load is drying, the next is being washed.

A classic five-stage pipeline has these stages:

  1. IF (instruction fetch): read the instruction from memory.
  2. ID (instruction decode): decode it and read the registers it uses.
  3. EX (execute): the ALU computes the result or an address.
  4. MEM (memory access): read or write memory, if the instruction needs it.
  5. WB (write back): write the result into a register.

The table shows three instructions, I1 to I3, moving through the pipeline. Each row is an instruction, and each column is a clock cycle. Read across a row to follow one instruction; read down a column to see what every stage is doing in that cycle.

In cycle 3, three different instructions are in three different stages. Each instruction still takes five cycles from start to finish, so the pipeline does not make one instruction faster. It makes the processor finish about one instruction per cycle once the pipeline is full. This difference between how long one instruction takes (latency) and how many finish per unit time (throughput) is the key idea.

How much faster is it?

With k stages and n instructions and no hazards, a non-pipelined processor needs n * k cycles. A pipelined processor needs k cycles to finish the first instruction, then one more cycle for each of the other n - 1 instructions: k + (n - 1) cycles in total.

stages = 5
n = 100
no_pipeline = n * stages           # each instruction uses all five stages before the next starts
pipelined = stages + (n - 1)       # first instruction takes 5 cycles, then one finishes each cycle
print("cycles without pipelining:", no_pipeline)
print("cycles with pipelining:", pipelined)
print("speedup:", round(no_pipeline / pipelined, 2))
cycles without pipelining: 500
cycles with pipelining: 104
speedup: 4.81

The ideal speedup approaches the number of stages as n grows, but it never reaches it in practice, because of hazards.

Hazards

A hazard is a situation that stops the next instruction from running in the next cycle. There are three kinds.

  • Structural hazard. Two instructions need the same hardware in the same cycle, for example one memory unit used for both instruction fetch and data access. The fix is more hardware (separate instruction and data caches) or a stall.
  • Data hazard. An instruction needs a value that an earlier instruction has not yet written. The most common case is read-after-write (RAW): ADD R1, R2, R3 followed by SUB R4, R1, R5. The second instruction needs R1 before the first has written it.
  • Control hazard. The pipeline does not know yet which instruction comes next, because of a branch. Instructions fetched after the branch may be the wrong ones, and they must be discarded (flushed).

Fixing data hazards

Forwarding (also called bypassing) sends a result straight from the EX or MEM stage to the next instruction's EX stage, without waiting for the write-back. Most RAW hazards disappear this way. The exception is a load-use hazard: an instruction that loads a value from memory and the next instruction uses it immediately. The loaded value is not ready until after the MEM stage, so one stall cycle is still needed.

Worked example: in LOAD R1, [x] followed by ADD R2, R1, R3, the ADD needs R1 in its EX stage. The LOAD only has the value at the end of its MEM stage. The pipeline inserts one bubble (an empty stage) between them, and forwarding carries the loaded value into the ADD without a second stall.

Fixing control hazards

Two common approaches are stalling until the branch is resolved, which wastes cycles, and branch prediction, which guesses the outcome and continues. If the guess is right, nothing is lost. If it is wrong, the instructions fetched on the wrong path are flushed and the correct ones are fetched. Modern processors predict branches very accurately, using the history of past branches.

Key ideaA pipeline runs at full speed only when the next instruction does not need the result of the current one, and when the next instruction is known. Hazards are the reasons it does not.

TrapForwarding does not remove every stall. Explain the load-use case explicitly; saying "forwarding removes all data hazards" is a common wrong answer.

Interviewers ask"What are the three kinds of pipeline hazard, and how do you handle each?" Answer: structural hazards are handled by duplicating hardware or stalling; data hazards by forwarding and stalling for loads; control hazards by stalling or branch prediction with flushing.

Cache memory and AMAT

Memory is slow compared with the CPU. A register access takes about one clock cycle, under a nanosecond on a modern CPU, while a main memory access takes on the order of 100 nanoseconds. A cache is a small, fast memory between the CPU and main memory that keeps copies of recently used data. The memory hierarchy has layers, from fastest and smallest to slowest and largest: registers, L1 cache, L2 cache, L3 cache, main memory (RAM), and then storage such as an SSD or disk.

Caches work because programs have locality:

  • Temporal locality. A recently used item is likely to be used again soon. A loop counter is a good example.
  • Spatial locality. Items near a recently used item are likely to be used soon. Walking an array in order is a good example.

Caches move data in fixed-size chunks called blocks or cache lines, often 64 bytes. When the CPU asks for an address, the cache checks whether that block is present. A hit means the block is there, and a miss means it is not, so the block must be fetched from the next level, which takes longer.

Splitting an address: tag, index and offset

To find a block, the cache splits the address into three fields. The offset selects a byte inside the block. The index selects the set (or line) in the cache. The tag is the remaining high bits, which identify which memory block is stored there.

The code below splits a 32-bit address for a cache with 16-byte blocks (4 offset bits) and 64 sets (6 index bits). Since 16 is 2 to the power 4 and 64 is 2 to the power 6, each field is a group of bits.

def split_address(address, offset_bits, index_bits):
    offset = address & ((1 << offset_bits) - 1)
    index = (address >> offset_bits) & ((1 << index_bits) - 1)
    tag = address >> (offset_bits + index_bits)
    return tag, index, offset

# 32-bit addresses, 16-byte blocks (4 offset bits), 64 sets (6 index bits)
for address in [0x00000000, 0x00000010, 0x00000400, 0x12345678]:
    tag, index, offset = split_address(address, 4, 6)
    print(f"address {address:#010x}: tag={tag:#x} index={index} offset={offset}")

address 0x00000010: tag=0x0 index=1 offset=0
address 0x00000400: tag=0x1 index=0 offset=0
address 0x12345678: tag=0x48d15 index=39 offset=8

Look at the third address, 0x400. It is 1024, which is 16 blocks times 64 sets. Its block number is 64, and 64 modulo 64 is 0, so it maps to set 0 again. Its tag is 1. The same set is shared by many addresses with different tags.

Mapping: where can a block go?

  • Direct-mapped. Each block has exactly one possible slot, chosen by its index. Simple and fast, but two busy blocks with the same index keep evicting each other. This is a conflict miss.
  • Fully associative. A block can go in any slot. There are no conflict misses, but finding a block requires comparing every tag, so it is expensive for large caches.
  • Set-associative. A block can go in any of a few slots (for example 2, 4 or 8 ways) within one set. It is the usual compromise.

The simulator below runs a direct-mapped cache with 8 slots. It takes a list of block numbers and reports a hit or miss for each. Block 0 and block 8 both map to slot 0, so they keep evicting each other.

def simulate_direct_mapped(refs, slots):
    cache = [None] * slots            # each slot holds one block number, or None when empty
    results = []
    for block in refs:
        slot = block % slots          # the index is the block number modulo the number of slots
        if cache[slot] == block:
            results.append("hit")
        else:
            results.append("miss")
            cache[slot] = block       # fetch the block and evict whatever was there
    return results

print(simulate_direct_mapped([0, 8, 0, 8, 1, 1], 8))
['miss', 'miss', 'miss', 'miss', 'miss', 'hit']

Trace the list. Block 0 misses and fills slot 0. Block 8 maps to slot 0 too, so it misses and evicts block 0. Block 0 misses again and evicts block 8, and block 8 misses once more. Block 1 is a cold miss in slot 1, and the second access to block 1 is a hit. The four alternating accesses are all misses, even though seven of the eight slots are never used by these accesses. This is a conflict miss.

TrapA direct-mapped cache can miss even when most of its slots are unused. Interviewers often use this to test whether you understand conflict misses.

Write policies and replacement

  • Write-through. Every write goes to the cache and to memory. Simple, but slow for frequent writes.
  • Write-back. A write changes only the cache and sets a dirty bit. The block is written to memory when it is evicted. Faster, and the usual choice for L1 and L2.
  • Write-allocate. On a write miss, the block is loaded into the cache first. The two write policies above are usually paired with this choice.
  • Replacement. In a set-associative cache, when a set is full, a policy picks the victim. LRU (least recently used) evicts the block that has gone unused the longest. It works well because of temporal locality. FIFO and random are cheaper alternatives.

The three classic causes of misses are compulsory (the first access to a block, which no cache can avoid), capacity (the working set is larger than the cache), and conflict (blocks compete for the same slot, as in the example above).

Average memory access time (AMAT)

AMAT is the average time for one memory access, counting hits and misses. Its formula is:

AMAT = hit time + miss rate * miss penalty

Every access pays the hit time, because the cache is always checked first. Only the misses pay the extra penalty, which is the time to fetch from the next level. A two-level cache has a penalty that is itself an AMAT: the time for the L2 access, including its own misses.

def amat(hit_time, miss_rate, miss_penalty):
    return hit_time + miss_rate * miss_penalty

# One level: hit time 1 cycle, 5% misses, 100 cycle penalty to memory.
print("one level:", amat(1, 0.05, 100))

# Two levels: L1 hit 1 cycle, 10% L1 misses. The L1 penalty is the L2 AMAT:
# L2 hit 10 cycles, 20% of L2 lookups miss, and memory costs 100 cycles.
l2_amat = amat(10, 0.20, 100)
print("two levels:", amat(1, 0.10, l2_amat))
one level: 6.0
two levels: 4.0

Check the one-level answer by hand. Every access costs 1 cycle. Five in every hundred accesses also pay 100 more cycles. So the average is 1 + 0.05 * 100 = 1 + 5 = 6 cycles. For the two-level case, the L1 miss penalty is the L2 AMAT, which is 10 + 0.20 * 100 = 30 cycles. The overall average is 1 + 0.10 * 30 = 4 cycles.

Key ideaAMAT = hit time + miss rate * miss penalty. To cut AMAT, you can lower the hit time (a small, fast L1), the miss rate (a bigger or better-organised cache), or the miss penalty (a second-level cache). Improving the miss rate by a small amount can help more than any other change when the penalty is large.

Interviewers ask"Why does a larger cache not always help?" Answer: a bigger cache usually has a longer hit time, because checking more slots and tags takes longer. The best size balances hit time against miss rate.

Input and output: interrupts versus DMA

A computer talks to devices such as keyboards, disks and network cards. There are two main ways for data to move between a device and memory. In both, the device needs the CPU's attention at some point, but the amount of CPU work is very different.

Interrupts

An interrupt is a signal that tells the CPU to stop what it is doing and handle an event. A device raises an interrupt request (IRQ) when it needs service, for example when a key is pressed or a network packet has arrived. The steps are:

  1. The device raises the IRQ line.
  2. The CPU finishes the current instruction, then saves the PC and the status flags, usually on the stack.
  3. The CPU looks up the handler address in the interrupt vector table, using the interrupt number.
  4. The CPU runs the interrupt service routine (ISR), which reads the device's data and clears the request.
  5. The ISR returns, the saved state is restored, and the interrupted program continues.

Interrupts are efficient when events are infrequent or each event carries only a little data, such as a key press. The cost is that the CPU handles every single event, and the time between the event and the handler starting is the interrupt latency.

Direct memory access (DMA)

DMA lets a device move a block of data to or from memory without the CPU copying each byte. A DMA controller, a separate piece of hardware, does the transfer. The steps are:

  1. The CPU programs the DMA controller with the source address, the destination address and the number of bytes.
  2. The CPU starts the transfer and goes on with other work.
  3. The DMA controller moves the data directly between the device and memory. It takes control of the memory bus for short periods, a method called cycle stealing, or for one long burst.
  4. When the transfer completes, the DMA controller raises one interrupt, and the CPU's ISR does the final bookkeeping.

Comparing the two

QuestionInterrupt-driven I/ODMA
Who moves each byte?The CPU, in the ISRThe DMA controller
CPU involvementOne interrupt per event or unit of dataSetup and one completion interrupt per block

A concrete example: reading 4 KB from a disk. With interrupts, the CPU might take one interrupt for each byte or word, which is many interrupts and much CPU time. With DMA, the CPU sets up one transfer and gets one interrupt at the end, so it is free to run other programs during the transfer.

TrapDMA does not mean the CPU is never involved. The CPU sets up the transfer, and it can be slowed down when the DMA controller uses the memory bus. Also, the CPU must not read the buffer before the completion interrupt says the data is ready.

Interviewers ask"When would you choose DMA over interrupts?" Answer: when the device transfers large blocks of data, because DMA removes the per-byte work from the CPU and needs only one interrupt per block.

Polling

A third method is polling: the CPU repeatedly checks a device status register. Polling is simple, but it wastes CPU time while the device is idle. Interrupts were designed to avoid that waste.

Parallel hardware: multicore CPUs and GPUs

For decades, processors became faster by raising the clock rate. That stopped being practical, so manufacturers now add more cores to one chip. A core is a complete processing unit with its own ALU, control unit and registers. A multicore processor runs several threads at the same time, and the cores usually share a larger cache (L3) and main memory.

Because the cores share memory, they must keep their own caches consistent. A cache coherence protocol, such as MESI (Modified, Exclusive, Shared, Invalid), makes sure that when one core writes a value, other cores do not keep using an old copy. Coherence traffic is one reason that adding cores does not give a perfect speedup.

Amdahl's law

Amdahl's law gives the best speedup you can get from parallel hardware. Let p be the fraction of the program that can run in parallel, and n the number of cores. The serial part (1 - p) does not speed up. The speedup is:

speedup = 1 / ((1 - p) + p / n)

Worked example: if 90% of a program is parallel (p = 0.9), then with 4 cores the serial 10% still takes its full time, and the parallel 90% takes a quarter of its time. The new running time is 0.1 + 0.9 / 4 = 0.325 of the original, so the speedup is about 3.08, not 4. Even with infinitely many cores, the serial 10% limits the speedup to 1 / 0.1 = 10.

def amdahl(parallel_fraction, cores):
    serial = 1 - parallel_fraction
    return 1 / (serial + parallel_fraction / cores)

for cores in [2, 4, 16]:
    print(cores, "cores:", round(amdahl(0.9, cores), 2))
print("limit with unlimited cores:", round(amdahl(0.9, 10**9), 2))
2 cores: 1.82
4 cores: 3.08
16 cores: 6.4
limit with unlimited cores: 10.0

Key ideaThe speedup from parallel hardware is limited by the serial part of the program. Reducing the serial fraction matters more than adding cores once there are many cores.

GPUs

A GPU (graphics processing unit) is built for the opposite trade-off from a CPU. A CPU has a few powerful cores that are optimised for low latency: finishing one thread quickly. A GPU has thousands of simpler cores that are optimised for throughput: doing a huge amount of identical work at once.

GPUs use a style called SIMT (single instruction, multiple threads). A group of threads runs the same instruction on different data. NVIDIA calls such a group a warp. This suits data-parallel work, such as applying the same calculation to every pixel of an image or every element of a large matrix. Work that branches a lot or needs many small, dependent steps runs poorly on a GPU.

  • CPU: a few fast cores, large caches, good for branchy and sequential code.
  • GPU: thousands of simple cores, high memory bandwidth, good for data-parallel work.

Interviewers ask"Why does a GPU use many simple cores instead of a few complex ones?" Answer: the work is data-parallel, so the total throughput matters more than the speed of one thread. Simple cores take less area and power, so many more fit on the chip.

Interview questions

Answer each question out loud before you open the model answer. A good answer is short, correct, and gives one example.

Why does a computer use two's complement for negative integers?

So that addition works the same way for positive and negative numbers, and the hardware needs only one adder. For example, -1 plus 1 in 8 bits is 11111111 + 00000001 = 100000000, and dropping the carry out of the top bit gives 0.

What are the three fields of an IEEE 754 single-precision float?

One sign bit, eight exponent bits (stored with a bias of 127), and 23 fraction bits. The value of a normal number is (-1) to the power sign, times (1 + fraction), times 2 to the power (exponent minus 127).

Describe the fetch-decode-execute cycle in one sentence.

The CPU reads the instruction at the address in the PC into the IR and advances the PC, decodes the opcode and operands, then executes the operation, which may use the ALU or access memory, and writes the result.

What is the difference between direct and indirect addressing?

Direct addressing puts the address of the operand in the instruction, so one memory read gets the operand. Indirect addressing puts the address of a memory cell in the instruction; that cell holds the real address, so two reads are needed.

What is the difference between RISC and CISC?

RISC uses a small set of simple, mostly fixed-length instructions, with memory access only through load and store instructions. CISC offers many complex instructions, some of which access memory directly. Modern CISC chips decode into simpler internal operations.

Name the three kinds of pipeline hazard and one fix for each.

Structural: duplicate the hardware, for example separate instruction and data caches. Data: forwarding, plus a stall for a load followed by a use. Control: stall until the branch is resolved, or predict the branch and flush wrong-path instructions.

Explain why a direct-mapped cache can have misses when most of its slots are empty.

Two blocks that map to the same index compete for one slot. Accessing them alternately evicts each other every time, so each access misses. These are conflict misses, and a set-associative cache reduces them.

A cache hit takes 1 cycle, the miss rate is 5%, and a miss costs 100 extra cycles. What is the AMAT?

AMAT = 1 + 0.05 * 100 = 6 cycles. Every access pays the hit time, and only the misses pay the penalty.

When would you use DMA instead of interrupt-driven transfer?

For large blocks of data, such as disk or network transfers. The CPU sets up the DMA controller and receives one completion interrupt, instead of handling an interrupt for every unit of data.

A program is 80% parallel. What is the speedup on 4 cores, and why is it not 4?

Speedup = 1 / (0.2 + 0.8 / 4) = 1 / 0.4 = 2.5. The serial 20% does not speed up, so it limits the result. Even with unlimited cores, the speedup cannot exceed 1 / 0.2 = 5.

Why are GPUs good at matrix operations but poor at tasks with many branches?

Threads in a GPU group run the same instruction together. Matrix operations apply the same arithmetic to many elements, so every thread is busy. When threads take different branches, some must wait, which reduces throughput.

DSA: linked lists

A linked list is a chain of nodes. Each node holds a value and a pointer (a reference, in Python) to the next node. The list is known by its first node, the head. Unlike an array, a linked list does not store its nodes side by side, so inserting or removing a node means changing pointers, not moving elements.

Most linked-list problems are about pointer handling. Three techniques cover most of them:

  • Dummy head. Create a placeholder node before the real head. It removes special cases when the head itself changes, because every node now has a previous node.
  • Two pointers. Use a fast pointer and a slow pointer, or two pointers a fixed distance apart, to find positions in one pass.
  • Save before you overwrite. When you change a next pointer, first save the node it pointed to, or the rest of the list is lost.

Each problem below includes a small helper that builds a list from Python values and turns a list back into Python values, so you can check the output easily. Each code block is complete on its own.

Reverse Linked List (LeetCode 206)

Given the head of a singly linked list, reverse the list and return the new head. Example: 1 to 2 to 3 to 4 to 5 becomes 5 to 4 to 3 to 2 to 1. Reversing an empty list or a single node returns it unchanged.

How to think about it

  1. Understand. Every next pointer must point the other way. There are no extra nodes to create, so the answer reuses the same nodes.
  2. Brute force. Copy the values into an array, reverse the array, and rebuild the list. This takes O(n) extra space.
  3. Find the waste. The copy is unnecessary. Each node only needs its pointer flipped, and the previous node is the one to point to.
  4. Optimise. Walk the list with three variables: prev (the already reversed part, starting empty), curr (the node being processed), and a saved nxt. For each node, save nxt, point curr.next at prev, then move both pointers forward. O(n) time and O(1) space.
  5. Dry run. List 1, 2, 3. Start: prev = None, curr = 1. Step 1: nxt = 2, 1.next = None, prev = 1, curr = 2. Step 2: nxt = 3, 2.next = 1, prev = 2, curr = 3. Step 3: nxt = None, 3.next = 2, prev = 3, curr = None. Result: 3, 2, 1.

Code

class ListNode:
    def __init__(self, val=0, next=None):
        self.val = val
        self.next = next

def reverse_list(head):
    prev = None
    curr = head
    while curr is not None:
        nxt = curr.next        # 1. save the rest of the list
        curr.next = prev       # 2. point this node backwards
        prev = curr            # 3. move prev forward
        curr = nxt             # 4. move curr forward
    return prev                # prev is now the new head

def build(values):
    head = None
    for v in reversed(values):
        head = ListNode(v, head)
    return head

def to_list(head):
    out = []
    while head is not None:
        out.append(head.val)
        head = head.next
    return out

print(to_list(reverse_list(build([1, 2, 3, 4, 5]))))
print(to_list(reverse_list(build([1, 2]))))
print(to_list(reverse_list(build([]))))
[5, 4, 3, 2, 1]
[2, 1]
[]

Time O(n) · Space O(1)

Pattern to rememberWhen you must reverse pointers in place, keep a prev and a curr, and save curr.next before you overwrite it.

Add Two Numbers (LeetCode 2)

You are given two linked lists that represent two non-negative integers. The digits are stored in reverse order, one digit per node. Add the two numbers and return the sum as a linked list in the same format. Example: 2 to 4 to 3 (that is 342) plus 5 to 6 to 4 (that is 465) gives 7 to 0 to 8 (that is 807).

How to think about it

  1. Understand. Reversed order means the first node holds the ones digit, so we can add from the head just as we add by hand. A carry is passed to the next position. The lists may have different lengths, and a final carry can make one more digit.
  2. Brute force. Convert each list to a Python integer, add them, and convert the result back to a list. This works, but it is not what the problem asks for: it hides the digit-by-digit addition the interviewer wants to see.
  3. Find the waste. Converting to integers is unnecessary. We only need the digit sum at each position and one carry value.
  4. Optimise. Walk both lists together. At each step, add the two digits (0 if a list has ended) and the carry. The new digit is the total modulo 10, and the new carry is the total divided by 10. Use a dummy head to collect the result. Continue while either list has nodes or a carry is left. O(max(m, n)) time.
  5. Dry run. 2,4,3 plus 5,6,4. Position 1: 2 + 5 + carry 0 = 7, digit 7, carry 0. Position 2: 4 + 6 + 0 = 10, digit 0, carry 1. Position 3: 3 + 4 + 1 = 8, digit 8, carry 0. No lists left, no carry. Result 7, 0, 8, which is 807.

Code

class ListNode:
    def __init__(self, val=0, next=None):
        self.val = val
        self.next = next

def add_two_numbers(l1, l2):
    dummy = ListNode()             # placeholder head; the answer starts at dummy.next
    tail = dummy
    carry = 0
    while l1 or l2 or carry:
        total = carry
        if l1:
            total += l1.val
            l1 = l1.next
        if l2:
            total += l2.val
            l2 = l2.next
        carry = total // 10        # the carry is the tens part
        tail.next = ListNode(total % 10)   # the digit is the ones part
        tail = tail.next
    return dummy.next

def build(values):
    head = None
    for v in reversed(values):
        head = ListNode(v, head)
    return head

def to_list(head):
    out = []
    while head is not None:
        out.append(head.val)
        head = head.next
    return out

print(to_list(add_two_numbers(build([2, 4, 3]), build([5, 6, 4]))))
print(to_list(add_two_numbers(build([0]), build([0]))))
print(to_list(add_two_numbers(build([9, 9, 9, 9, 9, 9, 9]), build([9, 9, 9, 9]))))
[7, 0, 8]
[0]
[8, 9, 9, 9, 0, 0, 0, 1]

Time O(max(m, n)) · Space O(max(m, n)) for the result list

TrapForgetting the final carry. Inputs 5 and 5 give 0 with a carry of 1, and the answer must be 10. The loop condition or carry handles it.

Pattern to rememberWhen you combine two lists digit by digit, use a dummy head, a carry variable, and a loop that runs while either list or the carry still has something to add.

Remove Nth Node From End of List (LeetCode 19)

Given the head of a linked list and an integer n, remove the nth node counted from the end of the list, and return the head. Example: list 1 to 2 to 3 to 4 to 5 with n = 2 removes the node 4, giving 1 to 2 to 3 to 5. The value n is always valid, so the node exists.

How to think about it

  1. Understand. "From the end" means the position counted from the last node. Removing the head is a special case, which is why a dummy head helps. A single-node list with n = 1 must also work.
  2. Brute force. Count the length L with one pass. Then walk to the node at position L - n from the start with a second pass, and remove the next node. This is correct and O(n) time, but it needs two passes.
  3. Find the waste. The two passes count the same list twice. We want the answer in one pass.
  4. Optimise. Use two pointers with a gap of n. Move fast n steps ahead. Then move fast and slow together until fast reaches the last node. At that point slow is just before the node to remove, so set slow.next = slow.next.next. One pass, O(1) extra space.
  5. Dry run. List 1, 2, 3, 4, 5 with a dummy in front, n = 2. Move fast 2 steps from the dummy: fast is now at node 2. Now move both pointers until fast.next is None. Fast moves to 3, 4, 5 and slow moves to 1, 2, 3. Fast.next is None, with fast at 5. So slow is at 3, and slow.next is 4, which is the node to remove. Set 3.next = 5. Result 1, 2, 3, 5.

Code

class ListNode:
    def __init__(self, val=0, next=None):
        self.val = val
        self.next = next

def remove_nth_from_end(head, n):
    dummy = ListNode(0, head)      # the dummy lets us remove the real head too
    fast = slow = dummy
    for _ in range(n):             # move fast n steps ahead, creating the gap
        fast = fast.next
    while fast.next is not None:   # move both until fast is on the last node
        fast = fast.next
        slow = slow.next
    slow.next = slow.next.next     # slow is just before the node to remove
    return dummy.next

def build(values):
    head = None
    for v in reversed(values):
        head = ListNode(v, head)
    return head

def to_list(head):
    out = []
    while head is not None:
        out.append(head.val)
        head = head.next
    return out

print(to_list(remove_nth_from_end(build([1, 2, 3, 4, 5]), 2)))
print(to_list(remove_nth_from_end(build([1, 2, 3, 4, 5]), 5)))
print(to_list(remove_nth_from_end(build([1]), 1)))
[1, 2, 3, 5]
[2, 3, 4, 5]
[]

Time O(L) with one pass, where L is the list length · Space O(1)

TrapStarting fast at the real head instead of the dummy. Then removing the head (n equal to the length) has no node before it, and the code breaks.

Pattern to rememberTo find something a fixed distance from the end of a list in one pass, move one pointer n steps ahead, then move both together until the leading pointer reaches the end.

Reverse Nodes in k-Group (LeetCode 25)

Given the head of a linked list and a positive integer k, reverse the nodes in groups of k, and return the new head. If the number of nodes left at the end is less than k, leave them as they are. You may not change the values in the nodes, only the pointers. Example: 1 to 2 to 3 to 4 to 5 with k = 2 gives 2 to 1 to 4 to 3 to 5. With k = 3 it gives 3 to 2 to 1 to 4 to 5.

How to think about it

  1. Understand. The list is split into consecutive groups of k. Each complete group is reversed as a unit, and its neighbours are reconnected. A short group at the end is left alone. The rule "do not change values" means we must rewire pointers.
  2. Brute force. Copy all values into an array, reverse each chunk of k in the array, and build a new list. This is correct and simple, and it runs in O(n) time. It uses O(n) extra space, and it creates new nodes instead of rewiring the existing ones. The brute-force code below is a useful check.
  3. Find the waste. The array copy is the extra space. The same reversal we used in Reverse Linked List can be applied to each group, if we reconnect the group before and after it.
  4. Optimise. Keep group_prev, the node just before the current group, starting at the dummy. For each group: find the k-th node kth ahead of group_prev. If there is no k-th node, stop. Save group_next, the node after kth. Reverse the k nodes using group_next as the starting prev, so the first node of the group points to group_next automatically. Then connect group_prev.next to kth, and move group_prev to the old first node of the group, which is now its tail. O(n) time and O(1) extra space.
  5. Dry run. 1,2,3,4,5 with k = 2. Group 1: group_prev = dummy, kth = node 2, group_next = node 3. Reverse 1 and 2 with prev starting at node 3: 2 points to 1, 1 points to 3. Connect dummy to 2. group_prev = node 1. Group 2: node 1 now links to node 3, so the two steps from node 1 reach node 3, then node 4. So kth = node 4, and group_next = node 5. Reverse 3 and 4: 4 points to 3, 3 points to 5. Connect node 1 to node 4. group_prev = node 3. Group 3: node 3 links to 5, so the first step reaches 5 and the second step reaches None. The group is incomplete, so stop. Result: 2, 1, 4, 3, 5.

Code

class ListNode:
    def __init__(self, val=0, next=None):
        self.val = val
        self.next = next

def reverse_k_group(head, k):
    dummy = ListNode(0, head)
    group_prev = dummy                       # the node just before the current group
    while True:
        # Find the k-th node counting from group_prev. Stop if the group is incomplete.
        kth = group_prev
        for _ in range(k):
            kth = kth.next
            if kth is None:
                return dummy.next
        group_next = kth.next                # the first node after this group
        # Reverse the k nodes. Start prev at group_next so the group's tail links forward.
        prev = group_next
        curr = group_prev.next
        while curr is not group_next:
            nxt = curr.next
            curr.next = prev
            prev = curr
            curr = nxt
        # Reconnect: the previous group now ends at kth, and the old first node is the new tail.
        first = group_prev.next
        group_prev.next = kth
        group_prev = first

def build(values):
    head = None
    for v in reversed(values):
        head = ListNode(v, head)
    return head

def to_list(head):
    out = []
    while head is not None:
        out.append(head.val)
        head = head.next
    return out

print(to_list(reverse_k_group(build([1, 2, 3, 4, 5]), 2)))
print(to_list(reverse_k_group(build([1, 2, 3, 4, 5]), 3)))
print(to_list(reverse_k_group(build([1, 2, 3, 4, 5]), 1)))
[2, 1, 4, 3, 5]
[3, 2, 1, 4, 5]
[1, 2, 3, 4, 5]

A brute-force check

The simpler version copies values into an array. It is useful for checking the pointer version on small inputs, and it helps you explain the idea before you optimise.

def reverse_k_group_brute(values, k):
    out = []
    for start in range(0, len(values), k):
        chunk = values[start:start + k]
        if len(chunk) == k:               # only complete groups are reversed
            chunk.reverse()
        out.extend(chunk)
    return out

print(reverse_k_group_brute([1, 2, 3, 4, 5], 2))
print(reverse_k_group_brute([1, 2, 3, 4, 5], 3))
[2, 1, 4, 3, 5]
[3, 2, 1, 4, 5]

Time O(n) · Space O(1) for the pointer version, O(n) for the brute-force copy

TrapForgetting to check that a full group of k exists before reversing. Reversing a short tail group breaks the rule that it must stay as it is.

TrapLosing the rest of the list. Save group_next before you touch any next pointer in the group, or the nodes after the group disappear.

Pattern to rememberTo reverse a block inside a list, find the boundary nodes first, reverse the block with the usual prev and curr loop starting from the node after the block, then reconnect the boundary nodes to the block's new ends.

Summary

Byte
A group of 8 bits, the basic unit of addressable memory.
Two's complement
The standard way to store negative integers, so that addition works without special cases.
IEEE 754
The standard for floating-point numbers: sign, exponent and fraction fields.
Bias
A fixed number added to the exponent when it is stored (127 for single precision).
Program counter (PC)
The register holding the address of the next instruction.
Instruction cycle
Fetch, decode and execute, repeated for every instruction.
Effective address
The final memory address an instruction uses, after the addressing mode is applied.
Addressing mode
The rule for finding an operand: immediate, direct, indirect, register, indexed, relative and so on.
RISC
Reduced instruction set: simple instructions and a load/store design, such as ARM, RISC-V and MIPS.
CISC
Complex instruction set: powerful instructions that can access memory directly, such as x86.
Pipeline
Overlapping the stages of several instructions so that one finishes per cycle once the pipeline is full.
Latency and throughput
Latency is how long one instruction takes; throughput is how many finish per unit time.
Hazard
A situation that prevents the next instruction from running in its planned cycle.
Forwarding
Passing a result directly to a later stage, so that a data hazard does not need a stall.
Branch prediction
Guessing the outcome of a branch and continuing; wrong guesses are flushed.
Cache hit and miss
A hit finds the data in the cache; a miss must fetch it from the next level.
Locality
Programs reuse recent data (temporal) and nearby data (spatial), which makes caches work.
Tag, index, offset
The three parts of an address used to find a block in a cache.
Conflict miss
A miss caused by two blocks competing for the same slot.
Write-back and dirty bit
Writes stay in the cache until eviction, and a dirty bit marks blocks that need saving.
AMAT
Average memory access time: hit time plus miss rate times miss penalty.
Interrupt
A signal that makes the CPU stop and run a handler for an event.
Interrupt service routine (ISR)
The handler that runs in response to an interrupt.
DMA
Direct memory access: a controller moves a block of data without the CPU copying each byte.
Polling
The CPU repeatedly checks a device's status, which wastes time when the device is idle.
Multicore
A chip with several complete cores that run threads in parallel.
Cache coherence
Rules, such as MESI, that keep copies of shared data consistent across cores.
Amdahl's law
Speedup = 1 / ((1 - p) + p / n): the serial part limits the gain from more cores.
GPU and SIMT
Many simple cores that run the same instruction across many threads on different data.
Dummy head
A placeholder node before the real head, which removes special cases in linked-list code.
