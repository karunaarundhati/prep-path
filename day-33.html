Variables, scope, hoisting and closures

JavaScript has three ways to declare a variable. var is the old form. It is function-scoped (visible throughout the whole function that contains it), and it can be redeclared. let and const are block-scoped (visible only inside the nearest pair of curly braces), and they cannot be redeclared in the same scope. const also forbids reassigning the binding, although an object it points to can still change its properties. Prefer const by default and let when a value must change. Avoid var in new code.

Hoisting

Before any code in a scope runs, the engine scans the scope for declarations and sets them up. This is called hoisting. The effect differs by kind. A var is hoisted and starts as undefined, so reading it early gives undefined and no error. A function declaration is hoisted with its body, so you can call it above the line where it is written. A let or const is also hoisted, but it stays uninitialised until its declaration runs. Reading it in that period throws a ReferenceError. The period between the start of the scope and the declaration is the temporal dead zone (TDZ).

console.log(a);          // undefined: var is hoisted and set to undefined
var a = 5;

console.log(hello());    // "hi": the whole function is hoisted
function hello() {
  return "hi";
}

try {
  console.log(b);        // reading b inside its TDZ
} catch (error) {
  console.log(error.name + ": " + error.message);
}
let b = 10;
console.log(b);          // 10: by now the declaration has run
undefined
hi

10

Read the output from top to bottom. The first line is undefined because var a exists before its assignment. The function call works because the whole declaration is hoisted. The let b line fails because the code runs before the declaration, inside the TDZ. The final line works because the declaration has run by then.

A closure is a function that remembers the variables of the scope where it was created, even after that scope has finished. Closures are how JavaScript does private state. The counter below keeps count hidden: only the two returned methods can reach it. Each call to makeCounter creates a new scope, so two counters do not share state.

function makeCounter() {
  let count = 0;
  return {
    next() { count += 1; return count; },
    peek() { return count; },
  };
}

console.log("c2:", c2.next());

The second half is a classic interview question. With var, all three closures share one i, and by the time they run the loop has finished with i equal to 3. With let, each loop iteration gets a fresh j, so each closure keeps its own value.

TrapAssuming a closure captures the value of a variable at the moment it is created. It captures the variable itself, so later changes to that variable are visible to the closure.

What does this print, and why: for (var i = 0; i < 3; i++) setTimeout(() => console.log(i));

It prints 3 three times, because var has one binding for the whole function. The timers run after the loop has finished, when i is already 3. Replacing var with let gives 0, 1 and 2, because each iteration has its own binding.

Type coercion, null and undefined, and equality

JavaScript converts values between types automatically when an operation needs a different type. This is called coercion. The rules are consistent but surprising. The operator + turns a number into a string if either side is a string, so "5" + 3 gives "53". The operator - converts to numbers, so "5" - 3 gives 2. Knowing the rules matters less than knowing when to avoid them.

null is an intentional "no value" that a programmer assigns. undefined means a value was never given, such as a missing argument or property. typeof null returns "object", which is a historical bug that cannot be fixed without breaking existing code. The double equals == converts types before comparing, while === compares type and value with no conversion. Use === by default.

console.log("5" + 3, "5" - 3);

The falsy values are false, 0, "", null, undefined and NaN. Every other value is truthy, including the string "0" and the empty array. NaN is the only value not equal to itself, so use Number.isNaN to test for it.

TrapUsing || for default values. count || 10 replaces a legitimate 0 with 10. Use ??, the nullish coalescing operator, which only replaces null and undefined.

Why does [] == false evaluate to true?

When one side is a boolean, == converts it to a number, so false becomes 0. The array is then converted to a primitive, which is its string form, the empty string. The empty string converts to the number 0, and 0 == 0 is true. The chain of conversions is the reason == is hard to reason about.

this, bind, prototypes and classes

The value of this depends on how a function is called, not where it is written. In a method call such as user.greet(), this is the object before the dot. In a plain call such as greet() it is undefined in strict mode (the default in classes and modules), or the global object in sloppy mode. An arrow function has no this of its own; it uses the this of the scope where it was written. call and apply invoke a function with a chosen this, and bind returns a new function with this fixed.

The prototype chain is how objects share methods. When you read a property, the engine looks at the object itself, then at its prototype, then at that prototype's prototype, until it reaches null. dog.speak is not stored on dog; it is found on Animal.prototype. The in operator searches the whole chain, while hasOwnProperty checks only the object itself. A class is syntax over this same mechanism: extends sets up the prototype link, and super calls the parent's method.

Arrow functions are a common source of this bugs when used as object methods. An arrow method inherits this from the module or script scope, not from the object, so this.name is not what you expect.

Key ideaA function's this is decided at the call site. Use bind or an arrow function when a callback must keep the object it was written in.

What is the difference between call, apply and bind?

call and apply invoke the function immediately with a chosen this. call takes the arguments one by one, and apply takes them as an array. bind does not invoke anything. It returns a new function with this fixed, and that function can be called later, with any extra arguments placed after the bound ones.

The event loop, promises and async/await

JavaScript runs one piece of code at a time on a single thread. The event loop decides what runs next. Each macrotask (a timer, an I/O callback, a user event) runs to completion. Between macrotasks, the engine drains the microtask queue, which holds promise callbacks and queueMicrotask callbacks. Microtasks queued during a microtask also run before the next macrotask. Node adds process.nextTick, which runs before promise callbacks. Output-order questions are answered by remembering this sequence: all synchronous code, then the nextTick and microtask queues, then one timer, and repeat.

console.log("5");

The two synchronous lines print first. The promise callback and the queueMicrotask callback are microtasks, so they run in the order they were queued, before the timer, even though the timer was queued first with a delay of zero.

Promises and async/await

A promise is an object that represents a value that will be available later. It is pending, then either fulfilled with a value or rejected with an error. then and catch attach callbacks, and each returns a new promise, so chains can be flattened. async functions always return a promise, and await pauses the function until a promise settles, without blocking the thread. The helpers Promise.all (all succeed, or the first failure rejects), Promise.allSettled (wait for every outcome) and Promise.race (the first to settle) cover most combinations.

const delay = (ms, value) => new Promise((resolve) => setTimeout(() => resolve(value), ms));

async function main() {
  const a = await delay(20, "first");
  console.log(a);
  const [b, c] = await Promise.all([delay(30, "second"), delay(10, "third")]);
  console.log(b, c);
  try {
    await Promise.reject(new Error("boom"));
  } catch (err) {
    console.log("caught", err.message);
  }
  const result = await Promise.allSettled([Promise.resolve(1), Promise.reject(new Error("no"))]);
  console.log(result.map((r) => r.status).join(","));
}
main();

second third

Notice that the two delays in Promise.all run at the same time. The whole group takes about the longest delay, not the sum, which is the most common performance mistake with await in a loop: awaiting each independent request one after another makes them run in series.

TrapWriting await inside a loop over independent work. The requests run one after another. Start them all first, then await Promise.all on the array.

Interviewers askWhy does a setTimeout of zero run after a promise callback? Answer: the promise callback is a microtask, and microtasks drain completely before the next macrotask, which a timer always is.

Why is an unhandled promise rejection a problem in Node?

A rejection with no catch handler is an error that nothing observes. Modern Node treats unhandled rejections as fatal by default, so the process exits. Always end a chain with a catch or await inside a try block, and handle rejections of promises that you start but do not await.

DOM events, Node.js and TypeScript basics

In the browser, JavaScript reads and changes the DOM and reacts to user events. An event travels in two phases: capture from the window down to the target, then bubble from the target back up. addEventListener attaches a handler, and event.target is the element that was clicked.

Event delegation

Attaching one listener to a parent, instead of one listener to each child, is called delegation. It works because clicks bubble. The handler finds the relevant child with closest(). Delegation handles items added later, uses less memory, and needs fewer listeners to remove.

// Browser code: runs in a page, not in Node, so there is no output block
const list = document.querySelector("#todo-list");
list.addEventListener("click", (event) => {
  const item = event.target.closest("li");
  if (!item || !list.contains(item)) return;
  item.classList.toggle("done");
});

Debounce and throttle

A debounced function waits until calls stop for a set time, then runs once, which suits search boxes. A throttled function runs at most once per time window, which suits scroll and resize handlers. The example passes the clock as an argument, so the throttle output does not depend on the real time.

function debounce(fn, wait) {
  let timer = null;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), wait);
  };
}

function throttle(fn, wait, clock = Date.now) {
  let last = -Infinity;
  return function (...args) {
    const now = clock();
    if (now - last >= wait) {
      last = now;
      return fn.apply(this, args);
    }
  };
}

const search = debounce((q) => console.log("search:", q), 50);
search("a");
search("ab");
search("abc");

let fakeNow = 0;
const logged = throttle((x) => console.log("ran with", x), 100, () => fakeNow);
fakeNow = 0;
logged(1);
fakeNow = 50;
logged(2);
fakeNow = 120;
logged(3);
ran with 1
ran with 3
search: abc

The three search calls cancel each other until the last one, so the debounced function runs once after 50 milliseconds with "abc". The throttled calls at fake times 0 and 120 run, and the one at 50 is skipped because only 50 of the 100 millisecond window has passed.

Node.js basics

Node.js runs JavaScript outside the browser, with access to the file system, the network and the operating system. It is single-threaded like the browser, and it uses the same event loop. Its built-in modules are loaded with require in CommonJS files, or with import in ES module files (a .mjs file or a package whose package.json says "type": "module"). Packages come from npm, and package.json lists them. Use node: prefixes for built-in modules, such as require("node:fs"), so a package with the same name cannot shadow them. File and network operations offer callback and promise versions, and the promise versions work well with async/await.

const { readFile } = require("node:fs/promises");

async function loadConfig(path) {
  const text = await readFile(path, "utf8");
  return JSON.parse(text);
}

TypeScript basics

TypeScript is JavaScript with static types, checked before the code runs and then removed. It is not run directly by Node, so the snippet below is shown for reading only. Types describe the shape of data, and an interface names a shape that objects must have. The compiler reports mistakes such as passing a string where a number is required, or reading a property the type does not declare.

// TypeScript (not plain JavaScript; shown for reading, not run here)
interface Product {
  id: number;
  name: string;
  price?: number;   // optional property
}

function total(items: Product[]): number {
  return items.reduce((sum, p) => sum + (p.price ?? 0), 0);
}
Why is event delegation useful for a list whose items are added later?

Because click events bubble, a single listener on the list receives clicks on every current and future item, without needing to be attached to each new element. The handler finds the clicked item with closest("li"). This avoids forgetting to attach listeners to new items and keeps memory use low.

Polyfills: map, bind and Promise.all

A polyfill is code that adds a feature missing from an older runtime, usually by implementing the standard behaviour on top of existing features. Interviewers ask for polyfills because they test your understanding of the feature itself. Write each one from the specification, handle the edge cases you can name, and explain what you left out.

Array.prototype.myMap = function (fn) {
  const out = [];
  for (let i = 0; i < this.length; i++) {
    out.push(fn(this[i], i, this));
  }
  return out;
};

Function.prototype.myBind = function (context, ...boundArgs) {
  const fn = this;
  return function (...args) {
    return fn.apply(context, [...boundArgs, ...args]);
  };
};

function promiseAll(items) {
  return new Promise((resolve, reject) => {
    const results = new Array(items.length);
    let remaining = items.length;
    if (remaining === 0) {
      resolve(results);
      return;
    }
    items.forEach((item, i) => {
      Promise.resolve(item).then((value) => {
        results[i] = value;
        remaining -= 1;
        if (remaining === 0) resolve(results);
      }, reject);
    });
  });
}

console.log([1, 2, 3].myMap((x) => x * 2).join(","));
function greet(greeting, punct) { return greeting + ", " + this.name + punct; }
const bob = greet.myBind({ name: "Bob" }, "Hello");
console.log(bob("!"));
promiseAll([1, Promise.resolve(2), new Promise((r) => setTimeout(() => r(3), 5))])
  .then((values) => console.log(values.join(" ")));
2,4,6
Hello, Bob!
1 2 3

Three points matter in an interview. The myMap polyfill passes the index and the array as the extra arguments, as the real method does, and it skips holes only if you add that check. The myBind polyfill puts the bound arguments first, then the call arguments, so bob("!") is the same as calling greet with "Hello" and "!". Neither polyfill supports new on a bound function, which the real bind does. The promiseAll polyfill returns results in input order even when promises finish in a different order, because it writes each value to its index. It resolves immediately for an empty array, which is an edge case people forget.

TrapForgetting that promiseAll must reject on the first failure. The example above passes reject to each then, so the outer promise rejects as soon as any input rejects.

Why does the promiseAll polyfill store results by index instead of pushing them?

Promises settle in whatever order their work finishes, but the result array must match the input order. Writing results[i] puts each value in the right position no matter when it arrives, while pushing would give results in completion order.

Interview questions

Answer each question aloud before opening the model answer.

What is the difference between var, let and const?

var is function-scoped, hoisted with the value undefined, and can be redeclared. let and const are block-scoped and sit in the temporal dead zone until their declaration runs. const also prevents reassigning the binding, though it does not freeze an object.

What is the temporal dead zone?

It is the period between the start of a block and the execution of a let or const declaration. Reading the variable in that period throws a ReferenceError, which protects against using a value before it has been set.

What does typeof null return, and why?

It returns "object". This is a bug from the first version of JavaScript, kept for compatibility. To test for null, compare with === null.

When should you use == instead of ===?

Almost never. The one common exception is value == null, which is true for both null and undefined. Otherwise use === so that no hidden conversion happens.

In what order do these run: a setTimeout of 0, a resolved promise's then, and synchronous code?

Synchronous code first, then the promise callback (a microtask), then the timer (a macrotask). Microtasks drain completely before the next timer runs.

What does an arrow function do with this?

It has no this of its own. It uses the this of the surrounding scope, which is fixed when the arrow is created. It cannot be changed with call, apply or bind.

What is the difference between a microtask and a macrotask?

Macrotasks are timers, I/O callbacks and user events. Microtasks are promise callbacks and queueMicrotask callbacks. After each macrotask the engine runs every queued microtask before taking the next macrotask.

How does event delegation work?

One listener on a parent receives bubbling events from its children. The handler identifies the target with event.target.closest(selector). It covers elements added later and reduces the number of listeners.

Why does debounce differ from throttle?

Debounce runs once after calls stop for a delay, so the last call wins. Throttle runs at most once per window, so calls are sampled at a steady rate. Search boxes usually debounce, and scroll handlers usually throttle.

DSA: design problems (LRU, min stack, nested iterator, LFU)

Design problems ask you to build a data structure that supports several operations, each with a time target. Start by listing the operations and their cost goals. Then choose the structures that meet each goal, and keep them consistent with each other. Most solutions combine a hash map (O(1) lookup) with a second structure that tracks order, a minimum, or a stack of states.

  1. Name the operations and the complexity each must have, such as O(1) get and put.
  2. Pick one structure per need: a hash map for lookup, a linked list or stack for order, and extra data for a value such as the minimum.
  3. Write the invariant that must hold after every operation, and check each method keeps it.
  4. Test the sequence the problem gives, and one edge case, such as an update of an existing key.

LRU Cache (LeetCode 146)

Design a cache with a fixed capacity. get(key) returns the value or -1 if the key is absent, and it marks the key as recently used. put(key, value) inserts or updates a key, and when the cache is full it first evicts the least recently used key. Both operations must run in O(1) time.

How to think about it

  1. Understand. Two rules: the cache never holds more than capacity keys, and recency changes on every get and put.
  2. Brute force. Keep a list of keys ordered by recency. Each get searches the list, O(n), and each move shifts elements.
  3. Find the waste. Finding a key is a lookup (a hash map does it in O(1)), and reordering needs to unlink and relink one node (a doubly linked list does it in O(1) when we hold the node).
  4. Optimise. Combine both: the hash map maps keys to nodes, and the doubly linked list keeps nodes from most to least recent. Dummy head and tail nodes remove the edge cases at the ends. The least recent real node sits just before the tail.
  5. Dry run. With capacity 2, put 1 and put 2 give the order 2, 1 (most recent first). get 1 gives the order 1, 2. put 3 evicts 2, so the order is 3, 1. The later get calls return -1 for evicted keys, matching the expected output.

Code

class Node:
    def __init__(self, key=0, value=0):
        self.key = key
        self.value = value
        self.prev = None
        self.next = None


class LRUCache:
    def __init__(self, capacity):
        self.capacity = capacity
        self.map = {}                  # key to Node
        self.head = Node()             # dummy: head.next is the most recent node
        self.tail = Node()             # dummy: tail.prev is the least recent node
        self.head.next = self.tail
        self.tail.prev = self.head

    def _unlink(self, node):
        node.prev.next = node.next
        node.next.prev = node.prev

    def _push_front(self, node):
        node.prev = self.head
        node.next = self.head.next
        self.head.next.prev = node
        self.head.next = node

    def get(self, key):
        node = self.map.get(key)
        if node is None:
            return -1
        self._unlink(node)
        self._push_front(node)
        return node.value

    def put(self, key, value):
        node = self.map.get(key)
        if node is not None:
            node.value = value
            self._unlink(node)
            self._push_front(node)
            return
        if len(self.map) == self.capacity:
            lru = self.tail.prev       # least recently used real node
            self._unlink(lru)
            del self.map[lru.key]
        node = Node(key, value)
        self.map[key] = node
        self._push_front(node)

cache.put(1, 1)
cache.put(2, 2)
results = [cache.get(1)]
cache.put(3, 3)
results.append(cache.get(2))
cache.put(4, 4)
results.append(cache.get(1))
results.append(cache.get(3))
results.append(cache.get(4))

Pattern to rememberHash map for finding, doubly linked list for ordering. Whenever a design needs O(1) lookup and O(1) reordering, the pair is the usual answer.

Min Stack (LeetCode 155)

Design a stack that supports push, pop, top and getMin, each in constant time. getMin returns the smallest value currently in the stack. For example, after pushing -2, 0 and -3, getMin returns -3. After popping -3, getMin returns -2.

How to think about it

  1. Understand. The minimum must be correct after every pop, not only after pushes.
  2. Brute force. Scan the whole stack in getMin. That is O(n).
  3. Find the waste. The minimum only changes when a value is pushed or popped. If each stack entry remembers the minimum of everything at or below it, popping restores the previous minimum without any search.
  4. Optimise. Store pairs (value, minimum so far). A push computes the new minimum from the previous top's minimum. A pop removes the pair, which exposes the previous minimum automatically.
  5. Dry run. Push -2 gives pair (-2, -2). Push 0 gives (0, -2). Push -3 gives (-3, -3). getMin returns -3. After pop, the top is (0, -2), so getMin returns -2.

Code

class MinStack:
    def __init__(self):
        self.items = []                # (value, minimum of this value and everything below)

    def push(self, val):
        if self.items:
            current_min = min(val, self.items[-1][1])
        else:
            current_min = val
        self.items.append((val, current_min))

    def pop(self):
        self.items.pop()

    def top(self):
        return self.items[-1][0]

    def get_min(self):
        return self.items[-1][1]


s = MinStack()
s.push(-2)
s.push(0)
s.push(-3)
out = [s.get_min()]
s.pop()
out.append(s.top())
out.append(s.get_min())
print(out)
[-3, 0, -2]

Time O(1) per operation · Space O(n)

TrapKeeping one global minimum variable and updating it only on push. After popping the minimum, the variable is wrong. Storing the minimum per entry fixes it.

Pattern to rememberWhen a stack must answer an aggregate question (minimum, maximum, sum) in O(1), store the aggregate with each entry, computed from the entry below it.

Flatten Nested List Iterator (LeetCode 341)

You are given a list whose elements are either integers or other lists. Build an iterator with hasNext() and next() that returns every integer in order, left to right, flattening nested lists. For example, [[1, 1], 2, [1, 1]] yields 1, 1, 2, 1, 1. LeetCode provides a NestedInteger interface, and the code below includes a small stand-in with the same three methods so it can run.

How to think about it

  1. Understand. The iterator must be lazy: it should not flatten the whole structure up front. next() is only called after hasNext() returns true.
  2. Brute force. Flatten everything into a list in the constructor, then walk it. That is correct, but it uses memory for the entire result and does work the caller may never need.
  3. Find the waste. We only need to expand a nested list when the next integer is inside it.
  4. Optimise. Keep a stack of pending NestedInteger items, with the next one on top. In hasNext(), while the top is a list, pop it and push its elements in reverse, so the first element ends up on top. Stop when the top is an integer or the stack is empty.
  5. Dry run. For [[1, 1], 2, [1, 1]], the stack starts as [list2, 2, list1] with list1 on top. hasNext expands list1 and sees 1 on top, so next returns 1. The second 1 follows the same way, then 2, then the last list.

Code

class NestedInteger:
    """A stand-in for the NestedInteger interface that LeetCode provides."""
    def __init__(self, value):
        self.value = value             # an int, or a list of NestedInteger

    def isInteger(self):
        return isinstance(self.value, int)

    def getInteger(self):
        return self.value

    def getList(self):
        return self.value


class NestedIterator:
    def __init__(self, nested_list):
        self.stack = list(reversed(nested_list))    # the top of the stack is the next item

    def hasNext(self):
        while self.stack:
            top = self.stack[-1]
            if top.isInteger():
                return True
            self.stack.pop()
            self.stack.extend(reversed(top.getList()))   # expand the list in place
        return False

    def next(self):
        return self.stack.pop().getInteger()          # call hasNext() first


def wrap(x):
    if isinstance(x, int):
        return NestedInteger(x)
    return NestedInteger([wrap(item) for item in x])


def flatten_all(nested):
    it = NestedIterator(wrap(nested).getList())
    out = []
    while it.hasNext():
        out.append(it.next())
    return out


print(flatten_all([[1, 1], 2, [1, 1]]))
print(flatten_all([1, [4, [6]]]))
print(flatten_all([[], [[]], 7]))
[1, 1, 2, 1, 1]
[1, 4, 6]
[7]

Time O(total elements) overall, O(depth) extra space per step, amortised O(1) per next

TrapExpanding a nested list inside next() and forgetting that hasNext() may be called several times. Keeping the expansion in hasNext() makes repeated calls safe, because the expansion only happens once for each list.

Pattern to rememberA stack of pending work, with the next item on top, gives a lazy depth-first traversal. Pushing children in reverse order keeps the left-to-right order.

LFU Cache (LeetCode 460)

Design a cache with a fixed capacity that evicts the least frequently used key. Each get or put of a key counts as a use. When the cache is full, evict the key with the lowest use count, and if several keys tie, evict the least recently used among them. get returns -1 for a missing key. Both operations must run in O(1) time.

How to think about it

  1. Understand. Two orderings matter: first by use count, then by recency inside the same count. A put of an existing key counts as a use and updates its value.
  2. Brute force. Store each key's count and time of last use, and scan for the minimum on eviction. Eviction is O(n).
  3. Find the waste. The keys with the same count form a group, and inside a group the order is recency. If every count has its own LRU ordering, eviction only needs the group for the smallest count.
  4. Optimise. Keep three structures: a map from key to value, a map from key to count, and a map from count to an ordered set of keys (an OrderedDict, oldest first). Track min_freq, the smallest count present. Touching a key moves it from its count bucket to the next one, and if its old bucket becomes empty while it was the minimum, min_freq increases by one, because the key now sits in the next bucket. Eviction takes the oldest key in the min_freq bucket.
  5. Dry run. Capacity 2: put 1 and put 2 put both keys in bucket 1 (order 1, 2). get 1 moves key 1 to bucket 2, leaving bucket 1 with key 2. put 3 evicts key 2 (the only key at the minimum count of 1). get 3 moves key 3 to bucket 2, which empties bucket 1 and makes min_freq 2.

Code

from collections import OrderedDict, defaultdict


class LFUCache:
    def __init__(self, capacity):
        self.capacity = capacity
        self.values = {}                          # key to value
        self.freq = {}                            # key to use count
        self.buckets = defaultdict(OrderedDict)   # count to keys, oldest first
        self.min_freq = 0

    def _touch(self, key):
        f = self.freq[key]
        del self.buckets[f][key]
        if not self.buckets[f]:
            del self.buckets[f]
            if self.min_freq == f:
                self.min_freq += 1
        self.freq[key] = f + 1
        self.buckets[f + 1][key] = None

    def get(self, key):
        if key not in self.values:
            return -1
        self._touch(key)
        return self.values[key]

    def put(self, key, value):
        if self.capacity == 0:
            return
        if key in self.values:
            self.values[key] = value
            self._touch(key)
            return
        if len(self.values) == self.capacity:
            bucket = self.buckets[self.min_freq]
            victim, _ = bucket.popitem(last=False)   # least recent among the least used
            if not bucket:
                del self.buckets[self.min_freq]
            del self.values[victim]
            del self.freq[victim]
        self.values[key] = value
        self.freq[key] = 1
        self.buckets[1][key] = None
        self.min_freq = 1


cache = LFUCache(2)
cache.put(1, 1)
cache.put(2, 2)
out = [cache.get(1)]
cache.put(3, 3)
out.append(cache.get(2))
out.append(cache.get(3))
cache.put(4, 4)
out.append(cache.get(1))
out.append(cache.get(3))
out.append(cache.get(4))
print(out)
[1, -1, 3, -1, 3, 4]

Time O(1) per operation · Space O(capacity)

TrapForgetting to reset min_freq to 1 after inserting a new key. A new key has count 1, which is always the smallest possible, so the minimum must go back to 1.

Pattern to rememberWhen eviction depends on two keys (frequency, then recency), group by the first key and keep each group in recency order. Track the smallest group so eviction is one lookup.
