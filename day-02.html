Object-oriented programming in Python

A class is a blueprint. An object (also called an instance) is one thing built from that blueprint, with its own data. Methods are functions defined inside a class. Python's object model is simple to start with and deep underneath. The first part of this unit covers the basics you must write fluently. The rest covers the parts interviewers use to test depth.

Classes, instances and self

When you call a class like a function, Python creates a new object and runs __init__ on it. The first parameter of every method is the object the method was called on, which is conventionally named self. Writing self.name = name stores data on that particular object.

class Dog:
    species = "canis"                  # class attribute: shared by all dogs

    def __init__(self, name):          # runs when you write Dog("Rex")
        self.name = name               # instance attribute: one per dog

    def speak(self):                   # self is the dog the method was called on
        return f"{self.name} says woof"

d = Dog("Rex")
print(d.speak())
print(Dog.species, d.species)
Rex says woof
canis canis

Attribute lookup on an instance first checks the instance's own dictionary, then the class. That is why d.species finds the class attribute. Setting d.species = "other" would create an instance attribute that hides the class one for that object only.

TrapA mutable class attribute is shared by every instance, because the instances do not each get a copy of it. Create per-object mutable state in __init__ instead.

class Bag:
    items = []                         # one list shared by the whole class

    def add(self, x):
        self.items.append(x)

a, b = Bag(), Bag()
a.add(1)
print(b.items)
[1]

The fix is to write self.items = [] inside __init__, so each object gets its own list.

Name mangling

A name that starts with two underscores and does not end with two underscores is rewritten to _ClassName__name. This prevents accidental clashes when a subclass uses the same attribute name. It is not privacy.

@property: attributes with rules

A property lets you write obj.attr while running a function behind the scenes. It is the Pythonic replacement for explicit getter and setter methods. The setter below rejects impossible temperatures, and the read-only property computes Fahrenheit from the stored Celsius value.

class Temperature:
    def __init__(self, celsius):
        self.celsius = celsius         # goes through the setter below

    @property
    def celsius(self):
        return self._c

    @celsius.setter
    def celsius(self, value):
        if value < -273.15:
            raise ValueError("below absolute zero")
        self._c = value

    @property
    def fahrenheit(self):              # computed on each read, no setter, so read-only
        return self._c * 9 / 5 + 32

t = Temperature(25)
print(t.fahrenheit)
try:
    t.celsius = -300
except ValueError as e:
    print("ValueError:", e)
77.0
ValueError: below absolute zero

Instance methods, @classmethod and @staticmethod

An ordinary method receives the instance. A @classmethod receives the class itself, conventionally named cls, which makes it a good alternative constructor. A @staticmethod receives neither, so it is just a function grouped inside the class for organisation.

class Date:
    def __init__(self, y, m, d):
        self.y, self.m, self.d = y, m, d

    @classmethod
    def from_string(cls, s):           # cls is Date, or a subclass if one calls it
        return cls(*map(int, s.split("-")))

    @staticmethod
    def is_leap(year):                 # no self, no cls: a plain function
        return year % 4 == 0 and (year % 100 != 0 or year % 400 == 0)

d = Date.from_string("2026-11-03")
print(d.y, d.m, d.d)
print(Date.is_leap(2024), Date.is_leap(1900))
2026 11 3
True False

Using cls(...) instead of Date(...) matters when you subclass Date. Calling SubDate.from_string(...) then produces a SubDate. The leap year rule in is_leap is the Gregorian one: years divisible by 4 are leap years, except centuries not divisible by 400. That is why 1900 is not a leap year and 2024 is.

Inheritance, super() and the MRO

A subclass inherits every attribute of its parent and can override any of them. To call the overridden version from the subclass, use super(). The subtle point is that super() does not mean "my parent class". It means "the next class in the method resolution order (MRO) of the object's actual class".

The MRO is the list of classes Python searches, in order, when it looks up an attribute. Python computes it with the C3 linearization algorithm. In plain terms: a class always comes before its parents, and the parents keep the order you listed them in. You can read any class's MRO through ClassName.__mro__.

class A:
    def hello(self):
        print("A")

class B(A):
    def hello(self):
        print("B")
        super().hello()

class C(A):
    def hello(self):
        print("C")
        super().hello()

class D(B, C):                         # the "diamond": D inherits from B and C, both from A
    def hello(self):
        print("D")
        super().hello()

D().hello()
print([k.__name__ for k in D.__mro__])
D
B
C
A
['D', 'B', 'C', 'A', 'object']

Read the output as a trace. D().hello() prints "D", then its super() call goes to the next class in the MRO, which is B. B prints "B", and its super() call goes to C, not to A. That is the important detail: inside B, super() follows the MRO of the object, which is a D, so C comes next. C then calls super(), which reaches A. A does not call super(), so the chain ends. Each class runs exactly once.

Interviewers askWhat is the MRO and how does super() use it? The MRO is a fixed linear order of the classes for each type. super() calls the next class after the current one in the MRO of the object's real type, which is why it can call a sibling class in a diamond.

Because of this, every class in a cooperative hierarchy should call super(), and the methods should accept the same arguments. Otherwise the chain breaks partway through.

Dunder (magic) methods

Methods whose names start and end with two underscores are called dunder methods, short for double underscore. Python calls them when you use built-in syntax on your object. Defining __add__ lets + work, and defining __len__ lets len() work. This is how Python's own types behave, so your classes can behave the same way.

class Vector:
    def __init__(self, x, y):
        self.x, self.y = x, y
    def __repr__(self):                # the developer view, used by print when no __str__ exists
        return f"Vector({self.x}, {self.y})"
    def __add__(self, other):          # v1 + v2
        return Vector(self.x + other.x, self.y + other.y)
    def __eq__(self, other):           # v1 == v2
        return (self.x, self.y) == (other.x, other.y)
    def __len__(self):                 # len(v)
        return 2
    def __getitem__(self, i):          # v[i]; also makes the object iterable
        return (self.x, self.y)[i]

v = Vector(1, 2) + Vector(3, 4)
print(v, v == Vector(4, 6), len(v), v[0], list(v))
Vector(4, 6) True 2 4 [4, 6]

list(v) works even though we never wrote __iter__. Python falls back to calling __getitem__(0), __getitem__(1), and so on until an IndexError stops the process. Writing __iter__ is cleaner and is the modern approach.

Abstract base classes

An abstract base class (ABC) describes an interface that subclasses must implement. Methods marked @abstractmethod must be overridden. Python refuses to create an instance of any class that still has an unimplemented abstract method.

from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self):
        ...

class Square(Shape):
    def __init__(self, side):
        self.side = side
    def area(self):
        return self.side ** 2

print(Square(3).area())
try:
    Shape()
except TypeError as e:
    print("TypeError:", e)
9
TypeError: Can't instantiate abstract class Shape without an implementation for abstract method 'area'

The check happens when the object is created, not when the class is defined. A subclass that forgets one abstract method is also refused at creation time, so the mistake is caught early.

Dataclasses: less boilerplate for data holders

A dataclass is a class whose __init__, __repr__ and __eq__ are generated from annotated fields. You declare the fields with type annotations, and the decorator writes the methods. Options change the result. order=True adds comparison methods. frozen=True makes instances immutable and hashable. slots=True, available from Python 3.10, stores attributes in a fixed layout, which saves memory and blocks new attributes.

from dataclasses import dataclass, field

@dataclass(order=True, frozen=True)
class Point:
    x: int
    y: int = 0

@dataclass
class Student:
    name: str
    marks: list = field(default_factory=list)   # a fresh list per student; never write marks: list = []

p = Point(1, 2)
print(p)
print(Point(1, 2) == Point(1, 2), Point(1, 2) < Point(2, 0))
print(Student("Asha"))
try:
    p.x = 5
except Exception as e:
    print(type(e).__name__, e)
Point(x=1, y=2)
True True
Student(name='Asha', marks=[])
FrozenInstanceError cannot assign to field 'x'

The field(default_factory=list) line is the dataclass version of the mutable default trap from day 1. A plain marks: list = [] is rejected by the decorator with an error, because it would share one list between all instances. The factory runs once for each new object.

Point(1, 2) < Point(2, 0) is True because order=True compares the fields as tuples: (1, 2) is less than (2, 0) since 1 is less than 2.

Iterators and generators

An iterable is anything you can loop over with for. An iterator is the object that hands out the values one at a time when asked. A generator is the easiest way to write an iterator, because Python builds the iterator for you from a function that uses yield.

The iterator protocol

A for loop is a shortcut for two steps. It calls iter(x) once to get an iterator, then calls next() repeatedly until the iterator raises StopIteration. You can do those steps by hand, which makes the protocol visible.

nums = [10, 20]
it = iter(nums)            # calls nums.__iter__() and returns an iterator
print(next(it))            # calls it.__next__()
print(next(it))
try:
    print(next(it))
except StopIteration:
    print("no more items")
10
20
no more items

The list itself is an iterable but not an iterator, because it has no __next__ and does not remember a position. The iterator returned by iter remembers the position. This distinction is a common interview question.

Generators with yield

A function that contains yield does not run its body when you call it. It returns a generator object. Each call to next() runs the body until the next yield, hands that value out, and pauses with all its local variables intact. The next next() call resumes right after the yield.

def countdown(n):
    print("start")
    while n > 0:
        yield n
        n -= 1
    print("done")

g = countdown(3)           # nothing is printed yet: the body has not started
print(next(g))
print(list(g))
start
3
done
[2, 1]

Trace the output. The first next(g) runs the body up to yield 3, which prints "start" and returns 3. The list(g) call resumes the generator after the yield, so n becomes 2 and yields 2, then 1. When n reaches 0, the loop ends, "done" is printed, and the generator finishes. Only then does list build its result, so "done" appears before the list.

Why use generators: memory and laziness

A generator produces values on demand. It never stores the whole sequence. A list comprehension builds the entire list in memory before anything else happens. A generator expression, written with round brackets, does the same work lazily. For large data this is the difference between using a few bytes and using gigabytes.

squares_gen = (x * x for x in range(1_000_000))
print(sum(squares_gen))
333332833333500000

The generator holds only its current state, a few hundred bytes, and computes each square when sum asks for it. A list of the same million squares would need several megabytes before sum even starts. The sum is 0 squared plus 1 squared plus and so on up to 999999 squared, which is the closed form (n-1) n (2n-1) / 6 for n = 1000000, here printed exactly by Python's big integers.

TrapA generator can be consumed only once. After the first pass it is empty, so a second list() returns nothing, with no error.

g = (x for x in range(3))
print(list(g), list(g))
[0, 1, 2] []

If you need to loop twice, either build a list once or create the generator again. Keeping the generator in a variable and expecting it to restart is a classic mistake.

yield from and lazy pipelines

yield from delegates to another iterable, passing each of its values straight out. It is the standard way to write a recursive generator, such as one that flattens a nested list.

def flatten(nested):
    for item in nested:
        if isinstance(item, list):
            yield from flatten(item)    # hand over every value the inner generator makes
        else:
            yield item

print(list(flatten([1, [2, [3, 4]], 5])))

lines = ["10", "x", "25", "7"]
numbers = (int(s) for s in lines if s.isdigit())     # stage 1: parse digits only
big = (n for n in numbers if n > 8)                  # stage 2: keep values above 8
print(list(big))
[1, 2, 3, 4, 5]
[10, 25]

The second example is a pipeline. Nothing runs until list(big) asks for a value. That value asks numbers for one, which asks the source for one line. Each item flows through all the stages before the next item is read, so the stages never build intermediate lists. This is how large log files or database rows are processed in Python.

Interviewers askWhat is the difference between return and yield? return ends the function and sends one value. yield pauses the function, sends a value, and can resume later, so the function produces a sequence over time.

What is the difference between an iterable and an iterator?

An iterable can produce an iterator through iter(). Examples are lists, strings and dicts. An iterator has a __next__ method and remembers its position, and it is exhausted after one pass. A list is iterable but not an iterator.

Decorators

A decorator is a function that takes another function and returns a new function that adds behaviour around it. The @ syntax is shorthand. Writing @logged above def add is exactly the same as writing add = logged(add) after the definition. Decorators rely on two ideas you already know: functions are objects you can pass around, and closures remember variables from their enclosing scope.

A logging decorator, step by step

The outer function receives the original function. It defines a wrapper that accepts any arguments, calls the original with them, and returns the result. The wrapper is what the name add refers to after decoration.

import functools

def logged(func):
    @functools.wraps(func)                # copy the name and docstring of func onto wrapper
    def wrapper(*args, **kwargs):         # accepts whatever the caller passes
        print(f"calling {func.__name__} with {args} {kwargs}")
        result = func(*args, **kwargs)    # call the original function
        print(f"{func.__name__} returned {result!r}")
        return result
    return wrapper

@logged
def add(a, b=0):
    """Add two numbers."""
    return a + b

print(add(2, b=3))
print(add.__name__, add.__doc__)
calling add with (2,) {'b': 3}
add returned 5
5
add Add two numbers.

Without @functools.wraps(func), the last line would print wrapper and None instead of the original name and docstring. Debuggers, documentation tools and test frameworks rely on those attributes, so always use wraps in a decorator. Notice also that the wrapper uses *args and **kwargs, so it works for any signature.

A decorator that takes arguments

If the decorator itself needs settings, it needs one more layer. The outermost function takes the settings and returns the real decorator. Read it as three nested functions: the factory with the settings, the decorator that receives the function, and the wrapper that runs at call time.

import functools

def repeat(n):                             # level 1: takes the setting
    def decorator(func):                   # level 2: takes the function
        @functools.wraps(func)
        def wrapper(*args, **kwargs):      # level 3: runs on each call
            return [func(*args, **kwargs) for _ in range(n)]
        return wrapper
    return decorator

@repeat(3)                                 # repeat(3) returns the real decorator
def greet(name):
    return f"hi {name}"

print(greet("Karuna"))
['hi Karuna', 'hi Karuna', 'hi Karuna']

The line @repeat(3) is evaluated first. It calls repeat(3), which returns decorator. Then Python applies that decorator to greet. Forgetting the parentheses, as in @repeat, passes the function as n and produces a confusing error.

lru_cache: a decorator from the standard library

functools.lru_cache remembers the results of previous calls and returns them for repeated arguments. Naive recursive Fibonacci makes an exponential number of calls, because it recomputes the same values again and again. With a cache, each value is computed once.

from functools import lru_cache

@lru_cache(maxsize=None)
def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

print(fib(80))
print(fib.cache_info().hits > 0)
23416728348467685
True

Without the cache, computing fib(80) would take an enormous number of calls. With the cache, the function is effectively computed once per value from 0 to 80, which is O(n) calls. The cache is stored on the function and can be cleared with fib.cache_clear(). Use it only for pure functions, meaning functions whose result depends only on their arguments.

Stacking decorators

You can put several decorators on one function. They are applied from the bottom upward, and the top one becomes the outermost layer, so it runs first when the function is called.

def bracket(tag):
    def deco(func):
        def wrapper(*args):
            return f"<{tag}>" + func(*args) + f"</{tag}>"
        return wrapper
    return deco

@bracket("b")
@bracket("i")
def text(s):
    return s

print(text("hi"))
<b><i>hi</i></b>

The meaning of @bracket("b") above @bracket("i") is text = bracket("b")(bracket("i")(text)). The inner decorator wraps first, so the italic tags are closest to the text. The outer wrapper then adds the bold tags around the result.

Interviewers askWrite a decorator that logs or times a function. Why use functools.wraps? Name real uses. Good answers include Flask's @app.route, login checks, caching and retry logic.

What does @decorator above def f mean, exactly?

It means f = decorator(f). The name f is rebound to whatever the decorator returns, which is usually a wrapper function that calls the original.

Context managers and the with statement

The with statement guarantees that setup and cleanup code run around a block, even when an error happens inside the block. Files, locks, database connections and temporary directories all use it, because forgetting to clean up is a common source of bugs such as leaked file handles.

with open("notes.txt", "w") as f:
    f.write("hello")
# the file is closed here, even if write() had raised an error

Here is what Python does. It calls __enter__ on the object and binds its return value to the name after as. When the block ends, normally or through an exception, it calls __exit__ with details about any exception that occurred.

Writing a context manager as a class

A class needs two methods. __enter__ does the setup and returns the object to use inside the block. __exit__ does the cleanup. It receives three arguments describing the exception, or three None values if there was none.

class Resource:
    def __enter__(self):
        print("acquire")
        return self                        # this becomes the value after "as"

    def __exit__(self, exc_type, exc, tb):
        print("release", exc_type.__name__ if exc_type else None)
        return False                       # False: let any exception continue

with Resource() as r:
    print("working")

try:
    with Resource():
        raise ValueError("boom")
except ValueError as e:
    print("caught", e)
acquire
working
release None
acquire
release ValueError
caught boom

The second block shows the important guarantee. The exception was raised inside the block, __exit__ still ran and printed the release, and then the exception continued outward to the except clause. Returning False from __exit__ means "do not hide the exception".

TrapIf __exit__ returns a true value, the exception is swallowed and the program continues after the block. Only do that when you deliberately want to suppress the error, and be specific about which error.

class IgnoreValueError:
    def __enter__(self):
        return self

    def __exit__(self, exc_type, exc, tb):
        return exc_type is not None and issubclass(exc_type, ValueError)

with IgnoreValueError():
    raise ValueError("ignored")
print("after")
after

The standard library provides the same idea in contextlib.suppress(ValueError), which is clearer than writing this class yourself.

Writing one with the contextmanager decorator

For simple cases, @contextlib.contextmanager turns a generator function into a context manager. Everything before the yield is the setup. The value of yield is what goes after as. Everything after it is cleanup, and the cleanup belongs in a finally block so that it runs even when the body raises an error.

from contextlib import contextmanager

@contextmanager
def tag(name):
    print(f"<{name}>")               # setup, like __enter__
    try:
        yield                              # the with-block runs here
    finally:
        print(f"</{name}>")            # cleanup, like __exit__, always runs

with tag("p"):
    print("hello")
<p>
hello
</p>

Without the try/finally, an exception inside the block would skip the closing tag, because the code after the yield would never be reached. The finally keyword is what makes the cleanup reliable.

Interviewers askWhat happens under the hood in with open(...)? Python calls __enter__ on the file object, which returns the file. When the block ends, it calls __exit__, which closes the file, and it does so even if an exception was raised.

Name two context managers in the standard library and what each guarantees.

threading.Lock acquires the lock on entry and releases it on exit, so a block cannot forget to unlock. tempfile.TemporaryDirectory creates a directory on entry and deletes it on exit. contextlib.suppress ignores the listed exceptions. All three guarantee cleanup.

Exceptions: raising, catching and designing errors

An exception is Python's way of signalling that something went wrong. When code raises one, normal execution stops and Python looks for an except clause that matches. If none exists, the program ends with a traceback. Exceptions are objects, so you can inspect them, subclass them and chain them.

try, except, else and finally: the exact order

The four clauses run in a fixed order. The try block runs first. If it raises a matching exception, the except block runs. The else block runs only if no exception occurred. The finally block runs last, always, whatever happened, including after a return inside try.

def divide(x):
    try:
        r = 10 / x
    except ZeroDivisionError as e:
        print("error:", e)
        return None
    else:
        print("no error")
        return r
    finally:
        print("finally runs")

print(divide(2))
print(divide(0))
no error
finally runs
5.0
error: division by zero
finally runs
None

In the first call, else runs and returns 5.0, but finally still runs before the value reaches the caller. In the second call, except catches the division error and returns None, and finally still runs. The else clause is useful because it keeps code that should run only on success out of the try block, so that unrelated errors inside it are not caught by accident.

The exception hierarchy

All exceptions inherit from BaseException. Most of your code should deal with subclasses of Exception. The diagram below shows the main branches.

BaseException
 ├── SystemExit, KeyboardInterrupt, GeneratorExit
 └── Exception
      ├── ArithmeticError → ZeroDivisionError
      ├── LookupError → IndexError, KeyError
      ├── ValueError, TypeError, AttributeError
      └── OSError → FileNotFoundError, and others

Catch the most specific exception you can handle. A bare except: catches everything, including KeyboardInterrupt (Ctrl+C) and SystemExit, which should normally stop the program. Use except Exception at the widest, and a specific type wherever you can.

TrapA bare except: makes Ctrl+C stop working inside the protected code and hides real bugs. Catch the specific error you expect.

Custom exceptions and chaining

Define your own exception class when callers need to tell your error apart from others. Subclass Exception, and store any useful details as attributes. When you convert one error into another, use raise ... from, which keeps the original error attached as __cause__, so the traceback shows both.

class InsufficientFunds(Exception):
    def __init__(self, needed):
        super().__init__(f"need {needed} more")
        self.needed = needed

def withdraw(balance, amount):
    if amount > balance:
        raise InsufficientFunds(amount - balance)
    return balance - amount

try:
    withdraw(100, 150)
except InsufficientFunds as e:
    print(e, e.needed)

try:
    try:
        int("abc")
    except ValueError as e:
        raise RuntimeError("could not parse config") from e
except RuntimeError as e:
    print(e, "| cause:", repr(e.__cause__))
need 50 more 50
could not parse config | cause: ValueError("invalid literal for int() with base 10: 'abc'")

The custom class passes its message up to Exception with super().__init__, so print(e) shows it. The needed attribute gives the caller a number to act on, without parsing the message. The chained error keeps the original ValueError available for debugging.

TrapA return inside finally overrides the return from try, and it also silently discards any exception that was in flight. Never return from finally.

def g():
    try:
        return 1
    finally:
        return 2

print(g())
2

The function returns 2 even though the try block returned 1, because finally runs last and its return wins.

EAFP and LBYL: two styles of checking

EAFP stands for "easier to ask forgiveness than permission". You try the operation and catch the error if it fails. LBYL stands for "look before you leap". You check the condition first. Python code leans toward EAFP, because checking first can be racy (the file may disappear between the check and the open) and repeats work.

Interviewers askWhy does Python prefer EAFP? Because the try-and-catch version is shorter, and it handles conditions that a separate check might miss, such as a file deleted between the check and the read.

When does the else clause of a try statement run?

Only when the try block finishes without raising an exception. It is for code that should run on success, kept outside the try so that its own errors are not caught by the except clauses.

Why is a bare except: dangerous?

It catches every exception, including KeyboardInterrupt and SystemExit, so Ctrl+C and deliberate exits can be swallowed, and real bugs are hidden. Catch specific exception types, or at most Exception.

Copying, identity, memory and garbage collection

In Python, a variable is a name that refers to an object. Assignment never copies an object. It only adds another name. Once you accept that, most copy questions become simple to reason about.

Assignment, shallow copy and deep copy

A shallow copy creates a new outer container that holds the same inner objects. A deep copy creates new copies of the inner objects too, recursively. The copy module provides both.

import copy

a = [[1, 2], [3, 4]]
b = a                    # same object, a second name
c = copy.copy(a)         # shallow: new outer list, SAME inner lists
d = copy.deepcopy(a)     # deep: new outer list AND new inner lists

a[0].append(99)
print(b)
print(c)
print(d)
print(a is b, a is c, a[0] is c[0], a[0] is d[0])
[[1, 2, 99], [3, 4]]
[[1, 2, 99], [3, 4]]
[[1, 2], [3, 4]]
True False True False

Work through the output. b shows the change because it is the same object as a. c shows the change too, because its inner list is the same object as a[0]. Only d, the deep copy, is unaffected. The last line confirms the structure: a is b is True, a is c is False because the outer lists differ, and a[0] is c[0] is True because the inner lists are shared.

Shallow copies are also made by a[:], list(a), a.copy() and dict.copy(). All of them share the inner objects.

TrapRepeating a list with * repeats the reference, not the contents. [[0] * 3] * 3 makes three names for one row. The fix is a list comprehension, which creates a new row each time.

grid = [[0] * 3] * 3
grid[0][0] = 1
print(grid)

good = [[0] * 3 for _ in range(3)]
good[0][0] = 1

is versus ==

== compares values by calling __eq__. is compares identity, which means whether two names refer to the same object in memory. Use is for the singletons None, True and False, and for identity checks you truly need. CPython happens to share small integers, from -5 to 256, between uses, so x is y can be True for those values and False for larger equal numbers. That is an implementation detail, so never rely on it.

How CPython frees memory

CPython uses two mechanisms. The first is reference counting. Every object keeps a count of the names and containers that refer to it. When the count drops to zero, the object is freed immediately. This is why most objects disappear as soon as the last name is gone.

Reference counting cannot free a reference cycle, where objects refer to each other, so each one keeps the other's count above zero even when nothing else reaches them. The second mechanism is the cyclic garbage collector, which is the gc module. It periodically searches for groups of objects that are unreachable from the program and frees them. It is generational: newly created objects are examined often, and long-lived objects less often, because most objects die young.

import gc

class Node:
    pass

a, b = Node(), Node()
a.other, b.other = b, a      # a reference cycle: each refers to the other
del a, b                     # the names are gone, but the cycle keeps the objects alive
print(gc.collect() >= 2)     # the cyclic collector finds and frees them
True

Interviewers askHow does Python manage memory? Reference counting frees most objects immediately, and a cyclic garbage collector handles reference cycles. Memory is returned to the allocator, and small objects are served from pools, which is a detail you can mention if asked.

Why does modifying a copy sometimes change the original?

A shallow copy shares its inner objects with the original. Changing an inner object through the copy changes it for the original too. A deep copy avoids this, at the cost of more memory and time.

The GIL, threads, processes and asyncio

Concurrency means making progress on several tasks at once, either truly in parallel or by switching between them. Python offers three main tools, and the right choice depends on whether the work is waiting for input and output or doing heavy calculation.

What the GIL is

The Global Interpreter Lock is a lock inside the standard CPython interpreter. Only one thread can execute Python bytecode at a time. CPython needs it because its reference counts are not protected against simultaneous updates by several threads, and one lock is far simpler and faster than locking every object.

  • I/O-bound work (network calls, disk reads, waiting for a timer). Threads help, because a thread releases the GIL while it waits for the operating system.
  • CPU-bound work (pure Python arithmetic and loops). Adding threads does not make it faster. Use multiprocessing, where each process has its own interpreter and GIL, or a library such as NumPy that releases the GIL inside its compiled code.
  • Free-threaded builds. Python 3.13 introduced an optional build without the GIL, described in PEP 703. It is opt-in, and the default build still has the GIL. Mention it to show you follow the language's development.

Choosing the tool

Threads for I/O work

ThreadPoolExecutor.map runs a function over many inputs using a pool of threads and returns the results in input order. The function below sleeps to imitate a network call. While one thread waits, the others can run.

from concurrent.futures import ThreadPoolExecutor
import time

def download(n):
    time.sleep(0.1)          # stands in for a network call that mostly waits
    return n * 10

with ThreadPoolExecutor(max_workers=5) as ex:
    results = list(ex.map(download, range(5)))
print(results)
[0, 10, 20, 30, 40]

Five waits of 0.1 seconds take about 0.1 seconds in total, not 0.5, because they overlap. The results still arrive in input order, which is a property of map worth remembering.

asyncio: the same idea with coroutines

An async def function is a coroutine. Inside it, await marks a point where the coroutine can pause and let the event loop run other tasks. Only one coroutine runs at a time, so there is no GIL contention and no thread overhead. asyncio.gather runs several coroutines together and collects their results in order.

import asyncio

async def fetch(i):
    await asyncio.sleep(0.1)     # gives control back to the event loop while waiting
    return i * 10

async def main():
    return await asyncio.gather(*(fetch(i) for i in range(3)))

print(asyncio.run(main()))
[0, 10, 20]

TrapA plain time.sleep or a blocking library call inside a coroutine blocks the whole event loop, because it never reaches an await. Use await asyncio.sleep or an asynchronous library.

The GIL does not make your code thread-safe

counter += 1 is several bytecode steps: read the value, add one, write it back. Between those steps, another thread can run and write its own value, and one of the increments is lost. This is a race condition. The GIL does not prevent it. Protect shared state with a threading.Lock, and keep the critical section as short as possible.

import threading

counter = 0
lock = threading.Lock()

def work():
    global counter
    for _ in range(100_000):
        with lock:                 # only one thread at a time inside this block
            counter += 1

threads = [threading.Thread(target=work) for _ in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print(counter)
400000

Four threads each add 100,000 times, so the correct total is 400,000. The lock makes the result exact on every run. Remove the with lock line and the total may come out smaller, because the switches between threads can happen in the middle of an increment.

Interviewers askWhat is the GIL, and is Python multithreading useless? The GIL lets only one thread run Python bytecode at a time. Threads are still useful for I/O-bound work. For CPU-bound work, use processes. A deadlock is the opposite problem: two threads each wait for a lock the other holds, so neither can continue.

A program downloads 50 pages, each taking one second of network waiting, then does a heavy calculation on each. Which tools fit each part?

The downloads are I/O-bound, so a thread pool or asyncio fits, and they overlap their waiting. The calculations are CPU-bound, so a process pool is the right tool, because threads would not run them in parallel.

Testing with pytest and mocks

A test is a small function that calls your code and checks the result with assert. Automated tests protect you when you change code, and in interviews they show that you think about correctness. The standard third-party tool is pytest. It finds files named test_*.py and functions named test_*, and it reports which assertions failed.

Interview questions

Answer each question aloud before opening the answer. The model answers give the points to cover, so practise saying them in your own words.

What does super() do in a class with multiple inheritance?

It calls the next class after the current one in the MRO of the object's actual type, not necessarily the direct parent. This lets cooperative classes call each other in a fixed order, and it means each class in a diamond runs once.

What is the difference between __str__ and __repr__?

__str__ gives a readable form for end users and is used by print and str(). __repr__ gives an unambiguous developer form, ideally one that could recreate the object, and is used by repr() and the interactive prompt. If only __repr__ is defined, it serves as the fallback for str().

What is the difference between a classmethod and a staticmethod?

A classmethod receives the class as its first argument (cls) and can create instances of the right class, which makes it a good alternative constructor. A staticmethod receives neither the class nor the instance, and behaves like a function stored in the class namespace.

Why does defining __eq__ remove the default __hash__?

Objects that compare equal must hash equally, and the default hash is based on identity, which would break that rule. Python therefore sets __hash__ to None, which makes the objects unhashable. Define __hash__ explicitly if the objects should be hashable, typically from the same fields that __eq__ uses.

What does a generator function return, and when does its body run?

Calling it returns a generator object without running the body. The body runs step by step, each time next() is called, pausing at every yield.

Explain what a decorator does with @wraps and why it matters.

A decorator returns a wrapper function in place of the original. Without functools.wraps, the wrapper's name and docstring replace the original's, which breaks introspection, debugging and documentation. wraps copies those attributes onto the wrapper.

When does the __exit__ method of a context manager run, and what if the block raises?

It runs when the block ends, whether normally, through a return or break, or through an exception. If an exception occurred, its type, value and traceback are passed in. Returning a true value suppresses the exception, and returning False or None lets it continue.

What is the GIL and how does it affect threads and processes?

The GIL is a lock that lets only one thread run Python bytecode at a time in CPython. Threads still help with I/O, because they release the GIL while waiting. CPU-bound work does not speed up with threads, so use processes, which each have their own interpreter and GIL.

What is the difference between shallow and deep copy, and when does it matter?

A shallow copy creates a new container holding the same inner objects. A deep copy copies the inner objects as well. It matters whenever the structure contains mutable objects that are shared, because changes through one copy would appear in the other.

Why do you need a lock around counter += 1 even with the GIL?

The increment is several bytecode operations, and the interpreter can switch threads between them. Two threads can read the same old value and both write back the same result, losing one increment. A lock makes the read-add-write sequence atomic with respect to other threads that use the same lock.

DSA: Strings

A string in an interview problem is a sequence of characters, and most string questions reduce to one of four patterns: two pointers, a sliding window, counting with a hash map, or using a sorted version of the string as a key. This lesson first recalls the Python facts that make string code fast or slow, then works through four assigned problems.

Facts to know first

  • Python strings are immutable. s[0] = "x" raises a TypeError, so every apparent change creates a new string.
  • Building a string with += inside a loop can cost O(n squared), because each step copies the whole string so far. Collect the pieces in a list and join them once with "".join(parts), which is O(n) in total.
  • Indexing and len are O(1). Slicing s[i:j] copies the characters, so it costs O(j minus i). Membership with in scans, so it is O(n) on average.
  • ord gives the character code of a single character, and chr does the reverse. Subtracting ord("a") turns a lowercase letter into an index from 0 to 25, which is how small arrays of counts are indexed.

Valid Anagram (LeetCode 242)

Given two strings s and t, return True if t is an anagram of s, meaning both contain exactly the same letters with the same counts, in any order. For s = "anagram" and t = "nagaram", the answer is True. For "rat" and "car", it is False.

How to think about it

  1. Understand. The letters must match with counts. Different lengths mean the answer is False straight away. The constraints for this problem use lowercase English letters only.
  2. Brute force. Sort both strings and compare them. Correct, and O(n log n) time.
  3. Find the waste. Sorting puts the letters in order, which we do not need. We only need to know how many of each letter there are.
  4. Optimise. Keep one array of 26 counts. Add one for each letter of s and subtract one for each letter of t. The strings are anagrams exactly when every count ends at zero. This is O(n) time and O(1) space, because 26 is a fixed size.
  5. Dry run. For s = "rat" and t = "car", the table tracks the counts for the letters involved. The letter c has count minus 1 at the end, so the answer is False.
StepLetter from s, +1Letter from t, -1Non-zero counts afterwards
1r, count[r] = 1c, count[c] = -1r: 1, c: -1
2a, count[a] = 1a, count[a] = 0r: 1, c: -1
3t, count[t] = 1r, count[r] = 0t: 1, c: -1

Code

def is_anagram(s, t):
    if len(s) != len(t):
        return False
    counts = [0] * 26
    for a, b in zip(s, t):                 # walk both strings together
        counts[ord(a) - ord("a")] += 1     # one more of this letter in s
        counts[ord(b) - ord("a")] -= 1     # one fewer of this letter in t
    return all(c == 0 for c in counts)

print(is_anagram("anagram", "nagaram"))
print(is_anagram("rat", "car"))
True
False

Longest Palindromic Substring (LeetCode 5)

Given a string s, return the longest substring that reads the same forwards and backwards. A substring is a contiguous piece of the string. If several substrings tie for the longest, any one is accepted. For "babad", the answer is "bab" (or "aba"), and for "cbbd" it is "bb".

How to think about it

  1. Understand. A palindrome such as "racecar" or "abba" is the same read in both directions. A single letter is a palindrome. An empty string gives an empty answer. The string length is at most 1000 in LeetCode's constraints, so O(n squared) is acceptable.
  2. Brute force. Check every substring to see whether it is a palindrome. There are about n squared substrings, and each check costs up to n, so the total is O(n cubed).
  3. Find the waste. A palindrome is built outward from its middle. If the letters on both sides match, the palindrome grows. Checking each substring from scratch repeats that work.
  4. Optimise. Try every possible centre. A palindrome can have one centre letter (odd length, such as "aba") or two equal centre letters (even length, such as "abba"). From each centre, expand left and right while the letters match. That costs O(n) per centre, and there are about 2n centres, so the total is O(n squared) with O(1) extra space.
  5. Dry run. For "cbbd", the even-length centre between the two b letters expands once. The left letter c and the right letter d differ, so the best palindrome is "bb".
CentrePair checkedExpansionPalindrome found
index 1, even (between 1 and 2)s[1] = b and s[2] = b, matchs[0] = c and s[3] = d, no match, stops[1:3] = "bb"

Code

def longest_palindrome(s):
    best = ""
    for center in range(len(s)):
        # two kinds of centre: one letter (odd length) or the gap after it (even length)
        for left, right in ((center, center), (center, center + 1)):
            while left >= 0 and right < len(s) and s[left] == s[right]:
                left -= 1
                right += 1
            candidate = s[left + 1:right]    # the loop stopped one step too far
            if len(candidate) > len(best):
                best = candidate
    return best

print(longest_palindrome("babad"))
print(longest_palindrome("cbbd"))
print(longest_palindrome("a"))
print(repr(longest_palindrome("")))
bab
bb
a
''

The key detail is the slice s[left + 1:right]. When the loop stops, the letters at left and right do not match, or one of them is off the string. So the palindrome is the part strictly between them, which is why we add one to left. For "babad", the centre at index 1 finds "bab" first. The later centre at index 2 finds "aba", which has the same length, so the strict comparison keeps the first answer.

Pattern to rememberFor palindromes, expand around each centre. Remember both the odd and the even centres, and slice out the palindrome after the expansion stops.

Group Anagrams (LeetCode 49)

Given an array of strings, group the strings that are anagrams of each other. The groups can be returned in any order, and so can the strings inside each group. For ["eat", "tea", "tan", "ate", "nat", "bat"], one valid answer is [["bat"], ["nat", "tan"], ["ate", "eat", "tea"]].

How to think about it

  1. Understand. Two strings belong together exactly when they are anagrams. We need groups, so we need a key that every member of a group shares and that differs between groups.
  2. Brute force. Compare every pair of words with an anagram test. With n words that is O(n squared) comparisons, each costing up to the word length.
  3. Find the waste. The comparisons repeat the same question: are these two words anagrams? If each word is converted into a canonical form that is the same for all its anagrams, we only need to group by that form.
  4. Optimise. Use the sorted letters of each word as the key. "eat", "tea" and "ate" all sort to "aet". Store the words in a defaultdict(list) under that key, then return the lists.
  5. Dry run. The table follows the key for each word. Words with the same key land in the same group.
WordSorted keyGroups after this word
eataetaet: [eat]
teaaetaet: [eat, tea]
tanantaet: [eat, tea], ant: [tan]
ateaetaet: [eat, tea, ate], ant: [tan]
natantaet: [eat, tea, ate], ant: [tan, nat]

Code

from collections import defaultdict

def group_anagrams(words):
    groups = defaultdict(list)
    for w in words:
        key = "".join(sorted(w))           # every anagram of w gives the same key
        groups[key].append(w)
    return list(groups.values())

print(group_anagrams(["eat", "tea", "tan", "ate", "nat", "bat"]))
[['eat', 'tea', 'ate'], ['tan', 'nat'], ['bat']]

The groups come out in the order their first word appeared, because a dict keeps insertion order. Within each group the words keep their input order. Both facts are useful to know, but a judge would accept any order.

Text Justification (LeetCode 68)

Given an array of words and a width maxWidth, format the text so that each line has exactly maxWidth characters and is fully justified: the words are spread so that both the left and right edges line up. Pack as many words as possible on each line, with at least one space between words. Spaces are distributed as evenly as possible across the gaps, and when they do not divide evenly, the extra spaces go to the gaps on the left. The last line, and any line with only one word, is left-justified with single spaces between words and padded with spaces on the right.

For words = ["This", "is", "an", "example", "of", "text", "justification."] and maxWidth = 16, the answer is ["This is an", "example of text", "justification. "].

How to think about it

  1. Understand. Each output line is exactly maxWidth characters long. A line's length is the sum of its word lengths plus the spaces. Two rules are special: the last line is never fully justified, and a line with a single word is padded on the right, since there is no gap to stretch.
  2. Brute force. Build each line by trying to add the next word, then joining the current candidate words to measure the line each time. That re-measures the same line over and over, which costs far more than necessary, often O(n squared) work for a single line.
  3. Find the waste. We only need the total length of the words chosen so far, plus one space for each gap. Keeping that number as a running total makes each decision a single addition and comparison.
  4. Optimise. Work through the words from left to right, in three steps for each line. First, greedily take words while the running length, including one space before each new word, still fits in maxWidth. Second, count the spaces still needed: maxWidth minus the total word length. Third, split those spaces across the gaps. With gaps gaps, each gap gets spaces // gaps spaces, and the first spaces % gaps gaps get one extra. For the last line and single-word lines, use single spaces and pad on the right instead.
  5. Dry run. The table below follows the first line of the example, then the second line, to show the arithmetic.

Code

The first version below is the brute force idea written out: it joins the candidate words to measure them each time. It is correct, and it is useful to see before the optimised version.

def line_length_brute(words):
    return len(" ".join(words))        # rebuilds the whole line just to measure it

words = ["This", "is", "an", "example"]
print(line_length_brute(words[:3]), line_length_brute(words))

Here the measurement of "This is an" costs a join each time. Inside a greedy loop that is repeated for every candidate word, and the optimised version replaces it with a running number.

def full_justify(words, max_width):
    lines = []
    i = 0
    while i < len(words):
        # step 1: take as many words as fit, counting one space before each extra word
        line_words = [words[i]]
        length = len(words[i])
        i += 1
        while i < len(words) and length + 1 + len(words[i]) <= max_width:
            length += 1 + len(words[i])
            line_words.append(words[i])
            i += 1

        # step 2: a last line or a single word is left-justified and padded on the right
        is_last = i == len(words)
        if is_last or len(line_words) == 1:
            text = " ".join(line_words)
            lines.append(text + " " * (max_width - len(text)))
            continue

        # step 3: spread the spaces across the gaps, extra spaces to the left gaps first
        gaps = len(line_words) - 1
        spaces = max_width - sum(len(w) for w in line_words)
        each, extra = divmod(spaces, gaps)
        parts = []
        for k, w in enumerate(line_words[:-1]):
            parts.append(w)
            parts.append(" " * (each + (1 if k < extra else 0)))
        parts.append(line_words[-1])
        lines.append("".join(parts))
    return lines

for line in full_justify(["This", "is", "an", "example", "of", "text", "justification."], 16):
    print(repr(line))
'This    is    an'
'example  of text'
'justification.  '

Each line of output is exactly 16 characters wide, which is the easiest way to check the code by hand. "This is an" has 8 letters and 8 spaces. "example of text" has 13 letters and 3 spaces. "justification. " has 14 letters and 2 padding spaces. The loop never produces a line that is too long, because step 1 only accepts a word when the running length still fits.

The same code handles the other edge cases. A word longer than maxWidth cannot fit, and the constraints of the problem guarantee that every word fits, so the loop always takes at least one word per line. A line with a single word, such as "acknowledgment" on its own, takes the left-justified branch and is padded on the right. The arithmetic in step 3 never divides by zero, because a line with one word already left the spread branch.

TrapThe common error is to forget that spaces are distributed by gap count, not by word count. A line of three words has two gaps, so spaces // 2 goes into each gap and the leftover goes to the left gap, which is why the first gap in "example of text" is wider.

Key ideaGreedy packing plus integer division with remainder. Decide each line's words first, then split the spaces with divmod, and handle the last line and single-word lines as a separate case.

Time O(total characters in the output) · Space O(n) for the output lines

Interviewers askHow do you know the greedy choice is right? The problem's rules fix the layout. Each line must hold as many words as fit, so greedy packing produces the one valid set of line breaks, and no other choice of breaks is allowed.

Summary

Use this list to revise. If an entry feels unclear, go back to its section and rerun the example, because seeing the output settles most doubts about Python behaviour.

Class
A blueprint for objects, with attributes and methods.
Instance attribute
Data stored on one object, usually set in __init__.
Class attribute
Data shared by every instance of a class. Mutable ones are a shared-state trap.
Name mangling
Renaming of __name to _Class__name to avoid clashes in subclasses. It is not privacy.
Property
A method exposed as an attribute, with optional setter rules.
MRO
The method resolution order, a fixed linear search order of classes, computed with C3.
super()
Calls the next class in the MRO of the object's actual type.
Dunder method
A special method such as __add__ or __len__ that powers built-in syntax.
Abstract base class
A class with abstract methods that subclasses must implement before they can be instantiated.
Dataclass
A class whose init, repr and eq methods are generated from annotated fields.
Iterator
An object with __next__ that yields values one at a time and remembers its position.
Generator
A function containing yield, which returns an iterator that pauses between values.
yield from
Delegates iteration to another iterable or generator, passing its values through.
Generator expression
A lazy, round-bracket version of a list comprehension.
Decorator
A function that takes a function and returns a wrapper, applied with the @ syntax.
functools.wraps
Copies the name and docstring of the wrapped function onto the wrapper.
Closure in decorators
The wrapper keeps the original function alive by closing over it.
Context manager
An object with __enter__ and __exit__ that guarantees setup and cleanup around a block.
contextlib.contextmanager
Builds a context manager from a generator with a try and finally around the yield.
Exception
An object raised to signal an error. Catch the most specific type you can handle.
try, else, finally
The else runs on success only, and the finally always runs, even after a return.
Exception chaining
raise X from Y keeps Y as the cause of X, shown in the traceback.
EAFP
"Easier to ask forgiveness than permission": try the operation and catch errors.
Shallow copy
A new container that shares its inner objects with the original.
Deep copy
A copy that recursively copies the inner objects too.
Reference cycle
Objects that refer to each other, which reference counting alone cannot free.
GIL
The lock that lets one thread run Python bytecode at a time in CPython.
I/O-bound and CPU-bound
Work that waits on outside systems versus work that computes. Threads suit the first, processes the second.
asyncio
Single-threaded concurrency where coroutines switch at each await.
Race condition
A bug where the outcome depends on the timing of threads. A lock prevents it.
Fixture
A pytest function that prepares data for tests, requested by parameter name.
Mock
A stand-in object that records calls and returns chosen values.
Anagram
Two strings with the same letters and counts in any order.
Palindrome
A sequence that reads the same forwards and backwards.
Canonical key
A value, such as sorted letters, that is equal for all members of a group.
Greedy packing
Adding items to the current group as long as the rules still allow it.
