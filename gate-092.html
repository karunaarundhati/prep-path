File organization & indexing (B/B+ trees)

A database stores millions of records on disk, and reading them one by one is far too slow. File organization and indexes, especially the B-tree and B+ tree, are the tools that let a database find a record with only a few disk reads. GATE asks for the cost and the size of these structures.

The idea in plain words

Imagine a library with one million books on one long shelf, in no particular order. To find one book you must look at every book until you find it. That is slow. Now imagine the books are sorted by title, and there is a card catalogue at the front that says which shelf holds which title range. You go to the card catalogue, then walk straight to the right shelf. That is fast.

A database works the same way. Data lives on disk, and disks are read in fixed-size chunks called blocks. Reading one block is the expensive step, far slower than comparing values in memory. So a DBMS counts its work mainly in block accesses. The two ideas on this page are:

  • File organization: the order in which records are placed in blocks.
  • Indexing: a separate, smaller structure, like the card catalogue, that points to records quickly.

GATE Data Science and AI (paper DA) and Robotics and Automation (paper RA) ask numerical questions on these topics. You may be asked how many blocks a search reads, how many entries fit in a block, or how tall a B+ tree becomes. Each of these is a small calculation, and this page shows every step.

Key ideaThe number of block accesses is the main cost measure. A structure is good when it lets you reach the right block after reading very few blocks.

Key terms

Disk block
The unit in which data is read or written. Plain meaning: one chunk of disk. Precise definition: a fixed-size unit of storage, often 512 bytes or 4 KB, transferred in one I/O.
Record
One row of data in a file. Plain meaning: one entry, such as one student.
Heap file
A file where records are placed wherever there is room, with no order. Plain meaning: a pile.
Sequential file
A file where records are kept in order of a key. Plain meaning: a sorted list.
Hashed file
A file where a hash function on a key picks the block of each record. Plain meaning: the key is converted into an address.
Index
A separate structure of key and pointer pairs that helps find records. Plain meaning: a card catalogue.
Index key and pointer
The index entry stores a key value and a pointer to a block or record.
Primary index
An index on the ordering key of a sequential file, where each key value appears once in the file.
Clustering index
An index on a non-key field whose values are kept in order in the file.
Secondary index
An index on a field that is not the ordering field of the file.
Dense index
An index with one entry for every record.
Sparse index
An index with one entry for each block. It works only on a sorted file.
Multilevel index
An index built on top of another index, repeated until the top fits in one block.
B-tree
A balanced search tree where every node holds keys and record pointers. Plain meaning: a tree that stays flat and even.
B+ tree
A B-tree where internal nodes hold only keys and pointers, and all record pointers sit in the leaves. The leaves are linked in order.
Order p
The maximum number of child pointers an internal node can hold. An internal node holds at most p - 1 keys.
Height
The number of levels from the root to the leaves. On this page, a single node has height 1.
Balanced tree
A tree where all leaves are at the same depth.
Node
One block of a tree. Plain meaning: one box of the tree.

Concept 1: File organization and data types

Why the order of records matters

Records on disk are packed into blocks. How they are placed decides how quickly we can find one. There are three common organizations.

  • Heap (unordered) file. New records go into any block with free space. Inserting is cheap. Searching is slow, because we may have to read every block. For a file of b blocks, a search reads about b/2 blocks on average, and b blocks in the worst case.
  • Sequential (sorted) file. Records are kept in key order. Binary search can find a block in about log2(b) reads. Inserting is costly, because records must be shifted to keep the order.
  • Hashed file. A hash function turns the key into a block address. A search reads about one block if there are no collisions. Hashing is good for exact matches, but it does not help with range queries such as "all keys between 10 and 20".

A numerical example

A sorted file has b = 1024 blocks. Binary search checks the middle block, then halves the range each time. The number of halvings needed to go from 1024 blocks to 1 block is log2(1024) = 10. So a search reads about 10 blocks. A heap file with the same 1024 blocks reads about 512 blocks on average. The Python check at the end of this unit confirms the numbers.

TrapBinary search on a file works only when the file is sorted on the search key. On a heap file, you must read blocks one after another.

Data types in a DBMS

Every column has a data type, which decides how many bytes each value uses. Some common types are:

  • Numeric: INT (fixed size, for example 4 bytes), FLOAT and DECIMAL.
  • Character: CHAR(n) always uses n bytes, padding short values. VARCHAR(n) uses only as many bytes as the value needs, plus a small length field.
  • Date and time: DATE and TIMESTAMP, each with a fixed size.

Fixed-size types make it easy to compute where a field sits in a record. Variable-size types save space but make calculations less predictable. In the B+ tree calculations later on this page, we use the key size V and the pointer size P, which are simply the number of bytes each takes.

Question: Why is an unordered heap file cheap to insert into but expensive to search?

Inserting only needs a block with free space, so one block access is often enough. Searching has no order to use, so we may have to read many or all blocks.

Question: A sorted file has 256 blocks. About how many blocks does binary search read?

log2(256) = 8 blocks.

Concept 2: Index basics, primary, clustering and secondary

What an index is

An index is a second structure that stores pairs of the form (key value, pointer). To find a record with a given key, we search the index first, then follow the pointer. The index is much smaller than the data, so it is usually faster to search.

Think of the card catalogue again. Each card has a title and a shelf number. We search the cards, which are small and sorted, and then walk to the shelf.

Three kinds of index

  • Primary index. Built on the ordering key of a sorted file, where the key is unique. Each key value appears once.
  • Clustering index. Built on an ordering field that is not unique, such as dept. Records with the same value sit together in the file.
  • Secondary index. Built on a field that is not the ordering field. The records are not sorted by this field, so every record needs its own index entry. This is a dense index.

Dense and sparse

A dense index has one entry for every record. A sparse index has one entry for each block. A sparse index is smaller, and it works only on a file that is sorted by the indexed key.

A sorted file of 6 records in 3 blocks (block size 2 records)
BlockRecords (key values)
B110, 20
B230, 40
B350, 60

A sparse index on this file has three entries: (10, B1), (30, B2) and (50, B3). A dense index has six entries, one per key. To find 40, the sparse index tells us that 40 lies between 30 and 50, so the block is B2. We read B2 and find 40 there.

TipFor a sparse index, the number of index entries equals the number of data blocks. For a dense index, it equals the number of records.

Single-level and multilevel indexes

A single-level index is one list of entries. If the index itself has many blocks, searching it becomes slow. So we build an index on the index. This is a multilevel index. Each level is smaller than the one below, and the top level fits in one block. The number of block accesses for a search is the number of index levels plus one for the data block.

Question: A file has 1000 blocks. How many entries does a sparse index have?

1000, one for each block.

Question: Why must a sparse index use a sorted file?

A sparse index only stores the first key of each block. To find a key, we must know that the block's key range contains it, which needs the file to be in key order.

Concept 3: B-trees and B+ trees

Why a tree?

A multilevel index is a tree in disguise. A tree is a good fit for a database because it stays balanced: every leaf is the same distance from the root. A balanced tree with a large order has very few levels. A tree with a million keys and order 100 has only about three levels.

The structure of a B+ tree

A B+ tree of order p has these rules:

  1. Internal nodes hold at most p child pointers and at most p - 1 keys. They guide the search.
  2. Leaf nodes hold the keys and the record pointers. A leaf holds at most p - 1 keys. Each leaf also has one pointer to the next leaf, so the leaves form a sorted chain.
  3. All leaves are at the same level.
  4. Each internal node has at least ⌈p/2⌉ children, except the root. Each leaf has at least ⌈(p-1)/2⌉ keys, except possibly the root.

Notice that internal nodes do not store record pointers. This lets more keys fit in each internal node, so the tree is flatter.

Searching

To search for key k, start at the root. In each internal node, pick the child whose key range contains k. Repeat until a leaf is reached. Then look for k in the leaf. The number of block reads is the height h, plus one more read for the data record if the leaf holds only pointers.

Insertion, step by step

We use order p = 3, so a leaf holds at most 2 keys and an internal node holds at most 2 keys. Insert 10, 20, 30, 40 and 50 in this order.

  1. Insert 10 and 20. The root is a leaf: [10, 20].
  2. Insert 30. The leaf would have 3 keys, which is too many. Split it into [10] and [20, 30]. Copy 20 up as a separator. Root: [20].
  3. Insert 40. Go right, to [20, 30, 40]. Too many keys. Split into [20] and [30, 40]. Copy 30 up. Root: [20, 30], which is allowed because it has 2 keys.
  4. Insert 50. Go to the right leaf: [30, 40, 50]. Split into [30] and [40, 50]. Copy 40 up. The root would have [20, 30, 40], which has 3 keys. Split the internal node: move 30 up as the new root, with [20] on the left and [40] on the right.

The final tree has three levels. The root is [30]. Its left child is [20], with leaves [10] and [20]. Its right child is [40], with leaves [30] and [40, 50]. Notice that a leaf split copies the key up, while an internal split moves the key up, so it does not stay in the child.

TrapIn a leaf split, the separator key is copied up and still appears in the leaf. In an internal split, the middle key moves up and is removed from both halves. Mixing these up is a common error.

Deletion

When a key is deleted and a leaf has fewer keys than its minimum, the node either borrows a key from a sibling with extra keys, or merges with a sibling. A merge removes a separator from the parent. If the parent becomes too small, the same repair continues upward. Deletion can reduce the height of the tree.

Why B+ trees are used in DBMS

  • All record pointers are in the leaves, so internal nodes hold more keys and the tree is shorter.
  • The leaves are linked, so a range query such as "keys from 20 to 40" finds the first key and then follows the chain.
  • The tree is always balanced, so every search costs about the same.

GATE loves thisA B tree stores record pointers in every node, and a B+ tree stores them only in leaves. Expect questions comparing fan-out or range queries. For both, the B+ tree is the usual answer, because its internal nodes hold more keys and its leaves are linked.

Question: In a B+ tree of order 3, why is 20 still in the leaf after the first split?

A leaf split copies the separator up to the parent, but the key must remain in the leaf, because leaves hold all the record pointers.

Question: Why is a B+ tree better than a B tree for range queries?

The leaves form a sorted linked chain. A range query finds the start key once, then follows the links without going back up the tree.

Concept 4: Order and height calculations

Finding the order from block size

A block must hold an internal node. Suppose the block size is B bytes, a block pointer takes P bytes, and a key takes V bytes. An internal node has p pointers and p - 1 keys, so it needs:

p × P + (p - 1) × V ≤ B

Read the symbols: p is the order we want, P is the pointer size, V is the key size, and B is the block size. The largest p that fits is the order of internal nodes.

Example: B = 512 bytes, P = 6, V = 10. Try p = 32: 32 × 6 + 31 × 10 = 192 + 310 = 502, which fits in 512. Try p = 33: 33 × 6 + 32 × 10 = 198 + 320 = 518, which does not fit. So p = 32 for internal nodes.

Leaves also need space for record pointers Pr, and a next-leaf pointer P. A leaf with p - 1 keys, each with a record pointer, and one next pointer needs:

(p - 1) × (V + Pr) + P ≤ B

With Pr = 7 bytes, the same block gives (p - 1) × 17 + 6 ≤ 512. Try p = 30: 29 × 17 + 6 = 499, which fits. Try p = 31: 30 × 17 + 6 = 516, which does not. So the leaves allow p = 30. The order of the whole tree is the smaller of the two, which is 30.

Key ideaThe order of the tree is limited by whichever node type is larger. Always check both the internal node formula and the leaf formula, then take the smaller.

Height limits for n keys

Suppose we know the order p and want the height of a B+ tree that stores n keys. We use two extremes.

  • Minimum height comes from full nodes. A tree of height h has at most (p - 1) × ph-1 keys when every leaf is full. The smallest h with this capacity at least n is the minimum height.
  • Maximum height comes from minimally filled nodes. The fewest keys for height h uses the smallest allowed number of children and keys. The largest h whose minimum key count is at most n is the maximum height.

Example: order p = 4 and n = 100 keys. Full nodes: height 3 holds at most 3 × 42 = 48 keys, and height 4 holds at most 3 × 43 = 192 keys. Since 48 is less than 100 and 192 is at least 100, the minimum height is 4.

Minimal nodes: each internal node has at least ⌈4/2⌉ = 2 children, and each leaf has at least ⌈3/2⌉ = 2 keys. For height 6, the tree has at least 2 × 24 = 32 leaves, with at least 64 keys. For height 7, it has at least 64 leaves and 128 keys, which is more than 100. So the maximum height is 6.

The next program applies these formulas. It is a direct translation of the steps above.

import math

B, P, V, Pr = 512, 6, 10, 7

internal = max(p for p in range(1, 200) if p * P + (p - 1) * V <= B)
leaf = max(p for p in range(1, 200) if (p - 1) * (V + Pr) + P <= B)
print("internal order:", internal, "leaf order:", leaf, "tree order:", min(internal, leaf))

print("binary search on 1024 blocks:", math.ceil(math.log2(1024)), "blocks")

def max_keys(p, h):
    return (p - 1) * p ** (h - 1)

def min_keys(p, h):
    if h == 1:
        return 1
    leaves = 2 * math.ceil(p / 2) ** (h - 2)
    return leaves * math.ceil((p - 1) / 2)

p, n = 4, 100
print("minimum height for 100 keys:", min(h for h in range(1, 50) if max_keys(p, h) >= n))
print("maximum height for 100 keys:", max(h for h in range(1, 50) if min_keys(p, h) <= n))

internal order: 32 leaf order: 30 tree order: 30
binary search on 1024 blocks: 10 blocks
minimum height for 100 keys: 4
maximum height for 100 keys: 6

TrapHeight conventions differ. Some textbooks count edges, so a single root has height 0. A GATE question states its convention. This page counts levels, so a single root has height 1.

Question: Why must the order be taken from the smaller of the internal and leaf limits?

Every node of the tree must fit in one block. If either node type does not fit at order p, the tree cannot use that order.

Question: With order p = 4, how many keys can a full tree of height 2 hold?

(p - 1) × p = 3 × 4 = 12 keys. The root has 4 children, and each leaf has 3 keys.

Solved GATE-style problems

These problems are original, written in the GATE style. They are not past exam questions.

Blocks read in a heap search

A heap file has 200 blocks. On average, how many blocks does a successful search read?

How to think about it

  1. What is asked. The average block reads for a heap file.
  2. Which idea applies. A heap has no order, so we read blocks one at a time until we find the record. On average we read half the file.
  3. Work it out. Half of 200 is 100.
  4. Check. The worst case is 200, and the average must be less.

Answer: 100 blocks.

Index entries

A sorted file has 5000 records stored in 250 blocks. How many entries does a sparse index on the sort key have? Then how many entries does a dense index have?

How to think about it

  1. What is asked. Two counts.
  2. Which idea applies. Sparse: one entry per block. Dense: one entry per record.
  3. Work it out. Sparse: 250 entries. Dense: 5000 entries.
  4. Check. The dense index is larger, as expected.

Answer: sparse 250, dense 5000.

Statements about file organization

Select all that apply. For a file of b blocks:

(A) Binary search on a heap file takes about log2(b) reads.

(B) A sorted file supports binary search on its ordering key.

(C) A hashed file is good for range queries such as "keys between 10 and 20".

(D) A heap file is cheap to insert into.

How to think about it

  1. What is asked. Which statements are true.
  2. Which idea applies. Binary search needs sorted data. Hashing spreads keys randomly, so it loses order.
  3. Work it out. (A) False, a heap has no order. (B) True. (C) False, hashing does not keep keys in order. (D) True, a new record goes into any block with space.
  4. Check. The two true statements are about order (B) and about placement (D).

Answer: (B) and (D).

Search cost of a multilevel index

A B+ tree has height 3. How many block reads does a search for one key take if the leaf holds record pointers only, and the record must be read separately?

How to think about it

  1. What is asked. The total number of block reads.
  2. Which idea applies. One block per tree level, plus one block for the record.
  3. Work it out. 3 tree levels give 3 reads. The record adds 1. Total 4.
  4. Check. The answer is the height plus one.

Answer: 4.

Order of a B+ tree

Block size is 512 bytes, block pointer size is 6 bytes, and key size is 10 bytes. What is the largest order p for the internal nodes? Give a whole number.

How to think about it

  1. What is asked. The largest p that fits.
  2. Which idea applies. p × P + (p - 1) × V ≤ B.
  3. Work it out. Substitute: 6p + 10(p - 1) ≤ 512, so 16p - 10 ≤ 512, so 16p ≤ 522, so p ≤ 32.6. The largest whole p is 32.
  4. Check. For p = 32: 192 + 310 = 502 bytes, which fits. For p = 33: 518 bytes, which does not.

Answer: 32.

Height after insertions

A B+ tree of order 3 starts empty. The keys 10, 20, 30, 40 and 50 are inserted in that order. How many levels does the tree have after the last insertion? Use the convention that a single root has height 1.

How to think about it

  1. What is asked. The number of levels after five insertions.
  2. Which idea applies. Trace the splits, as in Concept 3.
  3. Work it out. After 10, 20 and 30 the root is [20] with two leaves, so 2 levels. After 40 the root is [20, 30]. After 50 the leaf [30, 40, 50] splits and the root overflows, so the root [30] has children [20] and [40], and the leaves below them. That makes 3 levels.
  4. Check. Leaves are at the bottom level, and the root level is above the internal level, so there are three levels.

Answer: 3.

Which statements about B and B+ trees

Select all that apply. Which statements about a B+ tree of order p are true?

(A) Internal nodes store record pointers.

(B) All leaves are at the same level.

(C) A range query can follow linked leaves in order.

(D) Deleting keys can reduce the height of a B+ tree.

How to think about it

  1. What is asked. Which statements are true.
  2. Which idea applies. The B+ tree rules: record pointers only in leaves, balanced, linked leaves.
  3. Work it out. (A) False, internal nodes hold only keys and child pointers. (B) True, the tree is balanced. (C) True, the leaves form a sorted chain. (D) True, when a merge leaves the root with one child, that child becomes the new root and the height drops.
  4. Check. The false statement is the one that says internal nodes hold data pointers.

Answer: (B), (C) and (D).

Exam-level 1: smallest B+ tree for 20 keys (NAT, 2 marks)

A B+ tree index is built on 20 distinct key values. Each leaf holds at most 3 keys. Each internal node has at most 4 children. To find the smallest possible tree, pack every node as full as the rules allow, one level at a time, until a single root remains. Count the total number of nodes, including the root and all the leaves.

How to think about it

  1. What is asked. The minimum total node count.
  2. Which idea applies. Pack each level full, then build the next level from those nodes.
  3. Work it out. 20 keys at 3 per leaf need 7 leaves (20 / 3 = 6.67, rounded up). 7 leaves under parents with 4 children need 2 internal nodes (7 / 4 = 1.75, rounded up). Two internal nodes fit under one root. The total is 7 + 2 + 1 = 10.
  4. Check. Six full leaves hold 18 keys and the seventh holds 2, so 20 keys fit in 7 leaves.

Answer: 10 nodes (7 leaves, 2 internal nodes and 1 root).

import math
keys=20
leaf_cap=3
fanout=4
n=math.ceil(keys/leaf_cap)
levels=[n]
total=n
while n>1:
    n=math.ceil(n/fanout)
    levels.append(n)
    total+=n
print(levels)
print(total)
[7, 2, 1]
10

Exam-level 2: levels of a B+ tree on a disk (NAT, 2 marks)

A disk block is 4096 bytes. A key takes 10 bytes and a pointer takes 6 bytes. An internal node with p pointers holds p - 1 keys and must fit in one block. Find the largest possible p. Each leaf holds p - 1 keys. A B+ tree is built over 1,000,000 keys. How many levels does the tree have, counting the root and the leaves?

How to think about it

  1. What is asked. The number of levels.
  2. Which idea applies. The block size fixes the fan-out. Then count the nodes on each level, from the bottom up.
  3. Work it out. The rule 6p + 10(p - 1) ≤ 4096 gives 16p ≤ 4106, so p = 256, since 16 × 256 = 4096 fits and 16 × 257 = 4112 does not. Leaves hold 255 keys, so 1,000,000 / 255 needs 3922 leaves (rounded up). Each parent has 256 children, so 3922 / 256 needs 16 nodes, and 16 / 256 needs 1 root.
  4. Check. The levels hold 3922, 16 and 1 nodes, so the tree has 3 levels, which is 2 edges from the root to a leaf.

Answer: 3 levels.

import math
block=4096
key=10
ptr=6
p=(block+key)//(ptr+key)
print(p)
records=10**6
leaf_keys=p-1
n=math.ceil(records/leaf_keys)
levels=[n]
while n>1:
    n=math.ceil(n/p)
    levels.append(n)
print(levels)
print(len(levels))
256
[3922, 16, 1]
3

Exam-level 3: true statements about a B+ tree (MSQ, 2 marks)

A B+ tree has order 6, so each internal node has at most 6 children. Select all that apply. Which of these statements about B+ trees are true?

(A) Every data pointer is stored in a leaf node.

(B) The root may have a single child.

(C) The leaves are linked, so a range query can scan forward along them.

(D) Internal nodes store full data records.

How to think about it

  1. What is asked. Which properties hold for a B+ tree of order 6.
  2. Which idea applies. In a B+ tree, data pointers sit only in leaves, the leaves form a linked list, and every non-root node must be at least half full.
  3. Work it out. The minimum number of children is 2 for the root and ceil(6/2) = 3 for other internal nodes. Non-root leaves need at least ceil(5/2) = 3 keys. A non-leaf root needs 2 children, so (B) is false.
  4. Check. (A) and (C) describe the defining features. (D) is false, because internal nodes hold only separator keys and child pointers.

Answer: (A) and (C). Why the others fail: (B) a non-leaf root needs at least 2 children; (D) internal nodes hold only separator keys and child pointers, so the records live in the leaves.

import math
p=6
min_root_children=2
min_internal_children=math.ceil(p/2)
min_leaf_keys=math.ceil((p-1)/2)
print(min_root_children, min_internal_children, min_leaf_keys)
print(min_leaf_keys)
2 3 3

Exam-level 4: block reads with a cached root (NAT, 2 marks)

A B+ tree index has 3 levels, counting the root and the leaves. The data file is separate from the index. A lookup reads one index block per level, then one data block. The root block is kept in memory, so reading it costs nothing. How many block reads do 50 independent lookups need in total?

How to think about it

  1. What is asked. The total block reads for 50 lookups.
  2. Which idea applies. Count the reads per lookup, leaving out the cached root, then multiply by the number of lookups.
  3. Work it out. 3 levels minus the cached root leaves 2 index blocks. Add 1 data block, which gives 3 reads per lookup. 50 × 3 = 150.
  4. Check. Two index reads and one data read make 3 per lookup, and 3 × 50 = 150.

Answer: 150 block reads.

levels=3
cached_root=1
lookups=50
per_lookup=(levels-cached_root)+1
print(per_lookup)
print(per_lookup*lookups)
3
150
